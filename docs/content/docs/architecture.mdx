Rift exposes code discovery and editing operations to an agent such as Claude Code or Codex through
[MCP](https://modelcontextprotocol.io/specification/latest).

When an agent has Rift configured as one of its MCP servers, the `rift mcp` process starts in one Git
working tree. This documentation calls that checkout and its reserved `.rift` directory a workspace.
The random ID in `.rift/workspace-id` is its durable identity, while the canonical root path is its
current location. Moving the complete directory preserves the workspace. A linked Git worktree has
its own `.rift` and therefore remains a separate Rift workspace even when it shares Git objects.

The `rift server` coordinates between one or several `rift mcp` instances and configured language
adapter processes for one workspace. A language
adapter is a subprocess that talks to the server and gives Rift its introspection into a language's
facts and operations. The server starts at most one configured gRPC adapter process for each exact
`Language` — a name plus an optional dialect. `sql:postgresql` and plain `sql` therefore select
different configured processes. Each process can hold separate `AdapterState`s for several snapshots
and back them with separate runtime workers.

<Callout type="info" title="Why the adapter is a process of its own">
  A [tree-sitter](https://tree-sitter.github.io/tree-sitter/) parser can recover concrete syntax, but
  it doesn't resolve bindings or types. [LSP](https://microsoft.github.io/language-server-protocol/)
  exposes the operations an editor needs, which doesn't include every fact or refactor Rift carries.
  A language adapter calls the language's compiler or analyzer APIs and translates their results
  into Rift messages. Running it as a subprocess keeps language runtimes and dependencies out of
  `rift server`. When two revisions require incompatible project runtimes, the adapter can put a
  separate runtime worker behind each adapter state while retaining one stable gRPC process.
</Callout>

Each `rift mcp` connects to the workspace server through `.rift/run/server.sock`, or through a named
pipe on Windows. If nothing is listening, the MCP process launches the server before forwarding the
request.

MCP's stdio transport gives each agent or subagent its own `rift mcp` subprocess. Those processes
cannot share in-memory state, so they forward repository operations to the common server instead.

The `rift server` keeps the state those clients must share: sessions, previews, worktrees, and semantic
facts. It also owns the language adapters, so every client in the workspace drives the same processes.
Linked Git workspaces have separate Rift servers and registries; shared-branch updates still coordinate
through Git locks and compare-and-swap ref updates.

`rift mcp` validates the agent's JSON against `mcp.json`, negotiates a protocol contract with the
server, converts the request to the Protobuf message named by that contract, and converts the response
back. The local server and every client run as the same OS user. Session IDs coordinate attachment but
provide no security boundary between processes owned by that user.

## Server lifecycle

`rift mcp` checks whether a `rift server` is already running for the workspace and starts one when
needed. The endpoint belongs to the workspace whose `.rift` directory contains it:

```
<workspace>/.rift/run/
  server.sock                         stable server endpoint
  start.lock                          held while a server starts
```

From the implementation perspective, `rift mcp` changes to the canonical workspace root before it
uses the relative socket path. The relative name stays below Unix-domain socket length limits even
when the workspace has a long absolute path. It takes an exclusive `flock` on `start.lock`, checks the
socket again, then spawns the server in a detached process group when no compatible server answers.

The server opens `.rift/workspace-id`, acquires an exclusive OS lock on `.rift/lease`, and keeps that
lock until exit. It writes its protocol major and a random process-generation value into the locked
file. Those bytes identify the live owner when another launcher encounters the lock; stale bytes have
no authority after the kernel releases it.

The `.rift` and `.rift/run` directories are mode `0700`, and `server.sock` is mode `0600`. A launcher
unlinks a socket that refuses connection only while it holds `start.lock` and can acquire `.rift/lease`.
The server verifies that the Unix peer UID, or the Windows pipe client identity, matches its own user
before `Connect`.

The socket path carries no version because the workspace lease admits one server. A launcher that
finds the lease held by another protocol major returns `unsupported_protocol` with the active and
requested majors; it does not send an incompatible Protobuf message to `server.sock`. Compatible
minor versions share the endpoint and negotiate during `Connect`. A new major migrates the registry
only after the previous server has released the lease.

After connecting, `rift mcp` sends the contract tuples it supports, each containing a major, minor,
and schema digest, plus its feature set. The server selects one tuple whose digest exactly matches its
descriptor for that minor and returns the compatible feature intersection. An unknown digest or
required feature rejects the connection before another RPC runs. Additive changes increment the minor
version; a changed field meaning, field number, or required behavior increments the major version.

The server exits after `server.idle-timeout` with no open connection. Adapter processes can retain
large indexes, so an idle repository should release them. A state-mutating CLI command goes through
the live server. An offline command such as `rift state reset` first asks that server to shut down,
then acquires `.rift/lease` before touching the registry, refs, or worktrees.

  and keeps its owner metadata under `.rift/run`; the pipe still checks the connecting user's identity.
</Callout>

## Repository and runtime state

Process memory holds live adapter workers, open handles, and semantic indexes reconstructed after
startup. The durable registry records session-creation retry keys alongside sessions and previews. It
also retains validation evidence, publication recovery, and bounded request logs. The reserved
repository-local `.rift` directory holds that registry beside the physical Git worktrees it describes.

Each server process owns one semantic store for its workspace. All facts and coverage stay in that
process and disappear when it exits. The existing Git repository remains the source of ordinary
objects, refs, indexes, and reflogs; Rift uses those Git stores but creates no additional durable
ledger inside `.git`.

The `run` directory contains rendezvous files. The OS lock on `.rift/lease` identifies a live server,
while the registry remains authoritative for retained resources. Startup can therefore replace a
stale socket after it acquires both locks.

```
<workspace>/.rift/
  workspace-id                         durable random workspace ID
  lease                                live server lock and owner metadata
  db/registry                          sessions, previews, retry keys, recovery, and request logs
  run/server.sock                      stable Unix server endpoint
  run/start.lock                       serializes server startup
  worktrees/session-f8py…/             session materialization
  worktrees/preview-04ad…/              immutable candidate
  worktrees/read-dae86e1/               detached semantic read
  worktrees/exec-71c2…/                 one-shot execution
  worktrees/debug-e003…/                retained failed evaluation
  state/<worktree-id>/<language>/       adapter-private caches and overlays
```

Rift reserves the root `.rift` path. Admission fails when Git tracks it, when it is a symlink, or when
its owner and permissions do not match the current user. Rift adds `.rift/` to local Git exclude data
without modifying committed `.gitignore`, and candidate edits cannot target it. Ordinary Git commands
leave it alone; `git clean -ffdx` or manual deletion can still destroy its registry and worktrees.

Mutable-worktree capture repeats the tracked-path check. If an external checkout introduces a tracked
`.rift`, the server stops admitting workspace operations until the collision is removed; it does not
traverse or overwrite the new path.

On first use Rift creates a random workspace ID in `.rift/workspace-id` and records the current
canonical path in `.rift/db/registry`. `rift state reset` reports the previews and sessions that will
be lost, requires confirmation, unregisters their worktrees, removes their session refs, replaces the
registry, and creates a new workspace ID.

### Moving and copying a workspace

A move carries `.rift`, including a live Unix socket, with the checkout. A client entering through the
new root reaches the same server through the relative `.rift/run/server.sock` path. The server checks
the canonical root supplied by `Connect` against the registry. When the previous path no longer
contains the workspace ID, it records `relocating` with the old and new paths, repairs Git's
administrative paths for every registered worktree, verifies their HEAD and tree values, then commits
the new path. Each repair step is idempotent, so startup resumes an interrupted relocation.

A copy leaves the previous path holding the same workspace ID. Rift refuses the copied state while
that source still exists, because two registries would otherwise claim one identity without sharing a
lease. Run `rift state reset` in the copy to discard its copied sessions and previews and mint a new
identity. A move or copy also changes the path used to select workspace policy, so executable and host
access grants must be made again for the new location.

Linked Git worktrees have independent `.rift` directories and workspace IDs. Their registries,
policies, and servers remain separate while Git locks and compare-and-swap protect shared refs.

### Durable identifiers

Rift gives random 128-bit values to workspaces and sessions. Their full protocol spellings are the 26
lowercase characters of unpadded RFC 4648 base32, with `ws_` and `ses_` prefixes. A preview has a
deterministic `prv_` identifier: SHA-256 over the fixed publication inputs, encoded as 52 characters
with the same alphabet.

The preview hash starts with the ASCII bytes `rift.preview.v1\0`. Each field frame is a one-byte tag,
a four-byte unsigned big-endian length, and the value bytes:

| tag | value bytes |
| --- | --- |
| `1` | raw 16-byte session ID |
| `2` | base Git object format and raw object ID |
| `3` | UTF-8 destination ref |
| `4` | expected-head Git object format and raw object ID |
| `5` | raw 32-byte parent preview ID, or an empty value |
| `6` | canonical operation encoded as `rift-json/1` |
| `7` | ordered validator declarations encoded as `rift-json/1` |

A Git object value starts with `1` for SHA-1 or `2` for SHA-256, followed by the corresponding raw
object ID. The framing prevents adjacent strings or two Git hash formats from producing the same hash
input.

The registry and protocol carry full identifiers. A CLI may accept a shorter suffix when it matches
exactly one record in the workspace. Filesystem names are deterministic projections: `ses_` becomes
`session-` and `prv_` becomes `preview-`, with every base32 character retained. Rift does not recover
identity from a directory name; the registry record remains authoritative.

## Sessions

A session is a durable accepted history. `rift mcp` opens a `Connect` control stream before another
RPC. The request either attaches a session selected by the local CLI or carries a random
`connect_attempt_id` from the MCP process. The server commits a new random 128-bit session ID and the
attempt mapping in one registry transaction, so a retry after a lost response returns the same
session. Session attachment is not an MCP operation.

The first stream event returns the session ID and a new connection ID. Later RPCs carry that
connection ID in gRPC metadata. The ID is a coordination handle; peer identity on the Unix socket or
named pipe supplies the same-user trust boundary. Connection IDs use a `con_` prefix, while creation
attempts use `try_`; each contains 26 lowercase characters of unpadded RFC 4648 base32 after its
prefix. Internally, a session owns:

```
id              ses_f8py...             random, repository-wide
base            B, the configured starting commit
worktree        <workspace>/.rift/worktrees/session-f8py..., detached at B
accepted ref    refs/rift/accepted/ses_f8py..., starting at B
```

A session starts from the last commit, so it excludes uncommitted workspace changes. Reads can still
select them through `rev: main-worktree`. Setting `session.base = "worktree"` instead records that
diff as the accepted ref's initial commit. The session worktree remains a detached materialization of
accepted state.

### Reconnecting and closing

When the server restarts, `rift mcp` reconnects with its session ID. The server reads the registry,
verifies the session worktree and accepted ref, then rebuilds adapter state. Retrying one
`connect_attempt_id` supersedes its previous control stream and returns a fresh connection ID.

Adapter states opened for a session are shared across its active connections. The server closes them
after the final connection and in-flight request release their references. Closing one control stream
cancels that connection's queued work and releases its debug sessions and execution workspaces. A
publication or `persist` call that passed its documented commit point continues to its durable result.
Complete semantic generations remain in the server cache until eviction or server exit. The session
remains in the registry with its worktree and accepted ref after every connection closes.

The connection fixtures exercise the interface at its failure points:

| fixture | required observation |
| --- | --- |
| concurrent startup | Two `rift mcp` processes produce one lease owner and both receive connections. |
| lost first event | Retrying one `connect_attempt_id` returns the same session with a fresh connection ID and closes the earlier stream. |
| shared session | Closing one of two attached connections leaves the other connection's adapter state usable. |
| final close | Connection-owned debug and execution workspaces are released; session adapter state closes after its last request. |
| live move | Moving the complete workspace preserves the socket connection and repairs the registry path and Git worktree metadata. |
| incompatible server | A launcher reads the held lease's major and returns `unsupported_protocol` before it sends a message to the socket. |

An untouched session may be collected after `session-retention`. An advanced, unintegrated session is
never removed automatically because its accepted ref may be the only reference to user work. An
integrated session becomes eligible only after retention, when its head is reachable from a non-Rift
ref and no ready preview depends on it. `rift session keep` pins a session against collection.

```
rift session list                   retained histories and their heads
rift session attach ses_f8py...     launch a client attached to one session
rift session keep ses_f8py...       prevent automatic collection
rift session remove ses_f8py...     explicitly abandon one history
rift preview list                  retained previews and terminal results
rift preview remove prv_04ad...    remove one preview after dependency checks
```

`rift session remove` reports commits that would lose their last ref and requires confirmation. All
state-management commands follow `rift <object> <verb>`.

### Reading across sessions

Any session can read a commit or branch the repository has. A session may also name another local
session worktree explicitly:

```
rift://file/src/api.rs?rev=worktrees/ses_f8py...
```

The server captures that worktree into an immutable tree before it answers. Session IDs carry no
write authority by themselves and provide no isolation from another process owned by the same user.

## Worktrees

A worktree's lifetime depends on what made it:

| worktree | created by | removed | written by |
| --- | --- | --- | --- |
| session `session-f8py…` | creating a session | explicit removal or eligible collection | `persist` |
| preview `preview-04ad…` | any candidate tool — `edit`, `rename`, `act` | explicit removal or terminal-record collection | that operation's resolved edits |
| read `read-dae86e1` | a semantic read at a revision nothing has checked out | idle timeout, or the LRU cap | nobody |
| execution `exec-71c2…` | `execute` | when the call returns | evaluated repository code |
| debug `debug-e003…` | `debug_start` | `debug_stop`, idle expiry, connection close, or adapter loss | evaluated repository code |

The registry owns every durable session and preview. Creation inserts a `creating` record
before Rift creates its deterministic ref and worktree. Once their identities match that record, one
registry transaction records the observed HEAD and tree and changes the resource to `ready`. Only a
ready resource can serve a request. Removal changes the record to `removing`, unregisters and deletes the
worktree and ref with idempotent Git operations, then records `deleted`; retention may remove that
terminal record later.

Startup resumes each incomplete transition by comparing the registry with `git worktree list
--porcelain` and the expected refs. A missing or changed worktree for a ready resource becomes
`corrupt`, because reconstructing it could overwrite evidence of an external change. An unregistered
directory under `.rift/worktrees` is quarantined from use and removed after the configured orphan
grace period; Rift never adopts it. Disposable read, execution, and debugging worktrees have no
durable owner after restart and can be removed immediately.

Adapters open source with `open(2)`, so a real tree on disk is the interface. Source bytes stay on
disk. Adapters return `Edit` values, and Rift is the only source writer. `git diff` therefore contains
the session's complete source change.

Worktree materialization and language runtime selection have separate owners. The server resolves a
revision to an exact `Snapshot`, decides whether an existing physical tree represents it, and reuses
or allocates the tree. Only then does it call `Open`. The adapter never checks out or switches a Git
worktree; after receiving the complete tree, it selects the analyzer or project runtime appropriate
for that adapter state. If a later write changes runtime-defining configuration, `Refresh` makes the
adapter re-evaluate that selection before it acknowledges the new state.

### Capturing a mutable worktree

A working tree can change while Rift is reading it, so the server does not hand its live path to an
adapter-backed operation. It first writes an immutable Git tree from the bytes it observed and pins
that tree for the call. The capture starts from the worktree's `HEAD`, applies tracked modifications
and deletions, and adds untracked files that are not ignored. A path absent under an index
`skip-worktree` entry keeps its `HEAD` value; another absent tracked path is a deletion. Gitlinks
remain opaque entries, and untracked directories contribute their files rather than an
empty-directory record. An unmerged index or an untracked socket, device, or FIFO returns
`worktree_busy`.

Each changed entry in the capture manifest contains its project path, entry kind, executable mode,
and object id. A deletion carries its path and a deletion tag. Rift reads symlinks with `lstat(2)` and
records their link text, so it never follows one while capturing source. The SHA-256 of the canonical
manifest becomes `Snapshot.changes`; a mode-only change and a content change therefore have different
snapshot identities.

Rift records the `HEAD` object id and index checksum, opens regular files relative to a directory
handle without following symlinks, and verifies each file's identity before and after reading it. It
then repeats the complete status enumeration and manifest construction, including newly created and
removed paths. A changed `HEAD`, index, entry identity, or manifest causes another capture up to the
configured retry limit. Exhaustion returns `worktree_busy` and no snapshot. A successful response
identifies the immutable tree Rift actually read, even when the live worktree moves immediately
afterwards.

Captured trees and preview commits use the repository's ordinary Git object database. Rift does not
maintain an object quarantine. A dirty read or abandoned preview can therefore leave unreachable Git
objects, which ordinary Git garbage collection may reclaim later.

## Durability and recovery

Rift admits a workspace only when its state directories provide reliable file locks, atomic
same-filesystem rename, durable flush, and the registry's locking contract. A network or virtual
filesystem that cannot provide those operations returns `storage_failure` during admission, with the
unsupported capability in the error evidence.

Before a preview becomes ready, Rift flushes its candidate Git objects and durably commits the
registry record. Publication commits its intent before it attempts Git compare-and-swap, flushes the
updated ref before recording the terminal result, and reconciles any process death between those
steps on startup.

The registry carries its own format version. Startup migrates a supported older format under
`.rift/lease` before it accepts a connection. A newer or unknown format blocks startup with its
version in the diagnostic; Rift does not discard it or infer compatibility.

These boundaries cover a server or adapter killed at any instruction and an ordinary host crash.
Facts can be recomputed, and a torn session materialization or adapter cache can be rebuilt or marked
corrupt from the registry and Git. Rift detects missing objects and mismatched worktrees before using
them. Storage-media corruption, filesystem rollback from a machine snapshot, and manual changes under
`.git` or `.rift` require `rift preview resolve`, resource removal, or `rift state reset`; startup does
not guess which copy was newer.

The recovery conformance runner kills the server after every registry, Git-ref, and worktree boundary
in create, remove, publish, and reset. On restart, each fixture must reach its recorded terminal state,
resume an incomplete idempotent step, or return `state_corrupt` without changing the registry or Git. A
platform suite also cuts the server across an OS restart to verify the flush ordering. Adapter fixtures
kill each process during a streamed read, returned edit, execution, and debugging call to verify the
replay rules on the adapter page.

## Reads

Where a read resolves decides what it costs:

1. **Git objects.** `tree`, the file and diff resources, and text `match`. No adapter is required: any
   revision Git can resolve, every language.
2. **Retained facts.** `outline`, `search`, symbol and relationship reads at a snapshot already
   analyzed. The adapter can be stopped.
3. **An adapter.** The snapshot or fact family isn't retained. The server starts the adapter if
   it isn't running, opens a workspace on the tree, and runs `Analyze`.

An agent doesn't pick between them, so a question asked of a repository nobody has indexed still gets
an answer. Indexing a large repository takes minutes, though, and the request has a deadline. When
analysis won't finish inside it, the answer comes back with `Coverage.state: partial` and a reason
naming the indexing state.

The first page fixes an immutable result generation containing both facts and coverage. Its cursor
encodes the contract version, canonical request digest, snapshot cache key, result generation,
ordering mode, and last sort key. Following pages read that generation even when analysis has since
published more facts. Repeating the request without a cursor polls the newest generation. A cursor
expires when its semantic generation is evicted or the server exits, and the client starts again at
the first page. Mechanical reads use the resolved Git tree or object as their generation, so their
stateless cursors remain usable across a server restart while Git retains that object.

### Reading an older revision

An adapter opens files by path, and a commit is not a path. A semantic read at a revision that nothing
has checked out therefore gets a tree:

```
rift://symbol/python/pkg.util.load_config?rev=v1.2.0
  ->  <workspace>/.rift/worktrees/read-dae86e1   v1.2.0 is dae86e1
```

The detached checkout is shared by every session asking about that commit, reference-counted, and
removed after `reads.worktree-idle-timeout`. `reads.max-worktrees` caps how many exist at once; the
default is 2 because each one is a full source checkout.

A revision that names a mutable worktree goes through the capture path above. A branch name resolves
to its commit and reuses a read worktree only when that physical tree already represents the same Git
tree. Mechanical reads use Git objects directly and allocate no worktree.

## Execution and debugging

Execution is adapter-backed but does not run in an adapter state shared with reads or edits. The
server resolves `rev` to a `Snapshot`, materializes that state as a disposable execution workspace,
opens a fresh `AdapterState`, and lets the adapter select the same revision-appropriate project
runtime it would use for analysis. The caller-provided `CodeBlock` crosses the adapter seam directly;
it is not added to the Git tree.

`execute` is one-shot. Rift calls the adapter's `Execute`, closes the adapter state, and removes the
workspace after returning bounded output and diagnostics. Files written by evaluated code disappear
with the workspace and never enter a candidate, the session worktree, or the accepted ref.

A debugging session uses the same preparation path but retains the execution workspace and adapter
state. `debug_start` runs the block to normal completion or its first unhandled failure. A failed run
retains the stack as an ordered set of `DebugFrame`s; `debug_get_frame` reads one frame without
resuming the program. `debug_stop` releases the adapter-local handle, closes its adapter state, and
removes the workspace. This is post-mortem inspection, not a stepping debugger: breakpoints,
continue, and variable mutation are outside the initial interface.

The server mints the public debugging-session ID and binds it to the MCP connection. It maps that ID
to the adapter's private `DebugSessionKey`, exact `Snapshot`, language, adapter state, execution
workspace, and last-access time. The key contains the adapter token and pinned state and never crosses
MCP. A caller cannot name another connection's debugging session.

The execution workspace is disposable and retains the host access of `rift server`. Consequently
these tools are absent from `tools/list` unless user-owned policy grants them for this repository, the
committed configuration requests the same exact `Language`, its adapter advertises the corresponding
operations, and the execution conformance fixtures pass on this host. `LanguageSupport.execution`
reports that intersection. A conformance profile grants no execution authority.

### Admission and budgets

Admission happens before Rift creates a worktree. For `execute`, the language must appear in
`execution.allow` and advertise `execute`. For debugging, it must also appear in `execution.debug` and
advertise the complete `debug_start`, `debug_get_frame`, `debug_stop` triplet. Rift then checks the
UTF-8 code size, workspace-wide concurrent evaluation count, workspace-wide retained debug-session
count, and the selected adapter's effective state capacity. A refusal before admission allocates
nothing.

The smallest ceiling from machine policy, workspace policy, repository configuration, adapter limits,
and the request becomes an exact `ExecutionBudget` or `DebugBudget`. The adapter enforces evaluation
time, captured stdout and stderr, retained frames, bindings per frame, and captured bytes per rendered
value. The gRPC deadline may be shorter than the budget; the earlier one wins.

Rift resolves the block's working directory one path component at a time with symlink following
disabled. A symlink, gitlink, or path outside the captured tree returns `permission_denied` before an
adapter state is opened.

### Execution leases

Every admitted call acquires an internal execution lease. The server does not expose its identity:

```
session     ses_f8py…
snapshot    dae86e1…
language    python
workspace   <workspace>/.rift/worktrees/exec-71c2…
state       AdapterState after Open, once available
debug key   adapter token plus state, only after DebugStart
phase       materializing | opening | running | retained | releasing
```

The lease owns cleanup from the moment its workspace path is reserved. A one-shot execution moves
through `materializing → opening → running → releasing`. A successful `debug_start` moves from
`running → retained`; frame reads leave it retained, and `debug_stop` moves it to releasing. Any
failure or cancellation from any phase also moves it to releasing.

Release is ordered and idempotent: `DebugStop` when a debug key exists, then `Close` when adapter
state exists, then removal of the state root and execution workspace, then release of admission
capacity. Failure of one cleanup step does not skip the later steps. `DebugStop` itself is idempotent
while the adapter state lives, so a lost response can be retried safely.

After evaluation starts, the execution workspace is tainted: arbitrary code may have changed source.
Rift never calls `Refresh`, `Analyze`, or another execution against that state, and never commits or
reuses its tree. Cleanup is its only successor.

### Debug-session ownership and recovery

The public debug map is connection-scoped. `debug_get_frame` refreshes the last-access time;
`debug_stop` removes the active mapping and retains a lightweight stopped tombstone so an exact retry
can return the same success without retaining the workspace. The tombstone lasts until connection
close. A well-formed ID never minted on this connection, or one expired by `debug-idle-timeout`,
returns `resource_not_found`. Presenting an ID minted by another connection returns
`permission_denied` without revealing its owner.

Connection close stops all of its debug sessions. Adapter exit invalidates every debug session backed
by that process and releases their workspaces; the in-flight call reports `adapter_unavailable`, and
later frame reads report `resource_not_found`. On server startup, every `exec-*` or `debug-*`
directory lacks a live in-memory lease by definition and is removed during reconciliation.
Cancellation during `debug_start` publishes no debug-session ID. Cancellation of a frame read leaves
the debug session retained; cancellation during stop does not cancel cleanup.

### Reuse and required changes

| concern | reused interface or implementation | execution/debug shape |
| --- | --- | --- |
| Revision context | `Revision` resolution, exact `Snapshot`, Git materialization | The worktree allocator adds disposable execution and retained debug lease lifetimes. |
| Project runtime | `Open`, `AdapterState`, revision-local runtime selection, `Close` | Every execution gets a fresh state; a tainted execution state has cleanup as its only successor. |
| Adapter discovery | `Capabilities.operations` and repository `LanguageSupport` | `execute` stands alone; the debug operation triplet is admitted and advertised atomically. |
| Agent routing | generated MCP JSON-to-Protobuf mapping and repository tool manifest | Four tools are projected through per-language effective `ExecutionAvailability`. |
| Bounds and cancellation | MCP response ceilings, gRPC deadlines, cancellation, `Diagnostic` | Typed policy produces adapter-enforced budgets; `CapturedText` is shared by validators, execution streams, and debug values. |
| Debug ownership | connection-bound debug runtime and close reconciliation | A public ID maps to a private `DebugSessionKey`; active mappings and stopped tombstones have explicit cleanup semantics. |
| Host execution | validation-workspace materialization and cleanup machinery | Execution has separate authorization and no guarantee-evidence semantics; it does not reuse `CommandValidator`. |

The protocol defines the interface and executable schema contracts. The server implementation must
realize the lease state machine and the runtime conformance scenarios below through the existing
public methods.

### Execution conformance

An implementation advertises execution only after these fixtures pass with a real adapter:

| fixture | required observation |
| --- | --- |
| policy intersection | Unauthorized languages are absent from effective availability and allocate no workspace; partial debug operation advertisement is rejected. |
| snapshot context | Imports and runtime selection come from the requested snapshot, including a dirty-worktree snapshot, while the block itself creates no repository entry. |
| write discard | A block that rewrites tracked source and creates files changes neither the named snapshot, session worktree, candidate history, nor accepted ref. |
| budgets | Code size and admission caps fail with `limit_exceeded`; stdout, stderr, and debug values truncate at their budgets while preserving complete byte counts and digests. |
| timeout and cancellation | Deadline expiry and cancellation release every lease stage, including a call cancelled during materialization, `Open`, and adapter evaluation. |
| frame bounds | A failure deeper than `max-debug-frames` and a frame wider than `max-debug-bindings` return bounded, innermost-first results. |
| ownership | Another connection cannot inspect or stop the session; an unknown or idle-expired ID is not found. |
| idempotent stop | Losing the first stop response and retrying returns the same success with no retained adapter state or worktree. |
| adapter loss | Killing the adapter invalidates its sessions and removes their workspaces without affecting other language adapters. |
| restart reconciliation | Killing the server in every lease phase leaves directories that the next server removes before serving calls. |
| capacity | Concurrent calls never exceed `max-concurrent`, retained sessions never exceed `max-debug-sessions`, and both remain within effective adapter state capacity. |

## Writes

Each candidate tool resolves one operation into a fresh candidate worktree, validates the result, and
retains the plan under an identity derived from the durable session and request. A change that takes
several steps chains them: every tool takes `on`, the candidate it continues, and each step resolves
against its predecessor's tree. A root request supplies a `PublicationPlan`; a chained request inherits
that plan when it omits the field or fixes a replacement on the new preview. The ready preview records
the plan beside the candidate commit and fixed ref update. `publish` runs the tip preview's validators,
while `persist` materializes selected paths from an accepted commit into the session worktree.

The [MCP page](/docs/protocol/mcp) has the surface; what matters here is what waits on what:

- **Candidates don't block each other.** Each one builds its own candidate worktree from a base
  commit, so two in flight in one session run in parallel and neither touches the session tree. Two
  steps of the same chain do serialize, because the second resolves on the first one's tree.
- **`publish` claims one ready preview in the registry.** The preview's fixed inputs make
  `PreviewId` the retry key. Validation and the Git compare-and-swap run once in the ordinary case;
  crash recovery may repeat a validator whose completion was not recorded.
- **`persist` takes the session's write lock**, because it's the only operation that writes to the
  session worktree.

Candidate creation and `persist` touch session-local state. Integration introduces cross-session
contention by advancing a shared target ref.

### Persisting accepted paths

`persist` preflights the complete path set and response size before it writes. Once writing starts,
Rift holds the session write lock and finishes the bounded set even if the MCP caller disconnects.
Each regular file is written to a same-directory temporary path and atomically renamed; a deletion or
mode change is applied as its own path operation.

The filesystem has no transaction spanning several paths, so a server or host crash may leave a
prefix of the set materialized. The accepted commit remains unchanged in Git. Repeating `persist`
converges from that state: a path already matching the accepted entry is `unchanged`, an eligible old
entry is written, and a path changed independently is `skipped_drift`. Rift keeps no rollback journal
for a valid partial materialization.

### Publication recovery and evidence

The internal registry state machine moves from `ready` through `validating` and `publishing`, then to
`published`, `rejected`, or `conflict`. It is not part of the MCP schema. MCP exposes the stable
preview resource and ordinary `publish` result, while the registry records transition phases,
validator evidence, and recovery data.

Missing confirmation or a checked-out target leaves the preview ready. Validators run after the
registry records `validating`; a crash may therefore run one again. User policy may admit only
repeat-safe validation commands. A validation rejection and its bounded evidence become the terminal
registry result for that preview.

Before changing a ref, Rift records `publishing`, the destination, expected head, and candidate commit
in one registry transaction. Git then performs one compare-and-swap update and writes
`rift:publish:<preview-id>` in that ref's reflog. After success, Rift records `published`.

Startup reconciles a publishing row before serving the preview. A destination at the candidate or a
matching reflog entry proves publication. An unchanged expected head with no matching entry returns the
preview to ready. A definite compare-and-swap loss records conflict. If reflog deletion or rewritten
history removes the evidence needed to decide, MCP returns `temporarily_unavailable`; it does not
expose an internal `indeterminate` state. The local operator resolves that row with:

```
rift preview resolve prv_04ad... --published
rift preview resolve prv_04ad... --ready
```

Repeating `publish` returns a terminal registry result. Changing the destination, expected head, or
validator declarations requires `refresh`, which creates a new preview and worktree.

## Integration

An accepted commit is reachable from the session's accepted ref. `integrate` merges it into a
local target branch. Git derives the merge base from the accepted commit and target head:

```
B ── X ── Y      main
 \
  └── A          refs/rift/accepted/ses_f8py…
```

Rift merges `A` into `Y` using `B`, in a candidate worktree. The merge result is a candidate like any
other: adapters refresh onto it, `Validate` runs over the closure the merge touched, and any declared
validators run. Two valid commits can form a broken merge: `Y` can rename a function that `A` added a
call to. Validation therefore runs on the merge candidate.

| result | what happened |
| --- | --- |
| `prepared` | a conflict-free merge candidate and its validation were retained; no ref moved |
| `merge_conflict` | a parseable provisional merge and the three entries for each conflict were retained |
| `refreshed` | the retained contract was rebuilt against the current target head |
| `integrated` | fresh validation passed and compare-and-swap advanced the target |
| `rejected` | fresh validation failed; the retained evidence names the failure |
| `refused` | repository state or policy prevented publication — `checked_out_target`, a missing confirmation, or an authorization failure — and a validated candidate is returned when available |
| `conflict` | the target moved after the candidate was built |

Compare-and-swap on the target is where two sessions actually contend. Both integrating into `main`
serialize, and the loser re-merges against the head that won.

### Conflicts

A conflicted result returns the base, source, and target entry for every conflicting path. Its
two-parent provisional merge contains automatic resolutions and retains the target entry at each
conflict. No conflict markers are written into any tree, because a tree full of `<<<<<<<` is a tree
no adapter can parse and therefore a tree
Rift can't validate or ask an adapter about.

Resolve the conflict with any candidate tool whose `on` is that provisional merge and whose
`expected_accepted` is the conflict result's `source` — concrete edits, a patch, or an adapter action.
The source must be an ancestor of the provisional merge, which gives publication a valid
compare-and-swap base. Publish the repair to the accepted ref, then integrate again. The new merge is
normally a fast-forward or a conflict-free merge because the repair commit descends from both
parents.

### Targets

Rift advances a local branch only when Git reports that no worktree has it checked out. When the target
is checked out, publication returns
`checked_out_target` with the prepared commit and leaves the branch, index, and working files
unchanged. The user can inspect the commit and merge it with ordinary Git.

Updating a checked-out branch would require changing its ref, index, and files across separate
filesystem operations. Git provides no transaction covering those three stores, so Rift does not
offer an automatic mode.

## Facts

The server stores results from `Analyze` in process memory. One analysis builds a private fact
generation while existing readers continue against the generation they already hold. Publishing that
generation makes its facts and family coverage visible together.

A retained snapshot key contains:

```
source tree id
protocol schema digest
adapter artifact digest and implementation version
exact Language
effective repository and workspace configuration digest
runtime-environment fingerprint
ordered virtual-input digests
```

The adapter artifact digest covers the executable Rift launched. A version string alone would let a
replaced binary reuse facts produced by different code. The runtime fingerprint covers dependency
and toolchain inputs that can change without changing the source tree.

Each `Analyze` result declares a cache scope:

| scope | retention rule |
| --- | --- |
| `snapshot` | Rift may reuse the result across adapter states and adapter-process restarts while the server lives |
| `process` | Rift keeps the result only while the adapter process and state generation that produced it remain valid |
| `none` | Rift does not retain the result |

A virtual-source chain inherits its shortest scope. Process-scoped producer output makes downstream
analysis process-scoped; request-volatile producer output prevents downstream retention.

An adapter may claim `snapshot` only when the same key produces byte-for-byte equal canonical records.
The conformance suite runs the same analysis in fresh processes and compares its ordered output.
Host state the adapter cannot fingerprint requires `process`; request-volatile output uses `none`.

Analysis builds facts and coverage privately, then publishes both under a new immutable generation
ID. A complete empty family therefore differs from a family with no coverage. Later analysis
publishes another generation without changing the one being paged. An active page read pins its
generation; between calls the generation follows the ordinary LRU policy, so its cursor can expire.
A ready preview pins the semantic entries used to inspect it until the server exits.

Nothing is analyzed when the server starts. The first semantic read of a snapshot triggers only the
analysis it needs. `rift facts warm` warms the store explicitly for callers that prefer the up-front
cost.

The store is a cache. `facts.max-size` evicts least-recently-used generations with no reader or
ready-preview pin. Server exit drops the complete store, so the first semantic read after restart runs
the required adapters again. Git-backed reads and the durable preview registry remain available while
that analysis warms.

## Scheduling and logs

The server puts each session into a bounded request queue. Connections attached to the same session
feed that queue in admission order. The scheduler dispatches one ready request per session in round-robin
order, then starts the next round. Adapter-wide and per-state in-flight
limits still apply, so one session waiting on a large analysis cannot fill every adapter slot.
Requests beyond the queue bound fail with `limit_exceeded` before allocating a worktree.

Every request gets a random request id. The id travels in gRPC metadata, structured MCP errors, and
the registry's bounded request log. Log records contain the session id, method, phase, duration,
byte counts, result code, and adapter generation. Source text, code blocks, environment values, and
debug bindings are redacted. Collection applies the configured byte and age bounds.

A panic or adapter protocol failure terminates its request boundary. The server records the request
id, releases the request's leases, and keeps unrelated sessions running.

## Paths Git doesn't track

Candidate commits are built from the base tree plus the resolved edits, with Git plumbing. There's no
index and no `git add` involved, so a file an `Edit` creates is in the candidate tree. Incidental
files created by an adapter process stay outside the commit.

An edit on a path matched by `.gitignore` fails the `writable` precondition, and the refusal carries
the path and the rule that matched it. The commit would otherwise carry a file that your own
`git status` hides from you, which puts what Rift validated and what you can see out of step.

Command validators start in a validation workspace copied from the candidate, which contains tracked
files only. A test suite that needs an untracked `.env.test` requests it through `validators.carry`.
User-owned workspace policy has to grant the same path. Rift opens every path component without
following symlinks and copies only a regular file or directory still contained by the workspace.
The validation workspace retains the command's host access.
