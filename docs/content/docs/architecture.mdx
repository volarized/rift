## Workspace layout

Rift keeps native control state separate from the mounted subtree:

```text
<workspace>/.rift/
├── lease                    # workspace identity, endpoint, and negotiated contract
├── run/                     # sockets and frontend state
├── store/                   # authoritative source store; engine deliberately unspecified
├── adapter-state/           # rebuildable adapter-owned state roots
├── projections/             # the only mountpoint
└── recovery/                # exceptional conventional Git worktrees
```

Mounting `.rift/projections` never hides the lease, socket, store, or recovery records. A fresh
mount refuses a symlink or non-empty directory. Before that check, a new lease owner compares the
platform mount record with Rift's persisted workspace identity and mount epoch. It reclaims a stale
Rift-owned mount whose previous lease is no longer held; it never unmounts an active or foreign
filesystem. Failure to prove ownership returns `projection_unavailable`. Windows applies the same
empty-directory rule after a stale reparse point has been reclaimed.

One server owns the workspace lease, the store writer, the projection registry, adapters, and Git
publication transactions. It stays resident while any projection is mounted. An idle policy can
stop adapters and derived indexes, but cannot exit the filesystem service. A clean stop withdraws
new opens, drains filesystem requests, unmounts, closes the store, and releases the lease in that
order. Restart reconciles incomplete integration intents before remounting.

Every frontend request carries the current mount epoch. Store admission rejects an older epoch even
if a crashed frontend delivers a late request. A server or frontend crash makes existing handles
return `ESTALE` or `EIO`; handles are not silently rebound to a remount. The next mount uses a fresh
epoch and accepts new opens after recovery.

The platform frontend is replaceable:

- Linux opens `/dev/fuse` through the installed FUSE helper.
- macOS uses a signed FSKit extension forwarding requests to the workspace server.
- Windows uses the installed WinFsp driver and a directory mount.

The frontend authenticates the peer user and workspace lease. The persistent store never depends
on one frontend's inode or path representation.

## Source state without Rift history

Rift separates content, concurrency, and namespace identity:

```text
SnapshotId
  content address of one complete immutable source tree

ProjectionHead
  fresh opaque token for one current mutable state

Projection
  stable identity of one mounted namespace

ProjectionState
  { projection, head, snapshot, base: { snapshot, Git commit }, dirty }
```

`ProjectionState.base` is the one retained baseline for restore and three-way integration. Its
snapshot is a complete store copy of the named Git commit's tree. The projection pins both its
current and base snapshots, so it remains readable if Git later removes an object. `dirty` is true
exactly when the two snapshot ids differ.

There is no Rift history graph. A successful source mutation atomically replaces the current
snapshot and mints a fresh `ProjectionHead`, even when content changes A→B→A. The store does not keep
parent links, old heads, sequence history, completed responses, or an operation journal. Git remains
available for navigating history that already exists, while superseded unpinned Rift snapshots are
collectible.

The authoritative store contains only:

- current projection and scratch records;
- immutable blobs and tree nodes reachable from current state or an active pin;
- the single base of each writable projection;
- active cursor, file-continuation, adapter, execution, read-projection, diff, and recovery pins;
- temporary integration intents needed for crash completion;
- rebuildable semantic facts and search indexes.

Copying a `SnapshotId`, match id, or action id does not create a retention lease. Cursors, returned
file-continuation URIs, diff links, and adapter calls create bounded connection-scoped pins.
Consumption, explicit close, server-defined expiry, or connection close releases them; the protocol
deliberately promises no minimum lifetime. A stateless id can therefore survive restart yet later
return `snapshot_not_found`.

## Snapshot encoding

`SnapshotId` is `snap_` followed by lowercase SHA-256 of this byte stream:

```text
"rift-snapshot\0" || u32be(1) || root-tree-digest
```

Tree nodes are Merkle records. Entries are sorted by unsigned UTF-8 path-component bytes and hash:

```text
u32be(name_length) || name_bytes || u8(kind) || u32be(payload_length) || payload
```

The kind and payload are:

| Kind | Byte | Payload |
| --- | ---: | --- |
| regular | `1` | `u8(executable) || u64be(size) || file_root` |
| symlink | `2` | `u32be(target_length) || raw_target_bytes` |
| gitlink | `3` | `u8(object_format) || raw_object_id_bytes` |
| subtree | `4` | child tree's 32-byte SHA-256 digest |

`object_format` is `1` for SHA-1 and `2` for SHA-256. Names are non-empty UTF-8 without `/` or NUL.
Symlink targets are the raw Git blob bytes and need not be UTF-8; `FileContentSymlink` exposes the
same bytes as canonical padded base64. Empty directories, scratch, synthetic `.git`, inode numbers,
timestamps, and host ownership are excluded. A tree digest is exactly:

```text
sha256("rift-tree\0" || u32be(1) || u64be(entry_count) || record_1 || ... || record_n)
```

Regular files use a fixed 65,536-byte chunk Merkle tree. A leaf is
`sha256("rift-blob-leaf\0" || u32be(length) || bytes)`. Consecutive hashes are grouped left to right
in groups of at most 256; level `n` is
`sha256("rift-blob-node\0" || u32be(n) || u16be(count) || child_hashes)`, starting with level 1 and
repeating until one hash remains. One non-empty chunk uses its leaf directly; an empty file uses
`sha256("rift-blob-empty\0")`. The public `file_root` and `FileContentRegular.digest` are:

```text
sha256("rift-blob\0" || u32be(1) || u64be(size) || u64be(chunk_count) || top_hash)
```

This byte-exact form commits to all raw bytes while a random write rehashes only touched chunks and
their logarithmic path. Conformance vectors cover empty files, chunk boundaries, partial final
chunks, all tree entry kinds, and both Git object formats.

## Projection kinds and discovery

Every MCP session immediately owns one persistent writable projection. `projection_open` adds an
explicit immutable read projection for an imported Git revision or retained snapshot. Internal
candidate, validation, execution, and debug mounts use unadvertised namespaces and never appear in
`rift://fs`.

`rift://fs` lists only session and explicit read projections, including their mounted paths, exact
snapshots, availability, write policy, scratch usage, and open-handle counts. Its first page captures
one identity-sorted inventory for that connection; a cursor reads later pages of the same capture or
expires. Reading the resource grants no close authority. Only the connection that called
`projection_open` can close that explicit read projection. Connection cleanup and explicit close
withdraw its namespace from discovery and reject new opens, while existing handles retain their
inode-version pins until the last close. It reports current namespaces, not a projection timeline.

Every advertised projection contains a read-only synthetic regular file named `.git` with the bytes
`Rift filesystem projection; Git is available only in .rift/recovery\n`. That deliberately invalid
gitfile makes Git stop discovery with a nonzero error instead of walking upward into the physical
checkout. The entry is not source, scratch, snapshot, tree-resource, or exportable content; import
rejects a repository tree that tries to supply the reserved root name. Git works normally only in
`.rift/recovery/<recovery>`.

## Source and scratch

Source snapshots contain Git-representable regular files, executable bits, symlinks, and opaque
gitlinks. Empty directories are persistent projection metadata but are absent from source snapshots,
tree resources, and Git export. Gitlinks render as non-writable empty directory boundaries; reads or
writes below them fail.

Generated output belongs to a separate scratch layer. Classification uses only `.gitignore` files
from the current source snapshot; global excludes and `.git/info/exclude` never change server
semantics. An existing source entry remains source when modified or renamed. A new ignored path is
scratch, while a new non-ignored path is source. Cross-layer rename follows the destination:

- scratch renamed over an existing source path atomically replaces source and mints a source head;
- scratch renamed to a new non-ignored path becomes source;
- source renamed anywhere remains source, matching Git's treatment of tracked ignored paths;
- scratch renamed to another absent ignored path remains scratch.

This covers editor temp-file-plus-rename saves without making compiler churn stale source
operations. Scratch is persistent for tool reuse but explicitly disposable: it is excluded from
snapshots, diffs, restore, integration, and source CAS. There is no initial scratch-promotion API.
Tools promote output by copying or renaming it to a non-ignored source destination. Session removal
reports an estimate of scratch bytes. Confirmation first requires no live connection or handle,
withdraws the namespace under the open-admission barrier, rescans the final scratch size, and may
then delete scratch without a review token. Scratch is never durable user source; confirmation
guards source exactly but intentionally treats all scratch as disposable.

Changing `.gitignore` does not migrate existing entries between layers. Existing source remains
source and existing scratch remains scratch; a path removed and later recreated is classified using
the then-current source ignore rules.

The merged namespace never contains two leaf entries at one path. A directory rename evaluates
every source and scratch descendant by the rules above and commits the complete subtree move in one
store transaction. The destination must be absent or an empty directory when the platform permits
replacement. Any collision, host-incompatible path, gitlink boundary, or quota failure rejects the
whole move. Directory enumeration derives the union of source, scratch, and persistent empty-
directory metadata after that transaction; no caller observes a half-moved mixed-layer subtree.

Whole-source publication also preserves the one-leaf invariant. Source wins over scratch for an
exact path and for file-versus-descendant prefix collisions. Restore, semantic publication, and
integration atomically unlink every conflicting scratch name before exposing the new source tree;
non-conflicting scratch remains. An already-open scratch handle retains its now-unlinked inode
version until close, exactly like an unlinked source handle. Scratch is disposable, so this needs no
confirmation or separate result variant.

## Filesystem mutation contract

The initial frontends disable deferred writeback for source and scratch files. Scratch writes are
durable too, but do not mint a source head. A successful mutating syscall returns only after its
authoritative store transaction is durable:

- `open(O_CREAT|O_EXCL)` checks the merged namespace atomically; `O_TRUNC` publishes an empty file,
  and each `O_APPEND` write chooses end-of-file while holding that inode's write lock;
- `write`, truncate, executable-bit change, source rename, symlink creation, and source unlink
  commit a complete new source snapshot and fresh projection head;
- `fsync` and `fdatasync` wait through the latest store commit touching that handle;
- `close` reports a deferred write error when the platform can surface one;
- `mkdir`, empty `rmdir`, and directory metadata affect projection metadata, not source identity;
- ordinary rename and `RENAME_NOREPLACE` are supported; `RENAME_EXCHANGE`, whiteouts, and replacing
  a non-empty directory return `EOPNOTSUPP` or `ENOTEMPTY` without mutation;
- `symlink` stores raw target bytes and `readlink` returns them without following; traversal never
  crosses a symlink or gitlink inside a server operation;
- `chmod` changes only the Git executable bit; `utimens` persists requested `mtime` while the server
  assigns `ctime`; neither timestamp participates in source identity;
- whole-file and byte-range advisory locks are volatile server locks scoped to the live mount;
- writable shared `mmap`, xattrs, ACLs, hard links, ownership changes, sockets, devices, and other
  special files are refused. Read-only and private mappings use the immutable bytes of their handle.

Concurrent writes may be batched into one store transaction, but every successful call waits for
the batch containing it and visibility remains ordered: readers see the state before or after that
transaction, never partial file content. Multi-syscall editor saves are not globally atomic. MCP
changes and external writes serialize at a short projection publication barrier; a stale expected
head is never overwritten.

Open file descriptions use stable inode identities independent of paths. Unlink removes the name
while existing handles retain that inode's bytes. Atomic replacement gives later opens a new inode,
while old handles keep the replaced inode. Rename preserves inode identity. A directory handle sees
the enumeration captured on its first read. Ordinary in-place writes update a handle's current inode
version and do not pin every previous projection snapshot.

A write through an unlinked handle durably updates only that handle's inode version; it cannot
re-enter source and does not mint a projection head. The inode becomes collectible after its final
handle closes. An MCP publication treats each changed path as an atomic replacement, so handles
opened before publication keep their prior inode versions while later opens resolve the new tree.
Unchanged paths preserve inode identity.

For writable projections, inode numbers derive from workspace identity plus stable inode identity.
For immutable projections, they also include `SnapshotId`. `mtime` and `ctime` use the server's
monotonic-clamped wall clock at the durable mutation; rename updates the moved entry's `ctime` and
both parent directories, content and mode changes update both file times, and reads do not update
`atime`. Timestamps are stable across restart because current inode metadata is stored.

Frontend error mapping is stable: missing and existing-name conflicts use `ENOENT` and `EEXIST`, a
non-empty directory uses `ENOTEMPTY`, a read projection or gitlink boundary uses `EROFS`, unsupported
operations use `EOPNOTSUPP`, quota exhaustion uses `ENOSPC`, and a fenced or incoherent mount uses
`ESTALE` or `EIO`. Windows frontends map these to their documented Win32 equivalents. A failed
precondition never publishes part of a mutation.

## Cache coherence and watchers

Each committed source mutation follows this observable order:

1. Commit source bytes, tree nodes, inode metadata, and the fresh head in one durable transaction.
2. Invalidate affected inode attributes, directory entries, and page-cache ranges.
3. Emit an internal normalized path event carrying the new head and request platform watcher hints.
4. Admit adapter refresh from the last acknowledged snapshot to the new complete snapshot.
5. Return to the syscall or MCP caller.

The frontend uses direct I/O or the platform's coherent invalidation primitive; it may not serve
unvalidated cached file bytes. Invalidation failure fences the mount epoch, revokes or force-detaches
the frontend, and makes later calls and already-idle handles return `ESTALE` or `EIO` instead of
stale page, attribute, or dentry cache data. A mutating syscall whose durable store transaction
completed returns success when its reply channel still exists, even if fencing is required; Rift
does not invite a retry that could duplicate `O_APPEND`. A crash or lost transport can still make a
syscall outcome unknowable, as with an ordinary local filesystem. New opens fail until a fresh
remount. An MCP mutation returns committed-but-degraded with its current state.

Mutations entering through a mount produce that platform's ordinary native watcher events.
Out-of-band MCP/store publication requests the strongest invalidation or change hint the frontend
offers, but does not promise a synthetic inotify, FSEvents, or Windows move sequence where the host
API cannot inject one. Such consumers treat a hint or overflow as a rescan request; Rift adapters
use the exact internal head-bearing stream. Adapter refresh failure closes that adapter state and
rebuilds it lazily without rolling back source.

The filesystem mutation barrier is never held across adapter RPC, validator execution, evaluated
code, or watcher consumption. A separate adapter-admission gate prevents analysis calls from using
an acknowledged state while refresh replaces it. Multiple filesystem mutations coalesce into one
delta from the adapter's last acknowledged snapshot.

## Sessions and changes

A new session can import an explicit Git revision supplied during `Connect`. Otherwise
`session.base = "head"` resolves and imports HEAD once. An unborn repository is refused until it has
an initial commit. Rift never captures physical working-tree bytes: doing so would mix
clean/smudge, line-ending, encoding, LFS, and submodule checkout representations with canonical Git
blob bytes.

Ordinary FUSE writes and semantic tools both persist directly in the source store. Neither creates
a Git commit or ref. A semantic change:

1. compares and pins the complete expected `ProjectionState`;
2. forks a private copy-on-write candidate from its current snapshot;
3. resolves edits and formatting in that candidate;
4. refreshes adapters and validates the exact candidate snapshot;
5. acquires the short publication barrier and compares the expected head again;
6. atomically publishes the candidate with a fresh head, then releases the barrier;
7. invalidates caches, notifies watchers, refreshes public adapter state, and returns.

No lock is held during steps 3 or 4. Refusal, validation failure, cancellation, and a stale head
leave public source unchanged. The response diff uses immutable snapshot selectors and owns a
bounded connection-scoped pin for both sides. A lost successful response is not replayable: retrying
the old expected state returns `stale_projection`, and the caller reads current state and its diff.

`projection_restore` compares the exact current state and returns to the pinned base snapshot with a
fresh head. `session_remove` previews `state.dirty`, scratch bytes, and reclaimable store bytes.
Confirmation compares the same source head, requires no live connection or handle, withdraws the
namespace under the open-admission barrier, and removes the session. Because there are no session
Git refs, removal cannot orphan Git history.

## The narrow Git boundary

Rift uses Git only where its existing format and algorithms are useful:

- resolve a branch, tag, or commit once, peel it to a commit, and import its tree for historical
  navigation or a new session base;
- read and write canonical blobs, modes, trees, commits, and refs through a library API;
- apply Git-compatible built-in three-way merge rules during integration;
- use an atomic target-ref compare-and-swap as the external publication boundary;
- provide a conventional recovery worktree only when the merge cannot be completed safely.

Rift does not use a Git index, worktree, commit, or ref for ordinary projection persistence. It does
not mirror every mutation into Git, run repository hooks, sign commits, fetch implicitly, or execute
clean/smudge filters, LFS downloads, `working-tree-encoding`, or custom merge drivers. Git blobs are
canonical bytes. Missing promisor objects and shallow-history gaps fail without network access.

An imported symbolic selector reports both the content-only `Snapshot` and the peeled Git commit as
resolution evidence. Moving the original ref never mutates the imported snapshot. Gitlinks remain
opaque object ids in the repository's configured object format.

Integration reads only committed `.gitattributes` from the expected target tree. It ignores global
attributes and `.git/info/attributes`. Built-in text/binary merge selection is supported. A custom
merge driver creates recovery; `merge.renormalize`, filter-dependent normalization, and attributes
whose semantics require an executable filter are refused as unsupported rather than guessed.

## Squash integration

`integrate` accepts an exact projection state, target branch, expected target commit, and subject.
Rift computes the source delta from `state.base.snapshot` to `state.snapshot`, merges it onto the
expected target tree, and validates the complete merged snapshot in a disposable projection. If the
merged tree equals the target tree, Rift creates no commit and only rebases the session to that
target. Otherwise it writes one commit whose sole parent is the expected target and whose tree is
the merged snapshot. This is an explicit squash publication; Rift creates no synthetic public
source branch or merge topology.

Commit encoding is UTF-8 with one subject and a trailing newline. The supplied subject contains no
NUL or line break. Author and committer are `Rift <rift@localhost>`. Their UTC timestamps, timezone
`+0000`, message bytes, parent, and tree are captured once in the integration intent. Rift runs no
hooks or signing. The target reflog message is `rift: integrate <session>`.

The target-equivalent `synchronized` path does not use the commit transaction below. Rift acquires
the projection barrier and the target ref lock, verifies both exact guards, and atomically rebases
the store projection to the already-imported target snapshot with a fresh head. It then releases the
ref lock without changing Git. A crash is therefore wholly before or after one store transaction.
For recovery synchronization, that same store transaction marks the recovery `cleanup`; restart
then idempotently removes its worktree, private ref, and pins before deleting the cleanup record.

Validation and Git object writes happen without the publication barrier. Final publication:

1. acquires the projection barrier and rechecks the exact source state;
2. reserves the store records needed for finalization and persists a `prepared` integration intent
   pinning source, base, target, merged snapshots, and the captured commit bytes; continuation also
   records its `RecoveryId`;
3. uses one Git ref transaction to verify and update target old→new and create the private marker
   `refs/rift/transactions/<intent>` at the new commit;
4. in one store transaction, rebases the projection to the merged snapshot and new Git base with a
   fresh head, marks the intent `finalized`, and changes a continued recovery from `active` to
   `cleanup`;
5. deletes the Git marker, then deletes the store intent;
6. releases the barrier and performs cache notification.

Restart reconciles intents before mounting. For a `prepared` intent, a present marker proves the Git
transaction committed: Rift verifies the commit tree and retries finalization even if another actor
later moved the target. A missing marker proves publication never committed, so Rift aborts that
intent. For a `finalized` intent, Rift deletes a remaining marker and then the intent; a missing
marker means cleanup had already reached that step. A storage failure after Git publication fences
the projection and keeps retrying the reserved finalization; the initiating call returns no normal
integration result and may end with `temporarily_unavailable`, explicitly noting that Git
publication completed. Rift never rolls the target back.

Startup also scans transaction markers. An orphan marker is removed only when a finalized
projection base names its commit; every other orphan is `state_corrupt` and requires `rift state
check`. Marker deletion always precedes intent deletion, so absence is never mistaken for an
unpublished transaction. Marker refs and intents are transient recovery state, not navigable
history.

Integration refuses a target checked out in any Git worktree, including the physical workspace
root. Rift never tries to synchronize an ordinary checkout, apply filters, overwrite an initialized
submodule, or leave a partially updated index. The caller selects an un-checked-out publication
branch or detaches that checkout before retrying.

## Merge recovery

Built-in clean merges never expose Git. Conflicts or a path selecting a custom merge driver create
one conventional worktree under `.rift/recovery/<RecoveryId>`. Rift creates a synthetic base commit,
target and source commits parented by that base, and a private anchor commit whose parents are the
target and source commits. `refs/rift/recovery/<RecoveryId>` points to the anchor while Rift writes
the unmerged stages into that worktree's index. Every blob and commit needed by the stages is thus
reachable from the private ref as well as reconstructible from pinned snapshots; repository GC
cannot strand an active recovery. These commits never become public parents.

The durable recovery records the exact source state, target guard, message inputs, reason, conflict
or driver paths, and a canonical index/worktree manifest. The operation key is SHA-256 of RFC 8785
canonical JSON containing the exact source state, target, expected target, and normalized commit
subject. An exact retry after a lost conflict response therefore returns the active recovery instead
of creating a second one. `recovery_list` rescans and returns every active recovery and its latest
manifest.

The index manifest is SHA-256 of `"rift-recovery-index\0"`, an unsigned 64-bit entry count, then
entries sorted by path bytes and stage. Each entry contains length-prefixed path bytes, one stage
byte, a big-endian 32-bit mode, an object-id length, and raw object-id bytes. The worktree manifest
uses `"rift-recovery-worktree\0"` and records the sorted union of index and worktree paths with an
explicit absent, directory, regular, or symlink kind. Regular and symlink payloads use the snapshot
encoding; directories include mode and remain present even when empty. `.git` administrative state
is excluded. A special file makes the recovery ineligible for continue or protocol cleanup;
`recovery_continue` or confirmed abort returns `unsupported_path` until the user removes it and
reviews a new manifest.

The user resolves files and stages the intended result with ordinary Git commands in that one
directory. `recovery_continue` requires the supplied manifest to match, no unmerged index entries,
and no unstaged or untracked paths. Rift imports the index tree, validates it, rechecks both source
and target, and performs the same one-parent squash publication. Any commit the user created in the
recovery is ignored; only the staged tree is imported. A target-equivalent resolution synchronizes
without a commit. Validation rejection or a newly checked-out target retains the recovery and
returns refreshed evidence; successful integration or synchronization cleans it up. Obsolete
results return expected and current source, target, and manifest values, with a null current target
when the branch was deleted.

Recoveries have one durable lifecycle: `active` or `cleanup`. `recovery_list` returns only active
records. `recovery_abort` first previews the exact manifest; confirmation locks and rescans it, then
atomically changes the record to cleanup before touching Git. Successful continuation enters cleanup
in the same store transaction that publishes its rebased source state. Cleanup idempotently removes
the worktree and private ref, releases pins, and only then deletes the store record. Startup finishes
every cleanup record before serving recovery operations, so a crash cannot resurrect a completed
recovery or expose a half-removed one. Special-file rules still apply before the active→cleanup
transition. Recoveries survive restart and are never garbage-collected merely because the
originating response was lost.

## Store requirements

The database implementation is deliberately unspecified. It must provide atomic multi-record
writes, durable sync, content-addressed point reads, ordered projection metadata, checksums, crash
recovery, online reads during compaction, bounded write amplification, and atomic schema migration
under the workspace lease.

The engine's write-ahead state exists only for crash recovery, is periodically compacted, and
cannot be queried as mutation history. Current heads, bases, active pins, scratch, and integration
intents are authoritative. Semantic facts and indexes are keyed by snapshot and adapter build and
may be rebuilt after corruption or eviction.

The server advertises store-byte and record ceilings. A write exceeding either fails before source
publication with `limit_exceeded` and matching `LimitEvidence`. Garbage collection uses
transactional reachability from current states, bases, active resource pins, open unlinked inodes,
recoveries, and intents.

Pin acquisition and root removal serialize with the collector. A caller first inserts a pin only if
the complete object root is still live; a sweep cannot delete an object after that transaction.
Publishing a new state transfers the operation pin on the old snapshot to any returned diff,
cursor, or file-continuation pin in the same transaction that removes the old current-state root.
Reading file page N acquires page N+1's pin before releasing page N. Adapter refresh pins
both endpoints before admission. Closing a read projection transfers each live handle to an inode-
version pin before releasing the projection snapshot. A read of an unpinned id atomically acquires a
temporary pin or returns `snapshot_not_found`; it never races a successful sweep. These handoffs,
not copied identifiers, define retention.

## External-tool compatibility

Editors, compilers, language servers, formatters, and build systems can use a projection through
ordinary filesystem APIs. They observe persistent bytes, atomic rename, stable handles, executable
bits, symlinks, coherent timestamps, invalidation, and native watcher events for writes made through
that mount. Out-of-band MCP changes are always cache-coherent but watcher delivery is platform-best-
effort. Tools that require hard links, special files, host ACLs or ownership, repository filters,
submodule checkout, or a conventional Git worktree are not compatible with normal projections.

Conformance tests cover:

- source writes, temp-file replacement, fsync, rename, unlink-open, and crash restart;
- simultaneous MCP and external writes with ABA-safe stale detection;
- cache invalidation, mount-originated watcher events, out-of-band watcher hints and rescan,
  stable timestamps, and remount recovery;
- scratch classification and every cross-layer rename case;
- Git-discovery blocking in normal projections and working Git in recovery;
- snapshot hash vectors for every entry kind and repository object format;
- integration kills before and after intent sync, marker creation, target CAS, and store finalize;
- recovery retry, discovery, manifest comparison, continue, abort, and cleanup;
- garbage collection while every pin and open-handle kind is active;
- parity across FUSE, FSKit, and WinFsp frontends.
