Rift doesn't provide a standalone agent. It works as a toolkit for an agent like Claude Code, Codex,
or any other LLM appliance that speaks
[MCP](https://modelcontextprotocol.io/specification/latest).

When an agent has Rift configured as one of its MCP servers, the `rift mcp` process starts and checks
whether a `rift server` is already running for that particular folder — which we'll call the workspace
throughout this documentation.

The `rift server` coordinates between one or several `rift mcp` instances and configured language
adapter processes. A language adapter is a subprocess that talks to the server and gives Rift its
introspection into a language's facts and operations. The server starts at most one configured gRPC
adapter process for each exact `Language` — a name plus an optional dialect. `sql:postgresql` and
plain `sql` therefore select different configured processes. Each process can hold separate
`AdapterState`s for several snapshots and back them with separate runtime workers.

<Callout type="info" title="Why the adapter is a process of its own">
  A [tree-sitter](https://tree-sitter.github.io/tree-sitter/) parser can recover concrete syntax, but
  it doesn't resolve bindings or types. [LSP](https://microsoft.github.io/language-server-protocol/)
  exposes the operations an editor needs, which doesn't include every fact or refactor Rift carries.
  A language adapter calls the language's compiler or analyzer APIs and translates their results
  into Rift messages. Running it as a subprocess keeps language runtimes and dependencies out of
  `rift server`. When two revisions require incompatible project runtimes, the adapter can put a
  separate runtime worker behind each adapter state while retaining one stable gRPC process.
</Callout>

Each `rift mcp` connects to the shared server over a Unix domain socket, or a named pipe on Windows.
If nothing is listening, the MCP process launches the server before forwarding the request.

You might be asking what the actual reason for this is, and the answer is rooted in the MCP protocol
itself. Assume your agent launches a couple of subagents. Each of them might also want to read or edit
the codebase through Rift, and none of them can reach the `rift mcp` process the others are using —
each gets its own, because MCP's stdio transport has the client launch its server as a subprocess. We
use stdio to avoid managing ports.

At the same time, the `rift server` keeps state those editors have to agree on: the worktrees they
edit in, and the analysis results already computed over the code. It also owns the language adapters,
so every subagent drives the same set of them instead of paying to start its own. None of that
survives in a `rift mcp` process that exits with the subagent that launched it.

`rift mcp` holds no state of its own. It validates the agent's JSON against `mcp.json`, converts it to
the Protobuf message the schema names, calls the mapped gRPC method, and converts the response back.
Restarting it costs a process launch.

## Server lifecycle

As said above, `rift mcp` checks whether a `rift server` is already running for the workspace, and
starts one if it isn't:

```
~/projects/charming-aurora                  the workspace — a directory with a .git in it
  .rift/run/server-{version}.sock           the server listens here
```

From the implementation perspective, `rift mcp` takes an exclusive `flock` on
`.rift/run/server-{version}.lock` so two of them can't start a server at once, looks again in case
another `rift mcp` won that race, and spawns the server in a detached process group so that the agent
exiting later doesn't take the server with it. Once the socket accepts, `rift mcp` drops the lock. A
socket that exists but refuses a connection is a server that died, so the same path unlinks it and
starts a new one.

The `{version}` in those names is the protocol's major version, which is what keeps incompatible
builds apart: a `rift mcp` speaking protocol 2 finds no `server-2.sock`, so it starts its own rather
than talking to the protocol 1 server already listening. Within one protocol version the wire is
compatible, so a client uses whatever server it finds; run `rift server restart` when you want a
newer build to take over.

The server exits after `server.idle-timeout` with no open connection. Adapter processes can retain
large indexes, so an idle repository should release them.

<Callout>
  On Windows the socket is a named pipe, `\\.\pipe\rift.server-{version}.<digest of the workspace
  path>`. Nothing else in this page changes.
</Callout>

## The `.rift` directory

Everything the server owns on disk lives in one directory next to your source:

```
.rift/
  run/
    server-{version}.sock   the gRPC socket
    server-{version}.lock   held while a server is starting
    server-{version}.json   pid, build version, start time
  worktrees/
    a1/                     detached materialization tree for connection a1
    cand-a1-7/              a candidate under validation
    read-dae86e1/           a detached checkout, for reading an older revision
    exec-a1-8/              a disposable one-shot execution workspace
    debug-a1-9/             retained until its debugging session stops
  state/
    a1/rust/                one adapter's state_root for connection a1
  facts/                    the semantic database
  log/
```

The first run appends `.rift/` to `.git/info/exclude`, so none of it shows up in `git status` and you
don't have to commit a rule for a directory that only exists on your machine.

## Sessions

A session is server runtime state bound to one gRPC connection. Application messages use that
connection identity directly, so requests need no session field or handshake.

All tools use the connection-bound session implicitly. A session identifier on the wire would let one
caller address another caller's state. Internally, a connection owns:

```
id              a1
base            B, the configured starting commit
worktree        .rift/worktrees/a1, detached at B
accepted ref    refs/rift/accepted/a1, starting at B
```

A session starts from the last commit, so uncommitted changes in your own working tree aren't in it.
Reads still reach them — `rev: main-worktree` names your working tree, uncommitted edits included. If
you'd rather the agent start from what you have open, `session.base = "worktree"` records that diff as
the accepted ref's initial commit. The worktree remains a detached materialization of accepted state.

### Closing

The session ends when the connection closes, which covers the agent exiting and the agent crashing.
The server releases adapter state and removes connection, candidate, and read worktrees. An
accepted ref that advanced is the durable history; an untouched ref at the initial base can be
deleted. Retained previews also have durable metadata and refs to their candidate commits, so a
server restart does not turn a valid preview into an unreachable Git object.

A server that dies can leave runtime directories behind. Startup reconciles them against live
connections and retained refs before serving requests.

```
rift accepted                 retained accepted refs and their heads
rift accepted remove a1       explicitly deletes one accepted history
```

`RIFT_ACCEPTED=a1` opens a new connection on retained accepted history. This is local process control;
it does not appear in MCP JSON or gRPC messages.

### Reading across sessions

Any session can read any revision the repository has, including another session's worktree:

```
rift://file/src/api.rs?rev=worktrees/a2
```

Sessions isolate writes. Reading `a2` while `a2` is being written returns a working-tree snapshot with
`a2`'s base and change digest in it, so the answer says exactly which state it saw. This is how one
agent reviews another's work before integrating it.

## Worktrees

A worktree's lifetime depends on what made it:

| worktree | created by | removed | written by |
| --- | --- | --- | --- |
| session `a1` | opening a connection | connection close | `persist` |
| candidate `cand-a1-7` | `apply` in `preview` mode | when validation finishes | the preview's resolved edits |
| read `read-dae86e1` | a semantic read at a revision nothing has checked out | idle timeout, or the LRU cap | nobody |
| execution `exec-a1-8` | `execute` | when the call returns | evaluated repository code |
| debug `debug-a1-9` | `debug_start` | `debug_stop`, connection close, or adapter loss | evaluated repository code |

Adapters open source with `open(2)`, so a real tree on disk is the interface. Source bytes stay on
disk. Adapters return `Edit` values, and Rift is the only source writer. `git diff` therefore contains
the session's complete source change.

Worktree materialization and language runtime selection have separate owners. The server resolves a
revision to an exact `Snapshot`, decides whether an existing physical tree represents it, and reuses
or allocates the tree. Only then does it call `Open`. The adapter never checks out or switches a Git
worktree; after receiving the complete tree, it selects the analyzer or project runtime appropriate
for that adapter state. If a later write changes runtime-defining configuration, `Refresh` makes the
adapter re-evaluate that selection before it acknowledges the new state.

## Reads

Where a read resolves decides what it costs:

1. **Git objects.** `tree`, the file and diff resources, and text `match`. No adapter is required: any
   revision Git can resolve, every language.
2. **Retained facts.** `outline`, `search`, symbol and relationship reads at a snapshot already
   analyzed. The adapter can be stopped.
3. **An adapter.** The snapshot or fact family isn't retained. The server starts the adapter if
   it isn't running, opens a workspace on the tree, and runs `Analyze`.

An agent doesn't pick between them, so a question asked of a repository nobody has indexed still gets
an answer. Indexing a large repository takes minutes, though, and the request has a deadline. When
analysis won't finish inside it, the answer comes back with `Coverage.state: partial`, a reason naming
the indexing state, and a continuation to ask again. Cold indexing therefore uses the same response
shape as any other incomplete analysis.

### Reading an older revision

An adapter opens files by path, and a commit is not a path. A semantic read at a revision that nothing
has checked out therefore gets a tree:

```
rift://symbol/python/pkg.util.load_config?rev=v1.2.0
  ->  .rift/worktrees/read-dae86e1        v1.2.0 is dae86e1
```

It's a detached checkout, shared by every session asking about that commit, reference-counted, and
removed after `reads.worktree-idle-timeout`. `reads.max-worktrees` caps how many exist at once —
default 2, because each one is a full checkout of your source.

A revision that already has an exact tree is read where it is: `main-worktree`, `worktrees/a2`, the
session's own. A branch name alone does not make a working tree reusable: its commit and working-tree
changes must represent the resolved `Snapshot`. Mechanical reads never materialize anything, because
Git objects don't need a checkout.

## Execution and debugging

Execution is adapter-backed but does not run in an adapter state shared with reads or edits. The
server resolves `rev` to a `Snapshot`, materializes that state as a disposable execution workspace,
opens a fresh `AdapterState`, and lets the adapter select the same revision-appropriate project
runtime it would use for analysis. The caller-provided `CodeBlock` crosses the adapter seam directly;
it is not added to the Git tree.

`execute` is one-shot. Rift calls the adapter's `Execute`, closes the adapter state, and removes the
workspace after returning bounded output and diagnostics. Files written by evaluated code disappear
with the workspace and never enter a candidate, the connection worktree, or the accepted ref.

A debugging session uses the same preparation path but retains the execution workspace and adapter
state. `debug_start` runs the block to normal completion or its first unhandled failure. A failed run
retains the stack as an ordered set of `DebugFrame`s; `debug_get_frame` reads one frame without
resuming the program. `debug_stop` releases the adapter-local handle, closes its adapter state, and
removes the workspace. This is post-mortem inspection, not a stepping debugger: breakpoints,
continue, and variable mutation are outside the initial interface.

The server mints the public debugging-session ID and binds it to the MCP connection. It maps that ID
to the adapter's private token, exact `Snapshot`, language, adapter state, and execution workspace.
The token never crosses MCP, and a caller cannot name another connection's debugging session. The
same cleanup runs on `debug_stop`, connection close, adapter exit, server reconciliation, and
cancellation while starting.

The execution workspace is disposable, not isolated. Evaluated code and adapter runtime workers keep
the host filesystem, process, and network access of `rift server`, just as command validators do.
Consequently these tools are absent from `tools/list` unless host execution policy explicitly enables
them and the selected adapter advertises the corresponding operations. The conformance profile and
execution authorization remain separate decisions: passing `full` does not by itself authorize
caller-provided code.

### Reuse and required changes

| concern | reused interface or implementation | required change |
| --- | --- | --- |
| Revision context | `Revision` resolution, exact `Snapshot`, Git materialization | Add disposable execution and retained debug lifetimes to the worktree allocator. |
| Project runtime | `Open`, `AdapterState`, revision-local runtime selection, `Close` | Open a fresh state per execution workspace; never run caller code in a shared state. |
| Adapter discovery | `Capabilities.operations` and repository `LanguageSupport` | Add `execute` and the all-or-none debug operation triplet. |
| Agent routing | generated MCP JSON-to-Protobuf mapping and repository tool manifest | Add four tools and advertise them only where adapter support and host policy intersect. |
| Bounds and cancellation | MCP request/response ceilings, gRPC deadlines, cancellation, `Diagnostic` | Add bounded `CapturedOutput`, rendered debug bindings, and cleanup on every terminal path. |
| Connection ownership | connection-bound session runtime and close reconciliation | Add the public-debug-ID to private-adapter-token map and reject cross-connection access. |
| Host execution | disposable validation-workspace machinery can supply materialization and cleanup | Add separate execution policy; do not reuse `CommandValidator`, whose result is publication evidence and whose declaration is an executable argv rather than source for an adapter. |

The protocol and architecture define these seams now. An implementation still needs the execution
policy fields in `rift.toml`, admission and limit enforcement, workspace leases, cleanup/recovery, and
conformance fixtures for output truncation, timeouts, adapter loss, cross-connection handles, and
filesystem-write discard.

## Writes

`apply` resolves an ordered array of changes into a fresh candidate worktree, validates the result, and
retains the plan. `publish` replays that plan and advances the session's accepted ref. `persist`
materializes selected paths from an accepted commit into the session worktree.

      accepted -- "persist" --> session[".rift/worktrees/a1"]:::git

The [MCP page](/docs/protocol/mcp) has the surface; what matters here is what waits on what:

- **Previews don't block each other.** Each one builds its own candidate worktree from a base commit,
  so two in flight in one session run in parallel and neither touches the session tree.
- **`publish` takes the accepted ref by compare-and-swap.** Every session has its own accepted ref, so
  this guards one thing: an agent with two `publish` calls in flight against the same base. The loser
  gets a conflict result and can re-preview against the new head.
- **`persist` takes the session's write lock**, because it's the only operation that writes to the
  session worktree.

Apply and persist touch connection-local state. Integration introduces cross-session contention by
advancing a shared target ref.

## Integration

An accepted commit is reachable from the connection's accepted ref. `integrate` merges it into a
local target branch. Git derives the merge base from the accepted commit and target head:

```
B ── X ── Y      main
 \
  └── A          refs/rift/accepted/a1
```

Rift merges `A` into `Y` using `B`, in a candidate worktree. The merge result is a candidate like any
other: adapters refresh onto it, `Validate` runs over the closure the merge touched, and any declared
validators run. Two valid commits can form a broken merge: `Y` can rename a function that `A` added a
call to. Validation therefore runs on the merge candidate.

| result | what happened |
| --- | --- |
| `integration_preview` | a conflict-free merge candidate and its validation were retained; no ref moved |
| `integration_refresh` | the retained contract was rebuilt against the current target head |
| `merge_conflict` | a parseable provisional merge and the three entries for each conflict were retained |
| `integrated` | fresh validation passed and compare-and-swap advanced the target |
| `integration_rejected` | fresh validation failed; the retained evidence names the failure |
| `integration_refused` | repository state or policy prevented publication; a validated candidate is returned when available |
| `integration_conflict` | the target moved or an idempotency key was reused for different input |

Compare-and-swap on the target is where two sessions actually contend. Both integrating into `main`
serialize, and the loser re-merges against the head that won.

### Conflicts

A conflicted result returns the base, source, and target entry for every conflicting path. Its
two-parent provisional merge contains automatic resolutions and retains the target entry at each
conflict. No conflict markers are written into any tree, because a tree full of `<<<<<<<` is a tree
no adapter can parse and therefore a tree
Rift can't validate or ask an adapter about.

Resolve the conflict with an ordinary `apply` whose `rev` is that candidate and whose
`expected_accepted` is the conflict result's `source`: concrete edits, a patch, or an adapter action.
The source must be an ancestor of the provisional merge, which gives publication a valid
compare-and-swap base. Publish the repair to the accepted ref, then preview integration again. The new
merge is normally a fast-forward or a conflict-free merge because the repair commit descends from
both parents.

### Targets

Rift can update a checked-out target only when `session.integration = "auto"` and the worktree is
clean. Otherwise publication returns `integration_refused` with the validated candidate, leaving the
branch and worktree unchanged. A local branch that is not checked out advances by compare-and-swap.

## Facts

`.rift/facts` holds eligible results from `Analyze`. Each result declares a cache scope:

| scope | retention rule |
| --- | --- |
| `snapshot` | source snapshot, adapter implementation, exact `Language`, and derived virtual inputs determine the result |
| `process` | adapter-observed process or workspace-generation state also matters; retention ends with it |
| `none` | Rift does not retain the result |

A virtual-source chain inherits its shortest scope. Process-scoped producer output makes downstream
analysis process-scoped; request-volatile producer output prevents downstream retention.

Tracked manifests, schema files, and adapter configuration are part of the source snapshot. A
working-tree snapshot already identifies its base and changed bytes. Rift therefore needs no second
opaque context digest. Host-local toolchain state or a live adapter index requires `process`; a
request-volatile result uses `none`.

Nothing is analyzed when the server starts. Indexing a monorepo costs minutes and gigabytes, and a
session that reads three files shouldn't pay for it, so the first semantic read of a snapshot triggers
exactly the analysis it needs. `rift index` warms the store ahead of time when you'd rather wait once.

The store is a cache. `facts.max-size` evicts least-recently-used snapshots when it's reached, and
deleting `.rift/facts` costs you the re-analysis.

## Paths Git doesn't track

Candidate commits are built from the base tree plus the resolved edits, with Git plumbing. There's no
index and no `git add` involved, so a file an `Edit` creates is in the candidate tree. Incidental
files created by an adapter process stay outside the commit.

An `Edit` on a path matched by `.gitignore` fails the `writable` precondition, and the refusal carries
the path and the rule that matched it. The commit would otherwise carry a file that your own
`git status` hides from you, which puts what Rift validated and what you can see out of step.

Command validators start in a validation workspace copied from the candidate, which contains tracked
files only. A test suite that needs an untracked `.env.test` gets it through `validators.carry` in
[`rift.toml`](/docs/configuration#validators), an explicit list of ignored paths copied into that
workspace. The workspace is disposable, but it does not isolate the command from the host.
