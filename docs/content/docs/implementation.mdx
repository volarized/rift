## rift mcp

`rift mcp` is the CLI entry an agent launches — the `rift` binary, its commands parsed by
[clap](https://docs.rs/clap). It speaks MCP over stdio through
[rmcp](https://github.com/modelcontextprotocol/rust-sdk) and forwards each request to the
workspace's `rift server` over Streamable HTTP: a stdio-to-HTTP proxy, with no state of its
own. It reads [`ServerLock`](/docs/protocol/reference#ServerLock) from `.rift/server.json` for
the port and token, and starts the server first when no live one answers.

Today the one binary serves the tools in-process; the proxy split above is the planned shape.

## rift server

The server is an [Axum](https://docs.rs/axum) application on the [Tokio](https://tokio.rs)
runtime. MCP clients use its `/mcp` route, which serves Streamable HTTP through rmcp's service
layer; the rest of the router carries non-MCP surfaces such as the SCIP export.

Startup runs one cycle:

1. Parse `rift.toml` and admit the workspace; an invalid file refuses every request until fixed.
2. Win or lose the election: atomic creation of `.rift/server.json` picks one starter among
   racing `rift mcp` processes, and losers connect to the winner.
3. Bind a loopback port, mint the bearer token, and write both into the lock file.
4. Start the native filesystem watcher.
5. Schedule the initial scan and parse on a Tokio-managed blocking task, so traversal and
   parsing never occupy an async MCP worker.
6. Serve until thirty idle minutes pass, then remove the lock and exit.

Blocking work shares a bounded pool of slots behind a Tokio semaphore. When every slot is busy a
request waits in the queue; once the wait expires the server returns `temporarily_unavailable`,
so the client retries without adding another blocking worker. The
[`server` table](/docs/configuration#server) sets both bounds — four slots and a 30-second wait
by default — and the server sizes the pool once at startup.

The project resolver skips symlinks and the `.git`, `.rift`, and `target` directories. The
symbol index stays in memory as one immutable value: a rebuild constructs the next index and
admitted configuration outside the async lock, then swaps the complete value under its write
lock. Each request clones the published value under a read lock and retains that capture through
its result, so reads never combine state from two index revisions.

Watcher events and Rift-applied changes advance one workspace change counter and enter the same
serialized rebuild lane. Before each current-tree read, the server reconciles watcher state
against an exact fingerprint of the admitted workspace files, then waits until the published
index counter matches it — the mechanism behind the freshness the
[`ReadSnapshot`](/docs/protocol/reference#ReadSnapshot) reports.

## Rift FS

<VersionBadge version="planned" />

Rift FS mounts each served tree through the host's native client: NFSv3 loopback via
[nfsserve](https://github.com/xetdata/nfsserve) on macOS — an unprivileged mount, no kernel
extension — and FUSE via [fuser](https://github.com/cberner/fuser) on Linux, unprivileged
through `fusermount3`. A host where neither mounts falls back to the copy backing with the same
contract.

The overlay holds a pinned lower layer and a per-tree upper store. The first write to a path
detaches it into the store; a deletion leaves a whiteout; `.rift` is never served. Lower-layer
reads go through a [foyer](https://github.com/foyer-rs/foyer) hybrid cache — hot 256 KiB
segments in memory, warm segments on disk. Removal force-unmounts without waiting on processes
still inside.

## rift db

<VersionBadge version="v0.0.9" languages={["Rust"]} />

One [SQLite](https://www.sqlite.org/) database at `.rift/db` holds every store Rift persists
for the workspace — the
lexical index today, later stores beside it. The server lock, projection directories, and
execution copies stay separate entries under `.rift`; the database carries stores that are
rows, not trees. Access goes through [Toasty](https://github.com/tokio-rs/toasty) models; the
full-text surface is raw SQL, because Toasty 0.10 has no typed virtual-table or `MATCH` API,
and the raw boundary stays confined to the FTS table and its rows.

Publication replaces the whole unit set and restamps the revision, so the store is never a
partial mix of two trees.

The lexical index is three tables. `lexical_units` holds one row per indexed unit — a code
symbol, or a text file split into chunks past the
[`[search.text]`](/docs/configuration#search) chunk bound. `lexical_index_state` stamps the set
with the tree revision that published it; a search request trusts the store only when that
stamp equals the snapshot it reads. `lexical_units_fts` is the
[FTS5](https://www.sqlite.org/fts5.html) virtual table over `name`
and `content`, with `identity` riding unindexed as the join key; ranking is FTS5's `bm25` with
per-column weights, comparable only within one search.

Search is a layered configuration: the default is this full-text store alone, and naming a model
in [`search.embedding`](/docs/configuration#search) adds a per-model vector store whose cosine
similarity the server fuses into the lexical score — the layering the
[architecture](/docs/architecture#search) page describes.

## Language providers

A provider composition is a typed pipeline of named stages — source resolvers, fact providers,
enrichers, transforms — connected through declared input and output flows, with keyed joins for
revision-keyed history. The Rust builder inserts, replaces, branches, merges, and nests stages;
Rift validates types, capabilities, and cycles at build, then owns scheduling, caching, and
invalidation.

Syntax providers wrap [tree-sitter](https://tree-sitter.github.io/tree-sitter/) grammars behind
a Rift-owned adapter: grammar node kinds resolve to numeric ids once, and raw query and cursor
APIs never leave the syntax crate.

An LSP-backed language engine is a child process the server spawns in stdio mode — one per
language and targeted tree, rooted at that tree's directory. Semantic facts and edit plans
return through the provider contract, and the server notifies the engine of writes itself,
because no filesystem watcher sees inside a served tree.

## Hooks and configuration

`rift.toml` at the workspace root is admitted at startup and re-validated on change; its schema
is exported beside the MCP surface as [`rift.schema.json`](https://volar.sh/rift/rift.schema.json),
so editors validate the file as it is written. A quantity key spells its unit in the value —
`timeout = "120s"`, never a `_ms` suffix in the key.

A hook is a configured command the server runs inside the changed tree after a change lands,
with a declared environment, bounded output, and a timeout. Its verdict attaches to the change
as [`GuaranteeEvidence`](/docs/protocol/reference#GuaranteeEvidence) or an advisory, and a hook
that fails or does not finish gates publication in a projection. Keys and defaults live on the
[configuration](/docs/configuration) page.
