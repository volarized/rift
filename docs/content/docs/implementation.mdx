## The rift binary

<VersionBadge version="v0.0.11" />

Rift is delivered as one binary, installed as the [Install](/docs#install) section describes.
The CLI is implemented with [clap](https://docs.rs/clap), and Rift's two main capabilities are
implemented as `rift mcp` and `rift server`.

### rift mcp

`rift mcp` is the MCP stdio server an agent launches. Under the hood it takes input from the
agent over the stdio transport and forwards each request to the workspace's `rift server` over
Streamable HTTP; the process holds no state of its own - state lives in the `rift server`. To
reach the workspace's server it checks the server lock file -
[`ServerLock`](/docs/protocol/reference#ServerLock) at `.rift/server.json` - and starts a
server when no live one stands behind it.

### rift server

The server is an [Axum](https://docs.rs/axum) application on the [Tokio](https://tokio.rs)
runtime. MCP clients use its `/api/mcp` route, which serves Streamable HTTP through
[rmcp](https://github.com/modelcontextprotocol/rust-sdk)'s service layer; `/api/stop` serves
`rift server stop`, and the rest of the routes are reserved for other surfaces, the SCIP
export for example.

Startup runs one cycle:

1. Parse `rift.toml` and accept the workspace; an invalid file keeps the server running but
   refuses every request until fixed.
2. Take the exclusive file lock on `.rift/server.lock`, which picks one starter among racing
   `rift mcp` processes.
3. Bind the first free loopback port of the accepted
   [`[server]` selection](/docs/configuration#server) - the pinned `port` or the configured
   `port_range` - mint the bearer token, and write both into `.rift/server.json`.
4. Start the native filesystem watcher.
5. Schedule the initial scan and parse on a Tokio-managed blocking task, so traversal and
   parsing never occupy an async MCP worker.
6. Serve until no request arrives for the [`idle_timeout`](/docs/configuration#server) span
   `rift.toml` sets, then stop.

`rift server start` runs that cycle detached and waits for `.rift/server.json` to appear;
`rift server stop` sends the authorized stop request and waits for the election to release;
`rift server restart` chains the two. `rift server status` reports the workspace's current
state - a serving server with its port, pid, and version, a stale `.rift/server.json` with the
reason it went stale, or no server - and changes nothing. `--foreground` keeps the cycle in the
calling process, where Ctrl-C stops it.

Blocking tasks run on a Tokio-controlled worker pool. A request for blocking work lands in a
queue, and a worker picks it up when one is free. This behavior is configurable via the
`num_workers` and `worker_queue_timeout` keys in the
[`[server]` section](/docs/configuration#server).

The project resolver skips symlinks and the `.git`, `.rift`, and `target` directories.

The symbol index stays in memory as one immutable value: a rebuild constructs the next index and
accepted configuration outside the async lock, then swaps the complete value under its write
lock. Each request clones the published value under a read lock and retains that capture through
its result, so reads never combine state from two index revisions.

Watcher events and Rift-applied changes advance one workspace change counter and enter the same
serialized rebuild lane. Before each current-tree read, the server reconciles watcher state
against an exact fingerprint of the included workspace files, then waits until the published
index counter matches it; when the index still lags, the result carries a `stale_index` entry
in `warnings` with the two tree revision digests.

## Rift FS

<VersionBadge version="planned" />

Rift FS mounts each served tree through the host's native client: NFSv3 loopback via
[nfsserve](https://github.com/xetdata/nfsserve) on macOS - an unprivileged mount, no kernel
extension - and FUSE via [fuser](https://github.com/cberner/fuser) on Linux, unprivileged
through `fusermount3`. A host where neither mounts falls back to a copy-backed tree with the
same contract.

The overlay holds a pinned lower layer and a per-tree upper store. The first write to a path
detaches it into the store; a deletion leaves a whiteout; `.rift` is never served.

Lower-layer reads go through a [foyer](https://github.com/foyer-rs/foyer) hybrid cache - hot
256 KiB segments in memory, warm segments on disk. Removal force-unmounts without waiting on
processes still inside.

## rift db

<VersionBadge
  version="v0.0.9"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML"]}
/>

One [SQLite](https://www.sqlite.org/) database at `.rift/db` holds every store Rift persists
for the workspace - today, the lexical index. The server lock, projection directories, and
execution copies stay separate entries under `.rift`; the database carries stores that are
rows, not trees. Access goes through [Toasty](https://github.com/tokio-rs/toasty) models; the
full-text surface is raw SQL, because Toasty 0.10 has no typed virtual-table or `MATCH` API,
and the raw boundary stays confined to the FTS table and its rows.

Publication replaces the whole unit set and restamps the revision, so the store is never a
partial mix of two trees.

The lexical index's tables:

- `lexical_units` - one row per indexed unit: a code symbol, or a text file split into chunks
  past the [`[search.text]`](/docs/configuration#search) chunk bound.
- `lexical_index_state` - stamps the set with the tree revision that published it; a search
  request trusts the store only when that stamp equals the tree revision the read captured.
- `lexical_units_fts` - the [FTS5](https://www.sqlite.org/fts5.html) virtual table over `name`
  and `content`, with `identity` riding unindexed as the join key; ranking is FTS5's `bm25`
  with per-column weights, comparable only within one search.

Search is a layered configuration: the default is this full-text store alone, and
[`[search.semantic]`](/docs/configuration#search) adds the vector store below, whose ranking
the server fuses with this one by reciprocal rank.

## Semantic search

<VersionBadge version="planned" />

`rift-search` owns the tier. It loads a BERT checkpoint with
[candle](https://github.com/huggingface/candle) and runs the encoder in the server's own
process, so answering a query touches neither the network nor a subprocess.

Weights are read through candle's safetensors loader rather than its memory-mapped
constructor: mapping is an unsafe call, and this workspace forbids authored `unsafe`. The cost
is that a load holds the file's bytes once while the tensors are built.

Vectors are pooled from the CLS position and normalized to unit length, which is how the
default checkpoint was trained. A retrieval query carries the prefix that checkpoint was
trained with, applied where the query enters rather than left to each caller; a document
carries none.

Passes run one at a time, bounded by
[`batch_declarations` and `max_tokens`](/docs/configuration#search). Attention memory grows
with the square of the token window, and candle's kernels already spread one pass across the
thread pool, so running several at once buys nothing and costs the machine its memory.

## Language providers

<VersionBadge version="planned" />

A provider composition is a typed pipeline of named stages - source resolvers, fact providers,
enrichers, transforms - connected through declared input and output flows, with keyed joins for
revision-keyed history. The Rust builder inserts, replaces, branches, merges, and nests stages;
Rift validates types, capabilities, and cycles at build, then owns scheduling, caching, and
invalidation.

Syntax providers wrap [tree-sitter](https://tree-sitter.github.io/tree-sitter/) grammars behind
a Rift-owned adapter: grammar node kinds resolve to numeric ids once, and raw query and cursor
APIs never leave the syntax crate.

An LSP-backed language engine is a child process the server spawns in stdio mode - one per
language and targeted tree, rooted at that tree's directory. Semantic facts and edit plans
return through the provider contract, and the server notifies the engine of writes itself,
because no filesystem watcher sees inside a served tree.

## Hooks and configuration

<VersionBadge version="v0.0.5" />

`rift.toml` at the workspace root is accepted at startup and re-accepted on change; its schema
is exported beside the MCP surface as [`rift.schema.json`](https://volar.sh/rift/rift.schema.json),
so editors validate the file as it is written. A quantity value carries its unit:
`timeout = "120s"`.

A hook is a configured command the server runs inside the changed tree after a change lands,
with a declared environment, bounded output, and a timeout. Its verdict attaches to the change
as [`GuaranteeEvidence`](/docs/protocol/reference#GuaranteeEvidence) or an advisory, and a hook
that fails or does not finish gates publication in a projection. The
[configuration](/docs/configuration) page states the keys and defaults.
