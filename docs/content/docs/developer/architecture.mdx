Rift works as a toolkit for agents such as Claude Code and Codex - practically any agentic
appliance that supports MCP.

When an agent has Rift configured as one of its MCP servers, the `rift mcp` process starts and
checks whether a `rift server` is already running for that particular folder. We'll call this
folder a **workspace** throughout this documentation.

Each `rift mcp` process is short-lived and isolated, while development operations depend on
state shared across requests and agents. To bridge that gap, `rift mcp` acts as a small proxy: it
forwards every request to one `rift server` running locally for the workspace. The two processes
communicate over [Streamable
HTTP](https://modelcontextprotocol.io/specification/draft/basic/transports).

The `rift server` coordinates source discovery and providers. Source
resolvers identify project files, dependencies, and generated code. Providers analyze that source
and produce facts such as symbols, syntax nodes, relationships, and diagnostics.

The server stores searchable provider output in an embedded index under `.rift`. The
[`search`](/docs/mcp#tool-search) tool always retrieves lexical matches; when
`rift.toml` selects an embedding model, a local model adds vector ranking.

## Server lifecycle

<VersionBadge version="v0.0.11" />

When the server starts, it writes `.rift/server.json` following the
[`ServerLock`](/docs/developer/protocol/reference#ServerLock) model. The file gives each `rift mcp`
process the port and token it needs to reach that server. For example:

```json
{
  "port": 12345,
  "token": "Zk3mQ8xW1vY5uT9rN2bH7cJ4dL6fP0sA8gE5iK2oM7q",
  "pid": 4242,
  "identity": {
    "version": "0.0.25",
    "executable_digest": "eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee",
    "schema_digest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

When no live server stands behind the file, `rift mcp` starts one. An exclusive file lock
elects one starter if several processes race; the winner builds its index, binds a port, and
publishes the file, and the rest connect to it. The winner holds the lock from its election
onward, so a `rift mcp` or `rift server start` that arrives while it is still indexing waits
for its file instead of starting another server.

The proxy adopts that server only when package version, executable SHA-256, and served MCP schema
SHA-256 match its own identity. A mismatch is stale state, even when the recorded process and port
are live, so requests never cross between binaries or tool schemas that interpret them differently.

A reader that cannot reach the recorded port treats the file as stale. The election lock
releases with its holder, so a stale file never has a live server behind it, and the next
starter replaces the file. A server on its way out closes its port before it releases the
lock, and the next starter waits for the release before electing a fresh one.

To enforce a cross-process boundary between OS users, the server persists a token in
`.rift/server.json`, which only the file's owner can read. Every request carries this token,
and the server rejects one without it. Processes running as the same OS user can read the same
token and are not separated by this boundary.

A browser introduces another route to a localhost port: a remote page can issue requests through
DNS rebinding or a forged origin. The HTTP server therefore accepts only the literal loopback
`Host` for its bound port. It also rejects a present `Origin` unless that origin is loopback;
non-browser MCP clients omit `Origin` and still authenticate with the token.

<Callout type="info">
You might be asking why there's a server at all. Assume your agent launches a couple of
subagents. Each of them might also want to read the codebase through Rift, and each gets
its own `rift mcp`, because MCP's stdio transport has the client launch its server as a
subprocess.

None of those short-lived processes can hold the things that are expensive and shared - the
index - so a long-lived server holds them and every `rift mcp`
reaches the same one.

And why HTTP rather than a socket? Either way `rift mcp` has to find the running server, and
HTTP lets an HTTP-capable agent connect to the port without `rift mcp`.
</Callout>

On startup the server reads `rift.toml` from the workspace root and accepts the workspace. The
configuration allows you to describe:

- which embedding model, if any, ranks search
- which exact language entries select source files

A change to the file takes effect for later requests once the server accepts it again. An
invalid file keeps the workspace unusable until you fix it.

A rebuild that fails - the tree crossed a configured bound, a file could not be read - leaves the
last published snapshot served. A read answers from that snapshot and carries a `stale_index`
warning naming the failure. The next filesystem
event retries the rebuild, and a rebuild that publishes clears the warning.

The server stops itself once no request remains active and the
[`idle_timeout`](/docs/developer/configuration#server) span passes after the last response completes.
`rift server stop` ends it sooner. The server removes its lock file on the way out, and the next
`rift mcp` starts a fresh one. The database under `.rift` survives the exit.

`rift server status` reports which of these states the workspace is in - a serving server with
its port, pid, and version, a server still indexing, a stale `.rift/server.json`, or no server
- and changes nothing. A server that fails to start, or panics, records why under
`rift server logs --level error` before it exits, and a server `rift server start` spawned
writes its standard error to `.rift/server.stderr`, truncated at each start.

## Source discovery

Before Rift analyzes code, source resolvers discover what belongs to the project and what its
toolchain already resolved. The built-in project resolver catalogs workspace files.

Dependency resolvers catalog what the workspace's package managers resolved. Each resolver
claims one manifest file name, and every visible manifest with that name reaches it:

- the Cargo resolver claims `Cargo.toml`, runs `cargo metadata --locked --offline` for each
  top-level manifest, and catalogs every package outside the workspace members with the
  directory its source was unpacked to; it also asks `rustc` for its sysroot and catalogs the
  standard library source there
- the uv resolver claims `pyproject.toml`, reads the `uv.lock` beside it, and finds each
  distribution's installed source through the project environment: the `.venv` beside the
  manifest, or the directory `UV_PROJECT_ENVIRONMENT` names; it catalogs the interpreter's
  standard library from the environment's `pyvenv.cfg`
- the npm resolver claims `package.json`, reads the `package-lock.json` beside it, and finds
  each package under `node_modules`; when the lockfile pins `typescript`, it catalogs that
  compiler's `lib.*.d.ts` set as the TypeScript standard library
- the Bun resolver claims `package.json` too and reads `bun.lock` the same way, so a manifest
  reaches whichever of the two has a lockfile beside it

A resolver never downloads a package and never writes to the tree. The uv, npm, and Bun
resolvers read lockfiles and probe directories, and run nothing. The Cargo resolver is the one
that runs a toolchain, under `--locked`, which refuses to rewrite the lockfile, and `--offline`,
which refuses the network. When `cargo` is not on the server's `PATH`, or exits with an error
because `Cargo.lock` no longer matches `Cargo.toml`, it answers from the lockfile alone and
probes the machine's package cache for each package's source. That answer lists what the
lockfile pins, so it can over-approximate what the active feature set compiles; a package the
cache does not hold is cataloged without a source root, whichever resolver cataloged it.

The catalog keys each package by its
[`PackageIdentity`](/docs/developer/protocol/reference#PackageIdentity): the package manager, the name,
and the resolved version. Two versions of one package are two entries. Its inputs are the
manifests and lockfiles the resolvers read, so a change to any of them re-catalogs on the next
publication while every other file change leaves the catalog untouched. `rift://map` lists the
packages the manifests declare directly.

Each resolver reads at most 256 manifests per workspace, taken in path order from the visible
paths carrying its manifest file name. Selecting the top-level manifests compares every manifest
pair, so that work grows with the square of the manifest count.

A workspace holding more manifests catalogs the packages those 256 resolve, and the resolver
reports the rest as a degradation. A read whose `scope` reaches packages carries it as a
`package_context_degraded` warning: the next.js repository holds 876 `package.json` files,
so the warning reads `620 of 876 package.json manifests were not read: at most 256 are read
per workspace`.

Each readable file becomes a [`SourceUnit`](/docs/developer/protocol/reference#SourceUnit) in the
source catalog. Its `location` says whether it belongs to the project, a dependency, the standard
library, or an external source. Its `source_kind` separately says whether a human authored it or a
tool generated it.

Generated project code and generated dependency code therefore keep both facts. Declarations
invented by a language tool have `source_kind: "synthetic"` and no source unit.

A resolver publishes a new catalog revision when its inputs change: workspace files, manifests,
lockfiles, toolchains, installed packages, or generated-source metadata. Fact providers consume
that catalog. A parser such as tree-sitter can describe syntax in a supplied file, but cannot infer
which package owns it or which generator produced it.

### Dependency context

<VersionBadge version="v0.0.39" languages={["Rust", "Python", "TypeScript"]} />

Beside the catalog the resolvers build, each resolver reads a second, cheaper answer: the
packages the workspace's manifests and lockfiles name. That pass reads those files alone.
It runs no toolchain, inspects no package cache, and reads no environment value, because
it reaches the workspace through a reader that offers a file read and nothing else. A
workspace that never asks for a package read therefore never pays for one.

Each entry carries the package manager, the name, and exactly one selector: the exact
version a lockfile pins, or the version requirement a manifest declares. A manifest value
is reported as a requirement unless its form pins one exact version - Cargo's `1.2.3` is a
caret requirement and `=1.2.3` a pin - so a manifest-only project never invents a resolved
version. An entry a public registry serves is `canonical`; a path, git, or
custom-registry entry is `local_only`. Entries merge by manager, name, and selector, and
a requirement is dropped where some input pins that package's version. The
[`[dependencies]`](/docs/developer/configuration#dependencies) `packages` list merges with
what the files state, under the same rules.

`rift://map` lists this context, and its inputs are the manifests and lockfiles the
resolvers read, so a change to any of them reads the context again on the next
publication while every other file change leaves it untouched.

### Package index

<VersionBadge version="v0.0.43" languages={["Rust", "Python", "TypeScript"]} />

No package is analyzed until a read asks for one. A `global` or `all` read first resolves
the dependency context, then the local server asks the configured global REST API for
capabilities and package resolution. A valid response sends available packages to remote
pages and keeps missing or `local_only` packages on the local package index.

When global access is disabled or the REST API cannot answer, the server selects affected
packages for local indexing. The answer distinguishes `global_access_disabled`,
`global_api_unavailable`, `global_publication_incompatible`, and `global_response_invalid`.
A valid remote page can also report `global_page_warning` without discarding its items.
A valid resolution reports `package_absent` for an exact package or
`package_requirement_absent` for a declared requirement; local fallback reports
`package_unavailable` when it still cannot serve a package. Package reads reach the global service
through this local server route; `rift mcp` and `rift server` do not expose a direct global MCP
route.

For each package the local index analyzes, the walk selects files that spell the package's API
and keeps declarations a caller outside the package can use:

- Rust - every `.rs` file below the root; `pub` declarations, and the items of a `pub` trait
- Python - every `.pyi` stub when the package ships any, else every `.py` module; names
  without a leading underscore
- TypeScript - every `.d.ts` declaration file; every member but `private` and `protected`
  ones

Directories named `tests`, `benches`, `examples`, `target`, `node_modules`, `__pycache__`,
and `.git`, and any whose name ends in `tests`, are left out of every walk, and so is every
symlink. The same syntax providers that parse the project's files parse these, so a
package declaration is a [`Symbol`](/docs/developer/protocol/reference#Symbol) like any other and
answers a [`get_symbol`](/docs/mcp#get_symbol-scope) lookup whose `scope` reaches packages.

The package index is bounded per package and in total: the `package_size`, `package_files`,
and `index_size` keys of the [`[dependencies]`](/docs/developer/configuration#dependencies) table
set the bounds, and the walk below one source root stops at a directory depth and an entry
count of its own. A package that crosses a bound is skipped, and a read reports it as
`package_skipped` naming the bound that refused it. Raising a bound in `rift.toml` analyzes
the packages again on the next read, since every package the package index holds was read
under the old bounds. `resolution = "static"` keeps the resolvers off the toolchains, so the
catalog comes from the lockfiles and package caches alone, and `command_timeout` bounds each
run `auto` makes.

## Providers

Providers analyze cataloged source at different depths and publish immutable `Contribution`
records in provider-owned symbol spaces. Rift normalizes applicable Contributions into
workspace-local `SymbolRecord` values, then assembles readable `Symbol` values for one captured
index revision.

A condition the caller must weigh before relying on the answer - a stale index, an absent
capability - arrives as a typed entry in the result's `warnings`.

### Syntax

Rift ships syntax providers based on
[tree-sitter](https://tree-sitter.github.io/tree-sitter/) by default. They parse readable project,
dependency, and generated units into declarations, syntax structure, and parse diagnostics. Project
declarations also carry their syntax nodes and byte ranges.

The server invalidates a changed path's syntax facts and search-index entries.

### Language engines

A **language engine** resolves facts the grammar alone cannot provide, such as references to a
declaration in another file. Rift's LSP client requests references and diagnostics over
[LSP](https://microsoft.github.io/language-server-protocol/).

Each [`[languages.<identity>]`](/docs/developer/configuration#languages-and-lsp) table selects
one named or inline process for an exact language identity: rust-analyzer for `rust`, or
`typescript-language-server` for `typescript` and `typescript:tsx`. Several identities may
select the same named process.

[`search`](/docs/mcp#search-engine-references) uses the engine for incoming reference
traversal: the engine is the one source of resolved references a walk follows. Source and
configuration must match the captured index before and after the engine request.

The embedded [ty](https://github.com/astral-sh/ty) engine serves Python over an in-memory
transport through the same LSP session contract. Its version ships with the Rift binary.

### History

The history source resolver reads the workspace's git objects in place, with no checkout or `git`
subprocess. It publishes a bounded series of source catalogs keyed by revision. The same in-place
access serves revision-addressed reads: `get_symbol`, `search`, and `nodes` accept a `rev`, and
the server indexes that commit's tree - the same syntax providers, over committed bytes - without
touching the working tree.

<VersionBadge
  version="v0.0.13"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

Asking for a symbol's history walks that same object store: the server follows first parents
from the served revision along the declaration's current path and parses the committed bytes at
each revision that changed the file - the same syntax provider, per revision. Comparing adjacent
parsed states gives the symbol a timeline: introduced, body changed, signature changed, removed.

The walk is bounded by
[`providers.history.max_revisions`](/docs/developer/configuration#providers), because its cost scales
with how far back it reaches, and a workspace without version control serves no history facts.

### Custom

Custom integrations implement a [source resolver](/docs/developer/protocol/core#source-discovery), a
[fact provider](/docs/developer/protocol/core#semantic-facts), or both. The contracts stay separate even
when one integration implements both capabilities. A family with no serving provider surfaces
as a typed entry in `warnings`, which keeps an empty answer distinct from a complete answer with
no facts.

One integration can connect several cooperating pieces through a **provider composition**. Like a
[scikit-learn pipeline](https://scikit-learn.org/stable/modules/compose.html), the composition gives
each step a stable name and feeds its output into compatible inputs.

The composition API can change the flow before Rift starts:

- insert, replace, or remove a named step
- transform one step's input or output
- branch one output into several providers, then publish each provider's Contributions
- nest one composition inside another

Provider compositions support several flow shapes:

- syntax and semantics consume the same source catalog, then publish separate Contributions
- history maps syntax analysis over source catalogs keyed by Git revision, then aggregates
  revision-qualified facts
- a custom external step can produce generated source or facts for another provider to analyze

A transform that changes source units or facts becomes a named, revisioned step and publishes new
Contributions, so later answers still identify its inputs.

For example, a CSS integration can send templates and configuration to a registered Tailwind CLI,
parse its generated CSS with a CSS syntax provider, and publish those facts beside authored CSS. The
server runs the command with declared inputs, environment, timeout, and output limits; the
composition step decodes its output.

Rift validates the composition's inputs, outputs, merge rules, and cycles before it runs. The server
then owns scheduling, caching, and invalidation; MCP requests do not assemble or modify the
composition. Composition controls data flow and provider selection. It cannot establish
Contribution equivalence or `SymbolRecord` identity.

The workspace resource assigns each provider a stable
[`ProviderId`](/docs/developer/protocol/reference#ProviderId) and reports its lifecycle state. A
provider derives an immutable Contribution collection from one tree revision, then publishes the
collection atomically.

While a provider catches up after a change, requests may serve its previous revision, and the
result carries a `stale_index` entry in `warnings` naming the two tree revision digests. A
provider with no usable revision contributes nothing, and the result's `warnings` say so.

A read captures one tree revision, one index revision where it searches, and the provider
revisions it uses. Later writes create new revisions; they do not alter the captured result. A
request addresses one page with `page_index`, and a page past the end returns an empty page
with the true `total_pages`.

Normalization validates equivalence evidence without using provider order, candidate names, or
provider composition as identity evidence. It retains unresolved and conflicting records instead
of forcing one `SymbolId`. When Rift assembles a readable Symbol, provider order selects scalar
presentation fields and combines list facts without discarding conflicting Contributions.

## Index

<VersionBadge
  version="v0.0.8"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

The server keeps an immutable index over the project's source. Tree-sitter extracts
declarations and syntax nodes from the files the workspace's source policy includes.

The server watches the workspace and validates the published index against it before each
current-tree read, so a read serves the tree as it stands and never combines state from two
index revisions. The [implementation](/docs/developer/implementation#rift-server) page describes the
watcher, the rebuild lane, and the swap that keep this true.

When the published index lags the tree a read captured, the result says so: a `stale_index`
entry in `warnings` carries the digests of the tree revision the index covers and the revision
the read captured, so the caller knows the answer may miss the newest writes.

<VersionBadge
  version="v0.0.9"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

Each rebuild derives lexical units for [`search`](/docs/mcp#tool-search).

<VersionBadge version="v0.0.25" />

The rebuild derives one unit per indexed symbol, and chunks from every bounded UTF-8 file without
a NUL byte whose effective language entry or
[`[search.text].include`](/docs/developer/configuration#search) selects it. Visible Markdown, MDX,
reStructuredText, and notebook documentation also enter collection. Syntax providers enrich files
their effective language entry selects. The units persist in the workspace database at
`.rift/db`, stamped with the tree revision that published them.

The rebuilt index becomes current as soon as its syntax index is built, and the units are written
behind that publication, in one transaction with the stamp. A whole replace on a large workspace
runs for longer than a read is willing to wait, so the publication never waits for it.

A search that captures the publication before its transaction lands is ranked by identifier
matching alone and carries a `lexical_ranking_unavailable` warning naming the tree revision the
store is still committing; the store's ranking joins the answer once the transaction ends. A
transaction that refuses leaves the previous rows and stamp intact and is recorded in
[`rift://logs`](/docs/mcp#resource-logs), and the next publication replaces the whole
unit set rather than applying its change on top of rows the store missed.

The vector ranking's vectors are not part of that transaction. Embedding one declaration can cost
more than a read is willing to wait, so vectors are refreshed after the index publishes, and a
search whose vectors are still being written ranks lexically and reports the tier's readiness in
`warnings`.

Both tiers answer under one tree revision: the full-text store reads its stamp and its rows in
one transaction, and the vectors a pass published carry the tree they were described for. A store
that has moved past the tree a request captured returns nothing, and the request captures the
publication the store already answers for. What `lexical_ranking_unavailable` tells a caller
about is a store that has not yet committed the captured tree, one that missed a commit, or one
that will not answer at all because it refused to load or holds no indexed tree.

<VersionBadge version="v0.0.32" />

A file past the per-file byte bound, one its syntax provider refuses under a node or depth
bound, one holding a declaration the Contribution contract refuses, or one standing past the
[`[source]`](/docs/developer/configuration#source) `declarations` capacity, is left out of the
index: it answers no search or lookup, counts nowhere in
[`rift://map`](/docs/mcp#resource-map), and is named in
[`rift://logs`](/docs/mcp#resource-logs) with the bound it crossed or the field the
contract refused. One minified bundle therefore never blocks the workspace, and neither does
a workspace declaring more than the index holds: the files that fit are served and the rest
are reported. The [`[source]`](/docs/developer/configuration#source)
exclusion remains the way to keep such files out of the walk altogether.

### Search

[`search`](/docs/mcp#tool-search) is for reads where the exact name isn't known.
It ranks declaration names, signatures, documentation, declaration source, and file content
from the index.

#### The document shape

Every index publishes the same document shape, whether it holds the served project, a
cataloged package, or a fixture a test built in memory. A document carries a stable identity,
the project path or source unit it lives at, its language, its package when it came from one,
a content digest, and the searchable fields below:

| Field | What it holds | Weight |
| --- | --- | --- |
| `name` | A declaration's name, or a file's final path segment with its extension | 10 |
| `qualified_name` | The declaration's qualified name | 6 |
| `identifier_terms` | The names split on case, acronym, and separator boundaries | 4 |
| `signature` | The rendered signature, when a provider published one | 2 |
| `documentation` | The attached doc comment, when a provider published one | 1.5 |
| `declaration_source` | The declaration's own source text | 1 |
| `file_content` | A visible text file's content | 1 |

A fact no provider published stays absent. Nothing substitutes declaration source into the
signature or documentation field, because the two are weighed apart and filling one with the
other would count the same bytes twice. The weights are what make a name hit outrank a hit
buried in a comment, and the answer reports which field placed each hit, so a documentation
match and a name match are distinguishable rather than both reported as "the ranking found it".

The project path, the source unit, the package identity, the language, and the kind stay
metadata. None of them enters the ranked text: indexing one tree below two different host
roots must produce one order, and a path in the ranked text would make the clone directory
part of the score.

The index records a corpus revision covering the field shape, the derivation the identifier
terms were split with, the tokenizer, and the weights. A store stamped with another revision
holds rows this build cannot read, so it answers as if nothing had been published and the next
publication replaces it.

#### Documentation

`search` with `target: "documentation"` returns blocks from selected documentation sources.
Workspace selection includes `.md`, `.markdown`, `.mdx`, `.rst`, and `.ipynb`, plus `.txt`
selected by `[search.text].include`. Source visibility applies before collection.

Each regular source keeps its existing text chunks. Notebook markdown and code cells receive
separate content owners; outputs and raw notebook JSON stay outside ranking. Collection records
block ranges, headings, links, source digests, and exact-symbol references beside those owners.
It neither executes code nor follows links to acquire more sources.

Before fusion, the read maps existing ranked documents to block identities and keeps the best
position once per ranking input. A heading and its text chunk therefore return one documentation
hit. Under `target: "all"`, an attached comment keeps its symbol result when that symbol answered;
a file match outside the comment remains a file result.

For example, a guide containing the inline code `Compass` can contribute context to
`get_symbol` with `name: "Compass"` and `include: ["documentation"]`. The reference resolves only
when the selected declaration set establishes one exact target. Ambiguous names remain unresolved.
The read returns at most 32 references per symbol and 16 KiB of documentation excerpts across the
page, with typed warnings for missing bytes or reached bounds.

Local package collection reads already-present installed sources or verified cached archives.
It does not download missing package sources. Global documentation requests use the existing
package REST client only after the service advertises the corresponding capability. Workspace
paths and source bytes remain local.

#### Query phases

A caller's text is parsed once, into quoted phrases and unquoted terms, and every member is
rendered as a quoted string literal, so an FTS operator a caller typed cannot become an
operator the store executes. The parse is bounded: 4,096 bytes of query, 32 members, 256 bytes
per member. A question carrying more terms than the bound narrows rather than failing - every
quoted phrase survives and the longest remaining terms fill what is left - because a long
question deserves an answer, not a refusal. More quoted phrases than the bound is still
refused: dropping one would answer a question nobody asked.

Two expressions come out of one parse. The **precise** phase requires every member, which is
what answers a multi-term question exactly. The **broad** phase keeps every phrase required and
widens only the unquoted terms with `OR`, so `"impact radius" graph search` renders as
`"impact radius" AND ("graph"* OR "search"*)`.

Every selected index runs the precise phase first and the results fuse together. Only when that
merged answer leaves the candidate pool short does the broad phase join, and its identities
append after every precise one. One index's widened hit therefore cannot displace another
index's exact hit.

#### Ranking inputs and fusion

The rankings below answer, and their answers fuse together:

- **identifier matching** over the declaration names, for the identifiers the query carried;
- **full-text matching** over the document's searchable fields, by
  [BM25](https://en.wikipedia.org/wiki/Okapi_BM25) under the weights above;
- **vector similarity** over the embedded declarations, when a model is configured and its
  vectors are in.

The identifier input reads the query the way a reader would. The whole query counts when it is
one identifier-shaped token, a dotted name buried in prose counts along with its final segment,
and any token that splits into more than one word counts: `where does encode_path get its
escape set` reaches `encode_path` without the caller quoting it. A plain prose word contributes
nothing here, because it reaches the full-text ranking through its own input.

Each ranking scores in units nothing converts between: a match class, a BM25 rank, and a
cosine. What they agree on is the position they put a candidate in, so fusion reads positions
alone and combines them by weighted reciprocal rank.
[`[search.ranking]`](/docs/developer/configuration#search) carries that decision: `fusion_k`
sets how sharply a top rank counts, and `identifier_weight`, `lexical_weight`, and
`vector_weight` set each input's share. Only the inputs that answered take part, so an
unavailable vector ranking contributes nothing and leaves the order the other two state.
Several selected indexes may each contribute one kind; that kind's share then splits among
them, so reaching for a package index does not double what full-text matching is worth.

Fusion holds no project path and resolves no symbol. It answers ordered identities, and the
read path resolves them afterwards, which is what lets a package index rank source units
through the same code. A hit's `score` is derived from its place in the final order: it is
comparable inside one answer and nowhere else.

#### Vector ranking

<VersionBadge
  version="v0.0.16"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

Full-text matching answers a query that shares a token with the code. A query that shares
none - a description of what a declaration does, in the words a bug report would use - reaches
nothing that way, and no amount of ranking repairs that, because the words are not there.

An embedding puts the query and the declaration in one space, so a paraphrase finds code it
has no word in common with. It replaces nothing. A caller who quotes a real name - a symbol, a
configuration key, a line from a traceback - has handed the full-text ranking an exact token to
score, while the embedding maps that name into a space where its near neighbours crowd it.

A declaration is embedded as its own source under its qualified name. The name carries the
module the source doesn't state; the source carries the identifiers and documentation an
encoder trained on code reads best. The path is left out, because the full-text ranking already
covers it.

Every model runs through one contract, whether it is an encoder this process loaded or a
service answering the OpenAI embedding shape. Rift keeps what that contract does not cover:
acquiring the weights, cutting a pass into batches under
[`batch_inputs` and `max_in_flight`](/docs/developer/configuration#search), and narrowing the
coordinates to the stored format once at the boundary.

Vectors are filed under the identity of the space they were embedded into: the source kind, the
endpoint origin for a remote service, the model and its resolved revision, the width, and the
document and query transformations. Any change there mints another identity and the held
vectors are dropped rather than scored against, because two spaces are two coordinate systems.
Credentials never enter it.

A remote endpoint sends declaration text outside the project while the vectors are built, and
query text while a caller searches. The configuration page states both transfers. The local
default sends nothing: it starts without a key and makes no request once the weights are
acquired.

Preparation runs behind the answers. A search issued before the vectors are in is answered by
the other two inputs and says so, rather than waiting for a model to load.

### Retrieve symbol

[`get_symbol`](/docs/mcp#tool-get_symbol) retrieves a declaration when its name is
known. The answer carries the declaration's body inline, so reading a function takes one call
rather than a search followed by a file read.

A Symbol carries `id` when the index established one identity for the declaration; a symbol
the providers could not settle answers without an `id`, and a retained provider disagreement
lands as a `symbol_disagreement` entry in the result's `warnings`.

Asking for history attaches the symbol's committed timeline to the same answer.
