<VersionBadge version="v0.0.5" />

Rift reads `rift.toml` from the workspace root. The generated
[`rift.schema.json`](https://volar.sh/rift/rift.schema.json)
defines the file and rejects any key it doesn't know, so a typo fails at load rather than being
silently ignored. Changes take effect for later requests once validation passes; while the file is
invalid, requests fail with `configuration_invalid` until you fix it.

An editor that supports TOML schema directives can load the generated schema:

```toml
#:schema https://volar.sh/rift/rift.schema.json
```

Treat `rift.toml` as executable workspace configuration: a selected LSP process starts with
the server's OS permissions on its first request. Inspect the file before running Rift in a cloned repository.

Each section states its defaults below its example. Durations take `ms`, `s`, `m`, `h`, or `d`;
byte sizes take `b`, `kb`, `mb`, `gb`, or `tb` - binary units, so `1kb` is 1024 bytes.

## Environment variables

<VersionBadge version="v0.0.44" />

A CI job or a container often needs one bound raised without editing the workspace's
`rift.toml`. Every key has an environment variable for that: `RIFT_`, then the key's path with
its members joined by `_` and uppercased. `[providers.syntax] max_nodes` is
`RIFT_PROVIDERS_SYNTAX_MAX_NODES`, and `[server] port_range.min` is
`RIFT_SERVER_PORT_RANGE_MIN`:

```sh
RIFT_PROVIDERS_SYNTAX_MAX_NODES=5000000 RIFT_PROVIDERS_SYNTAX_MAX_FILE=16mb rift server start
```

- a variable's value replaces the file's value for its key; a key no variable names keeps the
  file's value, or its default
- a key that takes text, such as a size or a duration, takes the value as written, such as
  `16mb`; any other key takes one TOML value, such as `5000000`, `true`, or `["vendor/**"]`
- the merged configuration passes the same checks the file does, so a value outside its range
  fails with `configuration_invalid` naming the variable
- a variable that starts with a table's prefix, such as `RIFT_PROVIDERS_`, and names none of its
  keys fails the same way, listing the variables that table accepts - a misspelled key can't be
  silently ignored
- `[lsp.<name>]` entries have no variables, and neither does a `[languages.<name>]` entry for a
  language Rift doesn't ship

The server reads the variables from the environment of the `rift server start` or `rift mcp`
that started it. A running server keeps that environment, so a changed variable applies after
`rift server stop` and the next start.

<VersionBadge version="v0.0.46" />

A `[languages.<name>]` entry for a language Rift ships takes variables too, spelled
`RIFT_LANGUAGES_<NAME>_<KEY>`: `RIFT_LANGUAGES_PYTHON_STDLIB=false` sets the `stdlib` key of
`[languages.python]`. A dialect's `:` becomes `_`, so `RIFT_LANGUAGES_TYPESCRIPT_TSX_<KEY>` sets a
key of `[languages."typescript:tsx"]`, such as `RIFT_LANGUAGES_TYPESCRIPT_TSX_STDLIB`. A variable
naming a language Rift doesn't ship fails with `configuration_invalid`, as a misspelled key does.

## Server

<VersionBadge version="v0.0.8" />

`server` bounds the server's own blocking work - the filesystem scans and parses behind reads,
and index rebuilds:

```toml
[server]
num_workers = 4
worker_queue_timeout = "30s"
idle_timeout = "30m"
readiness_timeout = "30s"
```

- `num_workers` caps the workers running blocking operations at once, 1 to 64
- `worker_queue_timeout` bounds one request's wait for a free worker, 1ms to 1h - when it
  expires, the request fails with `temporarily_unavailable` and the client can retry without
  stacking another waiter
- `idle_timeout` stops the server once no request remains active and that span has passed after
  the last response completed, 1s to 1d; the next `rift mcp` or `rift server start` brings it back
- `readiness_timeout` bounds one request's waiting, 1s to 1h. A read takes the deadline once,
  where it enters, and the waits it makes - for the workspace's index, for the full-text tier's
  transaction, for a language engine's references - each spend what is left of that one budget
- `port` pins the exact loopback port, 1024 or above; omitted, the server picks the first free
  port from `port_range` - `port_range = { min = 12000, max = 13000 }` is the default - and the
  two keys exclude each other

The worker pool exists before the first request, so the server sizes it once at startup: a
change to this table applies on the next start, while every other table applies to later
requests as soon as the file is accepted.

## Logs

<VersionBadge version="v0.0.22" />

`logs` bounds what the server records about itself. Diagnostics admitted by `capture` enter a
bounded queue and land in the workspace database, where the `rift://logs` resource reads them
back for an agent and `rift server logs` reads the same records for an operator - so a refusal an
agent meets can be explained without an operator reading the server's terminal:

```toml
[logs]
retention_records = 50000
page_records = 500
capture = "rift=info,rift_mcp=info,rift_server=info,rift_index=warn"
```

- `retention_records` caps the records the store keeps, 100 to 1000000; a write past the cap
  drops the oldest records first
- `page_records` caps what one `rift://logs` read returns, 1 to 5000
- `capture` selects which targets are recorded, in the `RUST_LOG` spelling `tracing` takes -
  `rift_mcp=debug` records the index lane's own rebuild decisions. A target this filter
  excludes never reaches the store, whatever the terminal shows

The server reads this table at startup, so a change applies on the next start. The records
outlive the process that wrote them: they live beside the search index in `.rift/db`, and a
workspace whose index will not settle still answers `rift://logs`.

## Source

<VersionBadge version="v0.0.6" />

`source` controls which files below the workspace root the index and reads consider visible.
`include` and `exclude` take exact project-relative paths or globs, matched the same way
[`search`](/docs/mcp#tool-search)'s `paths` selector matches them:

```toml
[source]
include = []
exclude = []
force_include = []
respect_gitignore = true
files = 100000
workspace_size = "512mb"
declarations = 1000000
```

The four glob lists decide in one order:

1. `exclude` drops a file, whatever else matched it.
2. `force_include` keeps a file `.gitignore` would hide, and keeps it without an `include` match.
3. `respect_gitignore`, on by default, applies the workspace's own `.gitignore` files, root and
   nested; the server never reads global or parent-directory ignore sources.
4. `include`, when it is not empty, is what a remaining file has to match. Empty `include`
   includes every file the steps above leave standing.

`force_include` is what an operator reaches for when a directory belongs in the index and outside
version control at once - design documents, a scratch corpus, a generated tree the build ignores:

```toml
[source]
force_include = [".plans/**"]
```

A workspace naming no `force_include` pattern indexes exactly what it indexed before. A workspace
naming one walks those subtrees a second time with `.gitignore` not consulted, spending the same
`files` budget as the first walk.

`.git`, `.rift`, and `target` stay invisible whatever this table says: no `include`, `exclude`,
`force_include`, or `.gitignore` entry can make the server serve them.

`files` bounds how many files the index holds, 1000 to 5000000, and `workspace_size` bounds the
bytes they hold together, 16mb to 64gb. The server refuses to index a workspace past either bound
and names the key in the refusal; a change to either key rebuilds the index, as a change to
`include`, `exclude`, or `force_include` does.

`declarations` bounds how many declarations those files publish together, 10000 to 50000000.
This one is a capacity, not a refusal: a workspace declaring more indexes the files that fit,
leaves the rest out, and reports each one as an unavailable source naming this key. The default
holds a full index in about 5 GiB, which is room for a workspace twice the size of the largest
Rift is tested against - raise it on a machine with memory to spare, lower it on one without.

`source` shapes what the index walks: a file it excludes stops reaching `search` and
[`get_symbol`](/docs/mcp#tool-get_symbol) results. A single `search` request can still
reach one such file on demand, through the request-side `force_include` override on `search`'s
`paths` selector. The two differ in reach and lifetime: the request field pulls at most 256 files
into one answer, while this table's `force_include` puts them in the index every read serves from.

## Documentation

<VersionBadge version="v0.0.46" />

`documentation` describes which documentation files the index collects for
[`search`](/docs/mcp#tool-search) with `target: "documentation"` and for the `documentation`
field of a [`get_symbol`](/docs/mcp#tool-get_symbol) hit. By default the index collects every
visible Markdown, MDX, reStructuredText, and notebook file, and the `.txt` files
`[search.text].include` selects, except:

- change logs, licenses, and codes of conduct, wherever they sit: `CHANGELOG.md`,
  `CHANGELOG.mdx`, `LICENSE.md`, and `CODE_OF_CONDUCT.md`, each also spelled in lower case
- archived and superseded copies: any folder named `old`, `docs/old`, and any folder whose name
  holds `archive`, `deprecated`, `legacy`, `previous`, `outdated`, or `superseded`
- translations: language folders below a root `i18n` folder, such as `i18n/zh-cn` or
  `i18n/fr`, and folders named `zh-cn`, `zh-tw`, `zh-hk`, `zh-mo`, or `zh-sg`

The table overrides that default:

```toml
[documentation]
enabled = true
exclude = []
force_include = []
```

- `enabled` defaults to `true`; `false` collects no documentation file, while the documentation
  comments attached to declarations stay
- `exclude` leaves out what its globs match beside the default exclusions, at most 512 patterns
- `force_include` collects what a default exclusion leaves out, at most 512 patterns; a match
  `exclude` also names stays out

The patterns match project-relative paths the way [`[source]`](#source) patterns do. A workspace
whose change log belongs in search adds it back:

```toml
[documentation]
force_include = ["CHANGELOG.md"]
```

A change to the table rebuilds the index, and the `RIFT_DOCUMENTATION_ENABLED`,
`RIFT_DOCUMENTATION_EXCLUDE`, and `RIFT_DOCUMENTATION_FORCE_INCLUDE` variables override it like
any other key.

## Dependencies

<VersionBadge version="v0.0.39" languages={["Rust", "Python", "TypeScript"]} />

`dependencies` shapes the [dependency context](/docs/developer/architecture#dependency-context) a
`global` or `all` read sends to the global index: which packages you name beside the ones the
workspace's own files state, and whether a standard library version probe runs. The keys are
shown at their defaults:

```toml
[dependencies]
resolution = "auto"
packages = []
command_timeout = "2m"
```

- `resolution` selects whether a standard library version probe runs: `auto` runs
  `rustc --version`, and `node --version` when no Node.js pin names a version, in the workspace
  root; `static` runs no program, so every version comes from the pins and project files alone,
  or goes out as the requirement `>=0`
- `packages` names packages beside the ones the workspace's manifests and lockfiles state, at
  most 20000 of them. Each entry carries `manager`, `name`, and exactly one of `version` and
  `requirement`; an entry naming both, or neither, is refused
- `command_timeout` bounds one version probe, 1s to 1h; a probe past it is killed and the entry
  goes out with its static reading

A configured entry looks like this:

```toml
[[dependencies.packages]]
manager = "cargo"
name = "serde"
version = "1.0.228"

[[dependencies.packages]]
manager = "npm"
name = "typescript"
requirement = "^5.9.0"
```

## Global

<VersionBadge version="v0.0.43" />

`global` controls package reads through the configured REST API. The local server creates this
client on the first `global` or `all` read that can return package declarations.

```toml
[global]
enabled = true
endpoint = "https://api.volar.sh/rift/rest"
token_env = "RIFT_API_TOKEN"
connect_timeout = "3s"
request_timeout = "15s"
attempts = 3
max_in_flight = 4
capabilities_ttl = "15m"
resolution_ttl = "15m"
failure_ttl = "30s"
```

- `enabled` defaults to `true`; `false` sends no package read to the global API, so a
  package-scope read answers project hits alone and reports `global_access_disabled`
- `endpoint` defaults to `https://api.volar.sh/rift/rest`; it must be an absolute base URL without
  user information, query, fragment, or trailing slash
- `token_env` defaults to `RIFT_API_TOKEN` and names the environment variable holding the optional
  bearer token. An unset variable uses anonymous access
- `connect_timeout` defaults to `"3s"` and accepts `100ms` to `30s`
- `request_timeout` defaults to `"15s"` and accepts `1s` to `5m`; it covers connection, response,
  retry delays, and every attempt
- `attempts` defaults to `3` and accepts `1` to `5`
- `max_in_flight` defaults to `4` and accepts `1` to `32`
- `capabilities_ttl` and `resolution_ttl` default to `"15m"` and accept `1m` to `24h`
- `failure_ttl` defaults to `"30s"` and accepts `1s` to `1h`

When `token_env` names a non-empty valid value, the client sends it as the `Authorization: Bearer`
header to the configured endpoint. Empty or malformed values leave global access unavailable before
the client sends a request, and the token never enters logs, errors, metrics, or cache keys.

The client does not contact the endpoint at server startup. A `local` read and a file-only search
also make no global request.

A connection failure, timeout, retry exhaustion, authentication failure, invalid response, or
non-success response marks global access unavailable for `failure_ttl`. The package read that met
it, and every package read until `failure_ttl` passes, answers the project hits it has and reports
a typed warning with that failure's class. A valid remote page keeps its items and reports each
bounded service condition as `global_page_warning`.

A valid resolution answers package reads from the global index, and the nearest collected release
answers an entry whose version it lacks, reporting `package_substituted`. A package with no
collected release reports `package_absent`, or `package_requirement_absent` for a declared
requirement. A package no public registry serves - a path outside the workspace, a git
repository, a private registry, or a URL - never reaches the global API and reports
`package_unavailable`.

## Languages and LSP

<VersionBadge version="v0.0.25" />

An exact language entry connects visible paths to shipped syntax and an optional LSP process. Its key is a language name, or `name:dialect` for an exact dialect:

```toml
[languages.rust]
enabled = true
include = ["**/*.rs"]
exclude = ["vendor/**"]
lsp = "rust"

[lsp.rust]
command = ["rustup", "run", "1.98", "rust-analyzer"]
environment = {}
startup_timeout = "30s"
request_timeout = "1m"
settle_delay = "500ms"
output_limit = "4kb"

[lsp.rust.retry]
attempts = 8
delay = "250ms"
delay_limit = "2s"

[lsp.rust.restart]
attempts = 3
window = "5m"
```

Every shipped syntax provider contributes its file patterns. An absent `include` keeps those
patterns; a present list replaces them, and an empty list matches no file. `exclude` removes
matches from the effective list. `enabled` defaults to `true`, `exclude` defaults empty,
and `lsp` is absent by default. A bare language and each of its dialect entries are independent.
`enabled = false` turns off syntax and LSP service for paths the entry matches.

A language no shipped syntax provider knows must carry a nonempty `include` list. It can still
select an LSP process. One visible path may match one exact language; a current path two entries
claim refuses the workspace candidate, naming the path and both identities. The previously
published revision keeps serving.
A visible file no language claims remains available to generic reads, and joins lexical search as
plain text when `[search.text].include` selects it. So does a file whose entry is disabled, or
whose language ships no grammar: what those entries drop is syntax analysis, not the file.

<VersionBadge version="v0.0.46" languages={["Rust", "JavaScript", "TypeScript", "Python"]} />

`stdlib` decides whether the [dependency context](/docs/developer/architecture#standard-libraries)
names the language's standard library, so a `global` or `all` read can answer for it:
`stdlib/rust` for `rust`, `stdlib/node` and the npm `typescript` package for `javascript`,
`typescript`, and `typescript:tsx`, and `stdlib/python` for `python`. It defaults to `true`. A
Rust repository whose Python is a few build scripts can leave Python's standard library out of
package reads:

```toml
[languages.python]
stdlib = false
```

A library stays in the context while any language the workspace uses that names it keeps the key
on. A repository holding `.ts` and `.js` files therefore still names `stdlib/node` when only
`[languages.typescript]` sets `stdlib = false`, because `javascript` names it too.

`lsp` accepts an inline process table or the name of one shared top-level process. The inline
table collapses to one key when the program takes no arguments:

```toml
[languages.rust]
lsp.command = "rust-analyzer"
```

A named process may serve several exact identities, including dialects:

```toml
[languages.typescript]
lsp = "typescript"

[languages."typescript:tsx"]
lsp = "typescript"

[lsp.typescript]
command = ["node_modules/.bin/typescript-language-server", "--stdio"]

[lsp.typescript.initialization_options.tsserver]
useSyntaxServer = "never"
```

<VersionBadge version="v0.0.31" languages={["Python"]} />

An entry may select the embedded engine instead of a spawned command. The build links the
engine in, so nothing is installed or started beside the server:

```toml
[languages.python.lsp]
embedded = "ty"
```

`embedded` names an engine this build carries; `ty` serves Python. Exactly one of `command`
and `embedded` is present, and an embedded engine takes no `environment` and no
`initialization_options`: both configure a spawned process, so a table naming them beside
`embedded` is refused rather than silently ignored.

The embedded engine reads ty's configuration from the served tree alone: the root's own `ty.toml`,
or the `[tool.ty]` table in its `pyproject.toml`. A `ty.toml` or `pyproject.toml` in a directory
above the root is never read, so the project the engine analyzes is the served tree.

Its Python environment is the one that configuration names, else the project environment in
`.venv` when its `pyvenv.cfg` stands, else none, which leaves the tree's own modules and the
typeshed stubs the engine ships. The server's `VIRTUAL_ENV`, `CONDA_PREFIX`, `PYTHONPATH`, and
`PATH` never reach it, so the engine reads the same `.venv` the uv resolver reads beside a
`uv.lock` at the tree's root. Creating, removing, or recreating `.venv`, and each distribution
`uv sync` installs, removes, or upgrades in it, takes effect on the engine's next request, with no
server restart.

`command` accepts a program string without whitespace or a nonempty list holding the program and
its literal arguments. The list holds one program and at most 64 arguments; each argument holds
at most 4096 bytes. Rift starts the command directly without a shell. Absolute programs are
refused. A bare name resolves through the server's `PATH`, with `environment` applied on top.
`initialization_options` is absent by default and must be a JSON object when present;
`environment` defaults empty and holds at most 64 entries.

`startup_timeout` defaults to `"30s"` and takes `"1s"` to `"10m"`. `request_timeout` defaults
to `"1m"` and takes `"1s"` to `"10m"`. `settle_delay` defaults to `"500ms"` and takes `"10ms"` to
`"1m"`. `output_limit` defaults to `"4kb"` and takes `"1kb"` to
`"8mb"`; Rift still reports the full size, so you can tell a truncated log from a short one.

`retry` bounds repeated requests while an answer stays unsettled. `attempts` includes the first
request; waits start at `delay`, double, and stop at `delay_limit`. `restart` bounds replacement
processes after a process ends or stops answering. A replacement older than `window` stops
counting. The server starts a process on its first request and keeps it across later requests.
Configuration reload reuses unchanged process definitions and ends replaced processes.

`retry.attempts` defaults to `8` and takes `1` to `64`. `retry.delay` defaults to `"250ms"` and
takes `"1ms"` to `"1m"`; `retry.delay_limit` defaults to `"2s"` and takes `"1ms"` to `"10m"`.
`restart.attempts` defaults to `3` and takes `0` to `16`; `restart.window` defaults to `"5m"` and
takes `"1s"` to `"1d"`.

A named process that no language selects is accepted but never started. A language that names a
missing process is refused during configuration validation. The top-level table holds at most 16
processes. The workspace holds at most 64 language entries. Each language `include` and `exclude`
list holds at most 64 patterns.

A language server may decline a request it's already serving, report that the file moved under
it, or answer before it has loaded the declaration. Every such refusal gets the configured retry
schedule. If every attempt refuses, Rift returns the language server's latest words.

`settle_delay` decides when an answer stops being provisional. A language server reports what it
is loading over work-done progress, and rust-analyzer ends and begins those reports in bursts:
its outstanding work empties several times inside one project load, well before the phase that
resolves references has run. So Rift calls a process loaded only once its work has stayed
announced and empty for `settle_delay`, measured at the last output Rift read from it. Raise it
for a process whose load falls silent for longer than half a second between phases; the retry
schedule above is what carries a request across the wait.

A capability the server never advertised is not a refusal and returns at once.

`restart` bounds what Rift does when the process itself fails. One that ended, that couldn't be
started, or that stopped answering is replaced automatically, and the replacement serves the
request. Each replacement spends one of `restart.attempts`, and a replacement older than
`restart.window` stops counting, so a process that dies once a week never runs out.

One that crash-loops does: once the budget is spent, requests for its languages fail
`temporarily_unavailable` until the window passes, instead of starting a process that dies again.
The first process a workspace starts is the start, not a replacement, and a refused `command`
program, empty or an absolute path, is reported at once rather than started again.

A symbol address spells its language as an identity segment, and a declaration in a `.tsx` file
is addressed under the dialect: `rift://symbol/typescript:tsx/view.tsx/Banner`. The server looks
the entry up by that exact identity, so the bare language and the dialect are two independent
entries, each selecting its own process, and both may select the same named one. Each dialect needs its own entry.

A minimal entry names its process inline. This one names
[tombi](https://github.com/tombi-toml/tombi), a TOML formatter, linter, and language server:

```toml
[languages.toml.lsp]
command = ["tombi", "lsp"]
```

`lsp` is the subcommand that starts tombi's language server over stdio.

A language server that ships as a package runs from workspace-installed bytes. Pin both packages
in `package.json`, install from its lockfile, and point `command` at the local executable, the way
`[lsp.typescript]` above does. This avoids paying package runner resolution at startup.

typescript-language-server refuses its initialize request unless a `typescript` package resolves
from the workspace root, answering `Could not find a valid TypeScript installation`. Install that
package in the workspace, or name an existing one with the `tsserver.path` initialization option;
without either, language-server initialization fails with that message.

The index still walks what `source` leaves visible, so the installed package directory needs an
exclude:

```toml
[source]
exclude = ["node_modules/**"]
```

Without it the walk reaches `typescript`'s own sources, including files past the index's per-file
byte bound. Any workspace with an installed package directory needs the same entry.

`tsserver.useSyntaxServer = "never"` keeps the process to one semantic server. The default
`auto` also runs a syntax-only server.

## Providers

<VersionBadge
  version="v0.0.7"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

The built-in providers run without configuration; the `providers` table exists to bound or
disable them:

```toml
[providers.history]
enabled = true
strategy = "everything"
max_revisions = 100
batch_commits = 25
batch_size = "1000000b"
cpu_share = 0.25
```

`enabled = false` turns the history provider off: the server refuses a revision-addressed read -
`rev` on [`get_symbol`](/docs/mcp#tool-get_symbol), `search`, or `nodes` - a
[change comparison](/docs/mcp#search-change), and a [commit search](/docs/mcp#search-commits)
with `capability_unavailable`. A workspace without version control cannot serve those reads
whatever this table says.

<VersionBadge version="v0.0.46" />

The history provider fills the [history store](/docs/developer/architecture#history) in the
background, and the configuration allows you to describe:

- `strategy` - which revisions the store holds: `everything`, the newest first-parent commits of
  every live worktree, or `selective`, the releases `releases` names
- `releases` - tag names or tag patterns such as `v1.*`, at most 64, which `selective` requires and
  no other strategy accepts; a pattern that does not compile as a glob, such as the unclosed class
  `v[1`, is refused
- `max_revisions` - how many revisions the store holds, 1 to 100000: commits under `everything`,
  releases under `selective`
- `batch_commits` - how many commits one store write holds, 1 to 10000
- `batch_size` - how many parsed bytes one store write holds past its first commit, 1kb to 1gb
- `cpu_share` - the share of one core the fill parses at, above 0.0 up to 1.0

`selective` orders the releases by the version each tag name spells once the pattern's literal
text up to its first digit or wildcard is stripped: `1.*` reads `1.80.0` whole, and `v0.0.*`
strips the `v`. A matched tag whose rest is no semantic version, such as `0.10`, is left out, and
the server records it under `rift server logs --component history`.

A fill waits a bounded time for the server to run no request before each batch, then parses at
`cpu_share`, pausing after each commit. The server reads this table at startup, so a change applies
on the next start. The store keeps one file per server build and strategy, so changing `strategy`
or `releases` fills a new store file.

<VersionBadge version="v0.0.44" />

A syntax provider's cost grows with the source it parses, so `[providers.syntax]` bounds each
source every syntax provider takes:

```toml
[providers.syntax]
max_file = "4mb"
max_nodes = 250000
max_depth = 512
```

- `max_file` bounds the bytes of one source, 1b to 64mb
- `max_nodes` bounds the syntax nodes one source produces, 1 to 100000000
- `max_depth` bounds how deep one source's syntax tree nests, 1 to 65536

A source past any bound is left out of the index while the rest of the workspace serves: a
generated file of deeply nested literals answers no [`search`](/docs/mcp#tool-search), and
every other file still does. The server records each such file under
`rift server logs --component index`, with the path and the bound it crossed; raise that key to
index the file.

Provider configuration does not set merge order or freshness. A provider rebuilding after a file
change can serve its previous immutable revision; the result then carries a `stale_index` entry
in `warnings` naming the two tree revision digests.

## Search

<VersionBadge version="v0.0.9" />

[`search`](/docs/mcp#tool-search) runs on a lexical index. `[search.text]` selects the
plain-text files that join it through `include` and bounds their chunks. `pool_slots` bounds
pooled connections shared by search and stored logs; writes wait for one process-wide turn.

<VersionBadge version="v0.0.25" />

A visible file joins the lexical index through its effective language entry, or through
`[search.text].include` when no language claims it. Documentation collection also selects visible
`.md`, `.markdown`, `.mdx`, `.rst`, and `.ipynb` sources. Its `.txt` selection follows `include`.
Narrow that list where the workspace holds large unclaimed files search should not carry:

```toml
[search.text]
include = ["**/*.md", "**/*.mdx", "**/*.txt"]
max_chunk = "1mb"

[search]
pool_slots = 4
busy_timeout = "5s"
```

- `include` selects text files from the visible paths no language entry claimed, at most 64
  patterns. It defaults to `["**"]`, so every such path joins the lexical text index; an explicit
  empty list leaves only language-selected files and required documentation sources
- `max_chunk` bounds how large a selected text file may grow before it's split into several
  indexed chunks, 1kb to 16mb
- `pool_slots` bounds SQLite connections the workspace database may hold open at once, 1 to 16
- `busy_timeout` bounds how long a read or write waits for one of those connections to come
  free, and how long a connection waits for a database lock held by another process before
  failing with `SQLITE_BUSY`, 100ms to 30s

`large_files` decides what search does with a file whose text runs past `max_chunk`, and
`excluded_lockfiles` names the lockfiles search leaves out:

```toml
[search.text]
large_files = "split"
excluded_lockfiles = ["Cargo.lock", "uv.lock", "package-lock.json", "bun.lock"]
```

- `large_files` is `split`, the default, or `skip`. Under `split` the file is indexed as
  whole-line chunks of at most `max_chunk`, and a file past [`[providers.syntax]`](#providers)
  `max_file` is held as text the syntax provider does not parse, up to [`[source]`](#source)
  `workspace_size`; every answer names such files in a `large_file_unparsed` warning. Under
  `skip` the file leaves the text index, a file past `max_file` leaves the index entirely, and an
  answer whose `paths` reach one counts it in a `large_file_skipped` warning
- `excluded_lockfiles` names the lockfiles search leaves out, matched against each visible file's
  final path segment, at most 64 names of up to 255 bytes. The default lists `Cargo.lock`,
  `uv.lock`, `package-lock.json`, `bun.lock`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`,
  `Pipfile.lock`, `composer.lock`, `Gemfile.lock`, `go.sum`, and `deno.lock`; an empty list
  indexes every lockfile

A lockfile search leaves out answers no search and no symbol lookup, while
[`rift://map`](/docs/mcp#resource-map) still carries the versions it pins. A search whose
`paths.include` selects one warns `lockfile_excluded`, and naming it in `paths.force_include`
searches it for one request.

A regex [`pattern`](/docs/developer/protocol/mcp#search-pattern) search runs under four `[search]`
keys:

```toml
[search]
pattern_compiled_size = "1mb"
pattern_candidate_rows = 10000
pattern_verified_size = "128mb"
pattern_matches_per_file = 1000
```

- `pattern_compiled_size` bounds the bytes one pattern's matcher compiles to, 64kb to 64mb
- `pattern_candidate_rows` bounds the trigram index rows one search reads to select the files it
  verifies, 100 to 1000000; a file split into chunks counts once per chunk
- `pattern_verified_size` bounds the file text one search verifies, 1mb to 64gb
- `pattern_matches_per_file` bounds the matches one file contributes, 1 to 100000

A search that would pass one of the first three refuses naming the key. A file past
`pattern_matches_per_file` is cut there, and the answer warns `pattern_matches_truncated`.

While the trigram index catches up after a write, the rows it lacks are verified within what the
selection leaves of `pattern_candidate_rows` and `pattern_verified_size`. Past either, the search
answers from the rows the index holds and warns `pattern_index_preparing` rather than refusing.

The rankings are combined by reciprocal-rank fusion: a result scores as the weighted sum of
`1 / (k + rank)` over the rankings that returned it. `[search.ranking]` carries the weights
and the `k`:

```toml
[search.ranking]
identifier_weight = 0.35
lexical_weight = 0.35
vector_weight = 0.30
fusion_k = 60
```

- each weight is that ranking's share of a fused score, 0.0 to 1.0. They don't have to sum
  to 1: the server normalizes the weights of the rankings that actually answered, so an
  unavailable vector ranking doesn't rescale what the other two returned. At least one
  weight must be above 0
- `identifier_weight` weighs identifier matching, which ranks the identifiers a query
  carried against the indexed declaration and qualified names. A question naming a
  declaration in prose reaches it through this ranking
- `lexical_weight` weighs the full-text ranking over declaration names, signatures, and
  attached documentation, and over the text of every indexed file
- `vector_weight` weighs the vector ranking, which reaches code sharing no word with the
  query
- `fusion_k` sets how sharply a top rank counts, 1 to 1000; a larger value flattens the
  contribution curve and lets agreement between the rankings outweigh one ranking's top
  position

`[search.vector]` bounds the vector ranking, and `[search.vector.embedding]` names the model
it runs on:

```toml
[search.vector]
candidates = 200
candidates_per_file = 3
max_vectors = 200000

[search.vector.embedding]
kind = "hf"
model = "minishlab/potion-retrieval-32M"
download_timeout = "5m"
download_attempts = 3
batch_inputs = 32
max_tokens = 256
```

- `candidates` bounds how many declarations the vector ranking returns before the rankings
  are fused, 1 to 1000
- `candidates_per_file` bounds how many declarations one file contributes to that list, 1 to
  64; the rest of the file's declarations are dropped, so one file whose declarations all rank
  well can't fill the list on its own and leave every other file unreachable
- `max_vectors` bounds how many vectors the workspace holds, 1000 to 1000000; each vector
  costs the model's dimension in single-precision floats
- `kind` selects which embedding runs, and each kind carries only the keys its execution
  reads: `hf` downloads the weights from a Hugging Face repository and caches them where
  every other Hugging Face client on the machine caches them, `directory` reads a directory
  the workspace already holds and downloads nothing, and `openai_compatible` sends embedding
  inputs to a service implementing the OpenAI embedding shape
- `model` names which weights, in the form `kind` sets: under `hf` a repository identifier
  such as `minishlab/potion-retrieval-32M`, optionally carrying a revision after `@`; under
  `directory` a workspace-relative directory; under `openai_compatible` the model the
  service exposes. The server stores vectors per model - two models' vectors aren't
  comparable - so changing the value embeds the workspace again
- The model's own `config.json` decides how the server reads it. A `model_type` of
  `model2vec` names a static model, which embeds a declaration by averaging one row per
  token; anything else is read as a BERT checkpoint, which runs a forward pass per batch.
  The shipped default is static, because a forward pass over every declaration in a
  workspace costs minutes on a laptop CPU and a row gather costs seconds
- `download_timeout` and `download_attempts` bound one model acquisition under `hf`, 10s to
  1h and 1 to 10; a spent budget leaves search lexical for the life of the server
- `batch_inputs` and `max_tokens` bound one embedding pass, 1 to 256 and 32 to 512 under a
  local model. A BERT checkpoint's attention memory grows with the square of the token
  window, so a raised window wants a lowered batch; a static model reads one row per token,
  so its cost grows with the window rather than with its square

An `openai_compatible` embedding sends declaration text outside the project while vectors are
built, and query text while a search runs. The local default sends neither: it starts without
a key and makes no request once the weights are acquired.

```toml
[search.vector.embedding]
kind = "openai_compatible"
endpoint = "https://api.openai.com/v1"
model = "text-embedding-3-small"
revision = "2024-01-25"
dimensions = 1536
api_key_env = "OPENAI_API_KEY"
request_timeout = "30s"
attempts = 3
batch_inputs = 64
max_in_flight = 4
```

- `endpoint` is the base URL the request path is appended to. It uses `https`; `http` is
  accepted only when the host is `localhost`, `127.0.0.1`, or `::1`
- `revision` is a deployment identifier the operator states, such as a dated release. It
  participates in vector invalidation, so an endpoint serving new weights under one model
  name gets a new value here
- `dimensions` is how many coordinates one vector carries, 1 to 16384
- `api_key_env` names the environment variable holding the credential, and never carries the
  credential itself
- `request_timeout`, `attempts`, `batch_inputs`, and `max_in_flight` bound one embedding
  request and the requests running together: 1s to 5m, 1 to 10, 1 to 2048 inputs, and 1 to 32
  requests
- the service must answer one vector per input and declare each one's input `index`. The
  server associates by that index rather than by array order, and refuses a response that
  repeats an index, omits one, or names one past the request's own length: any of those
  would attach a vector to the wrong declaration

`disabled` keeps the workspace lexical without emptying the rest of the table. Set it where
the workspace must not fetch model weights:

```toml
[search.vector]
disabled = true
```

`[search.lexical].units_max` bounds how many units the lexical index holds, one per indexed
file, text chunk, and declaration, 1000 to 50000000:

```toml
[search.lexical]
units_max = 1000000
transaction_units = 5000
transaction_size = "16mb"
mmap_size = "1gb"
```

A workspace past it publishes its index without the lexical ranking: the store refuses the
commit, and `search` answers from identifier matching with a `lexical_ranking_unavailable`
warning naming `units_max`, the observed count, and the maximum. Raise the key, or narrow
[`[source]`](/docs/developer/configuration#source) so fewer files reach the index.

`transaction_units`, 100 to 1000000, and `transaction_size`, 1mb to 1gb, bound one
transaction of a lexical write. A write past either commits in several transactions, and the
last one stamps the tree it answers for. One file's units always share a transaction, so a
file holding more takes one of its own. The bounds are what a server asked to stop waits on:
it aborts the transaction running, and the next start writes what that transaction did not
reach. The trigram index behind regex search is filled after each write in transactions under
the same two bounds.

One unit holds at most 16mb of content, the largest chunk `max_chunk` accepts, so every chunk
the configuration derives fits. A declaration's unit carries its names, signature, and
documentation alone; its text lives in its file's chunks.

<VersionBadge version="v0.0.46" />

`mmap_size` sets how much of the workspace database each connection reads through a memory map,
0b to 2147418112b, the most the bundled SQLite maps; the default `1gb` maps the whole store of a
workspace the size of the Bun or Next.js repositories. `0b` reads through SQLite's page cache
alone. Every pooled connection maps the file on its own, so resident memory counts the mapped
pages once per open connection, and an I/O error on the mapped file ends the server with a
signal rather than an error; [SQLite's memory-map page](https://www.sqlite.org/mmap.html) states
both costs.
