This reference defines Rift's MCP tools and resources, including optional fields, paging,
limits, and failures. For an introduction through an agent's workflow, see the
[MCP guide](/docs/mcp).

The expandable tool examples come from the served [JSON schema](https://volar.sh/rift/mcp.json).
A result example on this page shows one answer in two tabs: its compact text and its JSON.
[Result content](#result-content) defines the compact text.

## Map [#resource-map]

`rift://map` reads a workspace orientation snapshot: a starting picture for a caller new to the
codebase. The answer carries:

- `revision` - an eight-character [`Digest`](/docs/developer/protocol/reference) of the indexed
  tree the map was computed from
- `languages` - per-language file and symbol counts, sorted by language spelling
- `modules` - the directory tree indexed files sit under, each entry's file and symbol counts
  inclusive of its descendants, folded three directories deep
- `hubs` - the most-referenced symbols, ranked by reference count descending
- `entry_points` - symbols where execution starts
- `docs` - markdown files, in path order
- `module_relationships` - the modules a resolved reference reaches between, ranked by that
  count descending
- `packages` - the packages the workspace's manifests and lockfiles state, in `manager`,
  `name`, then selector order
- `pagination` - always page zero of one, the whole map on one page
- `warnings` - conditions that qualify the answer, omitted when empty

During local preparation, the map carries [`local_index_preparing`](#reads). File counts and
documentation paths can describe discovered files before their declarations are prepared;
symbol counts describe prepared declarations. The server **MUST** return the map's revision,
counts, and warnings from the same publication.

`entry_points` lists symbols carrying the `entrypoint`
[`SymbolFacet`](/docs/developer/protocol/reference) - a file-scope `fn main`, not one
nested in a module, an `impl` block, or another function. It stays empty for a workspace with no
such facts.

`hubs` ranks [`SymbolId`](/docs/developer/protocol/reference)s by how often the index
holds a resolved reference to them, and `module_relationships` folds both ends of every such
reference to the module `modules` lists them under, drops a pair whose two ends fold to one
module, and counts what is left. `module_relationships` carries at most 100 entries, ordered
by `references` descending, then `from`, then `to`, so a workspace past that bound keeps the
strongest pairs and two reads of one tree agree. Both read the index alone: the language
engine resolves a reference for one read and publishes none, so both lists stay empty until a
provider publishes resolved references into the index.

`packages` lists the [dependency context](/docs/developer/architecture#dependency-context): what the
Cargo, uv, npm, and Bun resolvers read from `Cargo.toml` and `Cargo.lock`, `pyproject.toml` and
`uv.lock`, `package.json` and `package-lock.json`, and `package.json` and `bun.lock`. The
resolvers read those files and run no toolchain. Each entry is a
[`PackageContextEntry`](/docs/developer/protocol/reference) carrying the exact
`version` a lockfile pins or the `requirement` a manifest declares, never both, and the
`availability` a global package index could answer under. The list follows those files: one
rewritten while the server runs is read again on the next publication.

A resolver reads at most 256 manifests per workspace, taken in path order, so `packages` over a
workspace holding more lists what the manifests it read declare.

`packages` also lists one entry for each standard library a language the workspace uses relies
on, under the manager `stdlib`: `stdlib/rust`, `stdlib/node` beside the npm `typescript` package,
or `stdlib/python`. Its version comes from the workspace's pins, or from a version probe under
[`[dependencies]`](/docs/developer/configuration#dependencies) `resolution = "auto"`, and the
[dependency context](/docs/developer/architecture#standard-libraries) lists where each one is read.

## Search

<McpTool name="search" />

`search` accepts `query: string` and optional `language: "sparql"`. `language` defaults to
`sparql`; unknown languages and former top-level selectors fail request validation. The
query uses the library's SPARQL parser, algebra, and evaluator over immutable selected facts.

```json
{ "query": "SELECT ?symbol ?name { ?symbol a :Symbol; :name ?name } ORDER BY ?name LIMIT 20", "language": "sparql" }
```

### Vocabulary and terms

The default empty prefix is `urn:rift:vocabulary:`. The `r:` prefix names the same vocabulary;
`rdf:`, `rdfs:`, and `xsd:` name their standard namespaces. Explicit prefix declarations are
supported. The vocabulary follows existing fact fields, including `:name`, `:kind`,
`:language`, `:declarations`, `:source`, `:unit`, `:range`, `:start`, and `:end`.

Symbols with established identities use canonical `SymbolId` IRIs. Source units retain their
`SourceUnitId` IRIs. A physical occurrence or nested record uses a blank node, whose identity
is retained across pages of its execution. A symbol without an established canonical identity
also remains a blank node. Evaluation does not fabricate a canonical identity from its name.

Available nested records preserve existing fields, ordered array entries through `:index` and
`:value`, defaults, and opaque extensions as `rdf:JSON`. A bare `:name` query can match nested
records such as parameters. Use `a :Symbol` when the question requires symbols alone.

### Query forms

- `SELECT` returns `answer.result: "bindings"`, ordered `variables`, and `bindings` rows.
- `ASK` returns `answer.result: "boolean"` and `value`.
- `CONSTRUCT` and `DESCRIBE` return `answer.result: "graph"` and `triples`.

Each binding or triple term carries its kind: `iri`, `blank_node`, `literal` with `datatype`, or
`language_literal` with `language`. Unbound variables are omitted from the row. Duplicate
bindings and projected variable order follow SPARQL. Graph answers use RDF set semantics.

`DESCRIBE` uses the library's description behavior over all authoritative captured and published records in its selected dataset. It does not implicitly request every language-engine facet. Facts explicitly required by its `WHERE` pattern retain the same strict acquisition and missing-facts rules as other query forms; bounds still refuse incomplete admission.

### Full-text search [#search-fulltext]

The local `SERVICE :search` reuses identifier, lexical, and available vector ranking. Its
constant input triples select the producer request, while its graph pattern projects and
filters the acquired records:

```sparql
SELECT ?symbol ?name ?source ?score {
  SERVICE :search {
    ?hit :query "loads workspace configuration"; :target "symbol";
         :symbol ?symbol; :source ?source; :score ?score .
    ?symbol :name ?name
  }
}
ORDER BY DESC(?score)
LIMIT 5
```

`:query`, `:pattern`, `:scope`, `:target`, `:order`, `:rev`, `:paths`, `:packages`, `:include`,
`:change`, and `:view` retain their producer meanings inside the service. Structured inputs
use `rdf:JSON` literals. Conflicting constant inputs refuse. Requesting `:source` and `:score`
projects the corresponding producer payload. Service input triples select records rather than
require those input values as stored facts on every result.

Producer transport pages are acquired before evaluating the SPARQL result. Outer `LIMIT` and
`OFFSET` select query rows; a service batch size cannot silently narrow the domain of a count,
join, negation, or filter. Existing ranking and result bounds still apply. A required producer
warning indicating missing or truncated coverage makes the complete query unavailable.

### Pattern [#search-pattern]

`:pattern` in `SERVICE :search` uses the existing Rust regex matcher and trigram candidate
index. It preserves every file match, including several matches in one declaration:

```sparql
SELECT ?path ?start ?end ?source {
  SERVICE :search {
    ?hit :pattern "tokio::[A-Za-z_]+"; :target "file";
         :path ?path; :start ?start; :end ?end; :source ?source
  }
}
ORDER BY ?path ?start
```

Matching runs line by line. `(?i)` selects case-insensitive matching. Existing pattern length,
compiled size, candidate rows, verified text size, and matches-per-file bounds remain in
effect. Invalid patterns refuse with the registered field error. Incomplete pattern coverage
cannot be evaluated as a complete graph, boolean, aggregate, or binding result.

### References and calls [#search-traversal]

Graph predicates replace the former `traversal` selector:

```sparql
SELECT ?usage ?unit ?start ?end {
  <symbol-id> :usages ?usage .
  ?usage :unit ?unit; :start ?start; :end ?end
}
```

`:usages` exposes raw physical occurrences. Each occurrence retains target, enclosing symbol
when established, source unit, byte range, and supplied facets. Repeated locations in one
caller, recursive uses, and file-level uses remain distinct. The same physical occurrence
supplied under two facets has one occurrence identity with both facets.

Symbol adjacency remains separate:

```sparql
SELECT ?caller { ?caller :references <symbol-id> }
SELECT ?callee { <symbol-id> :calls/:calls/:calls ?callee }
SELECT ?caller { <symbol-id> ^:references+ ?caller }
```

The library evaluates property paths, unions, filters, subqueries, aggregates, and negation.
Acquisition may restrict a proven anchored shape to its required frontier; otherwise it
acquires the complete required domain. A valid generic query cannot be rejected solely for
not matching an acquisition optimization. Requested depth counts edges rather than shortest
paths. Cycles and duplicate intermediate bindings follow SPARQL semantics.

### Language-engine references [#search-engine-references]

Local required facts absent from the selected publication are acquired through the existing
configured engine. References retain physical locations before mapping optional enclosing
symbols. Call hierarchy retains all established edges and actual ranges. Acquisition and
evaluation share cancellation and request bounds.

Dependency continuation uses admitted source ownership and exact selected context. Supported
complete-empty facts establish an empty answer. Unsupported facets, an incomplete publication,
missing source authority, or a bound reached before completeness returns explicit
unavailability. Global query serving reads existing collected facts; it does not collect,
ingest, or backfill global language-engine facts. Local request facts do not enter collection.

### Change [#search-change]

`:change` selects the existing revision-comparison producer inside `SERVICE :search`:

```sparql
SELECT ?symbol ?kind ?base_path ?head_path {
  SERVICE :search {
    ?hit :change '{"base":"main","head":"HEAD"}'^^rdf:JSON;
         :symbol ?symbol; :change ?change .
    ?change :kind ?kind .
    OPTIONAL { ?change :base_path ?base_path }
    OPTIONAL { ?change :head_path ?head_path }
  }
}
```

The producer keeps existing classifications, base and head identities, source selection, and
history bounds. A working-tree head uses `{"kind":"working_tree"}`. Unsupported combinations
and invalid revisions keep their registered errors. An incomplete comparison refuses before
SPARQL evaluates the selected records.

### Commit search [#search-commits]

`:target "commit"` selects the existing commit-message producer:

```sparql
SELECT ?message ?revision {
  SERVICE :search {
    ?hit :target "commit"; :query "change path bound"; :hit ?record .
    ?record :commit ?commit .
    ?commit :message ?message; :revision ?revision
  }
}
```

Commit records preserve message, truncation fields, author, timestamp, revision, and ordered
paths. A filling or bounded history store cannot establish an answer requiring facts it has
not supplied. Existing history selection and commit-search refusals remain typed.

### Package scope [#search-scope]

`:scope "local"` selects the primary project; accepted `local@name` and `local#name` contexts
select an extra project or profile. `:scope "global"` selects dependency facts and `:scope "all"`
combines accepted contexts. `:packages` carries requested package selections as `rdf:JSON`.
Existing dependency resolution, exact package versions, unavailable-package warnings, and
explicit package constraints remain producer-owned.

`FROM`, `FROM NAMED`, and `GRAPH` select accepted datasets. Unknown, unaccepted, unavailable,
or incompatible selections refuse before evaluation. They cannot look like an empty dataset.
All required contexts are selected before evaluation; callbacks do not perform remote I/O.
Remote acquisition uses bounded batches and original selected-publication identity.

### Captured answers and pages

A successful answer carries `answer`, optional `view`, `pagination`, and optional `warnings`.
`pagination.page_index` and `total_pages` describe transport pages. When another page exists,
`pagination.next_query` contains its complete SPARQL request. Send it unchanged as `query`.
The server decodes that stored page rather than evaluating the original statement again.

The service IRI `urn:rift:result:<view-id>` exposes the whole retained binding or graph answer
to a new query. Binding duplicates, blank nodes, original rows, and graph triples are retained.
A new query can aggregate, filter, project, or join those facts. The result retains selected
source context and cannot extend the original expiry.

A retained query combined with local facts uses its captured publication. Incompatible
publications refuse. Expiry, missing captured material, or a changed owner does not select the
current publication as a replacement. Carry the returned view with exact symbol and source
reads. Transport pages remain separate from SPARQL `LIMIT` and `OFFSET`.

### Bounds and missing facts

`[search.query]` bounds statement bytes, algebra nodes, acquisition requests, fact records and
bytes, result records and bytes, and each transport page. Admission checks run before
unbounded work. Cancellation applies during acquisition and lazy evaluation.

A query requiring missing facts returns typed unavailability and warnings before evaluation.
This applies to `ASK`, counts, negation, bindings, and graphs. Available-empty facts differ
from unavailable facts. A query needing only published symbol names does not require
unavailable nodes, history, or engine facts. Supplied node facts are preserved; query evaluation
does not reparse source to manufacture a complete node family.

### Migration

Former top-level `target`, `scope`, `paths`, `include`, `limit`, `page_index`, `traversal`,
`change`, and `rev` are rejected. Express field projection, joins, paths, order, and slicing in
SPARQL. Use `SERVICE :search` for existing ranking, regex, revision comparison, and commit
producers. Follow `pagination.next_query` for transport pages.

## Nodes

<McpTool name="nodes" />

## Reads

Callers read code through these tools:

| Tool | Result |
| --- | --- |
| [`get_symbol`](#tool-get_symbol) | one logical symbol by canonical identity |
| [`get_source`](#tool-get_source) | one physical source unit or byte range |
| [`search`](#tool-search) | SPARQL bindings, a boolean, or a graph over captured facts |
| [`nodes`](#tool-nodes) | the syntax nodes covering one position, with byte ranges |

[Result content](#result-content) defines the representations a tool result carries and the proxy output selection that chooses them.

The index never follows or indexes a symlink, so no read returns one; the file a link points
at answers under its own path.

`search` returns the first bounded page of its captured answer. Its `pagination` carries
the served page, true page count, and `next_query` when another page remains. Submit that
query unchanged to read the next page. SPARQL `LIMIT` and `OFFSET` select rows before
transport paging.
`get_symbol` bounds declaration bindings with `declaration_limit` and continues with
`declaration_cursor`. Search and exact reads return an immutable `view` with an expiry;
later reads can retain that selection. Expiry never selects latest implicitly.

Every read result also carries `warnings`. A `stale_index` warning reports an answer computed
from an index that lags the tree the read captured, and names the two tree revision digests that
disagree.

The server **MUST** carry `local_index_preparing` once while the requested local scope remains
incomplete. `prepared` counts visible files whose capture and analysis finished, including files
refused under an accepted bound; `total` is omitted until discovery finishes. `ready_in` is
omitted because the server has no preparation estimate.

An exact symbol read cannot establish complete declaration coverage while selected files
remain unprepared. Global-only reads omit local preparation warnings. Preparation counts
describe the answer's publication and can decrease when source selection changes.

A read served while the last rebuild's failure stands carries `stale_index` too, with a `detail`
naming the failure; the next filesystem event retries the rebuild. When its two digests are equal,
the tree moved in recorded files outside the syntax-indexed ones or in the configuration file, and
`detail` says which.

The search ranking tiers carry their own warnings:

- `vector_index_preparing` - the vector ranking holds no vectors for the tree this answer
  was read from: the pass over that tree is still running, or the tree was published after
  the corpus the ranking holds was described. A query sharing no token with the code it
  describes reaches nothing until that pass lands; `prepared` and `total` state how far it
  has got, and an answer carrying no such warning is one the vector ranking took part in.
- `vector_ranking_unavailable` - the vector ranking will not answer for the life of this
  server: the model weights could not be acquired, or the model failed to load.
- `lexical_ranking_unavailable` - the full-text tier has not yet committed the captured tree,
  missed a commit, holds no indexed tree, failed to load, got no database connection within
  `[search] busy_timeout`, or still answers for a newer publication after the request's capture
  attempts; the `detail` names which, with the tree revision in the first three cases. Ranking
  falls back to identifier matching, so a query phrased as prose finds nothing. The tier is read
  under the answer's own tree revision, so one that has moved past it is recaptured, up to those
  attempts, rather than warned about, a case a caller cannot otherwise tell apart from a tier
  that searched and found nothing. A pending commit keeps this warning in the answer; a later
  search can use the full-text tier after the commit lands.
- `history_store_filling` - a [commit search](#search-commits) answered while the history store
  lacks some of the commits its latest fill selects, or the commit `HEAD` names; `analyzed` and
  `total` state how far the fill has got.
- `lexical_ranking_truncated` - the lexical ranking stopped at `matches_max` units, and hits
  past that bound never reach a page, whatever `paths` selects. `total_pages` counts the units
  that did; a narrower `query` brings the rest inside the bound.
- `documentation_unavailable` - the documentation this search projects onto crossed a bound, so
  no documentation block joins the answer and declarations and files answer as they would without
  it. The `detail` names the documentation left out - the project's, the `force_include` files',
  or the dependency packages' - and the bound it crossed.
- `query_narrowed` - the query carried more terms and quoted phrases than `terms_max`, so the
  server dropped the shortest unquoted terms and ranked the answer by the rest. Every quoted
  phrase is kept. Shorten `query`, or quote the terms that must be matched.
- `results_truncated` - the server reached `results_max`, its result bound, before ordering and
  paging. The bound covers both the candidates one read ranks and the hits it returns, so what
  it cut never reaches any page and `total_pages` counts only what fit. The warning means the
  bound was reached: a read that cut nothing else but filled the candidate pool carries it too.
  A narrower `query` or `paths` brings the read inside the bound.

A `symbol_disagreement` warning names a symbol whose selected presentation and at least one
provider's own facts disagree.

A `source_unavailable` warning names a file the index left out - bytes that are not valid UTF-8,
a file past its per-file bound, or a syntax tree the provider refused - so it answers no search or
lookup while every other file stays available. An answer carries at most eight of them, in
project-path order; when more files were left out, one more `source_unavailable` carries no `unit`
and counts the rest. `rift server logs` names each omitted file.

Text search answers can carry these warnings:

- `pattern_matches_truncated` - a file held more matches of `pattern` than the `[search]` key
  `pattern_matches_per_file`, so its later matches are missing while every other file answers in
  full. `files` names the cut files, at most eight, in project-path order.
- `pattern_index_preparing` - the trigram index lacks rows of stored file text, and verifying them
  beside the selected rows would pass `pattern_candidate_rows` or `pattern_verified_size`, so a
  match in those rows is missing from the answer. `prepared` counts the rows the index holds and
  `total` the rows the store holds; the warning stops once the index has caught up.
- `large_file_skipped` - under `[search.text] large_files = "skip"`, files past `max_chunk` are
  left out of the text index; `skipped` counts the ones the request's `paths` reach. A
  declaration such a file holds still answers.
- `large_file_unparsed` - files past `[providers.syntax] max_file` are held as text the syntax
  provider does not parse: their text answers `search`, and none of their declarations answers a
  symbol hit or `get_symbol`. `files` names them, at most eight, in project-path order.
- `lockfile_excluded` - a lockfile the request's `paths.include` selects is left out of search
  under the `[search.text]` key `excluded_lockfiles`. `rift://map` still carries the versions it
  pins, and naming the file in `paths.force_include` searches it for one request.

A package-scope answer whose read never reached the global API, or met no answer from it,
carries no package facts and one of these warnings naming why:

- `global_access_disabled` - `[global] enabled` is `false`, so no package read reaches the
  global API.
- `global_api_unavailable` - the global API could not answer. `failure_class` identifies the
  bounded failure.
- `global_publication_incompatible` - the global API advertised a publication format or corpus
  revision this client cannot read. `failure_class` names which.
- `global_response_invalid` - the global API response is invalid or truncated. `failure_class`
  names which.

Package-scope answers can also carry these package warnings:

- `global_page_warning` - a valid global page carried a bounded condition. `warning_code`
  identifies it and optional `detail` explains it. `result_truncated` names a page the global API
  stopped early, and the answer holds what that page held. `capability_unavailable` names a
  feature the global API's capabilities do not advertise, such as `patterns` for a `pattern`
  search, and the answer then holds the project hits alone.
- `package_absent` - the global publication holds no release of the exact `package` the
  dependency context names, so nothing answers for it.
- `package_requirement_absent` - the global publication holds no release the declared
  requirement in `entry` admits, so nothing answers for it.
- `package_substituted` - the global publication holds no release at the version `entry` names,
  or none inside the range its requirement states, so the nearest collected release, `package`,
  answers in its place.
- `package_unavailable` - the dependency context `entry` names a package no public registry
  serves, so no global package index answers for it. `reason` names the capability Rift does not
  have yet, by the entry's `availability`.
- `package_context_degraded` - a resolver read less than its manifests and lockfiles state, or a
  standard library probe answered nothing, so the dependency context can miss packages or name a
  standard library by its static reading. `resolver` names which, by manager name - `cargo`,
  `uv`, `npm`, or `bun` - or by standard library entry - `stdlib/rust`, `stdlib/node`, or
  `stdlib/python` - and `reason` says what it could not read. When the context passes the
  entries one read sends - 20,000, or fewer when the global API advertises a smaller
  `dependency_entries_max` - the entries sorted last leave, and `resolver` names their package
  manager, such as `pypi`. The request's `packages` leave only after every other entry has, the
  ones sorted last first, and `reason` then counts the requested packages not reported.

Each `availability` a `package_unavailable` warning names carries its own `reason`:

| `availability` | Source | `reason` |
| --- | --- | --- |
| `path` | a path outside the workspace, or an archive at a path | Currently rift doesn't support indexing dependencies by path. If you're interested in this capability, please upvote it at https://github.com/volarized/rift/issues/392. |
| `git` | a git repository | Currently rift doesn't support indexing dependencies from git repositories. If you're interested in this capability, please upvote it at https://github.com/volarized/rift/issues/393. |
| `private_registry` | a registry other than the public one its package manager reads | Currently rift doesn't support indexing dependencies from private registries. |
| `url` | a URL no registry serves, such as a uv wheel URL or an npm tarball URL | Currently rift doesn't support indexing dependencies from URLs. |

A path dependency inside the workspace is project source: the local index covers it, and the
dependency context names no entry for it.

An answer carries at most eight `package_context_degraded`, `package_unavailable`,
`package_absent`, `package_requirement_absent`, and `package_substituted` warnings together: the
degraded resolvers first, in resolver order, then the entries no public registry serves, then the
packages and requirements the global publication lacks, then the entries a nearest release
answers for. The global warning naming why the global API did not answer rides before them,
outside that bound. The `source_unavailable` bound above is separate, so an answer can carry
eight of each.

Every read carries an optional `rev`, and reads the workspace tree when it is absent.

### Result content [#result-content]

A completed tool result carries one compact text block in `content`. With `rift mcp --output all`,
it also carries canonical `structuredContent`, and the tool listing carries `outputSchema`.
Both representations come from the same answer.

- `all` forwards text, structured content, output schemas, and every resource representation.
- `text`, the default, omits structured tool content and output schemas. For a resource with both
  text and JSON, it omits JSON and retains text.

The proxy keeps that selection for its lifetime. Direct HTTP access to `rift server` returns
both tool representations. The workspace resource carries both representations over direct
HTTP; the map carries JSON.

For `search`, text retains the query's result form:

- A binding answer starts with `N results · page P/T`, then selected variable names in order,
  then one JSON object per binding row.
- A graph answer starts with `N triples · page P/T`, then one JSON triple per line.
- A boolean answer is `true` or `false`.

Rows and triples are indented by one tab. Their JSON preserves term kinds, datatype and language
values, full IRIs, blank node identifiers, and escaped literal bytes. An unbound variable is absent
from its row. Query text does not turn a relationship answer into a shortest-path tree or
replace projected facts with declaration summaries. A retained answer states its view and
expiry. The next-page query is written as `next_query ` followed by its JSON string at column zero; decode that string and send it unchanged as `query`.

For `get_symbol`, a found result writes the declaration, exact identity, exceptional facts,
then documentation and requested documentation context or history. A `declarations:` section
retains each physical location, byte range, available node identity, and requested source.
A returned `declaration_cursor` names remaining bindings. Exact reads have no hit count or hit
paging. A missing result writes `error: symbol_not_found`, the requested identity, and bounded
alternatives below `closest matches:` when available. An unavailable result writes its typed
reason and requested identity. A captured selection states `view ID · expires TIMESTAMP`.

A `nodes` result lists enclosing nodes from outermost to innermost. Each node states its kind,
line count when greater than one, exceptional generated or test facets, node identity, available
symbol identity, and named region byte ranges. After the last node, text carries the innermost
excerpt. Structured content retains every node's excerpt.

Exact reads and node excerpts use tabs for layout, preserving copied source whitespace after
the layout indent. Remove that indent to recover source bytes. A fact whose normal state is
implicit in this layout remains available in structured content. Exceptional origin, package,
source kind, deprecated and test facets, document-local identity, and incomplete history remain
visible in text. Query literals instead use their JSON encoding and preserve every projected
value regardless of its normal state.

Warnings follow the answer and its serving view. The warning title counts displayed groups and
distinct lines. Each line states its code, declared payload fields, and available detail.
Equal `framework_context_unresolved` entries with the same framework and detail are grouped;
the group lists sorted distinct source identities. Structured warnings retain their entries.
A canonical-symbol proxy suppresses repeated unchanged framework warning text for the same
originating project, owner, and framework on its connection. Changed facts or an intervening
answer without that framework make it visible again. The observation cache remains bounded.

Registered errors and typed unavailable outcomes remain distinct from complete empty query
answers. A missing family of facts is never rendered as `false`, zero, or an empty graph.
Every tool's text remains subject to its accepted byte bound.

### Revision-addressed reads [#revision-reads]

`get_symbol`, `get_source`, and `nodes` accept `rev`; `search` accepts it as the
`:rev` input of `SERVICE :search`. It names a branch, tag, or commit id, spelled the way git spells it:
`main`, `v0.0.6`, `dd0a482`. The server resolves the revision in place from the workspace's
git objects, with no checkout, and indexes that commit's tree under the same
[`[source]`](/docs/developer/configuration#source) policy and bounds as the working-tree scan. A revision
read answers from committed bytes, so uncommitted working-tree changes never appear in it.

This `get_symbol` request reads a declaration as it stands on `main`, whatever the working tree
currently holds:

```json
{ "id": "rift://symbol/local/rust/example_project/config/load_config", "rev": "main" }
```

A name may carry git's ancestry suffixes: `~N` walks `N` first parents and `^N` picks the `N`th
parent, each count defaulting to 1, so `HEAD~1` and `HEAD^` name the commit below `HEAD`. The server
resolves the spelling through git's revision syntax, and a spelling that carries anything else -
a reflog selector such as `HEAD@{1}`, or a path after a suffix - refuses `invalid_request` naming
the field. This request reads the declaration one commit back:

**Request:**

```json
{ "id": "rift://symbol/local/rust/example_project/config/load_config", "rev": "HEAD~1" }
```

A revision search refuses `force_include`: reaching index-excluded files is a walk of the
working tree, which a revision does not have.

### Requested packages [#requested-packages]

The `:packages` input of `SERVICE :search` names package versions it reaches beside the ones the
workspace's manifests and lockfiles name, at most 64 entries. Each entry is a
[`RequestedPackage`](/docs/developer/protocol/reference) carrying `manager`, `name`, and an
optional exact `version`. The server applies the list to this read's dependency context alone:

- an entry naming a package the context holds replaces every entry for that package, a `path`
  or `git` entry included
- an entry naming a package the context lacks adds it
- an entry without `version` goes out as the requirement `>=0`, which the global index answers
  from its newest collected release

Each entry then routes like any context entry. A requested version the global publication lacks
answers from the nearest collected release under `package_substituted`. A package with no
collected release answers `package_absent`, or `package_requirement_absent` for an entry without
`version`.

This search reads Tokio 1.47.1 beside the project, in place of the version the workspace's
`Cargo.lock` pins:

Pass this SPARQL as `query`:

```sparql
PREFIX : <urn:rift:vocabulary:>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
SELECT ?symbol ?name {
  SERVICE :search {
    ?hit :query "spawn_blocking";
         :scope "all";
         :target "symbol";
         :packages '[{"manager":"cargo","name":"tokio","version":"1.47.1"}]'^^rdf:JSON;
         :symbol ?symbol;
         :name ?name.
  }
} LIMIT 10
```

The server refuses `:packages` as `invalid_request` naming the field beside the `local` scope, the
default, since a project read consults no package, and beside `rev`, since package facts are
served for the current tree alone. A list past 64 entries, and an entry whose `manager`, `name`,
or `version` is empty or longer than its schema allows, refuse the same way before anything
reaches the global API.

## Resources

### Resource contents [#resource-contents]

A read of `rift://map` answers `contents` with one JSON entry whose `mimeType` is
`application/json`. A read of `rift://workspace` answers with two entries, both naming the
requested `uri`: compact text with `mimeType` `text/plain`, then the JSON body with `mimeType`
`application/json`. The server makes both workspace contents from the same data.

The map's `recommendations` entries carry `language`, `root`, and `command` for installed
language servers without a selected configuration. The server **MUST** omit `recommendations`
when none remain and remove a matching entry from the next publication after accepting its
configuration. `root` is relative to the map's project, with `.` selecting the project itself.
A `command` is a `rift config set` invocation quoted for the server's operating system;
the caller runs it from the map project's root.

The listings of resources and resource templates declare `application/json`, the type of the JSON body. A caller **SHOULD** select a content by its `mimeType`, because the `text` [output selection](#result-content) leaves compact text as the only content of a workspace read. The map remains JSON under both selections.

The compact text of the workspace resource follows the layout of a [tool result](#result-content): the facts of one line are separated by ` · `, a direction is written with `→`, a lowercase hex value of at least 8 characters is cut to its first 8, and the normal state of a fact is left out. Warnings form the section `N warnings`, or `1 warning`, after the last section, and a section with no entry is omitted. The server enforces a byte limit on the text and refuses a read whose text crosses it as a protocol failure, with the typed `ErrorData` as `data`.

### Workspace [#resource-workspace]

`rift://workspace` reads accepted configuration together with one captured source catalog page.
The answer carries:

- `configuration_revision` - an eight-character digest of the accepted `rift.toml` bytes
- `languages` - effective identities in order, with enabled state, include and exclude patterns,
  syntax availability, and selected LSP process state
- `source` - captured project paths, content digests, and matched language identities
- `pagination` - the zero-based page and total page count
- `warnings` - conditions that qualify the page, omitted when empty

The bare URI selects page zero. `rift://workspace?page_index=1` selects another page. Each page
holds at most 1000 source units; language summaries repeat so every page can be read
alone. A page past the end returns an empty `source` list with the true page count.

A read answers the [two contents](#resource-contents) of a resource. The compact text has these parts:

- the header `workspace <configuration_revision>`, with ` · page P/T` added under the rule of the [tool results](#result-content)
- directly below the header, the sections `languages` and `source`, in that order, each a title such as `languages:` with its entries indented by one level; the server **MUST** omit a section that has no entry
- a language entry: the language identity, `disabled` when `enabled` is `false`, `syntax` and `execution` when they hold, and `lsp <process> <state>` when the language has a selected LSP process
- under a language entry, `include` and `exclude` lines with their patterns joined by `, `, each only when the list is not empty
- a source entry as `path · language · digest`, without the language when none matched
- after the last section, when the page carries warnings, the section `N warnings`, or `1 warning`, with one line per warning as in a [tool result](#result-content)

## Errors

A failure travels by its class. A **tool execution failure** is a Rift operating failure on a
`get_symbol`, `search`, or `nodes` call, such as invalid input, a crossed limit, or a storage
failure. A **protocol failure** is any other failure: an unknown method or tool, a malformed
request envelope, a transport failure, a resource read failure, or an MCP error forwarded from
upstream.

### Tool execution failures [#tool-execution-failures]

The server **MUST** answer a registered tool execution failure with a completed tool result that has
`isError` set to `true` and one `content` text block of compact text. The result **MUST NOT**
carry `structuredContent` under either output selection. The MCP specification
[reports tool execution errors](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling)
in the result, where the model can read the failure and adjust its request.

The advertised `outputSchema` describes typed tool answers, including the `get_symbol`
`missing` outcome; registered operating failures carry no such answer. A proxy started
with `--output text` forwards the failure unchanged: it keeps `isError` and `content`, and the
result had no `structuredContent` to remove.

The text of a failure is one section. Its title is `N errors`, or `1 error`, where N is 1 plus the number of entries of `causes`. Its entries are the failure, then each entry of `causes`, outermost first, as one list. Each line is written on one line, with control characters as escapes:

- the head of an entry, at one level: `<code> · retry <directive>`, the `code` and `retry` of [`ErrorData`](/docs/developer/protocol/reference) or of the cause
- below the head, at two levels, the `message` of the entry; an empty message writes no line
- below the failure's message, `limit <field>: <required> over <limit>`, when the failure carries `limit`
- then one line for each entry of `diagnostics`, as the `severity`, the code in brackets, the file of the span followed by `:line:column`, and `: <message>`, each part only when the diagnostic carries it
- after the diagnostics, the registered identity on its own line, at two levels, for a registered failure

Every entry writes its `code` and `retry`, also a cause whose `code` or `retry` equals the failure's.

The text omits `phase`. The typed `ErrorData` model carries it, and a protocol failure carries it in the JSON-RPC `data` as described under [protocol failures](#protocol-failures).

Every failure carries a `retry` directive, which is the field to branch on - it rides each error
instance rather than the code, because the same `storage_failure` can be transient once and
permanent the next time:

- `never` - the same bytes will fail the same way
- `same_request` - it was transient: an index still filling, a tree with a filesystem
  write in flight
- `operator_action` - the workspace requires a local state or configuration change before retry

The `phase` field of `ErrorData` names the operation that failed while serving the request; its only value, `read`, covers reading
workspace or provider data. A `limit_exceeded` also carries which limit and by how much, so a
request can be resized without parsing the message meant for a human. Any other code omits
`limit`.

Each entry of `causes` holds a `code`, a `message`, and a `retry` for one link of the failure
chain, outermost first. The `retry` of the failure governs the call; a cause's own `retry`
says what could be done about that cause. The text writes the `code` and the `retry` of every cause.

### Protocol failures [#protocol-failures]

A protocol failure stays a JSON-RPC error. An MCP error forwarded from upstream keeps its received
code, message, and data, so the proxy adds nothing to a refusal the server classified.

A failure the proxy raises itself carries the same typed `ErrorData` as the JSON-RPC `data`
under code `-32000`: a `tools/call` whose `arguments` is not an object, a forwarded request that
the server did not answer within the proxy's budget, and a server that is still building or
failed to start. The caller **SHOULD** read `retry` from that `data` as it reads it from the
first entry of an execution failure. A resource read refusal, such as an unknown resource URI,
carries a code and a message and no `data`. A read whose compact text crosses the byte limit carries the typed `ErrorData` as `data`.
