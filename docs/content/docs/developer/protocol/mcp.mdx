This reference defines Rift's MCP tools and resources, including optional fields, paging,
limits, and failures. For an introduction through an agent's workflow, see the
[MCP guide](/docs/mcp).

The expandable tool properties and examples come from the served [JSON schema](https://volar.sh/rift/mcp.json).
The Request tab shows the MCP call and offers a SPARQL view for searches. The Response tab shows
tool text or JSON. [Result content](#result-content) defines both forms.

## Map [#resource-map]

`rift://map` reads a workspace orientation snapshot: a starting picture for a caller new to the
codebase. The answer carries:

- `revision` - an eight-character [`Digest`](/docs/developer/protocol/reference) of the indexed
  tree the map was computed from
- `languages` - per-language file and symbol counts, sorted by language spelling
- `modules` - the directory tree indexed files sit under, each entry's file and symbol counts
  inclusive of its descendants, folded three directories deep
- `hubs` - the most-referenced symbols, ranked by reference count descending
- `entry_points` - symbols where execution starts
- `docs` - markdown files, in path order
- `module_edges` - the modules a resolved reference reaches between, ranked by that
  count descending
- `packages` - the packages the workspace's manifests and lockfiles state, in `manager`,
  `name`, then selector order

During local preparation, file counts and documentation paths can describe discovered files
before their declarations are prepared. Symbol counts describe prepared declarations. The
server **MUST** take the map's revision and counts from the same publication and log
[`local_index_preparing`](#reads) for incomplete preparation.

`entry_points` lists symbols carrying the `entrypoint`
[`SymbolKind`](/docs/developer/protocol/reference) - a file-scope `fn main`, not one
nested in a module, an `impl` block, or another function. It stays empty for a workspace with no
such facts.

`hubs` ranks [`SymbolId`](/docs/developer/protocol/reference)s by how often the index
holds a resolved reference to them, and `module_edges` folds both ends of every such
reference to the module `modules` lists them under, drops a pair whose two ends fold to one
module, and counts what is left. `module_edges` carries at most 100 entries, ordered
by `references` descending, then `from`, then `to`, so a workspace past that bound keeps the
strongest pairs and two reads of one tree agree. Both read the index alone: the language
engine resolves a reference for one read and publishes none, so both lists stay empty until a
provider publishes resolved references into the index.

`packages` lists the [dependency context](/docs/developer/architecture#dependency-context): what the
Cargo, uv, npm, and Bun resolvers read from `Cargo.toml` and `Cargo.lock`, `pyproject.toml` and
`uv.lock`, `package.json` and `package-lock.json`, and `package.json` and `bun.lock`. The
resolvers read those files and run no toolchain. Each entry is a
[`PackageContextEntry`](/docs/developer/protocol/reference) carrying the exact
`version` a lockfile pins or the `requirement` a manifest declares, never both, and the
`availability` a global package index could answer under. The list follows those files: one
rewritten while the server runs is read again on the next publication.

A resolver reads at most 256 manifests per workspace, taken in path order, so `packages` over a
workspace holding more lists what the manifests it read declare.

`packages` also lists one entry for each standard library a language the workspace uses relies
on, under the manager `stdlib`: `stdlib/rust`, `stdlib/node` beside the npm `typescript` package,
or `stdlib/python`. Its version comes from the workspace's pins, or from a version probe under
[`[dependencies]`](/docs/developer/configuration#dependencies) `resolution = "auto"`, and the
[dependency context](/docs/developer/architecture#standard-libraries) lists where each one is read.

By default, `rift://map` returns a compact text overview with language counts, top-level
directories, entry points, most-referenced symbols, documentation, and available language
server recommendations. Each text section shows up to eight entries. With
`rift mcp --output=all`, the read also returns the JSON snapshot.

## Search

<McpTool name="search" />

`search` accepts `query: string` and optional `language: "sparql"`. `language` defaults to
`sparql`. Unknown languages and former top-level selectors fail request validation. The
query uses the library's SPARQL parser, algebra, and evaluator over immutable selected facts.

<ReadExample name="select-symbols" />

### Vocabulary and terms

The default empty prefix is `urn:rift:vocabulary:`. `rdf:` and `xsd:` name their standard namespaces. Explicit prefix declarations are
supported. The vocabulary follows existing fact fields, including `:name`, `:kind`,
`:language`, `:of`, `:source`, `:unit`, `:range`, `:start`, and `:end`.

Symbols with established identities use canonical `SymbolId` IRIs. Source units retain their
`SourceUnitId` IRIs. A physical occurrence or nested record uses a blank node, whose identity
is retained across pages of its execution. A symbol without an established canonical identity
also remains a blank node. Evaluation does not fabricate a canonical identity from its name.

Available nested records preserve existing fields, ordered array entries through `:index` and
`:value`, defaults, and opaque extensions as `rdf:JSON`. A bare `:name` query can match nested
records such as parameters. Use `a :Symbol` when the question requires symbols alone.

### Query forms

- `SELECT` returns `answer.result: "bindings"`, ordered `variables`, and `bindings` rows.
- `ASK` returns `answer.result: "boolean"` and `value`.
- `CONSTRUCT` and `DESCRIBE` return `answer.result: "graph"` and `triples`.

Each binding or triple term carries its kind: `iri`, `blank_node`, `literal` with `datatype`, or
`language_literal` with `language`. Unbound variables are omitted from the row. Duplicate
bindings and projected variable order follow SPARQL. Graph answers use RDF set semantics.

`DESCRIBE` uses the library's description behavior over all authoritative captured and published records in its selected dataset. It does not implicitly request every language-engine fact. Facts explicitly required by its `WHERE` pattern retain the same strict acquisition and missing-facts rules as other query forms. Bounds still refuse incomplete admission.

### Search result text [#search-result-text]

Search text for a nonempty result set starts with the rows on the current page, numbered from
one across the result set. The heading gives the total when the result set has multiple rows and
shows the current page and page count. A blank line separates it from the Markdown table.

A `SELECT` table has one column per projected variable, in projection order, with `?` before
each variable name. An unbound variable leaves an empty cell. A graph table has `subject`,
`predicate`, and `object` columns. An `ASK` answer uses `1/1` pages and shows `true` or `false`
in one row under `result`.

Text shortens common RDF namespaces and escapes Markdown syntax in cells. Structured content
carries the exact RDF terms and identities.

A query with zero results returns one sentence that points to the query examples.

<ReadExample name="empty-search" />

A page past the last page of a nonempty result set shows `0 rows` with the total and page numbers.
Its table has no rows.

### Full-text search [#search-fulltext]

The local `SERVICE :search` reuses identifier, lexical, and available vector ranking. Its
constant input triples select the producer request, while its graph pattern projects and
filters the acquired records:

<ReadExample name="full-text" />

`:query`, `:pattern`, `:scope`, `:target`, `:order`, `:rev`, `:paths`, `:packages`, `:include`,
`:change`, `:max_results`, `:page`, and `:view` retain their producer meanings inside the service. Structured inputs
use `rdf:JSON` literals. Conflicting constant inputs refuse. Portable categories use `:kinds`. The language-specific string uses `:kind`.
Requesting `:source` and `:score` projects the corresponding producer payload. Service input triples select records rather than
require those input values as stored facts on every result.

`:max_results` and `:page` select a producer page. Outer `LIMIT` and `OFFSET` apply to the
SPARQL result after evaluation. Missing producer coverage can make the query unavailable. A
producer bound does not. When a producer stops at one of its bounds (`results_truncated`,
`lexical_ranking_truncated`, `pattern_matches_truncated`, `query_narrowed`, `change_truncated`),
or the server reaches the solution, byte, or page bound of the producer pages it reads, the
query evaluates over the rows the producer returned and pages them, with `pagination.total`
counting those rows. The server records the bound in `rift server logs`.
A package answered from the nearest collected release under `package_substituted` is covered.
A global API read that fails answers `unavailable` with reason `read_failed`, and
`rift server logs` names its `failure_class`.

The library evaluates property paths, unions, filters, subqueries, aggregates, and negation.

### Language-engine references [#search-engine-references]

Local required facts absent from the selected publication are acquired through the existing
configured engine. References retain physical locations before mapping optional enclosing
symbols. Call hierarchy retains all established edges and actual ranges. Acquisition and
evaluation share cancellation and request bounds.

Dependency continuation uses admitted source ownership and exact selected context. Supported
complete-empty facts establish an empty answer. Unsupported kinds, an incomplete publication,
missing source authority, or a bound reached before completeness returns explicit
unavailability. Global query serving reads existing collected facts. It does not collect,
ingest, or backfill global language-engine facts. Local request facts do not enter collection.

### Flow search [#search-flows]

The local `SERVICE :flows` discovers paths of call edges through symbols matched by ranked text
retrieval. Each path contains at least one matched symbol and one resolved call edge. The server
can follow calls into and out of a matched symbol, so that symbol can be a step in the middle.

The caller supplies a constant string in `:query` and may supply an integer `:max_results` from 1 to 32.
The default is 5. The server rejects conflicting inputs before it runs retrieval.

<ReadExample name="flows" />

`:steps` links a flow to its ordered steps. Each step carries a zero-based `:index` and a
`:value` that identifies the symbol. The caller can join that value with symbol facts such as
`:name`.

The destination step of a call can carry multiple `:evidence` occurrences. Each occurrence
has a `:range` with `:unit`, `:start`, and `:end` for the original call site. Multiple call sites
between the same steps contribute evidence to the same path.

The server scores each path by the strongest matched symbol and adds a quarter of the second
strongest score when a distinct matched symbol is present. Step order follows the direction
of the calls in the graph. The Markdown table follows the projected variables, so callers can
include each step's index and symbol.

The service applies `:max_results` to whole flows before SPARQL evaluates the outer query. Outer
`LIMIT` and `OFFSET` apply to solution rows and can split a flow's steps. When the caller
sends the same `revision`, the server reads the same indexed source.

The server returns usable paths in a positive `SELECT` when a provider covers only part of the
required calls and logs `edge_coverage_missing`. The server returns typed unavailability when the
available calls cannot establish the requested result. A discovery bound that cuts the search
produces a `traversal_truncated` log record. A page continues the selected flow rows. If discovery
reaches a bound, narrow the flow query and run it again to discover paths within that request.

### Commit search [#search-commits]

`:target "commit"` selects the existing commit-message producer:

<ReadExample name="commits" />

Commit records preserve message, truncation fields, author, timestamp, revision, and ordered

### Package scope [#search-scope]

`:scope "local"` selects the primary project. Accepted `local@name` and `local@name:profile` contexts
select an extra project or profile. `:scope "global"` selects dependency facts and `:scope "all"`
combines accepted contexts. `:packages` carries requested package selections as an `rdf:JSON`
literal, such as `'[{"manager":"cargo","registry":"crates.io","name":"serde_core"}]'^^rdf:JSON`.
The producer handles dependency resolution, exact package versions, and explicit package constraints.
The server refuses `:paths`, `:packages`, or `:change` written as a plain string, and a
`:packages` entry that names no `registry`, with `rift.search.query_syntax_invalid`.

A `SERVICE :search` that selects no `:scope` reads the scope
[`[search] default_scope`](/docs/developer/configuration#search) names: `local` unless the
workspace configures `global` or `all`. `SERVICE :flows` reads `local`.

Remote acquisition uses bounded batches and holds the selected publication for the query.

### Captured answers and pages

A successful answer names the `revision` it read. The caller sends that `revision` for later pages.
An answer that combines extra projects names a tree revision over the revisions those projects
read. A later page sent with it reads the retained answer. Once any of those projects serves
another revision, the server refuses it.
`page` starts at 1 and defaults to 1. `max_results` defaults to 10 and accepts 1 to 1000.

`pagination` carries `page`, `pages`, `max_results`, and `total`. A page past the last returns
an empty list with the same counts. `pages` is 0 for an empty result set. `ASK` returns a boolean
without pagination. SPARQL `LIMIT` and `OFFSET` bound the result set before paging.

### Bounds and missing facts

The server bounds statement size, algebra, fact acquisition, and the evaluated answer.
`[search.query] page_limit` sets the maximum encoded bytes per page, from 1 KiB to 4 MiB.
An evaluated answer past its solution or byte bound holds the solutions before the bound, and
a graph walk past its acquisition budget answers over the facts it acquired. Both page like any
other answer, and `rift server logs` records the bound and its value.

A query over the captured inventory - every symbol, call, reference, or usage it holds - answers
from partly covered facts. This holds for a `SELECT` that joins, projects, filters, binds, orders,
or slices, and for an `ASK` that finds a witness. Every row such an answer returns stands.

The server records these conditions in `rift server logs`.

- `source_unavailable` - a file left out of the index although no bound excluded it: bytes that
  are not valid UTF-8, a NUL byte, or a refused declaration. A file a bound left out - past the
  per-file byte bound, past `[providers.syntax]` `max_file`, or past the declarations the index
  holds - is outside the indexed set, as a file the source policy excludes is: no answer names
  it, and `rift server logs` records it
- `framework_context_unresolved` - a framework whose context is unresolved. The file's ordinary
  declarations still answer
- `engine_analysis_unavailable` - a language whose engine analysis is missing. The captured static
  facts still answer

Any other query needs complete coverage and returns `insufficient_coverage` when facts are missing:

- an empty result or a false `ASK`, which claims an absence
- an aggregate such as a count
- a negation, `EXISTS`, `MINUS`, or `OPTIONAL`
- a graph result

Available-empty facts differ from unavailable facts. A query needing only published symbol names does not require
unavailable syntax elements, history, or engine facts. Supplied syntax facts are preserved. Query evaluation
does not reparse source to manufacture a complete syntax family.

### Migration

Former top-level `target`, `scope`, `paths`, `include`, `limit`, `traversal`, and `change`
are rejected. Express field projection, joins, paths, order, and slicing in
SPARQL. Use `SERVICE :search` for existing ranking, regex, revision comparison, and commit
producers. Send `page` and `max_results` for answer pages.

## Symbol retrieval

<McpTool name="get_symbol" />

`id` selects one canonical logical symbol. Ownership and language are encoded in that
identity. Declaration source addresses remain separate. `get_symbol` accepts neither
name discovery nor `scope`, `packages`, or `limit`.

Every declaration of one qualified path binds to that one identity, so `declarations` lists
repeated definitions, overloads, and `cfg` variants of one symbol together.

<ReadExample name="local-symbol" />

`outcome` distinguishes `found`, `missing`, and `unavailable`. `found` contains one
`symbol` and its declaration bindings, including an empty declaration list for a source-less
object. A runtime symbol's answer names the runtime release it read as `revision`:

<ReadExample name="runtime-symbol" />

`missing` means the exact selection was searched completely. `symbol_not_found`
names the requested identity and up to three actual structural alternatives. An incomplete
selection answers `unavailable` with a typed reason.

A Rust identity names a path inside a library crate. A declaration in a binary, example,
integration test, benchmark, or build script, or in a module one of these declares, carries no
identity, so a Cargo package with a binary still answers a miss with `missing`. A library file
that failed analysis, or a Rust file neither the library nor another Cargo target declares,
keeps Rust misses `unavailable` with `insufficient_coverage`.

For `missing`, the server **MUST** set MCP `isError` to `true` and retain the same typed
answer in `structuredContent` under `--output all`. The `--output text` policy removes
`structuredContent` while retaining the error flag and compact text.

The [search configuration](/docs/developer/configuration#search) bounds optional alternative
work through `symbol_alternatives_work` and `symbol_alternatives_lowercase_work`. Reached
bounds retain the definite miss and report incomplete alternative work.

`include` is an object of boolean members that selects projections: `documentation` adds
bounded referring documentation, and `history` adds the logical symbol's history edges. An
omitted member is `false`, and an omitted `include` requests none. The server refuses any other
member, `source` included, as an invalid request. A declaration's source is read by
[`facets`](#tool-facets) with `symbol`.

`max_results` defaults to 10 and accepts 1 through 10000. `page` selects declarations at the
revision the answer names. The server refuses a tree revision once the index serves another tree.
Each binding retains `origin`, exactly one of `path` and `unit`, `range`, `line`, and indices
into the symbol's signatures, types, and documentation. These calls read `data_dir`, which the
`sdk` project declares once under `cfg(unix)` and once under `cfg(windows)`:

`history` follows the commits held by the [history store](/docs/developer/architecture#history)
from the served revision and answers edges from the symbol. The commit edges come newest first:
`introduced_in`, `changed_in` with a `change` of `signature_changed`, `body_changed`, or
`decorators_changed`, `renamed_from` with the `from` path an unchanged file rename or unchanged
declaration move came from, and `removed_in`. Each names its commit as a
`rift://revision/git/<commit>` revision and the path the declaration lived at in it. A commit
whose source cannot be parsed, or where the symbol is absent, contributes no edge. Commit author
name and email remain the commit's author. Timestamps remain committer time.

The `co_changes` edges follow the commit edges, most shared commits first, then by symbol. Each
names a symbol the served tree binds to a declaration one of the listed commits changed, and the
number of listed commits that changed both. A commit that changed more than 256 declarations
counts toward no co-change edge, and the server answers at most 32 of them.
`co_changes_truncated` counts the commits and symbols past those bounds and is absent when they
left out nothing.

`complete: false` means history depth, a shallow clone, the oldest selected release, or a store
still filling ended the history before the repository's first commit. When the store did not
open, the server walks Git per request instead, and that history carries no `co_changes` edge.

A package or runtime symbol's `history` comes from the global API and names releases in place
of commits. Its edges come newest release first: `introduced_in_release` for the oldest
collected release that declares the symbol, `changed_in_release` with a `change` for a release
that changed the declaration from the collected release before it, and `removed_in_release` for
a release that no longer declares it. Each names its release as a
`rift://revision/<manager>/<registry>/<name>@<version>` or
`rift://revision/stdlib/<runtime>@<version>` revision of the symbol's owner.

A release history carries no commit edge, no `co_changes` edge, and no `co_changes_truncated`.
The server **MUST** treat a global API answer that breaks this, or a `found` answer that omits
the requested history, as invalid and fail the read. `complete: false` means the history ended
before the oldest collected release of the owner, and a project symbol's history carries no
release edge.

## Facets

<McpTool name="facets" />

The request carries `symbol`, an optional `revision`, `page`, and `max_results`.
The server returns the symbol's declarations in symbol order. One facet is one declaration,
with its location, exact source, and syntax structure.

Each declaration carries `declaration`, `kind`, `range`, `source`, and `syntax`.
The source span names the returned bytes. The syntax structure lists the declaration's
item and its descendants in pre-order. Elements of a nested
declaration belong to that declaration's facet. The item spans the declaration without
its attached documentation.

A syntax element carries its `index` within the declaration, from 0 at the root, and the
`parent` index when present. Its `unit`, `language`, and `range` locate it in the source.
The answer names the revision it read. A symbol with no declaration refuses
`resource_not_found`.

The server reads package and runtime symbols through the global API. The answer's
`revision` names the selected release. The server **MUST** refuse a revision that is not
a release of the symbol's owner with `invalid_request`.

`max_results` defaults to 10 and accepts 1 through 100. The source bound is 1 MiB across the
syntax elements. A page above that byte bound returns a typed error. The caller can reduce
`max_results`. A declaration's syntax structure stays with its source. The caller sends the same
symbol and revision for later pages.

## Feedback [#tool-feedback]

`feedback` submits one report to the HTTPS intake named by the server process's
`RIFT_FEEDBACK_URL`. When the variable is unset, the server submits to
`https://feedback.volar.sh/rift/feedback/v1/reports`. The URL carries no credentials, query,
or fragment.

A set value that is empty or breaks that form refuses every call with `capability_unavailable`.
The server never falls back to the default intake for such a value, so an empty value turns
submission off.

The server sends `text` verbatim. It MUST contain at least one non-whitespace character
and fit within 4,096 UTF-8 bytes. The optional `include` object takes two boolean members:
`os` sends the server's operating system name, and `rift_version` its package version. An
omitted member is `false`. Omit `include` or set both members to `false` to send only `text`.
The server reads no workspace files, logs, or conversation history to construct the report.

The caller MUST redact secrets, personal data, and private source material before sending
the report. The caller MUST obtain approval for the exact conversation excerpt before
sending it as part of `text`.

The server returns `{"submitted": true}` after the intake confirms storage with HTTP 204.
If confirmation is lost, the call reports an unconfirmed submission. Rift makes at most
one submission attempt per call.

## Reads

Callers read code through these tools:

| Tool | Result |
| --- | --- |
| [`get_symbol`](#tool-get_symbol) | one logical symbol by canonical identity |
| [`search`](#tool-search) | bindings, booleans, or RDF triples from selected facts |
| [`facets`](#tool-facets) | every declaration of a symbol with its location, source, and syntax structure |

[Result content](#result-content) defines the representations a tool result carries and the proxy output selection that chooses them.

The index never follows or indexes a symlink, so no read returns one. The file a link points
at answers under its own path.

`search`, `get_symbol`, and `facets` accept `page` and `max_results`. The response names the
`revision` it read. The caller sends that revision for later pages.

The server writes read diagnostics to its workspace logs. Use `rift server logs` to inspect them.
A `stale_index` record names the revision an answer used and the newer tree revision the read captured.

The server logs `local_index_preparing` while the requested local scope remains
incomplete. `prepared` counts visible files whose capture and analysis finished, including files
refused under an accepted bound. `total` is omitted until discovery finishes. `ready_in` is
omitted because the server has no preparation estimate.

An exact symbol read cannot establish complete declaration coverage while selected files
remain unprepared. The server logs local preparation for reads that select local source.
Preparation counts describe the answer's publication and can decrease when source selection changes.

An `unavailable` answer whose `reason` is `index_preparing` opens with
`unavailable | indexing is in progress`. Use the `local_index_preparing` and
`pattern_index_preparing` log records for counts.

The server also logs `stale_index` when the last rebuild failed, with a `detail`
naming the failure. The next filesystem event retries the rebuild. When its two digests are equal,
the tree moved in recorded files outside the syntax-indexed ones or in the configuration file, and
`detail` says which.

The server logs diagnostics for ranking and result bounds:

- `vector_index_preparing` - the vector ranking holds no vectors for the tree this answer
  was read from: the pass over that tree is still running, or the tree was published after
  the corpus the ranking holds was described. A query sharing no token with the code it
  describes reaches nothing until that pass lands. `prepared` and `total` state how far it
  has progressed.
- `vector_ranking_unavailable` - the vector ranking will not answer for the life of this
  server: the model weights could not be acquired, or the model failed to load.
- `lexical_ranking_unavailable` - the full-text tier has not yet committed the captured tree,
  missed a commit, holds no indexed tree, failed to load, got no database connection within
  `[search] busy_timeout`, or still answers for a newer publication after the request's capture
  attempts. The `detail` names which, with the tree revision in the first three cases. Ranking
  falls back to identifier matching, so a query phrased as prose finds nothing. The tier is read
  under the answer's own tree revision, so one that has moved past it is recaptured, up to those
  attempts, before the server logs the fallback. A later search can use the full-text tier after
  the commit lands.
- `history_store_filling` - a [commit search](#search-commits) answered while the history store
  lacks some of the commits its latest fill selects, or the commit `HEAD` names. `analyzed` and
  `total` state how far the fill has got.
- `lexical_ranking_truncated` - the lexical ranking stopped at `matches_max` units, and hits
  past that bound never reach a page, whatever `paths` selects. `pages` counts the units
  that did. A narrower `query` brings the rest inside the bound.
- `documentation_unavailable` - the documentation this search projects onto crossed a bound, so
  no documentation block joins the answer and declarations and files answer as they would without
  it. The `detail` names the documentation left out - the project's, the `force_include` files',
  or the dependency packages' - and the bound it crossed.
- `query_narrowed` - the query carried more terms and quoted phrases than `terms_max`, so the
  server dropped the shortest unquoted terms and ranked the answer by the rest. Every quoted
  phrase is kept. Shorten `query`, or quote the terms that must be matched.
- `results_truncated` - the server reached `results_max`, its result bound, before ordering and
  paging. The bound covers both the candidates one read ranks and the hits it returns, so what
  it cut never reaches any page and `pages` counts only what fit. The server logs this
  code whenever a read fills the candidate pool, including when every candidate fits.
  A narrower `query` or `paths` brings the read inside the bound.

A `symbol_disagreement` record names a symbol whose selected presentation and at least one
provider's own facts disagree.

A `source_unavailable` record names a file the index left out - bytes that are not valid UTF-8,
a file past its per-file bound, or a syntax tree the provider refused - so it answers no search or
lookup while every other file stays available. A read logs at most eight omitted files in
project-path order, followed by a `source_unavailable` summary if more files were omitted. A
file a bound left out is not among them. The index build records each omission with its bound
and measured value, one record per file for the first 64 files one build reads, then one record
per publication counting the rest.

Text search can produce these diagnostics:

- `pattern_matches_truncated` - a file held more matches of `pattern` than the `[search]` key
  `pattern_matches_per_file`, so its later matches are missing while every other file answers in
  full. `files` names the cut files, at most eight, in project-path order.
- `pattern_index_preparing` - the trigram index lacks rows of stored file text, and verifying them
  beside the selected rows would pass `pattern_candidate_rows` or `pattern_verified_size`, so a
  match in those rows is missing from the answer. `prepared` counts the rows the index holds and
  `total` the rows the store holds. The server stops recording it once the index has caught up.
- `large_file_skipped` - under `[search.text] large_files = "skip"`, files past `max_chunk` are
  left out of the text index. `skipped` counts the ones the request's `paths` reach. A
  declaration such a file holds still answers.
- `large_file_unparsed` - files past `[providers.syntax] max_file` are held as text the syntax
  provider does not parse: their text answers `search`, and none of their declarations answers a
  symbol hit or `get_symbol`. A read records at most eight such files in `files`, in project-path
  order, when the request names them in `paths.force_include` or a comparison. The index build
  records every other such file in the log.
- `lockfile_excluded` - a lockfile the request's `paths.include` selects is left out of search
  under the `[search.text]` key `excluded_lockfiles`. `rift://map` still carries the versions it
  pins, and naming the file in `paths.force_include` searches it for one request.

When a package read cannot obtain global facts, the server logs the cause:

- `global_access_disabled` - `[global] enabled` is `false`, so no package read reaches the
  global API.
- `global_api_unavailable` - the global API could not answer. `failure_class` identifies the
  bounded failure.
- `global_publication_incompatible` - the global API advertised a publication format or corpus
  revision this client cannot read. `failure_class` names which.
- `global_response_invalid` - the global API response is invalid or truncated. `failure_class`
  names which.

The server also logs these package diagnostics:

- `global_page_warning` - a valid global page carried a bounded condition. `warning_code`
  identifies it and optional `detail` explains it. `result_truncated` names a page the global API
  stopped early, and the answer holds what that page held. `capability_unavailable` names a
  feature the global API's capabilities do not advertise, such as `patterns` for a `pattern`
  search, and the answer then holds the project hits alone.
- `package_absent` - the global publication holds no release of the exact `package` the
  dependency context names, so nothing answers for it.
- `package_requirement_absent` - the global publication holds no release the declared
  requirement in `entry` admits, so nothing answers for it.
- `package_substituted` - the global publication holds no release at the version `entry` names,
  or none inside the range its requirement states, so the nearest collected release, `package`,
  answers in its place.
- `package_unavailable` - the dependency context `entry` names a package no public registry
  serves, so no global package index answers for it. `reason` names the capability Rift does not
  have yet, by the entry's `availability`.
- `package_context_degraded` - a resolver read less than its manifests and lockfiles state, or a
  standard library probe answered nothing, so the dependency context can miss packages or name a
  standard library by its static reading. `resolver` names which, by manager name - `cargo`,
  `uv`, `npm`, or `bun` - or by standard library entry - `stdlib/rust`, `stdlib/node`, or
  `stdlib/python` - and `reason` says what it could not read. When the context passes the
  entries one read sends - 20,000, or fewer when the global API advertises a smaller
  `dependency_entries_max` - the entries sorted last leave, and `resolver` names their package
  manager, such as `pypi`. The request's `packages` leave only after every other entry has, the
  ones sorted last first, and `reason` then counts the requested packages not reported.

`package_unavailable` records carry a `reason` for each `availability`:

| `availability` | Source | `reason` |
| --- | --- | --- |
| `path` | a path outside the workspace, or an archive at a path | Currently rift doesn't support indexing dependencies by path. If you're interested in this capability, please upvote it at https://github.com/volarized/rift/issues/392. |
| `git` | a git repository | Currently rift doesn't support indexing dependencies from git repositories. If you're interested in this capability, please upvote it at https://github.com/volarized/rift/issues/393. |
| `private_registry` | a registry other than the public one its package manager reads | Currently rift doesn't support indexing dependencies from private registries. |
| `url` | a URL no registry serves, such as a uv wheel URL or an npm tarball URL | Currently rift doesn't support indexing dependencies from URLs. |

A path dependency inside the workspace is project source: the local index covers it, and the
dependency context names no entry for it.

A read logs at most eight `package_context_degraded`, `package_unavailable`,
`package_absent`, `package_requirement_absent`, and `package_substituted` diagnostics together: the
degraded resolvers first, in resolver order, then the entries no public registry serves, then the
packages and requirements the global publication lacks, then the entries a nearest release
answers for. The global API failure and source omission diagnostics have separate bounds.

`get_symbol` and `facets` accept an optional `revision`. A local read with no revision
selects the working tree.

### Result content [#result-content]

A completed tool result carries one text block in `content`. When the proxy output selection is
`all`, the result also carries the canonical answer in `structuredContent`, and the tool listing
carries `outputSchema`. The text and structured content describe the same answer.

The caller selects the representations when it starts the proxy with `rift mcp --output`:

- `all` forwards the text, structured content, and every resource content, and lists output schemas.
- `text`, the default, omits structured content and output schemas. A resource that carries text and
  JSON returns the text. A resource that carries only JSON returns JSON.

The proxy **MUST** keep the selected output for its lifetime. Direct HTTP access to
`rift server` carries both tool representations.

Search uses [Markdown result text](#search-result-text). An exact read states its outcome and
selected object. Use `rift server logs` for diagnostic codes and details.
The [tool execution failure](#tool-execution-failures) form applies when `isError` is set.

### Revision-addressed reads [#revision-reads]

`get_symbol` and `facets` accept `revision`, a [`Revision`](/docs/developer/protocol/reference) IRI
that names one point on the history axis:

- `rift://revision/git/<commit>` - a complete lowercase git commit id
- `rift://revision/git/<reference>` - a branch, tag, or `HEAD`, optionally followed by `~N`
  ancestry suffixes, which the server resolves to a commit
- `rift://revision/<manager>/<registry>/<name>@<version>` - a package release, such as
  `rift://revision/cargo/crates.io/serde@1.0.228`
- `rift://revision/stdlib/<runtime>@<version>` - a runtime release, such as
  `rift://revision/stdlib/cpython@3.12.9`
- `rift://revision/tree/<digest>` - the working tree the index serves, by its complete SHA-256
  digest

A `get_symbol` or `facets` answer carries the `revision` it read. The answer names a commit, a
release, or a tree. A caller **MAY** send that revision to pin a later exact read to the same point.

A git revision reads committed bytes. The server resolves it in place from the workspace's git
objects, with no checkout, and indexes that commit's tree under the same
[`[source]`](/docs/developer/configuration#source) policy and bounds as the working-tree scan,
so uncommitted working-tree changes never appear in it. This `get_symbol` request reads a
declaration as it stands on `main`, whatever the working tree currently holds:

**Request:**

```json
{
  "id": "rift://symbol/local/rust/example_project/config/load_config",
  "revision": "rift://revision/git/main"
}
```

The answer reports the commit `main` resolved to, such as
`rift://revision/git/1f2080e49da12fee4431e6872630509355cd62d1`. `~N` walks `N` first parents,
defaulting to 1, so `rift://revision/git/HEAD~1` names the commit below `HEAD`. A reference that
carries anything else - a second-parent selector such as `^2`, or a reflog selector such as
`HEAD@{1}` - refuses `invalid_request` naming `revision`.

A tree revision reads the working tree the index serves. The server **MUST** refuse a tree
revision naming any other tree with `resource_not_found`
(`rift.server.read_revision_unserved`), naming the requested and the served revision, since the
index retains no earlier tree. A release revision **MUST** name the release a package or runtime
identity carries. Beside a project identity the server refuses it the same way.

A revision search refuses `force_include`: reaching index-excluded files is a walk of the
working tree, which a revision does not have.

[`[providers.history]`](/docs/developer/configuration#providers) owns the capability: `enabled = false`

### Requested packages [#requested-packages]

`:packages` in `SERVICE :search` names package versions beside those in the
workspace's manifests and lockfiles, at most 64 entries. Each entry is a
[`RequestedPackage`](/docs/developer/protocol/reference) carrying `manager`, `registry`, `name`,
and an optional exact `version`. The server applies the list to this read's dependency context alone:

- an entry naming a package the context holds replaces every entry for that package, a `path`
  or `git` entry included
- an entry naming a package the context lacks adds it
- an entry without `version` goes out as the requirement `>=0`, which the global index answers
  from its newest collected release

Each entry then routes like any context entry. A requested version the global publication lacks
answers from the nearest collected release under `package_substituted`. A package with no
collected release answers `package_absent`, or `package_requirement_absent` for an entry without
`version`.

or `version` is empty or longer than its schema allows, refuse the same way before anything
reaches the global API. A service that selects no `:scope` reads `local` unless

## Resources

### Resource contents [#resource-contents]

A read of `rift://map` or `rift://workspace` returns compact text with `mimeType` `text/plain`.
With `rift mcp --output=all`, the compact text is followed by JSON with `mimeType`
`application/json`. Both contents name the requested `uri` and read the same publication.

The map's `recommendations` entries carry `language`, `root`, and `command` for installed
language servers without a selected configuration. The server **MUST** omit `recommendations`
when none remain and remove a matching entry from the next publication after accepting its
configuration. `root` is relative to the map's project, with `.` selecting the project itself.
A `command` is a `rift config set` invocation quoted for the server's operating system.
The caller runs it from the map project's root.

The listings of resources and resource templates declare `application/json`, the type of the
JSON body. A caller **SHOULD** select a content by its `mimeType`.

Compact resource text uses ` | ` between facts on one line. The server omits sections with
no entries. It refuses a read whose text exceeds the byte limit, with typed `ErrorData` as
`data`.

### Workspace [#resource-workspace]

`rift://workspace` reads accepted configuration together with one captured source catalog page.
The answer carries:

- `configuration_revision` - an eight-character digest of the accepted `rift.toml` bytes
- `revision` - the indexed revision the page read
- `languages` - effective identities in order, with enabled state, include and exclude patterns,
  syntax availability, and selected LSP process state
- `source` - captured project paths, content digests, and matched language identities
- `pagination` - `page`, `pages`, `max_results`, and `total` of the source catalog

The bare URI selects page 1. `rift://workspace?page=2&max_results=50&revision=<revision>`
selects a later page of the catalog that `revision` names. `max_results` defaults to 10 and
accepts 1 through 50, and each page repeats the language summaries. The server refuses a
revision it no longer serves. When another page exists, the compact response ends with its URI,
which carries the revision. A page past the end returns an empty `source` list with the actual
page count.

The compact text has these parts:

- the header `workspace`, with ` | page P/T` on a multi-page answer
- directly below the header, the sections `languages` and `source`, in that order, each a title such as `languages:` with its entries indented by one level. The server **MUST** omit a section that has no entry
- a language entry: the language identity, `disabled` when `enabled` is `false`, `syntax` and `execution` when they hold, and `lsp <process> <state>` when the language has a selected LSP process
- under a language entry, `include` and `exclude` lines with their patterns joined by `, `, each only when the list is not empty
- a source entry as `path | language`, with only the path when no language matched

## Errors

The [error registry](/docs/developer/errors) lists registered slugs, messages, and evidence fields.

A failure travels by its class. A **tool execution failure** is a Rift operating failure on a
`get_symbol`, `search`, or `facets` call, such as invalid input, a crossed limit, or a storage
failure. A **protocol failure** is any other failure: an unknown method or tool, a malformed
request envelope, a transport failure, a resource read failure, or an MCP error forwarded from
upstream.

### Tool execution failures [#tool-execution-failures]

The server **MUST** answer a registered tool execution failure with a completed tool result that has
`isError` set to `true` and one `content` text block of compact text. The result **MUST NOT**
carry `structuredContent` under either output selection. The MCP specification
[reports tool execution errors](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling)
in the result, where the model can read the failure and adjust its request.

The advertised `outputSchema` describes typed tool answers, including the `get_symbol`
`missing` outcome. Registered operating failures carry no such answer. A proxy started
with `--output text` forwards the failure unchanged: it keeps `isError` and `content`, and the
result had no `structuredContent` to remove.

The text of a failure is one section. Its title is `N errors`, or `1 error`, where N is 1 plus the number of entries of `causes`. Its entries are the failure, then each entry of `causes`, outermost first, as one list. Each line is written on one line, with control characters as escapes:

- the head of an entry, at one level: `<code> | retry <directive>`, the `code` and `retry` of [`ErrorData`](/docs/developer/protocol/reference) or of the cause
- below the head, at two levels, the `message` of the entry. An empty message writes no line
- below the failure's message, `limit <field>: <required> over <limit>`, when the failure carries `limit`
- then one line for each entry of `diagnostics`, as the `severity`, the code in brackets, the file of the span followed by `:line:column`, and `: <message>`, each part only when the diagnostic carries it
- after the diagnostics, the registered identity on its own line, at two levels, for a registered failure

Every entry writes its `code` and `retry`, also a cause whose `code` or `retry` equals the failure's.

The text omits `phase`. The typed `ErrorData` model carries it, and a protocol failure carries it in the JSON-RPC `data` as described under [protocol failures](#protocol-failures).

Every failure carries a `retry` directive, which is the field to branch on - it rides each error
instance rather than the code, because the same `storage_failure` can be transient once and
permanent the next time:

- `never` - the caller cannot resolve the failure by retrying the same request
- `same_request` - it was transient: an index still filling, a tree with a filesystem
  write in flight
- `operator_action` - an operator must check or change state before a retry

The `phase` field of `ErrorData` names the operation that failed. `read` covers argument
acceptance and reading workspace or provider data. `submit` covers sending feedback.
A `limit_exceeded` also carries which limit and by how much, so a
request can be resized without parsing the message meant for a human. Any other code omits
`limit`.

Each entry of `causes` holds a `code`, a `message`, and a `retry` for one link of the failure
chain, outermost first. The `retry` of the failure governs the call. A cause's own `retry`
says what could be done about that cause. The text writes the `code` and the `retry` of every cause.

### Protocol failures [#protocol-failures]

A protocol failure stays a JSON-RPC error. An MCP error forwarded from upstream keeps its received
code, message, and data, so the proxy adds nothing to a refusal the server classified.

A failure the proxy raises itself carries the same typed `ErrorData` as the JSON-RPC `data`
under code `-32000`: a `tools/call` whose `arguments` is not an object, a forwarded request that
the server did not answer within the proxy's budget, and a server that is still building or
failed to start. The caller **SHOULD** read `retry` from that `data` as it reads it from the
first entry of an execution failure. A resource read refusal, such as an unknown resource URI,
carries a code and a message and no `data`. A read whose compact text crosses the byte limit carries the typed `ErrorData` as `data`.
