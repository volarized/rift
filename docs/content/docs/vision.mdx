## Preface

Over the last years, agents stepped from toy-like experiments to parallelizeable,
production-scale systems. In the software development lifecycle that shift ran through roughly
these stages:

- "smart" autocompletion
- per-file or per-function code generation
- multi-file generation, sometimes one-shot
- single-agent codebase reads and edits, with a high level of autonomous reasoning
- multi-agent development, where one agent writes the code and another reviews it

Model quality kept rising and the variety of agents grew with it. A lot of effort goes into
harnesses - the methods and tools that bring determinism into agent output.

The integration between the agents and the facts of the codebase lagged behind. The closest we
have are tools that read the codebase syntactically, such as tree-sitter based solutions, and
some level of LSP integration. `AGENTS.md`, skills, and memory carry the perspective of the
project, and for the code itself agents fall back to reading whole files or running grep, which
burns context and misses what a parser already knows.

That gap is what Rift fills: one composable system that collects codebase facts and serves them
to any MCP agent.

## Concept

Rift brings structure into the agentic development workflow by serving facts instead of file
dumps. Low-level facts come from the parse: byte positions, syntax trees, declarations. Facts
derived from them cover the rest: which declaration a reference names, how a symbol changed
across revisions, which package owns a source root.

Both kinds answer from the same index over the same tree, so a read tells the agent what the
code says rather than what a model recalls.

## Levels of intelligence

### Base facts

Rift starts from project-level facts, with the following assumptions in mind:

- A codebase is a collection of files, and each file its syntax provider selects parses into a
  syntax tree. Every bounded UTF-8 file also becomes lexical units, so a file no provider parses
  stays searchable and contributes signal.
- Files of the project have history, and reasoning about the codebase means reasoning about
  changes to it.
- A project may hold several languages, or several separate projects with their own dependency
  sets, as a monorepo does.
- Most projects have dependencies, and the packages a toolchain resolved are part of what the
  agent reads.

None of this needs a constantly-running sidecar such as an LSP process: tree-sitter parses the
bytes, and the source resolvers read manifests, lockfiles, and Git objects in place. These facts
form the base that the levels below enrich.

### Engine facts

Where a [language engine](/docs/developer/configuration#languages-and-lsp) is configured, it
resolves what the grammar alone cannot, such as a reference to a declaration in another file.
The most widely supported way to reach those facts is LSP, which costs configuration and returns
name and type resolution in exchange.

The embedded [ty](https://github.com/astral-sh/ty) engine serves Python over an in-memory
transport through the same session contract, with its version shipped in the Rift binary. Rust
takes the other route: the binding provider resolves names from the syntax facts alone, with no
process to configure.

### Derived knowledge

Base facts and engine facts combine into facts that neither level holds alone:

- [Semantic graph](#semantic-graph) - connects a declaration to the declarations its references
  name, so traversal follows callers and callees.
- [Symbol history](#symbol-history) - compares one declaration's parsed state across revisions,
  so a lookup shows when a body, a signature, or a decorator changed.
- [Dependency source](#dependency-source) - the public declarations of resolved packages, parsed
  by the same syntax providers as the project's own files.
- Package documentation <VersionBadge version="planned" inline /> - declaration documentation
  ranks in [`search`](/docs/mcp#tool-search) and the project's own Markdown is indexed, while a
  package's documentation files are not: the dependency index selects `.rs`, `.pyi`, `.py`, and
  `.d.ts` source alone.

## Codebase intelligence

Rift connects a declaration to the source that defines it, the references that use it, and its
committed history. An agent reaches those facts through [search](/docs/mcp#tool-search) and
[symbol lookup](/docs/mcp#tool-get_symbol), including public declarations from dependencies.

## Languages and providers

Rift selects a syntax provider by file type. [Tree-sitter](https://tree-sitter.github.io/tree-sitter/)
parses the source into declarations and syntax nodes; for project files, byte ranges identify the
text each read returns. Language engines add references that require name or type resolution.

<CodebaseLanguages />

Engine selection belongs to each [language identity](/docs/developer/configuration#languages-and-lsp).
Several identities can share one named process. Available facts depend on the syntax provider and
engine selected for that language.
Rift's own binding provider receives binding facts from Rust syntax. Python's embedded
ty engine and configured LSP engines perform name resolution through the language-engine path.

## Semantic graph

The binding provider resolves names using the scopes, definitions, references, and imports extracted
from syntax. It follows module layout across files, with nearer scopes and explicit imports taking
precedence. The resulting name bindings identify which declaration each resolved reference names.

Rift normalizes provider output into a shared symbol model across languages. From those name bindings,
the semantic graph connects the declaration containing a reference to its target, so
[relationship traversal](/docs/mcp#search-traversal) can follow referenced symbols outward or
callers inward. Rust's binding provider supplies the indexed reference relationships today.

For current-tree incoming traversal, [language engines](/docs/mcp#search-engine-references) can
add callers to the requested read. Rift maps the returned source locations to indexed declarations
and combines them with stored relationships. These engine results belong to that read.

A shared model allows symbols from different languages to appear in the same result. A connection
between them still requires a provider to resolve the reference; the language list alone does not
establish cross-language relationships <VersionBadge version="planned" inline />. The
[provider architecture](/docs/developer/architecture#providers) describes normalization and
binding support.

## Symbol history

Git supplies committed source along a file's first-parent history. Rift parses each revision with
the same syntax provider and compares adjacent symbol states, so a
[symbol lookup with history](/docs/mcp#tool-get_symbol) can show changes to a declaration's body,
signature, or decorators, as well as its introduction or removal.

[History reads](/docs/developer/architecture#history) follow the declaration's current path and stop
at the configured revision bound, comparing one declaration along one file's history.

Two committed revisions compare through the same parse. Rift reads the paths they hold differently,
parses each side with the file's syntax provider, and matches declarations across them. A
[change comparison](/docs/mcp#search-change) then names changed declarations, where `git diff` names
changed lines.

## Dependency source

Source resolvers discover resolved packages through Cargo, uv, npm, and Bun. The
[dependency index](/docs/developer/architecture#dependency-index) parses their available source
with the same syntax providers and retains public declarations, so search and symbol lookup can
reach beyond project files when their scope includes dependencies.

Dependency discovery establishes which package owns the source. Reference resolution determines
which declarations use it; indexing a package's public API does not establish those connections.

The index builds a package's declarations once and never revalidates them, because the package
manager resolved that source and nothing in the workspace moves it. Comparing one package across
its versions is a separate walk <VersionBadge version="planned" inline />.

## Composition

One `rift server` can join a space <VersionBadge version="planned" inline /> - a set of Rift
servers that answer together, each serving facts for different languages, projects, or
dependency sets.

The typical shape starts with the server that runs locally and serves the current project. A
public Rift server in the cloud joins it and serves dependency facts. A company-specific server
joins later and serves internal dependencies and repositories.

Each server keeps the facts it owns, and an agent reaches project, dependency, and internal facts
through one surface.

## Memory

Memory carries weight in agent workflows, and existing solutions are practically key-value stores
with search. Write a memory such as "DON'T USE THIS FUNCTION - IT'S DEPRECATED", and enforcing it
from that moment on leaves two choices:

- load the whole memory set into the agent context, so the memory stays in front of the model
- search the memory store before every read, which costs a lookup per read

Rift's memory model <VersionBadge version="planned" inline /> answers that with structured reads.
A memory is associated with a symbol, or a set of symbols, and rides the result of the `search`
or `get_symbol` call that returns them, so the agent meets the memory where the code it
constrains is returned.

A memory is written at one of these levels:

- local - the operator's own machine
- project-wide - the workspace every contributor shares
- company-wide - every workspace in the organization
