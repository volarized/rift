title: MCP

`rift mcp` is a thin process: it maps MCP JSON onto the local Rift service and owns one session
connection for its lifetime. Nothing below is decided in that process.

## Connection

The bridge finds or starts the server for its workspace, mints a session id, and opens `Connect`.
`Connected` comes back with the contract the two peers settled on, the workspace path, the session,
its `ProjectionState`, and a connection id that every later call carries.

A session takes one live connection. When your agent exits, the session and its projection stay
put, and three tools deal with what's left behind:

| Tool | What it does |
| --- | --- |
| `session_list` | retained sessions and the state of each projection |
| `session_continue` | rebinds this connection to a retained session |
| `session_remove` | discards a session and deletes its projection |

`session_continue` refuses a session that already has a live connection, and refuses to abandon a
current session that has changes of its own — otherwise picking up old work would silently throw
away new work.

## Reads

Three tools read the projection:

| Tool | Result |
| --- | --- |
| `outline` | declarations in one file, in source order |
| `search` | ranked files, nodes, or symbols |
| `match` | literal, regular-expression, or structural matches |

`search` takes a lexical `query`, a `filter` over resolved adapter facts, or both — the filter is
where adapter knowledge enters a search, so "implements this trait" and "called by that function"
are one request rather than three.

Resources carry the larger and reusable payloads:

| Resource | Content |
| --- | --- |
| `rift://workspace{?cursor}` | projection state, per-language capabilities, limits, and validators |
| `rift://projection` | the projection's path on disk, and the workspace it came from |
| `rift://changes{?cursor}` | every change this session applied, with its evidence |
| `rift://fs{/path}{?start,length,cursor}` | a directory's entries — subdirectories and files — or a bounded range of file bytes |
| `rift://symbol/{language}/{name}{?cursor}` | one symbol, its nodes, its edges, its diagnostics |
| `rift://actions/{address}{?only,cursor}` | the actions an adapter offers at one address |
| `rift://action/{token}` | one action and the JSON Schema of its arguments |

The split between the last two is about page size. A listing can hold many offers and each offer's
argument schema is large, so the listing leaves the schema out and you fetch it for the one action
you picked.

Paginated answers stop before `max_response_bytes` and hand back a cursor. A cursor is bound to the
request that minted it — same order, same page size — and expires when the server drops the
captured result set, which comes back as `cursor_expired` rather than a quietly different answer.

<Callout>
MCP's `roots` capability runs the other way: a client tells a server which directories it may work
in. That's why the projection path is a Rift resource rather than a root — a server has no way to
advertise one — and why the resource is named `rift://projection`, so the two ideas never share a
word.
</Callout>

## Changes

`edit`, `patch`, `rewrite`, `rename`, `move`, `delete`, `change_signature` and `act` all change the
projection, and all return the same `ChangeResult`. Rift resolves and validates the whole operation
before writing anything, and the result is one of two things.

**Refused**, when resolution produced no edits. The projection is untouched and `RefusalReason` says
what stopped it: the address hit several targets, a `rewrite` matched outside its cardinality, no
adapter implements the operation for that language, the offer carries a portable argument contract
and resolves through its own tool.

**Applied**, when it produced edits. The change lands and gets an id in the changeset, along with
its edits, its semantic effects, its guarantee evidence, its diagnostics — and its confirmations,
where an adapter or validator wouldn't vouch for the result. An unvalidated change is still a
change you can read, run tests against, and either keep or restore.

`projection_restore` refreshes selected changed paths from the workspace and drops the changes that
touched them; naming no paths restores all of them.

## Publication

`publish` takes the list of change ids whose confirmations you accept, and writes nothing unless it
can write everything:

- a change carrying a confirmation you didn't accept comes back in `unaccepted`
- a path the workspace changed since the projection took it comes back in `conflicts`

Either way both trees are left as they were. On success every changed path is written, the
projection is refreshed from the workspace, and the changeset is emptied.

## Execution

`execute` evaluates a block of code in a disposable copy of the projection, so anything it writes
is thrown away — the projection is the scratchpad your changes live in, and evaluated code doesn't
get to edit it as a side effect. `debug_start`, `debug_get_frame` and `debug_stop` do the same for
a failed evaluation, holding its stack frames for inspection until you stop the session or the
idle timeout does.

Both need `rift.toml` to allow the language *and* the adapter to advertise the operation. The
`rift://workspace` resource reports what's left after that intersection, so you never have to
discover it by being refused.

## Errors

A refusal is a normal tool result — Rift understood you and declined. `ErrorData` is for the call
itself failing: a request that doesn't fit the schema, an expired cursor, an adapter that isn't
running, a limit crossed, a timeout, a storage failure.

Every one carries a `retry` directive, which is the field to branch on. `never` means the same
bytes will fail the same way. `same_request` means it was transient — an adapter still starting, a
projection with a filesystem write in flight. `operator_action` means nothing will work until
someone fixes the workspace, usually `rift.toml`. A `limit_exceeded` also carries which limit and
by how much, so a request can be resized without parsing the message meant for a human.
