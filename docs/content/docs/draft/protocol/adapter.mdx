---
title: Adapter
---

A language adapter is a subprocess the workspace server starts and talks to over gRPC on a Unix
domain socket, or a named pipe on Windows. It owns everything about a language; Rift owns sessions, source state, ordering and
publication, and never guesses at what an adapter can do.

One process serves one exact `Language` — a name plus an optional dialect — and holds state for as
many projections as its limits allow. Plenty of tools use tree-sitter to collect language facts,
and LSP is there for operations. The trouble is that tree-sitter reaches only a small subset of the
facts that matter, and LSP's operations are shaped around what an IDE needs, so an adapter
reaches for the real toolchain instead.

## Process

The server starts each configured adapter with its `command` and passes the gRPC endpoint in the
`RIFT_ADAPTER_ENDPOINT` environment value — a `unix://` socket path, or a named pipe on Windows.
The adapter binds that endpoint, and the socket accepting is its readiness signal: the server
retries the connection for thirty seconds, then gives up and reports the adapter unavailable —
accepting a socket needs no analysis, so a process that can't manage it in that time is broken,
not busy. Once the socket accepts, the server calls `Describe`. Both stdout and stderr are
captured as the adapter's log.

Shutdown runs the same order backwards. The server closes every open state, sends `SIGTERM` — on
Windows, closes the pipe — and waits five seconds before `SIGKILL`. On that signal the adapter
fails in-flight calls with `UNAVAILABLE`, terminates the subprocesses it spawned, and exits; there
is nothing to flush, because Rift reads no adapter-written state.

## Discovery

Rift calls `Describe` once, right after starting the process, and holds the adapter to exactly what
comes back. There's no probing and no feature detection anywhere else, which is why the response
has to be complete:

- the exact language and dialect it handles
- which files it owns as source, which it reads as configuration or dependency metadata, and which
  paths it writes to while it works
- the syntax and symbol kinds it emits, and the portable facets each one carries
- the optional RPCs it implements and the fact families `Analyze` can produce
- the action families it can offer, its limits, and what its runtime does to the host
- the generated contracts it speaks, in preference order, and any versioned extension values it
  emits

The kinds matter more than they look. A filter can only negate on a facet somebody advertised, so
an adapter that never declares `test` makes "not a test" unanswerable for its language.

A source claim matches by suffix against the full path, by name against the final component, or by
shebang prefix against the first line, and carries a priority: where two adapters claim one path,
the higher priority owns it, and equal priorities are an ownership error.

Write claims are how build output stays out of analysis. An adapter naming `target` or
`node_modules` tells Rift those subtrees are its own output, not source — and two adapters that
could write the same path is a workspace admission error, because one of them has to redirect that
output into its private `state_root` instead.

`Describe` and its response stay decodable across protocol revisions, so a contract mismatch
surfaces as a clean workspace-admission failure rather than a decode error — the selection itself
happens at `Open`, which pins one revision from the advertised list.

Capabilities are fixed for the process's life; changing them means a new process. A process that
dies takes its states with it: the server re-runs `Describe` on the replacement, reopens states
lazily as calls need them, and treats the new answer as the truth, which can change what
`rift://workspace` reports. The server restarts a dead adapter on the next call that needs it,
doubling a one-second delay after each failed start; after three consecutive failures it stops
trying and answers `adapter_unavailable` with `operator_action` until the configuration changes,
because a command that failed three starts in a row needs a fix, not a fourth try.

## State

`Open` hands the adapter an absolute path to a tree, plus a `state_root` of its own that Rift
never reads — that's where `CARGO_TARGET_DIR` and friends should point. Rift creates it before
`Open`, deletes it once `Close` returns — so the adapter lets go of every handle into it before
returning — and reclaims orphans at server startup; every open state gets a distinct `state_root`,
never reused. Several adapters can be given the same path at once, because a Svelte file and the
TypeScript inside it are two adapters reading one tree.

While a session holds no changes, the tree is the workspace itself — a clean projection is
byte-identical to it, so one open state serves every clean session. A session's first change — or
the first read of its `rift://projection` resource — materializes the projection, and the server
opens a new state rooted there; an adapter softens that re-analysis with a shared read-only cache
outside `state_root`, where its toolchain supports safe sharing. When opening one more state would
cross `max_states`, the server closes an idle one first and reopens it on demand; the shared cache
is what keeps that reopen cheap. A state holding debug frames is pinned, not idle — the server
can't evict it without destroying the frames — so `debug_start` refuses with
`temporarily_unavailable` when granting it would leave the adapter no state to evict.

The shared clean state tracks a tree Rift doesn't control — your own `git pull` moves it. A
publication names the paths it wrote, so the server refreshes the state directly; an external
change is detected on the session's next read, and the server sends `Refresh` before serving
analysis from that state.

The returned `AdapterState` is a generation counter. `Open`
mints the first value; `Refresh` and `SyncVirtual` advance it; a call carrying an older generation
comes back as `StaleState` with the value the adapter actually holds, so the server resyncs and
retries rather than acting on offsets that have moved.

`Refresh` is what tells an adapter its files changed, and it carries the paths — `written` and
`removed`, with a rename arriving as one of each. Without that the adapter would have to stat the
tree to find out what happened, and rebuilding its state per edit would throw away the incremental
work that makes it fast. Rift serializes refreshes for one adapter state and drains its in-flight
calls first, so a generation never advances under an open stream; within one generation, calls up
to `max_in_flight_per_state` run concurrently, and the adapter has to be safe for that.

An adapter that produces source for another language publishes it through `SyncVirtual`. Each event
names the unit it belongs to and the mappings back to the ranges it came from, so a diagnostic on
generated TypeScript can be pointed at the Svelte a person can actually edit. Rift keeps those
paths in a namespace of their own.

## Analysis

`Analyze` streams facts for the requested source units: symbols, nodes, relationships, origin
mappings, diagnostics, and a per-file coverage event that closes each one. Files may interleave
in the stream; for one file the unit event comes first, its facts follow, and its coverage event
closes it — nothing for that file may come after. A source unit is a regular UTF-8 file, never a
symlink, and a unit the adapter declines to read — too large, wrong encoding — closes with
partial coverage and a diagnostic rather than silence. A final summary closes
the stream, states how long Rift may keep the facts, and lists files whose earlier facts no longer
hold — which is the only way to invalidate a file the stream said nothing about.

Every family is stated explicitly per file. A family the adapter can't produce is `unsupported`,
one the language has no concept of is `not_applicable`, and neither is spelled as silence, because
a caller reading silence as "none" would be wrong.

## Changes

For a change, the server asks the adapter to validate the affected source closure, format the
regions or files a change touched, find structural matches, list the actions available at an
address, and resolve the one action that got picked. `Actions` and `Resolve` are separate calls
because computing an action's edits costs about what performing it costs, and only one of the
offers is going to be chosen.

`Resolve` returns the edits plus the evidence: which preconditions it checked, what the change does
semantically, and one `GuaranteeEvidence` entry for every guarantee its descriptor advertised.
Coverage rides along, so Rift can tell a rename that reached everything from one that couldn't
follow a name into a macro. Rift re-validates every path in the returned edits before writing, so
the `ProjectPath` exclusions hold whether a path came from the caller or the adapter.

When the adapter understood the request and declined it — the target was ambiguous, the offer went
stale, the language forbids the new name — that's a `Refusal` in the status details. Everything
else is an ordinary gRPC status.

## Execution

An adapter that advertises execution gets a disposable copy of the session's projection for
`Execute` and for debugging, never the projection itself — the `execution_root` on each request,
which Rift materializes and deletes. Its `RuntimeRequirements` tell the server whether it runs
workspace code or spawns subprocesses; Rift doesn't sandbox either, so the declaration is there to
be acted on by whoever configures the workspace. Budgets bound wall time, captured output, retained
frames, bindings per frame, and each rendered value.

The generated [reference](/docs/draft/protocol/reference) defines every request, event and capability.
