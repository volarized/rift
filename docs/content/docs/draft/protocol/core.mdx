title: Core
---

The core schema holds the values MCP and the adapter protocol both use: the shape of the
projection, the structure of source, the semantic facts an adapter resolves, and the changes Rift
applies.

## Projection state

[`ProjectionState`](/docs/draft/protocol/reference#ProjectionState) is two booleans, because
everything else about a projection is paged and there's no point copying it into every response:

```json
{
  "dirty": true,
  "unaccepted": false
}
```

`dirty` says the projection holds something your workspace doesn't. `unaccepted` says the
changeset holds a change carrying a confirmation, so a
[`publish`](/docs/draft/protocol/mcp#tool-publish) that doesn't name it in `accept`
will refuse — the one stopper visible before calling `publish`; a workspace conflict only shows
up in the attempt. The changes themselves come from the
[`rift://changes`](/docs/draft/protocol/mcp#resource-changes) resource.

## Paths and files

[`ProjectPath`](/docs/draft/protocol/reference#ProjectPath) is a normalized UTF-8 path relative
to the workspace root. It uses `/`, contains no `.` or `..` component, and can't name `.rift` —
the projection directory lives under there, and a path that could address it would let a change
reach Rift's own state. Normalized means Unicode NFC: Rift normalizes what it emits and accepts,
then compares byte-for-byte, and on a case-insensitive filesystem a create or rename whose
destination case-folds onto a different existing path refuses with `destination_legal`.

Every identifier that embeds a path — [`FileId`](/docs/draft/protocol/reference#FileId), a node
id, the [`rift://fs`](/docs/draft/protocol/mcp#resource-fs) form — carries a `ProjectPath` in
canonical percent-encoding, and the server re-validates it after decoding. The generated schema
patterns don't carry the exclusions, so validation can't be left to the schema.

[`ProjectEntry`](/docs/draft/protocol/reference#ProjectEntry) is a visible directory, regular
file or symlink. Visible means below the workspace root, outside `.rift`, and not excluded by
the workspace's VCS ignore rules. Visibility governs reads; publication carries every changed
path, visible or not.

Each variant carries what a consumer can act on:

- a regular file — its size and executable bit
- a symlink — its target, as base64, because Rift never follows it and can't assume the bytes
  are text
- a directory — only its path, so an empty one is still listed once something in the projection
  creates it

A symlink is listed and never followed, in every traversal:

- reads
- materialization
- the disposable copy [`execute`](/docs/draft/protocol/mcp#tool-execute) runs in
- publication
- prune

A `copy` of a symlink reproduces the link. A path that addresses through a symlink component
fails with `permission_denied`, because following it could leave the workspace.

## Source locations

[`TextRange`](/docs/draft/protocol/reference#TextRange) is a pair of half-open UTF-8 byte
offsets, and [`SourceSpan`](/docs/draft/protocol/reference#SourceSpan) puts one against a file.
Byte offsets rather than line and column, because every adapter converts from whatever its own
toolchain counts in exactly once, at the adapter boundary, and after that a `rustc` column and a
`tsc` column are on the same scale.

[`NodeId`](/docs/draft/protocol/reference#NodeId),
[`SymbolId`](/docs/draft/protocol/reference#SymbolId),
[`MatchId`](/docs/draft/protocol/reference#MatchId) and
[`ActionOfferId`](/docs/draft/protocol/reference#ActionOfferId) address facts in the projection. A match or an
offer names the file it came from, so Rift rechecks that one file before acting on it — a write
somewhere else in the projection leaves it usable, which matters when a build is running in the
same directory. A node or source address is positional: it names the bytes at those offsets as
the projection stands, and resolution refuses with a failed `target_exists` unless the range is
exactly a current node of the addressed kind — after editing a file, re-read before addressing
into it.

## Semantic facts

Adapters return facts in families: symbols, the syntax nodes that write them, relationships
between symbols, resolved types, diagnostics, and origin mappings for generated source. Each of
those is a [`FactFamily`](/docs/draft/protocol/reference#FactFamily), and each comes back with a
[`Coverage`](/docs/draft/protocol/reference#Coverage). Signatures and documentation
travel on the symbol itself, covered under the `types` family.

Coverage is what separates "there is nothing here" from "I couldn't see far enough to tell." A
symbol with no `relationships` means the symbol has no edges only where that family reported
`complete`; anywhere else it means the adapter stopped early, and the coverage says why. Read it
before you read an empty list as an answer.

## Changes

An [`Edit`](/docs/draft/protocol/reference#Edit) is one filesystem effect: replace these bytes,
create this file, delete it, move it, copy it, flip its executable bit. Edits in one set share
one input state, can't overlap, and apply together or not at all.

Higher-level operations resolve down to a set of those, plus the preconditions Rift checked, the
semantic effects the change had, the diagnostics it produced, and
[`GuaranteeEvidence`](/docs/draft/protocol/reference#GuaranteeEvidence) for every property the
operation claimed.

When resolution yields no edits at all, that's a refusal and the projection is untouched:
`ambiguous_target`, `cardinality_mismatch`, `unsupported`, and the rest of
[`RefusalReason`](/docs/draft/protocol/reference#RefusalReason). When it yields edits that
nothing will vouch for, the change lands carrying a
[`ConfirmationRequirement`](/docs/draft/protocol/reference#ConfirmationRequirement) per
problem — a validator that didn't finish, a reference the adapter couldn't classify, a deletion —
and `publish` is where those get settled.

Transport and infrastructure failures aren't in either bucket. They're
[`ErrorData`](/docs/draft/protocol/reference#ErrorData), with a code, a phase, and a retry
directive saying whether the same bytes are worth sending again.

The full field definitions are in the generated [reference](/docs/draft/protocol/reference).
