`rift.toml` controls Rift's behavior for one physical workspace. It sits at the workspace root and
is meant to be committed, like `package.json` or `Cargo.toml`.

<ConfigFile />

The `rift server` reads this file from the canonical root where `rift mcp` was launched. A request
may read an older commit, another branch, or a retained session, but the `rift.toml` inside that
state never becomes server configuration. If an agent changes `rift.toml` in its session projection,
the edit remains projection source until an integration publishes it; it does not reconfigure the
running server by itself.

The shared server gets its settings from that root file. CLI flags and environment variables passed
to `rift mcp` affect only that MCP process. When an MCP-local setting also has a `rift.toml` default,
an explicit CLI value overrides that default. An MCP-local option cannot replace a setting owned by
the shared server. Rift reads no other configuration file.

<Callout type="warning" title="A workspace configuration runs commands">
  Rift starts the adapter and validator commands declared in `rift.toml`. A valid change at the
  physical workspace root can start another command while the server is running. Review the file
  before launch and review changes before they reach that root, as you would with a package script.
</Callout>

## Reloading

The server watches `<workspace>/rift.toml`. After a valid change, it activates one new configuration
generation for every connected `rift mcp` process. Those processes keep running with their existing
session IDs. The generated MCP tool catalog also stays fixed.

This file watcher is the reload mechanism. The MCP interface has no reload tool.

Each request uses the generation under which the server admitted it. A request already running
finishes with that configuration, while later requests use the new one.

When an adapter declaration changes, calls using the previous process finish before the server stops
it. Rift discards the adapter states backed by that process, and the next request that needs the
adapter starts the new command and opens fresh state. A changed adapter or execution declaration also
stops affected debugging sessions and removes their execution projections. Session defaults apply only
to sessions created after the reload.

An invalid `rift.toml` blocks new requests with `configuration_invalid`. The server keeps watching
the file and resumes admission after a valid configuration replaces it; it does not continue using
the previous generation.

A workspace with no `rift.toml` uses the schema defaults and starts no adapters. Git tree, text
matching, file reads, and diff reads remain available because they don't need language analysis.

## session

`base` selects the state imported into a new session projection:

- `head` resolves HEAD once and imports its canonical Git tree.

This creates the writable persistent session projection during connection and requires an initial
commit. A client that needs another point in existing Git history supplies `initial_revision` in
`Connect`. Rift does not capture physical working-tree bytes, because checkout filters, encodings,
line-ending conversion, LFS materialization, and submodules are not canonical Git blob content.

## adapters

Each `[adapters.<process>]` table declares one adapter subprocess:

```toml
[adapters.rust]
command = ["rift-adapter-rust"]
env = { RUSTUP_TOOLCHAIN = "stable" }
```

Rift starts `command` directly without a shell and supplies the configured environment additions.
An absolute first argument names the executable itself; a bare name such as `rift-adapter-rust`
resolves through the server process's `PATH`. Empty arguments and invalid environment names are
rejected while `rift.toml` is parsed.

The server passes a private socket endpoint and `RIFT_PROTOCOL_MAJOR`, then calls `Describe`. The
adapter answers with its exact language, supported operations, source ownership, hard limits, and
compatible contracts. The table name identifies the configured process; the adapter's answer
identifies the language it serves.

One process may keep several states for session, candidate, validation, execution, and read
projections. It can
select a different project runtime for each state after `Open`. For example, a Python adapter can
inspect `.python-version` in two snapshots and place a Python 3.11 worker behind one state and a
Python 3.12 worker behind the other.

## execution

Caller-provided code is disabled until `execution.allow` names an exact configured language:

```toml
[execution]
allow = ["python", "typescript"]
debug = ["python"]
max-code = "16KiB"
max-timeout = "30s"
max-output = "8KiB"
max-concurrent = 2
max-debug-sessions = 2
debug-idle-timeout = "5m"
max-debug-frames = 64
max-debug-bindings = 32
max-debug-value = "1KiB"
```

`execute` becomes available for a language when the configuration names it and its adapter
advertises `execute`. Debugging also requires the language under `debug` and the adapter's complete
`debug_start`, `debug_get_frame`, and `debug_stop` operation set.

The byte and duration fields become the exact `ExecutionBudget` or `DebugBudget` passed to the
adapter. `max-output` applies separately to stdout and stderr. Frame, binding, and value bounds limit
what a failed debugging evaluation may retain and return.

<Callout type="warning" title="An execution workspace provides no host isolation">
  Writes inside the disposable projection are discarded, but evaluated code keeps the filesystem,
  process, and network access of `rift server`. Enable only languages whose adapters and project
  runtime you trust with that access.
</Callout>

## validation

Adapter validation runs after a session change and before integration. The default
`require = "available"` asks every affected adapter that advertises `validate` for a complete
report. When none does, the result says validation was mechanical.

A repository can require exact languages:

```toml
[validation]
require = ["rust", "sql:postgresql", "json"]
```

When one of those languages is affected, a missing adapter, missing `validate` operation, or
incomplete coverage rejects the change or integration. The `name:dialect` spelling selects the same
exact language pair used in node and symbol identities.

| strength | evidence required |
| --- | --- |
| `mechanical` | schema, path, edit, snapshot, and expected Git object IDs |
| `available` | complete valid reports from every affected adapter that advertises `validate` |
| `required` | complete valid reports from every language listed in `validation.require` |

## validators

Command validators run over the complete merged tree before integration advances its target:

```toml
[validators]
carry = [".env.test"]

[[validators.commands]]
id = "tests"
kind = "test"
argv = ["cargo", "test", "--workspace"]
changed_paths = "none"
working_directory = ""
environment = {}
timeout_ms = 300000
output_limit_bytes = 4096
guarantees = []
determinism = "deterministic"
```

Rift mounts the exact merged store snapshot in a disposable validation projection and starts `argv`
directly without a shell. The working directory is project-relative, the environment is literal,
and the command's timeout and captured output follow the declaration.

`carry` copies selected ignored paths from the session projection's persistent scratch layer into the
disposable projection. Rift does not read them from the physical workspace root. A missing, changing,
escaping, or gitlink-descendant path rejects validation before the command starts.

<Callout type="warning" title="A validation workspace provides no host isolation">
  Writes made inside the workspace disappear with it, but the command can still access the host
  filesystem and network. Declare only commands you trust with the server process's access.
</Callout>

A passing command turns each declared guarantee into `GuaranteeEvidence` in the integration result.
Rift may reuse the result only when the merged tree, executable, arguments, environment, carried
files, and limits all match. A missing cache entry runs the command again, so validators need to be
safe to repeat.
