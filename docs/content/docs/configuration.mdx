<VersionBadge version="v0.0.5" />

Rift reads `rift.toml` from the workspace root. The generated
[`rift.schema.json`](https://volar.sh/rift/rift.schema.json)
defines the file and rejects any key it doesn't know, so a typo fails at load rather than being
silently ignored. Edits take effect for later requests once validation passes; while the file is
invalid, requests fail with `configuration_invalid` until you fix it.

An editor that supports TOML schema directives can load the generated schema:

```toml
#:schema https://volar.sh/rift/rift.schema.json
```

Treat `rift.toml` as executable workspace configuration: the hooks a repository names run with
the server's OS permissions after each applied change, and the engines it names start with them.
Inspect the file before running Rift in a cloned repository.

Each section's example shows its keys at their defaults. Durations take `ms`, `s`, `m`, `h`, or
`d`; byte sizes take `b`, `kb`, `mb`, `gb`, or `tb` - binary units, so `1kb` is 1024 bytes.

## Server

<VersionBadge version="v0.0.8" />

`server` bounds the server's own blocking work - the filesystem scans and parses behind reads,
changes, and index rebuilds:

```toml
[server]
num_workers = 4
worker_queue_timeout = "30s"
idle_timeout = "30m"
readiness_timeout = "30s"
```

- `num_workers` caps the workers running blocking operations at once, 1 to 64
- `worker_queue_timeout` bounds one request's wait for a free worker, 1ms to 1h - when it
  expires, the request fails with `temporarily_unavailable` and the client can retry without
  stacking another waiter
- `idle_timeout` stops the server after that long with no served request, 1s to 1d; the next
  `rift mcp` or `rift server start` brings it back
- `readiness_timeout` bounds one request's whole wait for the workspace's index and its language
  engines to prove they're ready to answer, 1s to 1h - index validation starts the clock, and
  once the request has resolved which engines it needs, waiting on them spends whatever time is
  left
- `port` pins the exact loopback port, 1024 or above; omitted, the server picks the first free
  port from `port_range` - `port_range = { min = 12000, max = 13000 }` is the default - and the
  two keys exclude each other

The worker pool exists before the first request, so the server sizes it once at startup: a
change to this table applies on the next start, while every other table applies to later
requests as soon as the file is accepted.

## Source

<VersionBadge version="v0.0.6" />

`source` controls which files below the workspace root the index and reads consider visible.
`include` and `exclude` take exact project-relative paths or globs, matched the same way
[`search`](/docs/protocol/mcp#tool-search)'s `paths` selector matches them:

```toml
[source]
include = []
exclude = []
respect_gitignore = true
```

Empty `include` includes every file `exclude` and `.gitignore` leave standing; a match in `exclude`
drops a file even when `include` also matches it. `respect_gitignore`, on by default, applies the
workspace's own `.gitignore` files, root and nested; the server never reads global or
parent-directory ignore sources.

`.git`, `.rift`, and `target` stay invisible whatever this table says: no `include`, `exclude`,
or `.gitignore` entry can make the server serve them.

`source` shapes what the index walks: a file it excludes stops reaching `search` and
[`get_symbol`](/docs/protocol/mcp#tool-get_symbol) results. A single `search` request can still
reach one such file on demand, through the request-side `force_include` override on `search`'s
`paths` selector.

## Execution

<VersionBadge version="planned" />

[`execute`](/docs/protocol/mcp#tool-execute) runs a block of code your agent wrote in the
targeted tree's execution copy. The code still runs on your machine, so `execute` stays off
until you name the languages it's allowed for. A selector is a language name, or
`name:dialect` to pin a dialect.

```toml
[execution]
allow = ["python"]
max_code = "16kb"
max_timeout = "30s"
max_output = "8kb"
max_concurrent = 2
```

`allow` has no default; the other keys are shown at theirs.

- `max_code` bounds one submitted block, 1b to 32kb
- `max_timeout` bounds one evaluation, 1ms to 1d - the evaluation only: refreshing the
  execution copy is extra, and a refresh that outruns the same bound fails the call
- `max_output` bounds each captured stream separately, up to 16kb, so a program that floods
  stdout gets a prefix and a byte count rather than a hung request
- `max_concurrent` caps evaluations running at once across the whole workspace, 1 to 64

The schema states each range as `rift:range` on the key, and the server enforces it at load -
schema validation alone can't compare `"16kb"` against a ceiling.

Listing a language under `allow` does nothing when no runtime serves it; the
[`rift://workspace`](/docs/protocol/mcp#resource-workspace) resource reports what survives that
intersection per language.

## Providers

<VersionBadge
  version="v0.0.7"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML"]}
/>

The built-in providers run without configuration; the `providers` table exists to bound or
disable them:

```toml
[providers.history]
enabled = true
max_revisions = 500
```

`enabled = false` turns the history provider off: the server refuses a revision-addressed read -
`rev` on [`get_symbol`](/docs/protocol/mcp#tool-get_symbol), `search`, or `nodes` - with
`capability_unavailable`. A workspace without version control cannot serve those reads whatever
this table says.

<VersionBadge version="v0.0.13" />

`max_revisions` bounds the timeline walk from the served revision, 1 to 100000, because the
walk's cost scales with how far back it reaches. The history provider computes a
[`SymbolHistory`](/docs/protocol/reference#SymbolHistory) timeline inside that depth; a
revision beyond it contributes no version.

Provider configuration does not set merge order or freshness. The server reports provider order,
state, and revision through `rift://workspace`. A provider rebuilding after a file change can
serve its previous immutable revision; the result then carries a `stale_index` entry in
`warnings` naming the two tree revision digests.

## Search

<VersionBadge version="v0.0.9" />

[`search`](/docs/protocol/mcp#tool-search) runs on a lexical index. `[search.text]` decides
which files join it beyond source files; `pool_slots` and `busy_timeout` bound the SQLite
connections behind the whole index:

```toml
[search.text]
extensions = ["md", "mdx", "txt"]
max_chunk = "1mb"

[search]
pool_slots = 4
busy_timeout = "1s"
```

- `extensions` names which file extensions, without the leading dot, join the index alongside
  source files - `md`, `mdx`, and `txt` by default, prose formats with no syntax provider of
  their own; a visible file with no extension - `justfile`, `Dockerfile` - joins by default too,
  since no configured extension could ever match it, unless its first 8 KiB holds a NUL byte,
  which excludes it as a compiled artifact
- `max_chunk` bounds how large a file may grow before it's split into several indexed chunks,
  1kb to 16mb; an operator who wants a file out of the index entirely excludes it in
  [`[source]`](/docs/configuration#source) or drops its extension from `extensions`
- `pool_slots` bounds SQLite connections the lexical index may hold open at once, 1 to 16
- `busy_timeout` bounds how long one of those connections waits on SQLite's own lock before
  failing with `SQLITE_BUSY`, 100ms to 30s

<VersionBadge
  version="v0.0.16"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML"]}
/>

The two rankings are combined by reciprocal-rank fusion: a result scores as the weighted sum
of `1 / (k + rank)` over the rankings that returned it. `[search.lexical]` and
`[search.semantic]` carry the weights, `fusion_k` carries the `k`, and `[search.semantic]`
names the model the second ranking runs on:

```toml
[search]
fusion_k = 60

[search.lexical]
weight = 0.7

[search.semantic]
weight = 0.3
source = "hf"
model = "minishlab/potion-retrieval-32M"
download_timeout = "5m"
download_attempts = 3
batch_declarations = 32
max_tokens = 256
candidates = 200
candidates_per_file = 3
max_vectors = 200000
```

- `weight` is each ranking's share of a fused score, 0.0 to 1.0; the two must sum to 1, so
  each reads as a share of one whole
- `fusion_k` sets how sharply a top rank counts, 1 to 1000; a larger value flattens the
  contribution curve and lets agreement between the two rankings outweigh one ranking's top
  position
- `[search.semantic].source` names where the weights come from: `hf` downloads them from a
  Hugging Face repository and caches them where every other Hugging Face client on the
  machine caches them, `directory` reads a directory the workspace already holds and
  downloads nothing
- `model` names which weights, in the form the semantic tier's `source` sets: under `hf` a
  repository identifier such as `minishlab/potion-retrieval-32M`, optionally carrying a
  revision after `@`; under `directory` a workspace-relative directory. The server stores
  vectors per model - two models' vectors aren't comparable - so changing the value embeds
  the workspace again
- The model's own `config.json` decides how the server reads it. A `model_type` of
  `model2vec` names a static model, which embeds a declaration by averaging one row per
  token; anything else is read as a BERT checkpoint, which runs a forward pass per batch.
  The shipped default is static, because a forward pass over every declaration in a
  workspace costs minutes on a laptop CPU and a row gather costs seconds
- `download_timeout` and `download_attempts` bound one model acquisition, 10s to 1h and 1 to
  10; a spent budget leaves search lexical for the life of the server
- `batch_declarations` and `max_tokens` bound one embedding pass, 1 to 256 and 32 to 512.
  A BERT checkpoint's attention memory grows with the square of the token window, so a
  raised window wants a lowered batch; a static model reads one row per token, so its cost
  grows with the window rather than with its square
- `candidates` bounds how many declarations the semantic ranking returns before the two
  rankings are fused, 1 to 1000, and `candidates_per_file` bounds any one file's share of them
- `candidates_per_file` bounds how many declarations one file contributes to that list, 1 to
  64; the rest of the file's declarations are dropped, so one file whose declarations all rank
  well can't fill the list on its own and leave every other file unreachable
- `max_vectors` bounds how many vectors the workspace holds, 1000 to 1000000; each vector
  costs the model's dimension in single-precision floats

`disabled` keeps the workspace lexical without emptying the rest of the table. Set it where
the workspace must not fetch model weights:

```toml
[search.semantic]
disabled = true
```

## Engines

<VersionBadge version="v0.0.14" />

A [language engine](/docs/architecture#semantics) is an external language server Rift starts for
the workspace and speaks LSP to. Each `[engines.<name>]` table names one program, the languages
it serves, and the bounds Rift holds it to;
[`rename_symbol`](/docs/protocol/mcp#tool-rename_symbol) and
[`move_file`](/docs/protocol/mcp#tool-move_file) refuse `unsupported` for a language no table
claims, so the entry is what turns those tools on:

```toml
[engines.rust]
program = "rust-analyzer"
arguments = []
languages = ["rust"]
environment = {}
startup_timeout = "30s"
request_timeout = "1m"
output_limit = "4kb"

[engines.rust.retry]
attempts = 8
delay = "250ms"
delay_limit = "2s"

[engines.rust.restart]
attempts = 3
window = "5m"
```

`program` and `languages` have no default, `initialization_options` is absent unless you write
it, and the other keys are shown at theirs.

- `program` - refuses an absolute path; a bare name resolves through the `PATH` of the
  environment the engine runs with - the server's, with `environment` applied on top
- `arguments` - the program's literal arguments, in order; may be empty, and holds at most 64
- `environment` - values added on top of the environment the server inherited
- `languages` - the language identity segments this engine answers for, 1 to 16 of them; each
  segment belongs to one engine across the whole table
- `initialization_options` - a JSON object handed to the engine in its initialize request; Rift
  passes it through untouched and the engine defines what the keys mean
- `startup_timeout` - bounds the initialize handshake, 1s to 10m; an engine that doesn't finish
  it in time is killed
- `request_timeout` - bounds each later request, 1s to 10m
- `output_limit` - bytes of the engine's standard error Rift keeps, 1kb to 8mb; Rift still
  reports the full size, so you can tell a truncated log from a short one
- `retry.attempts` - times one request is asked while its answer stays unsettled, the first ask
  counted, 1 to 64; `1` never asks twice
- `retry.delay` - the wait before the second ask, 1ms to 1m; every later wait doubles the one
  before it
- `retry.delay_limit` - the longest wait between two asks, 1ms to 10m; the doubling stops here
- `restart.attempts` - engines Rift starts to replace a failed one inside `restart.window`, 0
  to 16; `0` never replaces one
- `restart.window` - the span those restarts are counted over, 1s to 1d

The table holds at most 16 engines. The server starts one on the first request for a language it
serves and keeps the session across later requests, because a language server pays for its
project load once and answers from it afterwards.

`retry` bounds what Rift does while an engine's answer is not settled, and three things leave it
unsettled.

A language server may decline a request it is already serving, or report that the file moved
under it while it was answering. LSP asks the client to send such a request again, so Rift does.

A server still loading your project answers anyway, and answers thinly: rust-analyzer reports no
diagnostics at all for a file it has not analyzed, and refuses a rename with `No references found
at position` for a declaration it has not indexed. Neither is its verdict. The engine says which
it is, because a language server announces the work it is doing over LSP's `$/progress`, so Rift
treats an answer that arrives while that work is outstanding as provisional: it discards the
answer and asks again.

Before the first announcement arrives there is nothing to read, and one shape of thin answer says
exactly what a settled engine says: a `move_file` the engine answers with no edit, and a
diagnostics pull it answers with no finding, are also what a loaded engine answers for a move
with no import to rewrite and for a file that is clean. An engine that has announced no work at
all is therefore asked one more time for such an answer - once per operation, once per engine
process, however many attempts `retry.attempts` allows. An engine that has announced work is
asked once: its silence is its own answer. And the second answer is the engine's answer too. A
move whose engine proposed nothing twice applies with a `rift.move.references_not_updated`
warning naming that engine, and a pull that reported nothing twice contributes nothing, as a
clean file does.

The waits grow from `delay` and stop growing at `delay_limit`, which keeps the resends off an
engine that is busy indexing. At the defaults a request waits at most 9.75s across its eight
asks, which covers a rust-analyzer cold start on a small project.

What the caller sees when the attempts run out depends on what was being asked. `rename_symbol`
and `move_file` ask before anything is written, so the call fails `temporarily_unavailable` with
the tree untouched, and the same request is worth sending again once the engine has loaded. The
diagnostics pull runs after the change has already applied, so it cannot fail the call: the
summary carries one warning naming the engine - `rift.engine.analyzing` when the engine never
finished, `rift.engine.failed` when it failed outright - rather than an empty finding list, which
would tell the caller the changed file is clean.

A refusal the settled engine did not invite again - it disagrees with the new name, it has no
such capability - is never resent.

`restart` bounds what Rift does when the engine itself fails: one that ended, that could not be
started, or that stopped answering is replaced automatically, and the replacement serves the
request. Each replacement spends one of `restart.attempts`, and a replacement older than
`restart.window` stops counting, so an engine that dies once a week never runs out. An engine
that crash-loops does: once the budget is spent, requests for its languages fail
`temporarily_unavailable` until the window passes, instead of starting a process that dies
again. The first engine a workspace starts is the start, not a replacement, and a refused
`program` - empty, or an absolute path - is reported at once rather than started again.

A `languages` entry is a language identity segment: a bare name such as `rust`, or
`name:dialect` to pin one dialect. Segments are how a symbol address spells its language, and a
declaration in a `.tsx` file is addressed under the dialect -
`rift://symbol/typescript:tsx/view.tsx/Banner`.

The server looks the engine up by that exact segment, so an engine that should serve those
declarations lists the dialect beside the bare name:
`languages = ["typescript", "typescript:tsx"]`. Without the dialect entry the same rename
refuses `unsupported`.

A segment no syntax provider knows is accepted, because the engine tier may serve a language the
syntax tier does not. A misspelled segment therefore fails nothing at load and simply never
matches an address.

A minimal engine needs only `program` and `languages`. This table names
[tombi](https://github.com/tombi-toml/tombi), a TOML formatter, linter, and language server:

```toml
[engines.toml]
program = "tombi"
arguments = ["lsp"]
languages = ["toml"]
```

`lsp` is the subcommand that starts tombi's language server over stdio.

An engine that ships as a package runs through its package runner. This table serves both
TypeScript dialects through `bunx`, with the language server version pinned so a registry
publish can't move it under you:

```toml
[source]
exclude = ["node_modules/**"]

[engines.typescript]
program = "bunx"
arguments = ["typescript-language-server@6.0.0", "--stdio"]
languages = ["typescript", "typescript:tsx"]

[engines.typescript.initialization_options.tsserver]
useSyntaxServer = "never"
```

typescript-language-server refuses its initialize request unless a `typescript` package resolves
from the workspace root, answering `Could not find a valid TypeScript installation`. Install that
package in the workspace, or name an existing one with the `tsserver.path` initialization option;
without either, every rename and move for the language fails on the engine's own words.

`[source] exclude` keeps the installed package directory out of the index. Without it the walk
reaches `typescript`'s own sources and the first change fails with `limit_exceeded` on
`node_modules/typescript/lib/_tsc.js`, which is past the index's per-file byte bound. Any
workspace with an installed package directory needs the same entry.

`tsserver.useSyntaxServer = "never"` keeps the engine to one semantic server. Under the default
`auto` it also runs a syntax-only server, and that one can answer the first rename after startup
from the open file alone - the observed cold answer renamed the declaration and left both
importers standing. With one semantic server the rename waits for the loaded project and reaches
every file.

## Hooks

<VersionBadge version="v0.0.5" />

`hooks` adds your own checks, run in your workspace each time a change applies. A hook's
`type` selects how it runs; `command` - an executable Rift starts directly, without a
shell - is the only type:

```toml
[[hooks]]
type = "command"
id = "tests"
kind = "test"
program = "cargo"
arguments = ["test"]
changed_paths = "none"
working_directory = ""
environment = {}
timeout = "120s"
output_limit = "4kb"
guarantees = []
determinism = "deterministic"
```

The keys that shape how the command runs:

- `id` - unique within the list, labels the result
- `program` - refuses an absolute path; a bare name resolves through the `PATH` of the
  environment the command runs with - the server's, with `environment` applied on top - and a
  relative one below `working_directory`
- `working_directory` - relative to the workspace root; its empty value selects the root
- `arguments` - the program's literal arguments, in order; may be empty
- `changed_paths` - `"append"` adds the changed project paths after `arguments` in byte order,
  for a linter that takes files; `"none"` leaves the command alone

A hook runs in the tree it checks, so it executes the agent's change each time one applies -
`cargo test` compiles the very change it's checking.

Every key in the block is required - the schema carries no defaults, so a missing `environment`
fails the file with `configuration_invalid`. The list holds at most 32 hooks.

Two keys carry bounds: `timeout`, when Rift kills the process, takes `"1ms"` to `"1h"`, and
`output_limit`, how much of each stream Rift keeps, takes `"256b"` to `"4kb"`. Rift still
reports the full size, so you can tell a truncated log from a short one.

`guarantees` declares what a pass establishes, which turns a passing run into
[`GuaranteeEvidence`](/docs/protocol/reference#GuaranteeEvidence) on the change. Each entry
names the property (`kind`), what the check covers (`scope`), and the claim in words
(`detail`); the evidence on the change carries them alongside the hook's `id`. `determinism`
says whether the same tree and environment are expected to give the same answer twice.

A hook that exits nonzero, overruns `timeout`, or fails to launch contributes an error
finding under the code `rift.hook.failed`, naming what ended the run and quoting each non-empty
stream with its size. The change itself stays applied - hooks observe a change that has already
landed, so their verdicts ride the result instead of rolling it back.

A command starts from the environment the server inherited, with `environment` values added on
top. Store secrets outside the committed `rift.toml` and inject them into the server environment.
Every configured hook inherits that environment and can read those secrets.

<Callout type="warn">
A hook can write into the tree it checks - a formatter run as a hook edits your files directly,
and reads after the change serve what it wrote.
</Callout>
