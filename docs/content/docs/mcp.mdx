The main interface for agents to work with rift is the Model Context Protocol, aka
[MCP](https://modelcontextprotocol.io/specification/2026-07-28). The local `rift mcp` process is
launched via a CLI command by your agent (see [Usage](/docs/agentic-usage)).

<Accordions className="text-sm">
<Accordion title="Details">

We're using MCP because it's the de-facto standard in the agent infrastructure. However, MCP
requests are stateless, while rift needs a live local index running in the background.

Therefore, we start a long-running `rift server`, which can handle multiple MCP clients (agents)
and starts automatically. See [CLI commands](/docs/developer/implementation#rift-server) for server
controls.

</Accordion>
</Accordions>

Rift follows the MCP specifications, and all inputs and structured outputs have a strictly defined
JSON schema, available [here](https://volar.sh/rift/mcp.json).

An agent working on an unfamiliar project first needs to understand its structure, then find
and read the code relevant to its task. Rift provides context before an edit and updates its
local index as the agent changes project files, ready for the next read.

## Map [#resource-map]

Before searching, the agent is advised to read the map.
The map describes the project that the local index serves: its directories, languages,
documentation paths, and dependencies.

For any task, directories help the agent choose where to search.
Documentation paths point to project guidance, while dependency entries identify the packages
and versions used by the project.

The map's `recommendations` section lists installed language servers that the configuration has
not selected. Each entry carries `language`, `root`, and a `command` to apply with `rift config set`
from the map project's root.
After the configuration is accepted, the next map publication leaves that entry out.

## Search [#tool-search]

`search` evaluates SPARQL over the facts Rift holds. The request carries `query` and an
optional `language`, whose default is `sparql`:

<ReadExample name="select-symbols" />

The empty prefix names `urn:rift:vocabulary:`. `r:`, `rdf:`, `rdfs:`, and `xsd:` are also
available. An explicit `PREFIX` declaration can name another namespace.

`SELECT` returns typed bindings, `ASK` returns a boolean, and `CONSTRUCT` and `DESCRIBE`
return triples. The selected variables are the answer's columns. An unbound variable is
absent from its row. An IRI, blank node, literal with a datatype, and literal with a language
remain distinct terms.

### Names and declarations

A name is a fact rather than a ranking request:

<ReadExample name="symbol-name" />

A symbol's IRI is its canonical identity. A syntax element relates to its symbol through `:of`
and can carry a `:range` and `:source`. Pass the symbol IRI to `get_symbol` for its declarations,
or to `facets` for its syntax and source at a selected revision.

### Full-text search [#search-fulltext]

`SERVICE :search` exposes the existing full-text and identifier ranking:

<ReadExample name="full-text" />

The service's `:query` is the ranked text. The outer request's `query` is SPARQL.
Project `:source` or `:score` when needed. Use outer `ORDER BY`, `LIMIT`, and `OFFSET`
to order and select the rows. The service's `:max_results` and `:page` select a producer page
before SPARQL evaluates filters, joins, and aggregates.

### Hybrid search [#search-hybrid]

The same service combines identifier matching, full-text matching, and available vector
ranking. Existing [search configuration](/docs/developer/configuration#search) controls
weights, model selection, and indexed text. A query requiring unavailable or incomplete
ranking facts returns typed unavailability.

### Regex search [#search-pattern]

Use `:pattern` in the service to select every regex match:

<ReadExample name="regex" />

Matching uses Rust regex syntax and the existing trigram index, then verifies the selected
text. File results keep each physical match and its UTF-8 byte range. Producer bounds
remain in effect. A truncated acquisition cannot establish a complete SPARQL answer.

### Paths and package scope [#search-scope]

A service can select `:scope "global"` for collected dependency facts, or `:scope "all"`
for the accepted project and dependency contexts. `:paths`, `:packages`, and `:change`
carry their existing structured values as `rdf:JSON` literals. `:rev` selects a supported
committed revision. The [protocol reference](/docs/developer/protocol/mcp#search-scope)
describes selection and refusal behavior.

`:packages` names releases beside the ones the workspace depends on. Each entry names its
`manager`, `registry`, and `name`, and an optional exact `version`. Without one, the newest
collected release answers:

<ReadExample name="package-scope" />

The server refuses a `:packages` value written as a plain string, and an entry that names no
`registry`. A workspace whose [`[search] default_scope`](/docs/developer/configuration#search)
is `global` reads this service with no `:scope`.

Global edge queries read facts already collected for the selected package or runtime.

The local example project runs with the Global connection disabled. Its response shows what
happens when the named package index cannot be read.

### Edge provider

Read answers merge edges with the same source, exact kind, target, and physical occurrence.
They omit the [analyses that produced each edge](/docs/developer/protocol/core#edge-provider)
by default. The edge's `derivation` records how it was established, and optional `producer`
names an external producer.

`include: { providers: true }` attaches the sorted `providers` set to returned edge terms
and call steps. `SELECT` projects the edge or call step identity to carry that set. Explicit SPARQL bindings and filters on `:provider` keep their
selected producer facts.

A query can check for edges from static analysis with `:provider`:

<ReadExample name="edge-provider" />

The same pattern checks for embedded engine edges with `"engine"` or LSP edges with `"lsp"`.

### References and calls [#search-traversal]

These requests find `load_config` by name and use its canonical identity to traverse the graph.

<ReadExample name="physical-usages" />

Each usage is a physical occurrence. Repeated uses inside one declaration and uses at file
scope remain separate rows. Its enclosing declaration, when available, is a separate fact.

<ReadExample name="references" />

<ReadExample name="calls" />

<ReadExample name="transitive-references" />

Property paths express fixed depth, alternatives, and closure. SPARQL owns path and
binding semantics. A fixed two-step path can reach a symbol also reachable in one step.
Use `DISTINCT` when the question needs distinct endpoints.

### Language-engine references [#search-engine-references]

Local reference and call questions use the configured
[language engine](/docs/developer/configuration#languages-and-lsp) when required facts
are absent from the captured publication. Acquisition preserves physical locations and
continues through admitted dependency sources. These facts belong to the request and do
not enter global collection. Captured static calls and references answer first, and an
`engine_analysis_unavailable` warning names a language whose engine analysis is missing.

### Changes and commits [#search-change]

Revision comparisons use `SERVICE :search` with a `:change` JSON literal. Project the
returned change record's kind and base and head paths. The comparison producer preserves
its existing revision, history, and change bounds.

<ReadExample name="changes" />

### Commit messages [#search-commits]

Use `:target "commit"` and `:query` inside the service. Commit records retain their message,
author, timestamp, revision, and ordered paths. SPARQL chooses which fields to project.
An incomplete history store cannot establish a complete answer.

<ReadExample name="commits" />

### Paging and retained results

`page` starts at 1 and defaults to 1. `max_results` defaults to 10. The response carries
`pagination: { page, pages, max_results, total }`. A page past the last returns an empty list.
Send the returned `revision` with later pages. SPARQL `LIMIT` and `OFFSET` bound the result
set before paging. `ASK` returns a boolean without pagination.

## Symbols [#tool-get_symbol]

Search discovers a symbol and returns its canonical `id`. `get_symbol` reads that exact
logical symbol. Ownership and language come from the address.

The example project declares `load_config` in `src/config.rs`. Its identity names the Rust
crate and declaration, rather than the physical file:

<ReadExample name="local-symbol" />

The result carries `outcome: "found"`, one `symbol`, the `revision` it was read at, and
`declarations` in deterministic source order. Each declaration keeps its own origin,
source address, byte range, and indices into the symbol's signatures, types, and documentation.
Every declaration of one qualified path, such as two `cfg` variants of one Rust function, is a binding of that one logical symbol. A source-less object can
be found with no declarations. A runtime symbol, such as `readFile` in Node's `fs` module, reads
the same way, and its `revision` names the runtime release:

<ReadExample name="runtime-symbol" />

Use the `include` object to select optional projections, such as
`"include": {"documentation": true, "history": true}`:

| Member | Adds when `true` |
| --- | --- |
| `documentation` | Bounded documentation referring to the exact declaration |
| `history` | The logical symbol's history edges: the commits that touched a project symbol and the symbols changed beside it, or the releases that changed a package or runtime symbol |

The members combine. An omitted member is `false`, and an omitted `include` adds neither. A
declaration's source comes from [`facets`](#tool-facets) with the symbol's `id`.

`history` answers edges from the symbol. The commit edges come first, newest first, each naming
its commit as a `rift://revision/git/<commit>` revision with the commit's author and the path the
declaration lived at:

- `introduced_in` - the commit brought the symbol into existence
- `changed_in` - the commit changed the declaration in place. `change` says whether the
  signature, the body, or the decorators changed
- `renamed_from` - the commit moved the declaration unchanged. `from` is the path it came from
- `removed_in` - the commit deleted the declaration

The `co_changes` edges follow, most shared commits first: each names a symbol the listed commits
changed beside this one and how many of them did. A commit that changed more than 256
declarations, such as a sweeping rename, counts toward no co-change edge, and one history answers
at most 32 of them. `co_changes_truncated` counts what either bound left out.

The local server fills its history store in the background. An incomplete history answers
`complete: false` until the store holds the selected revision.

A package or runtime symbol has no commits in your project, so its `history` names releases
instead. Rift reads it from the global API: the collected releases of the symbol's owner that
introduced, changed, or removed its declaration, newest release first. Each edge names its
release as a revision such as `rift://revision/cargo/crates.io/demo@1.0.0`:

- `introduced_in_release` - the oldest collected release that declares the symbol
- `changed_in_release` - the release changed the declaration from the collected release before
  it. `change` names the part, as it does for `changed_in`
- `removed_in_release` - the release no longer declares the symbol the release before it declared

A release history carries no `co_changes` edges. `complete: false` means the history stopped
before the oldest collected release of the owner.

## Facets [#tool-facets]

`facets` reads every declaration of a symbol with its location, source, and syntax structure.
The agent passes the symbol identity returned by `search` or `get_symbol`:

<ReadExample name="symbol-facets" />

Each declaration carries exact source and its syntax tree.
`declaration` is its ordinal among the symbol's declarations. A syntax element's `index`
is its pre-order position within that declaration, from the root at 0. `parent` names the
index of the element around it. Nested declarations have their own facets.

For a package or runtime symbol, Rift reads the global API at the release `revision`
names, or at the version the project's dependencies pin when the request names none.
The declaration's `source.span.unit` names its source unit, such as
`rift://source/cargo/crates.io/itoa/src/lib.rs`.

Send `page` with the same symbol and revision to read later declarations.

## Feedback [#tool-feedback]

`feedback` sends a report from the local Rift server to the public Rift intake at
`https://feedback.volar.sh/rift/feedback/v1/reports`. To use another HTTPS intake, set
`RIFT_FEEDBACK_URL` to its full URL in the environment that starts the server. An empty value
turns submission off. If a workspace server is already running, restart it from that environment
for the change to apply.

Describe the Rift behavior and what the caller expected. A report can include a short,
redacted Rift error or response excerpt. Before including an exact excerpt from the
conversation, show the user that excerpt and get approval to send it in this report.

```json
{
  "text": "The facets tool returned an empty result for a symbol it found.",
  "include": {"os": true, "rift_version": true}
}
```

The server sends the diagnostic fields set to `true` in `include`. Omit it to send the text alone.
See the [feedback reference](/docs/developer/protocol/mcp#tool-feedback) for the payload and failure behavior.

## Edits and index updates [#edit-and-index-updates]

As the agents edit the codebase, rift watches the project files and updates the local index
when they change, so the next read can use the new code.

`search` also reaches collected package and runtime facts. `get_symbol` reads the exact
owner named in its canonical identity. Edits to project source update
the local index. See [Index](/docs/developer/architecture#index) for local updates and
[package scope](/docs/developer/protocol/mcp#get_symbol-scope) for dependency reads.

## Reading results [#reads]

`search` projects the variables named in `SELECT`, returns a boolean for `ASK`, or returns
RDF triples for a graph query. `page` and `max_results` select answer rows. Exact `get_symbol`
and `facets` reads select declarations with the same pair at the reported revision.

A query over the captured inventory answers from partly covered facts, and its `warnings` name
the files, languages, or engines left out. A query whose answer needs every fact returns
`outcome: "unavailable"` with `insufficient_coverage`: an empty result, a false `ASK`, a count,
a negation, or an `OPTIONAL`. Run `rift server logs` to inspect missing facts or preparation
still in progress.

The proxy returns compact text by default. Start `rift mcp --output=all` for structured
results and output schemas. The map and workspace resources then carry both compact text
and JSON.

The [result content reference](/docs/developer/protocol/mcp#result-content) defines the form.

<Accordions>
<Accordion title="Earlier revisions" id="revision-reads">

Every `get_symbol` and `facets` answer names the revision it was read at, such as
`rift://revision/tree/<digest>` for the working tree the index serves. The agent can read older
project code by adding `revision` to either tool. For example, this reads the function from
`main` without changing the working tree:

```json
{
  "id": "rift://symbol/local/rust/example_project/config/load_config",
  "revision": "rift://revision/git/main"
}
```

The server resolves `main` to its commit, and the answer reports that commit, such as
`rift://revision/git/1f2080e49da12fee4431e6872630509355cd62d1`, so a later read can name the
same point. Git's `~` ancestry suffix works too, so `rift://revision/git/HEAD~1` reads the commit
below `HEAD`. Revision reads use committed source and require a Git repository.

A tree revision pins a read to the working tree an earlier answer reported. Once the project
changes and the index serves another tree, the server refuses that read with
`resource_not_found` instead of answering from the newer tree.
See [revision-addressed reads](/docs/developer/protocol/mcp#revision-reads) for configuration
and argument constraints.

</Accordion>
<Accordion title="Errors" id="errors">

When a call fails, the agent gets a result marked as an error instead of an answer. Its text is one
section, titled with the count of errors, that lists the failure first and then its causes,
outermost first. Each entry names its `code` and a `retry` directive, which says whether sending
the same request again can help, and the line below states what failed:

<Tabs items={["invalid_request", "limit_exceeded", "causes"]}>

<Tab value="invalid_request">

**Tool execution failure, compact text** of a request whose `max_results` is below 1:

```text
1 error
	invalid_request · retry never
		the request does not match the documented form: field max_results, violation expected 1..=10000, received 0; correct the reported field and resend the request
```

</Tab>

<Tab value="limit_exceeded">

**Tool execution failure, compact text** of a request that crosses a limit on `source.files`, with one cause:

```text
2 errors
	limit_exceeded · retry never
		the request crosses a limit
		limit source.files: 11 over 10
	storage_failure · retry same_request
		the store refused
```

</Tab>

<Tab value="causes">

**Tool execution failure, compact text** of a history store that could not be opened, with two causes:

```text
3 errors
	storage_failure · retry same_request
		history store database operation failed: open: unable to open database file; check the history store database and retry
	storage_failure · retry same_request
		unable to open database file
	storage_failure · retry same_request
		Permission denied (os error 13)
```

</Tab>

</Tabs>

- `retry never` tells the agent to change its arguments first. `retry same_request` says the same
  request can succeed later.
- A `limit_exceeded` failure adds the limit it crossed, `limit source.files: 11 over 10`, so the
  agent can resize the request.
- The `retry` of the first entry governs the call. A cause's `retry` says what could be done
  about that cause.

See [tool execution failures](/docs/developer/protocol/mcp#tool-execution-failures) for the other
directives and the complete form.

</Accordion>
</Accordions>

The workspace resource comes as compact text, in the same form as a tool result:

**`rift://workspace`, compact text** of a workspace with one TypeScript language and one source file:

```text
workspace
languages:
	typescript:tsx · syntax · lsp typescript:tsx ready
		include src/**/*.tsx
		exclude src/generated/**
source:
	src/view.tsx · typescript:tsx
```


The workspace text lists effective languages with their include and exclude patterns, then
lists source paths with their languages. Follow the next URI when the catalog spans pages.

the JSON body a read carries.
