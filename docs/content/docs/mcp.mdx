The main interface for agents to work with rift is the Model Context Protocol, aka
[MCP](https://modelcontextprotocol.io/specification/2026-07-28). The local `rift mcp` process is
launched via a CLI command by your agent (see [Usage](/docs/agentic-usage)).

<Accordions className="text-sm">
<Accordion title="Details">

We're using MCP because it's the de-facto standard in the agent infrastructure. However, MCP
requests are stateless, while rift needs a live local index running in the background.

Therefore, we start a long-running `rift server`, which can handle multiple MCP clients (agents)
and starts automatically. See [CLI commands](/docs/developer/implementation#rift-server) for server
controls.

</Accordion>
</Accordions>

Rift follows the MCP specifications, and all inputs and structured outputs have a strictly defined
JSON schema, available [here](https://volar.sh/rift/mcp.json).

An agent working on an unfamiliar project first needs to understand its structure, then find
and read the code relevant to its task. Rift provides context before an edit and updates its
local index as the agent changes project files, ready for the next read.

## Map [#resource-map]

Before searching, the agent is advised to read the map.
The map describes the project that the local index serves: its directories, languages,
documentation paths, and dependencies.

For any task, directories help the agent choose where to search.
Documentation paths point to project guidance, while dependency entries identify the packages
and versions used by the project.

The map's `recommendations` section lists installed language servers that the configuration has
not selected. Each entry carries `language`, `root`, and a `command` to apply with `rift config set`
from the map project's root.
After the configuration is accepted, the next map publication leaves that entry out.

The [map reference](/docs/developer/protocol/mcp#resource-map) describes additional facts, such as
entry points and relationships, and when they are available. It also shows a map as compact text.

## Search [#tool-search]

`search` evaluates SPARQL over the facts Rift holds. The request carries `query` and an
optional `language`, whose default is `sparql`:

```json
{ "query": "SELECT ?symbol ?name { ?symbol a :Symbol; :name ?name } ORDER BY ?name LIMIT 10" }
```

The empty prefix names `urn:rift:vocabulary:`. `rdf:`, `rdfs:`, and `xsd:` are also
available. An explicit `PREFIX` declaration can name another namespace.

`SELECT` returns typed bindings, `ASK` returns a boolean, and `CONSTRUCT` and `DESCRIBE`
return triples. The selected variables are the answer's columns. An unbound variable is
absent from its row; an IRI, blank node, literal with a datatype, and literal with a language
remain distinct terms.

### Names and declarations

A name is a fact rather than a ranking request:

```sparql
SELECT ?symbol ?kind {
  ?symbol a :Symbol; :name "load_config"; :kind ?kind
}
```

A symbol's IRI is its canonical identity. Its declarations carry source units, paths, ranges,
and available source. Use returned identities with `get_symbol`. Read source units through `SERVICE :source`,
carrying the original captured view ID in its `:view` input to retain the selected bytes.

### Full-text search [#search-fulltext]

`SERVICE :search` exposes the existing full-text and identifier ranking:

```sparql
SELECT ?symbol ?name ?source {
  SERVICE :search {
    ?hit :query "load project settings"; :target "symbol";
         :symbol ?symbol; :source ?source .
    ?symbol :name ?name
  }
}
LIMIT 5
```

The service's `:query` is the ranked text. The outer request's `query` is SPARQL.
Project `:source` or `:score` when needed. Use outer `ORDER BY`, `LIMIT`, and `OFFSET`
to order and select the rows. The service acquires the producer pages the query needs
before SPARQL evaluates filters, joins, and aggregates.

### Hybrid search [#search-hybrid]

The same service combines identifier matching, full-text matching, and available vector
ranking. Existing [search configuration](/docs/developer/configuration#search) controls
weights, model selection, and indexed text. A query requiring unavailable or incomplete
ranking facts returns typed unavailability with warnings.

### Regex search [#search-pattern]

Use `:pattern` in the service to select every regex match:

```sparql
SELECT ?path ?start ?end ?source {
  SERVICE :search {
    ?hit :pattern "tokio::[A-Za-z_]+"; :target "file";
         :path ?path; :start ?start; :end ?end; :source ?source
  }
}
ORDER BY ?path ?start
```

Matching uses Rust regex syntax and the existing trigram index, then verifies the selected
text. File results keep each physical match and its UTF-8 byte range. Producer bounds
remain in effect; a truncated acquisition cannot establish a complete SPARQL answer.

### Paths and package scope [#search-scope]

A service can select `:scope "global"` for collected dependency facts, or `:scope "all"`
for the accepted project and dependency contexts. `:paths`, `:packages`, and `:change`
carry their existing structured values as `rdf:JSON` literals. `:rev` selects a supported
committed revision. The [protocol reference](/docs/developer/protocol/mcp#search-scope)
describes selection and refusal behavior.

`FROM`, `FROM NAMED`, and `GRAPH` select accepted datasets. A query naming an unknown
or unavailable dataset refuses before evaluation. A deployment serves its collected facts;
query evaluation does not collect or backfill global language-engine facts.

### References and calls [#search-traversal]

A canonical symbol identity anchors a graph question. These requests use a returned
identity in place of `<symbol-id>`:

```sparql
SELECT ?usage ?unit ?start ?end {
  <symbol-id> :usages ?usage .
  ?usage :unit ?unit; :start ?start; :end ?end
}
```

Each usage is a physical occurrence. Repeated uses inside one declaration and uses at file
scope remain separate rows. Its enclosing declaration, when available, is a separate fact.

```sparql
SELECT ?caller { ?caller :references <symbol-id> }
SELECT ?callee { <symbol-id> :calls/:calls/:calls ?callee }
SELECT ?caller { <symbol-id> ^:references+ ?caller }
```

Property paths express fixed depth, alternatives, and closure. SPARQL owns path and
binding semantics; a fixed three-step path can reach a symbol also reachable in one step.
Use `DISTINCT` when the question needs distinct endpoints.

### Language-engine references [#search-engine-references]

Local reference and call questions use the configured
[language engine](/docs/developer/configuration#languages-and-lsp) when required facts
are absent from the captured publication. Acquisition preserves physical locations and
continues through admitted dependency sources. These facts belong to the request and do
not enter global collection. Missing coverage refuses the query; it cannot produce a false
`ASK`, zero count, or empty graph.

### Changes and commits [#search-change]

Revision comparisons use `SERVICE :search` with a `:change` JSON literal. Project the
returned change record's kind and base and head paths. The comparison producer preserves
its existing revision, history, and change bounds.

### Commit messages [#search-commits]

Use `:target "commit"` and `:query` inside the service. Commit records retain their message,
author, timestamp, revision, and ordered paths. SPARQL chooses which fields to project.
An incomplete history store cannot establish a complete answer.

### Paging and retained results

The response's `pagination.next_query` is the next request's SPARQL statement. Send it
unchanged as `query` to read the next transport page of the original execution. A source
edit does not replace its rows, blank nodes, or selected source bytes.

The retained result service `urn:rift:result:<view-id>` exposes the whole original answer
for a new SPARQL question, such as `COUNT`, a filter, or a join. It has the original view's
expiry. Expiry or incompatible captured contexts refuses instead of reading a new
publication. Transport paging is separate from SPARQL `LIMIT` and `OFFSET`.

See the [protocol reference](/docs/developer/protocol/mcp#search) for result terms, bounds,
required facts, and migration from the former selector fields.

Use `include` to select optional projections:

| Include | Adds |
| --- | --- |
| `source` | Declaration source and node identity when available |
| `documentation` | Bounded documentation referring to the exact declaration |
| `history` | The logical symbol's version-control timeline |

Omitted `include` defaults to `["source"]`; an explicit empty list requests none of these
projections. `history` lists the revisions that changed the symbol, newest first, with each
commit's author. The local server fills its history store in the background; an incomplete
timeline answers `complete: false` until the store holds the selected revision.

Pass a preceding `view` to retain its immutable selection. Expiry refuses the read instead
of selecting latest implicitly. `declaration_limit` bounds returned declarations; a returned
`declaration_cursor` continues the same symbol, projections, and view. It is not hit paging.

## Source reads [#source-reads]

`SERVICE :source` reads one physical source unit independently of whether a declaration exists.
The request uses the same `query` and optional `language` as other SPARQL queries:

```sparql
SELECT ?outcome ?text ?complete {
  SERVICE :source {
    ?read :unit <rift://source/project/README.md>; :outcome ?outcome .
    OPTIONAL { ?read :source [ :text ?text ]; :source_complete ?complete }
  }
}
```

Omit `:range` to read the whole unit. A half-open UTF-8 byte range uses an `rdf:JSON` literal:

```sparql
SELECT ?outcome ?text ?start ?end {
  SERVICE :source {
    ?read :unit <rift://source/project/README.md>;
          :range '{"start":0,"end":4}'^^rdf:JSON; :outcome ?outcome .
    OPTIONAL {
      ?read :source [ :text ?text; :span [ :range [ :start ?start; :end ?end ] ] ]
    }
  }
}
```

Use an observed source-unit IRI. A captured read adds `:view` with the original captured view ID.
The projected source result retains that selection and its expiry; the surrounding query retains
its own result view for paging. A missing source binds `:outcome` to `"missing"`. Unavailable or
incomplete source material prevents evaluation, including under `SERVICE SILENT`.

## Nodes [#tool-nodes]

`nodes` accepts `query` and optional `language`, and uses the same SPARQL engine and vocabulary
as `search`. Syntax facts retain their original source unit, byte range, kind, parent and named
regions. A node's `:symbol` connects it to an established semantic identity when available.

Read captured syntax fields from one source unit:

```sparql
SELECT ?node ?kind ?start ?end {
  ?node a :Node; :unit <rift://source/project/src/config.rs>; :kind ?kind;
        :range [ :start ?start; :end ?end ] .
}
ORDER BY ?start DESC(?end)
```

<ReadExample name="local-nodes" />

The projected variables determine the answer. Required syntax facts must already belong to the
selected capture. A missing syntax family returns typed unavailability; evaluation does not
parse current files to fill it. The agent applies changes with its own editing tools.

## Edits and index updates [#edit-and-index-updates]

As the agents edit the codebase, rift watches the project files and updates the local index
when they change, so the next read can use the new code.

`search` also reaches collected package and runtime facts. `get_symbol` reads the exact
owner named in its canonical identity; edits to project source update
the local index. See [Index](/docs/developer/architecture#index) for local updates and
[package scope](/docs/developer/protocol/mcp#get_symbol-scope) for dependency reads.

## Reading results [#reads]

SPARQL `LIMIT` and `OFFSET` select the query window. The returned `pagination` carries
`next_query` when another transport page remains; submit it unchanged. An exact `get_symbol`
read bounds declaration bindings with `declaration_limit` and continues with
`declaration_cursor` in the same immutable `view`.

Warnings explain when an answer is incomplete or a capability could not contribute.
For example, `stale_index` reports an index behind the captured project state or a rebuild failure;
`results_truncated` means a narrower query or path selection can bring results within the bound.
Large files and lockfiles carry their own: `large_file_unparsed` names a file too large to parse,
whose text still answers, `large_file_skipped` counts files left out of text search, and
`lockfile_excluded` names a lockfile the path selection reached but search leaves out.
The [read reference](/docs/developer/protocol/mcp#reads) describes each warning.

The agent reads each answer as compact text. The text is a list of sections, and each section
starts with a title that counts its entries, such as `2 results` or `1 warning`, with the entries
indented under it. Warnings form their own section after the items:

<ReadExample name="local-search" />

A symbol hit shows its declaration, location and matched fields, canonical identity when
established, and requested source. A warning names its `code`, payload facts, and optional
detail. An exact read uses its outcome and declaration bindings instead of a hit count:

Compact text prints only what stands out, such as a requested `score`, a dependency origin, or a
truncated history. `rift mcp` returns compact text by default. A program that needs every field as JSON starts
`rift mcp --output=all`, which includes structured output and output schemas in the tool listing.
The workspace resource then carries both compact text and JSON. The map always returns JSON.

The [result content reference](/docs/developer/protocol/mcp#result-content) defines the form.

<Accordion title="Earlier revisions" id="revision-reads">

`get_symbol` accepts `rev` for older project code. Source reads and search producers accept
`:rev` inside `SERVICE :source` and `SERVICE :search`. For example, this reads the function
from `main` without changing the working tree:

```json
{ "id": "rift://symbol/local/rust/example_project/config/load_config", "rev": "main" }
```

Git's ancestry suffixes work too, so `"rev": "HEAD~1"` reads the commit below `HEAD`.
Revision reads use committed source from a branch, tag, or commit and require a Git repository.
See [revision-addressed reads](/docs/developer/protocol/mcp#revision-reads) for configuration
and argument constraints.

</Accordion>
<Accordion title="Errors" id="errors">

When a call fails, the agent gets a result marked as an error instead of an answer. Its text is one
section, titled with the count of errors, that lists the failure first and then its causes,
outermost first. Each entry names its `code` and a `retry` directive, which says whether sending
the same request again can help, and the line below states what failed:

**Tool execution failure, compact text** of a request whose `limit` is below 1:

```text
1 error
	invalid_request · retry never
		the request does not match the documented form: field limit, violation zero; correct the reported field and resend the request
```

</Tab>

<Tab value="limit_exceeded">

**Tool execution failure, compact text** of a request that crosses a limit on `source.files`, with one cause:

```text
2 errors
	limit_exceeded · retry never
		the request crosses a limit
		limit source.files: 11 over 10
	storage_failure · retry same_request
		the store refused
```

</Tab>

<Tab value="causes">

**Tool execution failure, compact text** of a history store that could not be opened, with two causes:

```text
3 errors
	storage_failure · retry same_request
		history store database operation failed: open: unable to open database file; check the history store database and retry
	storage_failure · retry same_request
		unable to open database file
	storage_failure · retry same_request
		Permission denied (os error 13)
```

</Tab>

- `retry never` tells the agent to change its arguments first; `retry same_request` says the same
  request can succeed later.
- A `limit_exceeded` failure adds the limit it crossed, `limit source.files: 11 over 10`, so the
  agent can resize the request.
- The `retry` of the first entry governs the call; a cause's `retry` says what could be done
  about that cause.

See [tool execution failures](/docs/developer/protocol/mcp#tool-execution-failures) for the other
directives and the complete form.

The workspace resource comes as compact text, in the same form as a tool result:

**`rift://workspace`, compact text** of a workspace with one TypeScript language and one source file:

```text
workspace 3f9a1c2e
languages:
	typescript:tsx · syntax · lsp typescript:tsx ready
		include src/**/*.tsx
		exclude src/generated/**
source:
	src/view.tsx · typescript:tsx · 8a4d20bc
```


- The workspace text starts with the digest of the accepted `rift.toml`, then lists each language
  with its include and exclude patterns, and each source file with its language and content
  digest.
