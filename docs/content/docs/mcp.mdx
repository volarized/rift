`rift mcp` serves MCP over stdio for harnesses that launch servers as subprocesses. Stdout carries
MCP frames; the process writes tracing events to stderr.

Requests do not open connection-scoped sessions. Each request carries its arguments; the server holds no per-caller state between calls.

A tool result rides MCP
[`structuredContent`](https://modelcontextprotocol.io/specification/draft/server/tools#structured-content),
typed by the tool's declared output schema, with the
same JSON mirrored as a `text` block for harnesses that ignore it.
[`ErrorData`](/docs/developer/protocol/reference#ErrorData) travels as the
[JSON-RPC error](https://www.jsonrpc.org/specification#error_object)
object's `data`, under code `-32000`. The exported schema at
[`mcp.json`](https://volar.sh/rift/mcp.json) is the authoritative served shape.

## Reads

Callers read code through these tools:

| Tool | Result |
| --- | --- |
| [`get_symbol`](#tool-get_symbol) | declarations and their source by known name |
| [`search`](#tool-search) | ranked files and symbols across the workspace tree |
| [`nodes`](#tool-nodes) | the syntax nodes covering one position, with byte ranges |

The index never follows or indexes a symlink, so no read returns one; the file a link points
at answers under its own path.

`get_symbol` and `search` page by `page_index`. The request names the zero-based page under its
`limit`, at most 10,000, and the result's `pagination` carries the served `page_index` and the
true `total_pages`; a larger `limit` is refused as `invalid_request` naming the field. The server
retains no capture between pages: each page is computed from the request, and a `page_index` past
the last page returns an empty page whose `pagination` still carries the true `total_pages`.

Every read result also carries `warnings`. A `stale_index` warning reports an answer computed
from an index that lags the tree the read captured, and names the two tree revision digests that
disagree.

A read served while the last rebuild's failure stands carries `stale_index` too, with a `detail`
naming the failure; the next filesystem event retries the rebuild. When its two digests are equal,
the tree moved in recorded files outside the syntax-indexed ones or in the configuration file, and
`detail` says which.

The search ranking tiers carry their own warnings:

- `vector_index_preparing` - the vector ranking holds no vectors for the tree this answer
  was read from: the pass over that tree is still running, or the tree was published after
  the corpus the ranking holds was described. A query sharing no token with the code it
  describes reaches nothing until that pass lands; `prepared` and `total` state how far it
  has got, and an answer carrying no such warning is one the vector ranking took part in.
- `vector_ranking_unavailable` - the vector ranking will not answer for the life of this
  server: the model weights could not be acquired, or the model failed to load.
- `lexical_ranking_unavailable` - the full-text tier has not yet committed the captured tree,
  missed a commit, failed to load, or holds no indexed tree; the `detail` names which, and the
  tree revision. Ranking falls back to identifier matching, so a query phrased as prose finds
  nothing; the tier is read under the answer's own tree revision, so one that has moved past it
  is recaptured rather than warned about, a case a caller cannot otherwise tell apart from a
  tier that searched and found nothing. A read waits for a commit in flight until its
  `[server] readiness_timeout` budget is spent, and warns only then; the wait shares that
  budget with everything else the read waits for.
- `lexical_ranking_truncated` - the lexical ranking stopped at `matches_max` units, and hits
  past that bound never reach a page, whatever `paths` selects. `total_pages` counts the units
  that did; a narrower `query` brings the rest inside the bound.
- `query_narrowed` - the query carried more terms and quoted phrases than `terms_max`, so the
  server dropped the shortest unquoted terms and ranked the answer by the rest. Every quoted
  phrase is kept. Shorten `query`, or quote the terms that must be matched.
- `results_truncated` - the server reached `results_max`, its result bound, before ordering and
  paging. The bound covers both the candidates one read ranks and the hits it returns, so what
  it cut never reaches any page and `total_pages` counts only what fit. The warning means the
  bound was reached: a read that cut nothing else but filled the candidate pool carries it too.
  A narrower `query` or `paths` brings the read inside the bound.

A `symbol_disagreement` warning names a symbol whose selected presentation and at least one
provider's own facts disagree.

A `source_unavailable` warning names a file the index left out - bytes that are not valid UTF-8,
a file past its per-file bound, or a syntax tree the provider refused - so it answers no search or
lookup while every other file stays available. An answer carries at most eight of them, in
project-path order; when more files were left out, one more `source_unavailable` carries no `unit`
and counts the rest, and `rift://logs` names each.

Three warnings ride a `get_symbol` or `search` answer whose `scope` reaches packages, and no
other answer:

- `global_index_unavailable` - no global package index answered, so the package facts came
  from the packages this machine indexed. `indexed` counts them.
- `package_skipped` - the local package index refused `package` for `reason`, so none of its
  declarations answers.
- `package_context_degraded` - `resolver` read less than its manifests and lockfiles state,
  for `reason`, so the dependency context can miss packages.

An answer carries at most eight `package_skipped` and `package_context_degraded` warnings
together: the skipped packages first, in package identity order, then the degraded resolvers
in resolver order. The `source_unavailable` bound above is separate, so an answer can carry
eight of each.

Every read carries an optional `rev`, and reads the workspace tree when it is absent.

### Revision-addressed reads [#revision-reads]

<VersionBadge
  version="v0.0.7"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

Every read also accepts `rev` - a branch, tag, or commit id, spelled the way git spells it:
`main`, `v0.0.6`, `dd0a482`. The server resolves the revision in place from the workspace's
git objects, with no checkout, and indexes that commit's tree under the same
[`[source]`](/docs/developer/configuration#source) policy and bounds as the working-tree scan. A revision
read answers from committed bytes, so uncommitted working-tree changes never appear in it.

This `get_symbol` request reads a declaration as it stands on `main`, whatever the working tree
currently holds:

```json
{ "name": "ReadService", "rev": "main" }
```

A revision search refuses `force_include`: reaching index-excluded files is a walk of the
working tree, which a revision does not have.

A workspace with no git repository refuses a revision read and names the remedy:

**Error:**

```json
{
  "code": "capability_unavailable",
  "message": "no configured provider serves this request: workspace /Users/alice/projects/charming-aurora, requires a git repository - run `git init`, or omit `rev` to read the current tree; adjust the request to a served capability, or configure a provider that serves it",
  "retry": "operator_action",
  "phase": "read"
}
```

An unknown revision refuses with `resource_not_found`, and
[`[providers.history]`](/docs/developer/configuration#providers) owns the capability: `enabled = false`
refuses every revision read.

<McpTool name="get_symbol" />

<VersionBadge version="v0.0.13" />

`include` selects the optional fields a hit carries: `source` - the node identity and
declaration excerpt - and `history` - the version-control timeline. An omitted `include`
defaults to `["source"]`; an explicit empty list carries neither.

`include: ["history"]` attaches the symbol's version-control timeline as a
[`SymbolHistory`](/docs/developer/protocol/reference#SymbolHistory). The server follows first parents
from the served revision along the declaration's current path, bounded by the `max_revisions`
key in [`[providers.history]`](/docs/developer/configuration#providers) and by a shallow clone's
boundary, and classifies what each touching revision did: `introduced`, `body_changed`,
`signature_changed`, `removed`, or `decorators_changed`. A revision whose source cannot be
parsed, or where the symbol is absent, contributes no version. `complete` says whether the
walk reached the repository's first commit; `false` means one of those bounds ended it first,
so revisions older than the listed ones may have touched the symbol.

### Package scope [#get_symbol-scope]

<VersionBadge version="v0.0.39" languages={["Rust", "Python", "TypeScript"]} />

`scope` selects which corpus the lookup searches, by what the corpus holds rather than by
where it is stored. `local`, the default, searches the workspace tree. `global` searches the
public declarations of the workspace's dependency packages. `all` searches both and lists a
project hit before a package hit of equal rank.

A package hit carries `unit` in place of `path`: the
[`SourceUnitId`](/docs/developer/protocol/reference#SourceUnitId) of the package file, spelled
`rift://source/<manager>/<name>@<version>/<file>`. Its `symbol.origin` names the owning
package. The hit carries neither `node` nor `history`.

A `local` read reaches no package declaration and resolves no package. The first `global` or
`all` read indexes the workspace's dependency packages on this machine within the
[`[dependencies]`](/docs/developer/configuration#dependencies) bounds, then reuses what it
built. No global package index exists yet, so every package read carries a
`global_index_unavailable` warning stating what the local fallback produced.

The server refuses `rev` together with a scope beyond `local` as `invalid_request`: package
facts are served for the current tree alone.

This lookup reaches the `helper` crate a workspace's `Cargo.toml` names by path:

**Request:**

```json
{ "name": "helper_beacon", "scope": "global" }
```

**Response:**

```json
{
  "hits": [
    {
      "symbol": {
        "id": "rift://symbol/rust/cargo/helper@0.1.0/src/lib.rs/helper_beacon",
        "language": "rust",
        "name": "helper_beacon",
        "kind": "function",
        "facets": ["value", "callable", "public"],
        "visibility": "pub",
        "signatures": [{ "display": "pub fn helper_beacon()", "language": "rust" }],
        "origin": {
          "location": "dependency",
          "package": { "manager": "cargo", "name": "helper", "version": "0.1.0" },
          "source_kind": "authored"
        }
      },
      "unit": "rift://source/cargo/helper@0.1.0/src/lib.rs",
      "range": { "start": 0, "end": 25 },
      "line": 1,
      "source": "pub fn helper_beacon() {}"
    }
  ],
  "pagination": { "page_index": 0, "total_pages": 1 },
  "warnings": [
    {
      "code": "global_index_unavailable",
      "indexed": 1,
      "detail": "no global package index answered; 1 of the workspace's packages were analyzed on this machine, and 0 named no source this machine holds"
    }
  ]
}
```

<McpTool name="search" />

`search` takes a lexical `query`, narrowed or extended by a `paths` selector. `paths.include` and
`paths.exclude` glob the project-relative path - the same glob engine backs the workspace's
[`[source]`](/docs/developer/configuration#source) policy - narrowing the indexed candidates before
scoring.

`paths.force_include` reaches past both: a file `[source]` or `.gitignore` excluded from the
index is parsed on demand and searched alongside the indexed hits, up to 256 matched files per
request - the bound counts the files the request reaches outside the index, so a glob whose
matches the index already holds adds none. A request whose `paths.force_include` matches more
than that refuses with `limit_exceeded` rather than searching a silently truncated set; the
`limit` evidence names `paths.force_include`, the bound, and the match count.

The top-level `include` field is a separate selector: it requests extra payload per hit instead
of narrowing which files are searched. `source` attaches the excerpt around the hit; `score`
attaches the fused ranking value used to order the page, comparable only within this one answer.

This request narrows the search to the tests tree, then reaches one file the workspace's
`[source]` policy excludes from the index:

```json
{
  "query": "test_fit",
  "paths": {
    "include": ["tests/**"],
    "force_include": ["tests/legacy/test_solver.py"]
  }
}
```

### Full-text search [#search-fulltext]

<VersionBadge
  version="v0.0.9"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

`query` matches declaration names, qualified names, signatures, attached documentation,
declaration sources, and file contents through a full-text index, and the identifiers it
carries against the indexed names. A multi-word query is answered first by the documents
carrying every term; only when that leaves the answer short do documents carrying some of
them join, behind every exact one. Double quotes keep a phrase together in both passes.

An identifier written inside a question reaches its declaration without being quoted:
`where does encode_path get its escape set` ranks `encode_path` through the identifier
matching, while the prose around it ranks through the full-text index.

The index ranks at most 1,000 units for one request. When more units match, the answer
carries a `lexical_ranking_truncated` warning naming that bound, and hits past it never reach
a page: `paths` selects among the ranked units, so only a narrower `query` brings the rest
inside the bound.

The read has its own bound of 1,000, applied to the candidates it ranks and again to the hits
it orders and pages: a read that reached it warns `results_truncated`.

A symbol whose only match sits in its documentation and its source, not in its name, still
returns as a `symbol` hit. `matched_by` names every field that carried a term, so this one
is tagged `["documentation", "content"]`: the attached doc comment carried both words, and
the declaration's own source carries that comment. A hit tagged `["ranked"]` is one the
vector ranking placed, where no indexed field carries the query's literal bytes at all.

**Request:**

```json
{ "query": "literal minted" }
```

**Search hit:**

```json
{
  "hit": {
    "target": "symbol",
    "symbol": {
      "id": "rift://symbol/rust/crates/rift-core/src/identity.rs/encode_path",
      "language": "rust",
      "name": "encode_path",
      "kind": "function",
      "facets": ["value", "callable", "public"],
      "visibility": "pub"
    }
  },
  "matched_by": ["documentation", "content"],
  "range": { "start": 1496, "end": 1925 },
  "line": 43,
  "path": "crates/rift-core/src/identity.rs"
}
```

<VersionBadge version="v0.0.25" />

Every visible bounded UTF-8 file without a NUL byte joins the same index when its effective
language entry or [`[search.text].include`](/docs/developer/configuration#search) selects it. A hit on one
of those files returns as a `file` hit, tagged `matched_by: ["content"]` the same way:

**Request:**

```json
{ "query": "install checksum", "target": "file" }
```

**Search hit:**

```json
{
  "hit": {
    "target": "file",
    "size": 3546
  },
  "matched_by": ["content"],
  "range": { "start": 820, "end": 920 },
  "line": 35,
  "path": "README.md"
}
```

A path carrying no extension - `justfile`, `Dockerfile` - is selected by the same patterns and
returns the same way, because the selection reads the whole project-relative path. A file hit
carries `languages` only where a syntax provider claims the path; the full-text index also
reaches a file no provider claims, as this one does.

The hit above carries no `source`: a request pays that lookup only when `include` names it.
`include: ["source"]` attaches the excerpt as `source` on every hit; an omitted `include` returns
the hit's symbol or file, `path`, `range`, and `line` alone, as both hits above do.

A hit's `score` follows the same rule: absent unless `include` names it. `include: ["score"]`
attaches the fused ranking value that ordered the page, comparable only within this one
answer.

### Traversal [#search-traversal]

<VersionBadge version="v0.0.29" languages={["Rust"]} />

`traversal` walks the references a configured
[language engine](/docs/developer/configuration#languages-and-lsp) resolves: a bounded search
from one `seed`, following `direction` and narrowed to `facets`, up to `depth` hops. `seed` and
the optional `to` are declaration [`SymbolId`](/docs/developer/protocol/reference#SymbolId)
values, the same identity a `get_symbol` or `search` hit already carries.

`traversal` stands alone as a pure graph walk or rides beside `query`; a symbol both lanes
reach keeps its lexical `score` and gains the walk's `traversal_path`, and its `matched_by`
carries both entries.

`direction` takes `incoming`, its default and its one value: the engine answers which
declarations reference the seed, and no lane resolves what a declaration reaches outward. Two
shapes cover most questions:

- **Impact** - `seed` alone, `depth` at its default: what would change if this symbol did.
- **Path** - `to` set: whether, and by which shortest route, the walk reaches one named symbol.

Each reached symbol becomes a hit tagged `matched_by: ["relationship"]`, carrying `distance` -
the path length - and `traversal_path`, the [`GraphHop`](/docs/developer/protocol/reference#GraphHop) list
from `seed` to the hit. Every `GraphHop` carries the
[`Relationship`](/docs/developer/protocol/reference#Relationship) it followed and the direction it
followed it in; `seed` itself is never a hit.

For a Python workspace with the embedded engine configured, this request asks which declarations
reference `serve` in `service.py`:

**Request:**

```json
{
  "traversal": {
    "seed": "rift://symbol/python/service.py/serve",
    "direction": "incoming",
    "facets": ["references"],
    "depth": 1
  },
  "target": "symbol"
}
```

Each caller's `traversal_path` carries a relationship from the caller to `serve`, with
`facets: ["references"]` and `derivation: "resolution"`. The hop's direction is `incoming`.

`facets` narrows the walk to [`RelationshipFacet`](/docs/developer/protocol/reference#RelationshipFacet)
values; an empty or omitted list follows every facet a lane populates, which is `references`
today. `target: "file"` never carries a walked hit, since a traversal only reaches symbols.

A `traversal` names the declaration its walk starts at, so a request carrying no `seed`
refuses `invalid_request` naming the field.

A walk whose seed no engine answers for refuses `capability_unavailable` naming
`relationship traversal (no language engine serves the seed)`: nothing this workspace holds
resolves a reference to that declaration, and a resend changes nothing. A `facets` list naming
no facet a lane populates draws the same refusal. An engine session serves the current tree, so
`traversal` combines with neither `rev` nor `change`, and refuses `capability_unavailable` for
each. A `seed` that resolves to no declaration refuses `resource_not_found`; one the engine
answers for with no callers returns an empty result set, since an isolated declaration is a
legitimate answer.

A walk the server stops at its node bound attaches a `traversal_truncated` entry to
`warnings`, naming how many symbols it visited: hits reachable beyond the bound are missing,
and a tighter `facets` list, a smaller `depth`, or a less-connected `seed` fits the walk under it.

A walk asking for coverage no lane populates attaches a `relationship_coverage_missing` entry
to `warnings`. Its `facets` names the requested facets no lane populates, such as `implements`
beside the `references` the engine lane resolves. An empty answer carrying it means the walk
could not run; an empty answer without it means the walk ran and the seed has no neighbor
under the request.

### Language-engine references [#search-engine-references]

<VersionBadge version="v0.0.35" languages={["Rust", "TypeScript", "Python"]} />

A current-tree symbol traversal consults the configured
[language engine](/docs/developer/configuration#languages-and-lsp) when `facets` contains
`references` or is empty. The engine's answer is what the walk follows, under the same
traversal depth and result bounds.

The server maps each reference location to the smallest indexed declaration containing it.
Locations outside the workspace or without an indexed declaration contribute no hit. When no
engine is configured, or the engine lacks reference support, the walk refuses
`capability_unavailable`. A configured engine that fails to start returns its failure through
[`ErrorData`](/docs/developer/protocol/reference#ErrorData).

The server captures source and configuration before and after the engine request. If either
changes, the server captures the current publication, refreshes the search ranking, and repeats
the reference request, with at most three attempts. The publication wait, the search ranking,
reference resolution, and these retries share one `[server] readiness_timeout` deadline, taken
once where the request enters. Exhausted attempts or an expired deadline return
`temporarily_unavailable` with `retry: "same_request"`.

A stale publication uses indexed relationships and carries `stale_index`. Each engine request
also uses the configured engine retry and restart bounds.

### Change [#search-change]

<VersionBadge
  version="v0.0.36"
  languages={["Rust", "JavaScript", "TypeScript", "Markdown", "JSON", "YAML", "TOML", "Python"]}
/>

`change` answers the declarations two committed revisions hold differently. `base` names the
revision compared from and `head` the revision compared to, each a branch, tag, or commit id
spelled the way git spells it; an omitted `head` is `HEAD`. Both sides name a commit, so
uncommitted working-tree bytes take part in no comparison.

The server lists the paths the two revisions hold differently, reads and parses those paths
alone on each side, and matches declarations within one path by the provider's qualified name
and kind. A declaration both revisions hold whose bytes are equal produces no hit; one whose
bytes differ is classified the way a [symbol timeline](#revision-reads) classifies two adjacent
revisions, into `signature_changed`, `body_changed`, or `decorators_changed`. A declaration only
`head` holds is `introduced`, and one only `base` holds is `removed`.

A deletion and an addition in two different paths whose declarations match one to one - same
qualified name, same kind, same bytes - are one declaration that `moved`. Anything ambiguous
stays an addition beside a removal: two same-named declarations removed against one added leave
three hits, because no evidence says which removal the addition answers.

Each hit is tagged `matched_by: ["change"]` and carries a
[`SymbolChange`](/docs/developer/protocol/reference#SymbolChange) as `change`, naming the `kind`
above and the `base_path` and `head_path` the declaration lives at on each side. The hit's
`symbol`, `path`, `range`, `line`, and `source` read the head revision:

**Request:**

```json
{ "change": { "base": "main", "head": "HEAD" }, "include": ["source"] }
```

**Search hit:**

```json
{
  "hit": {
    "target": "symbol",
    "symbol": {
      "id": "rift://symbol/rust/src/config.rs/load_config",
      "language": "rust",
      "name": "load_config",
      "kind": "function",
      "facets": ["value", "callable", "public"],
      "visibility": "pub"
    }
  },
  "matched_by": ["change"],
  "change": {
    "kind": "signature_changed",
    "base_path": "src/config.rs",
    "head_path": "src/config.rs"
  },
  "source": "/// Loads the workspace configuration from `rift.toml`.\npub fn load_config(path: &Path, strict: bool) -> Result<Config, ConfigError> {\n    let text = std::fs::read_to_string(path)?;\n    parse_config(&text)\n}",
  "range": { "start": 0, "end": 207 },
  "line": 1,
  "path": "src/config.rs"
}
```

A removed declaration is the exception: the head revision no longer holds it, so its hit keeps
its base-side identity, path, range, and source, and its `change` carries `base_path` alone:

**Search hit:**

```json
{
  "hit": {
    "target": "symbol",
    "symbol": {
      "id": "rift://symbol/rust/src/legacy.rs/load_legacy_config",
      "language": "rust",
      "name": "load_legacy_config",
      "kind": "function",
      "facets": ["value", "callable", "public"],
      "visibility": "pub"
    }
  },
  "matched_by": ["change"],
  "change": { "kind": "removed", "base_path": "src/legacy.rs" },
  "source": "pub fn load_legacy_config() {}",
  "range": { "start": 0, "end": 30 },
  "line": 1,
  "path": "src/legacy.rs"
}
```

A comparison ranks nothing, so no hit carries a `score` even when `include` names one. Ordering
is deterministic for identical inputs: `relevance` has no score to rank by here and orders
changed declarations by path, then by name, while `path` and `identity` order as they do in
every other search answer. `paths` narrows which changed paths are compared, through the same
glob engine every other selector uses. `target: "file"` never carries a change hit, since the
comparison reaches declarations alone.

A comparison the server stops at its changed-path bound attaches a `change_truncated` entry to
`warnings` naming that bound: declarations in the changed paths past it are absent from the
answer, and `paths` narrows a further comparison onto them. The result set keeps its own bound
and its `results_truncated` warning. A changed file either revision cannot read - bytes past the
per-file byte bound, bytes that are not UTF-8, or a syntax tree the provider refuses -
contributes no declaration, and the changed paths beside it still answer.

The server refuses `change` beside `rev` with `invalid_request`, since `change` names its own
revisions, and beside `query` with `invalid_request`, since the two select different result
sets. A `traversal` beside it refuses `capability_unavailable`, since a language engine serves
the current tree and a comparison names two committed revisions. A `scope` past `local`
refuses with `invalid_request`, because package facts are served for the current tree alone.
[`[providers.history]`](/docs/developer/configuration#providers) owns the capability the way it owns
[revision-addressed reads](#revision-reads): `enabled = false` refuses a comparison, a workspace
with no git repository refuses `capability_unavailable`, and a revision neither side resolves
refuses `resource_not_found`.

### Package scope [#search-scope]

<VersionBadge version="v0.0.39" languages={["Rust", "Python", "TypeScript"]} />

`scope` selects what `query` runs over, with the three values
[`get_symbol`](#get_symbol-scope) takes. `local`, the default, runs the lanes above: the
indexed declarations and lines, the `paths.force_include` files, the ranked tier, and
`traversal`. `global` runs none of them and answers from the public declarations of the
workspace's dependency packages, ranked the way the project index ranks a name. `all` runs
both and orders the two sides together under `order`: by score under `relevance`; under
`path`, every project path first, then the package hits in unit order.

A package hit is a `symbol` hit tagged `matched_by: ["name"]`, addressed by `unit` in place
of `path` - the [`SourceUnitId`](/docs/developer/protocol/reference#SourceUnitId) of the package file -
with `range` and `line` inside that unit, and `source` when `include` names it. A package
contributes declarations alone, so `target: "file"` answers nothing from it.

The server refuses `rev` together with a scope beyond `local` as `invalid_request`, since
package facts are served for the current tree alone, and refuses `traversal` together with
`global` the same way, since a walk runs over the project alone; `all` still walks the
project graph. The three package warnings under [Reads](#reads) ride a `search` answer whose
`scope` reaches packages, as they ride a `get_symbol` answer.

The resolvers read at most 256 manifests per workspace, taken in path order, so a `global` or
`all` search over a workspace holding more answers from the packages those manifests declare.

This search reaches the `helper` crate the `get_symbol` lookup above reaches:

**Request:**

```json
{ "query": "helper_beacon", "scope": "global" }
```

**Response:**

```json
{
  "results": [
```

## Resources

### Server logs [#resource-logs]

<VersionBadge version="v0.0.22" />

`rift://logs` reads the server's own diagnostics back, newest first. Events admitted by the
`[logs] capture` filter enter a bounded queue and one task writes them to the workspace database,
so an agent that met a refusal can ask what the server was doing without an operator reading its
terminal. When the queue fills, the task drops later events and records the dropped count:

| Resource | Content |
| --- | --- |
| `rift://logs` | every recorded diagnostic, newest first |
| `rift://logs/level/{level}` | one severity: `trace`, `debug`, `info`, `warn`, or `error` |
| `rift://logs/component/{component}` | one component's records, as its spans label them |

The answer is a JSON object carrying `records` and `record_count`. Each record names its
`identity` (the store's own ascending number), `recorded_at_ms`, `level`, `target`,
`component`, `operation`, `message`, and the remaining `fields` as an object. A span that
closed carries the fields it recorded beside `elapsed_ms`, which is how long the work it
wrapped took.

The read never waits on workspace readiness. A request that refuses because the index will not
settle is exactly the request whose reason these records hold, so the log read answers while
every workspace read is still refusing. A store that could not be opened answers with an empty
set and an `unavailable` reason rather than a refusal.

`[logs] page_records` bounds one read; `retention_records` bounds the store. Both are
[workspace configuration](/docs/developer/configuration#logs).

### Workspace [#resource-workspace]

<VersionBadge version="v0.0.25" />

`rift://workspace` reads accepted configuration together with one captured source catalog page.
The answer carries:

- `configuration_revision` - an eight-character digest of the accepted `rift.toml` bytes
- `languages` - effective identities in order, with enabled state, include and exclude patterns,
  syntax availability, and selected LSP process state
- `source` - captured project paths, content digests, and matched language identities
- `pagination` - the zero-based page and total page count

The bare URI selects page zero. `rift://workspace?page_index=1` selects another page. Each page
holds at most 1000 source units; language summaries repeat so every page can be read
alone. A page past the end returns an empty `source` list with the true page count.

### Map [#resource-map]

<VersionBadge version="v0.0.29" />

`rift://map` reads a workspace orientation snapshot: a starting picture for an agent new to the
codebase, computed once when the index publishes and served from cache after that, so a read
costs a lookup. The answer carries:

- `revision` - an eight-character [`Digest`](/docs/developer/protocol/reference#Digest) of the indexed
  tree the map was computed from
- `languages` - per-language file and symbol counts, sorted by language spelling
- `modules` - the directory tree indexed files sit under, each entry's file and symbol counts
  inclusive of its descendants, folded three directories deep
- `hubs` - the most-referenced symbols, ranked by reference count descending
- `entry_points` - symbols where execution starts
- `docs` - markdown files, in path order
- `module_relationships` - the modules a resolved reference reaches between, ranked by that
  count descending
- `packages` - the packages the workspace's manifests and lockfiles state, in `manager`,
  `name`, then selector order
- `pagination` - always page zero of one, the whole map on one page

<VersionBadge version="v0.0.29" languages={["Rust"]} />

`entry_points` lists symbols carrying the `entrypoint`
[`SymbolFacet`](/docs/developer/protocol/reference#SymbolFacet) - a file-scope `fn main`, not one
nested in a module, an `impl` block, or another function. It stays empty for a workspace with no
such facts.

`hubs` ranks [`SymbolId`](/docs/developer/protocol/reference#SymbolId)s by how often the index
holds a resolved reference to them, and `module_relationships` folds both ends of every such
reference to the module `modules` lists them under, drops a pair whose two ends fold to one
module, and counts what is left. `module_relationships` carries at most 100 entries, ordered
by `references` descending, then `from`, then `to`, so a workspace past that bound keeps the
strongest pairs and two reads of one tree agree. Both read the index alone: the language
engine resolves a reference for one read and publishes none, so both lists stay empty until a
provider publishes resolved references into the index.

<VersionBadge version="v0.0.32" languages={["Rust", "Python", "TypeScript"]} />

`packages` lists the [dependency context](/docs/developer/architecture#dependency-context): what the
Cargo, uv, npm, and Bun resolvers read from `Cargo.toml` and `Cargo.lock`, `pyproject.toml` and
`uv.lock`, `package.json` and `package-lock.json`, and `package.json` and `bun.lock`. The pass
reads those files and nothing else, so it runs no toolchain. Each entry is a
[`PackageContextEntry`](/docs/developer/protocol/reference#PackageContextEntry) carrying the exact
`version` a lockfile pins or the `requirement` a manifest declares, never both, and the
`availability` a global package index could answer under. The list follows those files: one
rewritten while the server runs is read again on the next publication.

A resolver reads at most 256 manifests per workspace, taken in path order, so `packages` over a
workspace holding more lists what the manifests it read declare.

## Errors

[`ErrorData`](/docs/developer/protocol/reference#ErrorData) reports request and infrastructure failures
such as invalid input, a crossed limit, or a storage failure.

Every one carries a `retry` directive, which is the field to branch on - it rides each error
instance rather than the code, because the same `storage_failure` can be transient once and
permanent the next time:

- `never` - the same bytes will fail the same way
- `same_request` - it was transient: an index still filling, a tree with a filesystem
  write in flight
- `operator_action` - the workspace requires a local state or configuration change before retry

A `limit_exceeded` also carries which limit and by how much, so a request can be resized without
parsing the message meant for a human.
