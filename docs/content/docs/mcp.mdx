The main interface for agents to work with rift is the Model Context Protocol, aka
[MCP](https://modelcontextprotocol.io/specification/2026-07-28). The local `rift mcp` process is
launched via a CLI command by your agent (see [Usage](/docs/agentic-usage)).

<Accordions className="text-sm">
<Accordion title="Details">

We're using MCP because it's the de-facto standard in the agent infrastructure. However, MCP
requests are stateless, while rift needs a live local index running in the background.

Therefore, we start a long-running `rift server`, which can handle multiple MCP clients (agents)
and starts automatically. See [CLI commands](/docs/developer/implementation#rift-server) for server
controls.

</Accordion>
</Accordions>

Rift follows the MCP specifications, and all inputs and structured outputs have a strictly defined
JSON schema, available [here](https://volar.sh/rift/mcp.json).

An agent working on an unfamiliar project first needs to understand its structure, then find
and read the code relevant to its task. Rift provides context before an edit and updates its
local index as the agent changes project files, ready for the next read.

## Map [#resource-map]

Before searching, the agent is advised to read the map.
The map describes the project that the local index serves: its directories, languages,
documentation paths, and dependencies.

For any task, directories help the agent choose where to search.
Documentation paths point to project guidance, while dependency entries identify the packages
and versions used by the project.

For the example project, a map can look like this:

In the text, the first line names the map's revision. Each section, such as `languages:` or `packages:`, lists
its entries indented under it, and a package shows the version the project locks or, as for
`tokio` here, the requirement its manifest declares.

<Callout type="info">

Rift updates the map when it publishes a new index, so later reads follow changes to the project.

While Rift prepares the local index, the map can show discovered files before their symbols

The [map reference](/docs/developer/protocol/mcp#resource-map) describes additional facts, such as
entry points and relationships, and when they are available. It also shows a map as compact text.

Each result identifies what matched and where it was found. A declaration result includes its
symbol name and identity, so the agent can use that name with [get_symbol](#tool-get_symbol)

### Full-text search (FTS) [#search-fulltext]

Full-text search matches words in declaration names, signatures, documentation, source code,
and included text files. Rift also recognizes identifier words, so `loadConfig` can find
`load_config`. A word that only appears in a function's body still finds that function: Rift
looks it up in the file's text and answers the declaration holding it.

Double quotes keep a phrase together. For example, the agent can look for this wording in
indexed content:

```json
{ "query": "\"workspace configuration\"", "include": ["source"] }
```

Results include `matched_by`, which identifies the fields that matched. The agent can narrow
the result kind with `target`: `symbol` for declarations, `documentation` for collected
documentation, or `file` for file results; the default, `all`, allows every kind.

### Hybrid search [#search-hybrid]

An agent can describe a behavior without knowing the words used in its implementation.
Hybrid search combines identifier and full-text matches with vector ranking, which compares
the query's meaning with indexed declarations.

For example, the agent can ask where the project reads its settings:

```json
{ "query": "read project settings from disk", "target": "symbol", "limit": 5 }
```

This uses the same `query` argument as full-text search. When vector ranking is available,
it contributes to the combined result order. The [search configuration](/docs/developer/configuration#search)
controls ranking weights, embedding options, and included text files.

<Accordions>
<Accordion title="Ranking details">

`include: ["score"]` exposes the ranking value for comparison within one answer.
A result tagged `matched_by: ["ranked"]` can come from vector ranking without a literal text match.

While vectors are being prepared, or when their model cannot load, results carry a warning.
Identifier and full-text matching remain available independently of vector ranking.
The [read reference](/docs/developer/protocol/mcp#reads) describes these warnings.

</Accordion>
</Accordions>

### Regex search [#search-pattern]

Sometimes the agent needs every place a piece of code occurs, not the best matches for a phrase:
every `TODO`, every call written as `spawn_blocking(`, every path into a crate. It then sends a
regular expression as `pattern` instead of `query`. The syntax is the one ripgrep reads, so a pattern the
agent would write for `Grep` or `rg` works unchanged:

<ExampleTabs items={["call", "text", "json"]}>

<Tab value="call">

```json
{ "pattern": "tokio::\\w+", "paths": { "include": ["src/**"] }, "target": "file" }
```

In the example project, the pattern matches two lines of `src/main.rs`. Every match comes back as a file hit with its byte range and line; the text shows its path and
line, with the source line below it. A match shows its own line only, so a statement that
continues on later lines looks cut; `nodes` or `get_symbol` reads the rest. `target: "symbol"` answers
each declaration holding a match instead. Matching runs line by line, and a `(?i)` prefix makes it
case-insensitive. Rift reads only the files a trigram index says can match, then checks them
with the pattern, so the answer holds every match the files carry.

Rift fills the trigram index in the background once the project's text is stored, so a search
right after startup or an edit doesn't wait for it. Files the index doesn't hold yet are checked
too, and when they're too many for one search, the answer covers the files the index holds and
carries a `pattern_index_preparing` warning until the index catches up.

`pattern` doesn't combine with `query`, `traversal`, `change`, or `rev`. With `scope` set to
`global` or `all`, it also searches the package files the global index holds. The
[pattern reference](/docs/developer/protocol/mcp#search-pattern) describes the bounds a search
runs under and the warning a file with too many matches carries.

### More search options

The agent can narrow the files it searches, look into dependencies, follow references,
compare revisions, or search commit messages. These options use the same `search` tool:

<Accordions>
<Accordion title="Path filters" id="search-paths">

The map can help the agent restrict a search to the relevant part of the repository.
`paths.include` selects project-relative paths, and `paths.exclude` removes matches from that selection:

```json
{
  "query": "load configuration",
  "paths": { "include": ["src/**"], "exclude": ["src/generated/**"] },
  "include": ["source"]
}
```

Here, `paths.include` selects files, while the top-level `include` asks for source excerpts.
If a needed file is excluded from the index, `paths.force_include` can request an on-demand
search, subject to the [search limits](/docs/developer/protocol/mcp#search).

</Accordion>
<Accordion title="Dependencies" id="search-scope">

Reading project code often leads to a library call. The agent can search public declarations
in the project's dependencies by changing `scope`:

| Scope | Searches |
| --- | --- |
| `local` | Project code, the default |
| `global` | Public declarations of the project's dependency packages |
| `all` | Both project code and dependency declarations |

For example, a project using Tokio can search its dependency declarations for `spawn_blocking`:

```json
{ "query": "spawn_blocking", "scope": "global", "target": "symbol", "limit": 5 }
```

Rift uses the project's manifests and lockfiles to select packages, adds the standard library of
each language the project uses, and asks the global index for their declarations. A package
result identifies its package and version, and carries `unit` instead of a local `path`. When the
global index holds no release at the version the project locks, the nearest collected release
answers, and the result names both versions in a `package_substituted` warning.

Sometimes the agent needs a version other than the one the project resolves, such as an upgrade
target, or a package the project does not use yet. `packages` names package versions for one
read: an entry naming a dependency replaces its version, and an entry naming another package adds
it. This request searches Tokio 1.47.1 beside the project code:

```json
{
  "query": "spawn_blocking",
  "scope": "all",
  "target": "symbol",
  "limit": 10,
  "packages": [{ "manager": "cargo", "name": "tokio", "version": "1.47.1" }]
}
```

An entry without `version` reads the newest release the global index has collected. `packages`
takes effect with `scope` set to `global` or `all` on the current tree, and the server refuses it
beside the `local` scope or `rev`.

A dependency no public registry serves, such as a path outside the project or a git repository,
has no declarations in the global index, and the answer names it in a `package_unavailable`
warning. See [package scope](/docs/developer/protocol/mcp#search-scope) for package results,
nearest releases, and paging, [requested packages](/docs/developer/protocol/mcp#requested-packages)
for the argument's constraints, and the [read reference](/docs/developer/protocol/mcp#reads) for
the warnings a package read carries.

</Accordion>

For the example project, the result is `main`. The text shows the walk as a tree: the first line
starts with `at` and the symbol identity the walk starts from, and each `↳` line starts a declaration that references the
one above it. Below that line, `by` gives the declaration, `in` its location, and `at` its symbol
identity. A deeper reference sits one tab further in.

At `depth: 1`, the result contains declarations that reference `load_config`. At `depth: 2`,
Rift also follows references to those declarations, helping the agent inspect the effect of a change.
Use the returned symbol identity for `seed`, since names alone do not identify a declaration.

In a larger project, a walk at `depth: 2` returns a deeper tree. Here `run` and
`reload_config` reference `load_config`, and `main` references `run`:

```text
3 results
	at rift://symbol/rust/src/config.rs/load_config

		↳ referenced
			by fn run(args: &Arguments) -> Result<(), ConfigError>
			in src/app.rs:20
			at rift://symbol/rust/src/app.rs/run

			↳ referenced
				by async fn main() -> Result<(), ConfigError>
				in src/main.rs:9
				at rift://symbol/rust/src/main.rs/main

		↳ referenced
			by fn reload_config() -> Result<(), ConfigError>
			in src/watch.rs:41
			at rift://symbol/rust/src/watch.rs/reload_config
```

Reading a declaration raises the opposite question: what does it rely on? `direction: "outgoing"`
follows the calls the declaration makes, and each hop carries the `calls` facet:

```json
{
  "traversal": {
    "seed": "rift://symbol/rust/src/config.rs/load_config",
    "direction": "outgoing",
    "facets": ["calls"],
    "depth": 1
  },
  "target": "symbol"
}
```

For the example project, the result contains `parse_config` and the standard library's
`std::fs::read_to_string`. The local index holds no declaration of the standard library, so the
global index names it: its hit carries the same identity a `get_symbol` hit with
`scope: "global"` carries, and the walk does not continue from it.

Traversal works on current local code and needs a configured
[language engine](/docs/developer/configuration#languages-and-lsp) that resolves references and
calls. The [traversal reference](/docs/developer/protocol/mcp#search-traversal) describes result
paths, coverage warnings, and unsupported requests.

</Accordion>
<Accordion title="Language-engine references" id="search-engine-references">

During traversal, the configured language engine resolves reference locations, or the callees of
an outgoing walk. Rift finds the smallest indexed declaration containing each location, so the
result identifies the caller or the callee. A callee in an installed package or a standard library
is named by the global index. These relationships belong to this read and do not become indexed
relationships in the map.

See [language-engine references](/docs/developer/protocol/mcp#search-engine-references) for
validation, retries, and failure behavior.

</Accordion>
<Accordion title="Changes between revisions" id="search-change">

When reviewing a branch, the agent can search for declarations that differ between committed
revisions. This request compares `main` with `HEAD`:

```json
{ "change": { "base": "main", "head": "HEAD" }, "target": "symbol" }
```

Each result describes what changed and identifies the declaration on each side of the comparison.

To check its own uncommitted edits, the agent names the working tree as `head`. The working-tree
side is the current local index, so staged, unstaged, untracked, and deleted files all take part:

```json
{ "change": { "base": "HEAD", "head": { "kind": "working_tree" } }, "target": "symbol" }
```

`change` selects the result set on its own; see the
[change reference](/docs/developer/protocol/mcp#search-change) for classifications and argument
constraints.

</Accordion>

| Include | Adds |
| --- | --- |
| `source` | Source code, with a node identity for project declarations |
| `documentation` | Collected documentation referring to the declaration |
| `history` | The declaration's version-control timeline |

`include: []` returns the symbol and its location without these additions.

with its author:

## Edits and index updates [#edit-and-index-updates]

As the agents edit the codebase, rift watches the project files and updates the local index
when they change, so the next read can use the new code.

`search` and `get_symbol` can also reach the global index for dependency declarations and
documentation. Those reads use the project's package context; edits to project source update
the local index. See [Index](/docs/developer/architecture#index) for local updates and
[package scope](/docs/developer/protocol/mcp#get_symbol-scope) for dependency reads.

## Reading results [#reads]

As the agent moves between these tools, it can keep responses small with `limit` and request
another page using `page_index` on `search` and `get_symbol`. The returned `pagination` tells
it which page was served and how many pages are available.

Warnings explain when an answer is incomplete or a capability could not contribute.
For example, `stale_index` reports an index behind the captured project state or a rebuild failure;
`results_truncated` means a narrower query or path selection can bring results within the bound.
Large files and lockfiles carry their own: `large_file_unparsed` names a file too large to parse,
whose text still answers, `large_file_skipped` counts files left out of text search, and
`lockfile_excluded` names a lockfile the path selection reached but search leaves out.
The [read reference](/docs/developer/protocol/mcp#reads) describes each warning.

The agent reads each answer as compact text. The text is a list of sections, and each section
starts with a title that counts its entries, such as `2 results` or `1 warning`, with the entries
indented under it. Warnings form their own section after the items:

- The title is written even when nothing matched, so `0 results` with a warning tells the agent
  why the answer is empty.

Compact text prints only what stands out, such as a requested `score`, a dependency origin, or a
truncated history. Everything else is in the structured output, which by default `rift mcp` sends
beside the text, so a program calling the tools can read every field as JSON.

When the agent only needs the text, start `rift mcp --output=text`. It leaves out the structured
output and the output schemas in the tool listing, which makes each response smaller. A resource read
then returns its compact text without the JSON body.

<Accordion title="Earlier revisions" id="revision-reads">

The agent can read older project code by adding `rev` to `search`, `get_symbol`, or `nodes`.
For example, this reads the function from `main` without changing the working tree:

```json
{ "name": "load_config", "rev": "main" }
```

Git's ancestry suffixes work too, so `"rev": "HEAD~1"` reads the commit below `HEAD`.
Revision reads use committed source from a branch, tag, or commit and require a Git repository.
See [revision-addressed reads](/docs/developer/protocol/mcp#revision-reads) for configuration
and argument constraints.

</Accordion>
