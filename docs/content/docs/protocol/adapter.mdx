---
title: Adapter
---

Language adapters are gRPC subprocesses started by the workspace server. They parse source, publish
semantic facts, resolve formatting and refactors, validate candidates, and optionally evaluate code.
Rift owns revision resolution, persistent source, filesystem projections, and Git integration.

## Admission

The server starts at most one configured process for each exact `Language` name and dialect. It calls
`Describe` once and checks the returned contracts, message limits, state limits, operations, fact
families, action families, source claims, write claims, extensions, and runtime requirements.

An adapter is admitted only when:

- one advertised contract exactly matches the server's major, minor, and schema digest;
- source and write claims do not conflict with another configured adapter;
- every advertised optional operation has its complete request and response contract;
- declared extension schemas are local and self-contained;
- execution and debugging capabilities satisfy their all-or-none method sets.

Returning `UNIMPLEMENTED` from an advertised operation is an adapter protocol error.

## Filesystem projections

An `AdapterState` identifies a Rift `Projection`, exact `Snapshot`, and adapter-local generation.
`OpenRequest` supplies:

- the stable projection id;
- its absolute mounted `root`;
- the exact source snapshot rendered there;
- a distinct native `state_root` owned by this adapter state;
- the selected wire contract.

Several language adapters can open the same projection root and receive separate `state_root`
directories. One adapter process can hold states for sessions, read projections, candidates,
validation, execution, and debugging within its advertised `max_states` bound.

The adapter does not allocate, mount, unmount, or rebind projections. It opens source with ordinary
filesystem APIs. The root-level synthetic `.git` entry prevents Git discovery from escaping to the
physical workspace checkout and never appears in source analysis.

`state_root` is the preferred location for build output, package caches, sockets, databases, and
runtime state. Rift never reads it as source. An adapter can point `CARGO_TARGET_DIR`, package caches,
or equivalent tool settings there. Shared caches outside it are the adapter's responsibility.

## State lifecycle

The lifecycle is:

```text
Describe once per process
Open(projection, root, snapshot, state_root)
Refresh(from, to, written, removed) zero or more times
SyncVirtual zero or more times
Close(projection)
```

`Open` mints the first adapter-local generation. `Refresh` acknowledges that the same projection root
now renders an exact new snapshot after Rift has committed store state and invalidated kernel
caches. The short filesystem publication barrier is already released; an adapter-admission gate
prevents analysis calls against the state being replaced. `written` and `removed` contain the
complete delta from the last acknowledged snapshot; a rename is one of each. The adapter re-evaluates
runtime-defining inputs before returning the new state.

`SyncVirtual` atomically replaces the private virtual-source overlay consumed by one adapter. The
stream begins with the current `AdapterState`, carries the complete unit set, and advances the
adapter-local generation only after the final chunk succeeds.

A call using an earlier generation returns `StaleState`. Adapter generation is process-local cache
coherence. It is unrelated to `ProjectionHead`, snapshot retention, or history.

## Locking and re-entry

Adapters read through the mounted filesystem while the server waits for their RPCs. The server must
therefore obey these invariants:

- no store transaction, store-actor lock, filesystem publication barrier, or Git ref lock is held
  while awaiting an adapter RPC;
- filesystem requests run on an independently serviced executor with reserved capacity;
- notification delivery runs after the store writer lock is released;
- cancellation releases adapter barriers without rolling back a filesystem transaction that already
  committed;
- a candidate becomes public only after all required adapter calls and validation have completed.

Reads pinned to one adapter state can run concurrently. To refresh a shared root, Rift stops
admitting new state-pinned calls, drains current calls, and calls `Refresh` after source publication
and invalidation. This admission gate is not a store or filesystem lock, so the adapter can re-enter
through the mount. A failed refresh closes and rebuilds that adapter state; it does not roll back
already published source.

## Source ownership

`SourceClaim` decides which adapter owns a physical source path. Claims match language, path, and
optional project markers. One exact language owns each selected physical region. Container adapters
can publish virtual units for embedded languages; virtual routing must be acyclic and unambiguous.

`WriteClaim` identifies generated subtrees an adapter can write while analyzing or building. These
paths enter projection scratch, remain visible through the mount, and are excluded from source
snapshots and Git integration. Write claims from adapters sharing a projection cannot overlap.

The adapter never mutates source as the side effect of a semantic RPC. Formatting, fixes, and
refactors return typed `Edit` values. Rift applies them to a private copy-on-write candidate, refreshes
candidate adapter states, validates the exact result, and only then swaps the public session
projection.

External editors are also source writers. Each successful mounted source mutation commits a store
transaction and advances the session `ProjectionHead`. A later MCP mutation must supply that exact
state. Adapters observe external changes through cache invalidation, watcher events, and `Refresh`;
they do not infer authority from file mtimes.

## Analysis

`Analyze` streams facts for selected physical and virtual units at one exact adapter state. Facts are
derived data. The server can evict and rebuild them without changing authoritative source.

The stream declares coverage and invalidation explicitly:

- unit coverage says which requested source was complete, partial, or unsupported;
- fact-family coverage distinguishes a known empty result from an unavailable family;
- invalidated paths retract facts that no longer hold;
- cache scope determines reuse across calls, adapter generations, or process lifetime.

Every file, node, symbol, relationship, diagnostic, and origin mapping uses the core source identity
and UTF-8 byte-coordinate rules. A gitlink is one opaque entry; analysis cannot descend through it.

## Resolution and formatting

Discovery methods return portable action descriptors and opaque adapter tokens bound to the exact
snapshot. `Resolve` checks that adapter state, token, arguments, and target still agree. It returns
edits, preconditions, effects, guarantees, blockers, diagnostics, and confirmations. Rift remains the
only component that applies those edits.

Formatting runs in the candidate projection. `touched_regions` limits formatting to the operation's
changed grammar regions. `affected_files` allows complete affected files. `workspace` requires
explicit workspace policy because it can rewrite unrelated paths. Formatter output is another typed
edit set and is validated before publication.

## Validation

`Validate` receives the exact candidate `AdapterState` plus changed project paths. The adapter expands
that seed to the closure its language validity rules require and returns diagnostics followed by one
summary. Coverage is part of the verdict. Required incomplete coverage rejects the change even if no
diagnostic has error severity.

Validation source is immutable for the duration of the call. Adapter-generated output goes to
`state_root` or candidate scratch. The public session projection is unchanged until the transaction's
final compare-and-swap.

## Execution and debugging

Execution uses a disposable projection for the requested snapshot and a distinct `state_root`.
`Execute` receives a code block and exact budgets. Every projection write made by evaluated code is
discarded when the call ends.

Debugging adds a retained adapter-owned runtime session. `DebugStart` either completes normally or
retains bounded frames after an unhandled failure. `DebugGetFrame` reads one frame without resuming.
`DebugStop`, connection close, or expiry releases the runtime, adapter state, projection, scratch, and
snapshot pins.

The projection and adapter process are not a host security sandbox. Repository code, plugins, macros,
and evaluated code can reach resources allowed to the user unless Rift's caller supplies an OS-level
sandbox. `RuntimeRequirements` makes execution behavior visible for admission and diagnostics.

## Scratch and ignored output

Session scratch persists with its session; candidate, validation, execution, and debug scratch follow
their projection lifetime. `validators.carry` copies selected session scratch into a validator's
disposable projection. It does not read the physical workspace root.

When ignore rules change, existing source remains source and existing scratch remains scratch. There
is no scratch-promotion RPC in the initial contract. A tool promotes bytes by copying or renaming
them to a new non-ignored source path or over an existing source path; Rift applies the destination
layer rules atomically.

## Conformance

An adapter implementation must pass fixtures for shared projection roots, refresh after MCP and
filesystem writes, stale generations, virtual overlays, conflicting claims, source-write refusal,
candidate-only mutation, complete validation, disposable output, runtime reselection, gitlink
boundaries, and calls that re-enter through the mounted filesystem without deadlock.
