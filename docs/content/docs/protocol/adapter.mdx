---
title: Adapter
---

A language adapter is a subprocess started by the workspace server. It owns language analysis while
Rift owns sessions, source state, concurrency, and publication.

## Discovery

Rift calls `Describe` once after starting the process. The response declares:

- the exact language and dialect;
- source, auxiliary, and write claims;
- semantic fact families and kinds;
- supported operations and action families;
- limits and runtime requirements;
- compatible generated contracts.

Rift uses these declarations for routing and admission. A capability change requires a new adapter
process.

## State

`Open` gives the adapter a Rift FS path and its current `ProjectionHead`. The adapter returns an
`AdapterState` for later calls. Several adapters may analyze the same projection.

After a source change, `Refresh` advances the adapter to the new head and carries the changed files.
Rift serializes refreshes for one adapter state. A stale call returns the adapter's actual state so
the server can refresh before retrying.

`Close` releases the adapter state. Adapter indexes and caches are rebuildable.

Virtual documents use `VirtualSync` events. Each event names its owning source unit and mappings
back to source ranges. Rift keeps virtual paths in a separate namespace.

## Analysis

`Analyze` streams facts for requested source units. Events carry symbols, nodes, relationships,
diagnostics, origin mappings, and coverage. A final summary reports the complete coverage of that
analysis.

Claims decide which adapter owns a source file. Auxiliary claims add supporting files. Write claims
bound the files an operation may change.

## Changes

The server asks the adapter to:

- validate a changed source closure;
- format changed regions or files;
- find structural matches;
- list actions at an address;
- resolve one action to edits and evidence.

Rift checks paths, limits, expected heads, and atomicity around these calls. Adapter results include
coverage so Rift can refuse an operation whose required semantic reach is incomplete.

## Execution

Adapters that advertise execution receive a disposable workspace for `Execute` and debugging.
Runtime requirements tell the server whether the adapter executes workspace code or starts child
processes. Execution budgets bound time, output, frames, bindings, and rendered values.

The generated [reference](/docs/protocol/reference) defines every request, event, and capability.
