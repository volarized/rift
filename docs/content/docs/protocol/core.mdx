Rift resolves every request against a Git revision, so the workspace must be a Git repository.

<Callout type="info" title="Git is required">
    If it isn't already enabled, run `git init` in the workspace.
</Callout>

`core.json` assigns each definition to a group under `rift:axes`. That assignment is part of the
contract. This page explains the groups that describe code; the [reference](/docs/protocol/reference)
also includes protocol machinery and MCP-specific shapes.

## Versioning

A request names Git state. The protocol calls that input a `Revision`. Rift resolves it to a commit or
working tree and returns the exact state, called a `Snapshot`, so another call can reuse it.

### Revision

By default Rift works with the default branch at its latest commit. Every tool and every resource also
takes an optional `rev` that points somewhere else. It is a git revision parameter —
[`gitrevisions(7)`](https://git-scm.com/docs/gitrevisions) — so anything git accepts on a command line
works here:

| `rev` | Points at |
| --- | --- |
| *(omitted)* | default branch, latest commit |
| `main`, `refs/heads/main` | a branch |
| `v1.2.0`, `tags/v1.2.0` | a tag |
| `dae86e1` | a commit |
| `HEAD~3`, `main@{yesterday}` | anything else the syntax allows |
| `worktrees/feature-x/HEAD` | the commit a linked worktree sits on |
| `worktrees/feature-x` | that worktree's **working** tree, uncommitted edits included |
| `main-worktree` | the main working tree, uncommitted edits included |

The worktree spellings are git's own — per-worktree refs are reachable from any other worktree as
`worktrees/<id>/HEAD` and `main-worktree/HEAD`. Dropping the `/HEAD` is Rift's one addition, because
gitrevisions has no way to name work that isn't committed yet, and that is usually what you are editing.

### Snapshot

Because `main` names a different commit tomorrow, and a working tree changes under you, the answer says
what it actually resolved to. A [`Snapshot`](/docs/protocol/reference#Snapshot) comes back with every
response:

```
{ "kind": "commit",   "commit": "dae86e1…" }
{ "kind": "worktree", "worktree": "worktrees/feature-x",
                      "base": "dae86e1…", "changes": "9f2c…" }
```

A working-tree snapshot contains its base commit and a digest of the files that differ from it.
Editing one file therefore leaves every other file's state unchanged.

The tree also contains dependency and compiler configuration files. An adapter tracks changes to
those inputs across `Refresh`. The repository resource identifies the compiler serving the snapshot.

## Filesystem

File and leaf identities use project-relative paths and byte offsets. Editing a file can change those
identities.

### File

Physically, a codebase is files. A file is identified by its path, relative to the project root:

```
rift://file/pkg/util.py
```

The URI contains the path. The resource returns the Git entry and file content. It also reports which
languages read the file. The same resource reads `LICENSE` and compiler-owned source.

Where more than one language claims a file, the entry says which bytes each one owns. In `App.svelte`,
the `regions` field can record that TypeScript starts at byte 412.

### Leaf

Parsing turns those bytes into a
[concrete syntax tree](https://en.wikipedia.org/wiki/Parse_tree): every token the source contains, in
the shape the grammar gives it. A leaf is one node of that tree. Its identity contains the grammar and
file, followed by the byte range it spans:

```
rift://leaf/python/pkg/util.py@1204-1266
```

The grammar determines the tree, so the language is part of the leaf identity. One file can contain
several grammars. For example, Svelte and TypeScript adapters can parse the same byte range into
different nodes:

```
rift://leaf/svelte/App.svelte@100-200
rift://leaf/typescript/App.svelte@100-200
```

A leaf also marks named regions. For a function, an operation can address its `body` independently
from its `documentation`.

A leaf is where a [symbol](#symbol) is written. One symbol has many leaves: the place it is declared,
and every place it is mentioned.

### Edit

A change to the code is a value before it is a write to disk. An
[`Edit`](/docs/protocol/reference#Edit) can replace a byte range with new text. Other variants create
or delete a file. A rename changes its path:

```
{ "kind": "replace",
  "span": { "unit":  "rift://file/pkg/util.py",
            "range": { "start": 1204, "end": 1266 } },
  "text": "def load_config(path: Path) -> Config:" }
```

An adapter returns proposed source changes to Rift as `Edit` values. Rift can inspect the values before
writing them to the task worktree. The [adapter contract](/docs/protocol/adapter#source-ownership)
defines that ownership boundary.

The same shape reads a change that already happened. A
[`FileChange`](/docs/protocol/reference#FileChange) is the file entry on each side of a comparison and
the edits between them. The same byte replacement can therefore appear in a diff or a proposed
refactor:

```
before: rift://file/pkg/util.py   digest 3f8a…  1204 bytes
after:  rift://file/pkg/util.py   digest 9c21…  1198 bytes
edits:  [ { "kind": "replace", … } ]
```

The two entries determine the file-level change. A created file has an `after` entry. A deleted file
has a `before` entry. A rename has different paths on each side. The nested edits then describe byte
replacements within those entries. Read the whole comparison at
[`rift://diff/main..feature-x`](/docs/protocol/mcp).

## Semantic

Semantic identities use compiler names, so moving a file preserves them when the language's name stays
the same.

### Symbol

A symbol is a compiler-recognized entity at one revision. For example, the Python function
`pkg.util.load_config` is one symbol. The server indexes symbols and the relationships returned by the
compiler, so a caller can retrieve the function's callers.

A declared type is also a symbol. The portable marker for a type declaration is stored in the symbol's
`facets` field as `type`. A Python adapter can emit a function symbol without attaching that facet.

A symbol is identified by the URI that resolves it: the language, then the name the language itself
gives the declaration.

```
rift://symbol/python/pkg.util.load_config
rift://symbol/rust/serde::de::Deserialize
```

The URI follows the language's naming rules. A TypeScript module name includes its file path; a Rust
module name follows the module tree. Leaves record where the symbol is written, so the symbol URI can
survive a file move. The `origin` field records whether Rift can open the declaration and what can
replace it. A dependency upgrade replaces a package symbol. Rebuilding can replace a generated one.

Symbols live across revisions. That identity is the symbol itself, at whichever revision the request
resolved; attach `?rev=` to pin it to one:

```
rift://symbol/python/pkg.util.load_config?rev=v1.2.0
```

### Relationship

A [`Relationship`](/docs/protocol/reference#Relationship) is a directed edge between symbols. A call
from `handler` to `load_config` is one such edge. Rift indexes these edges, so a caller query reads the
index.

An edge carries `evidence` — the leaves the compiler read it from:

```
from:     rift://symbol/python/pkg.api.handler
to:       rift://symbol/python/pkg.util.load_config
evidence: rift://leaf/python/pkg/api.py@880-899
```

`Leaf.symbol` links a syntax-tree node to semantic identity. `Relationship.evidence` links a semantic
edge back to the node that established it. The symbol URI remains stable when only the file path
changes.

The compiler also reports how it derived each edge. In the `derivation` field, `resolution` comes from
the compiler's name resolver or type checker. `syntax` comes from the parsed tree. `heuristic` marks a
guess with a confidence value.

## Discovery

Callers use a `Filter` to test compiler facts. A `StructuralQuery` parses a source-shaped pattern with
the target language's grammar.

### Filter

A [`Filter`](/docs/protocol/reference#Filter) asks by what the compiler knows. Each node has a tag.
`field` tests a value, while `relation` follows an edge. `all` and `any` combine child nodes;
`not` negates one. The tags make nesting explicit:

```
all: [ { field:    { field: "facets", op: "contains", value: "function" } },
       { relation: { direction: "incoming", facet: "call",
                     target: { field: { field: "facets", op: "contains", value: "test" } } } } ]
```

That reads "functions called from a test". The nested `target` performs the relationship join inside
the query.

A `relation` node can traverse a cyclic graph, so `max_depth` bounds the walk. The
`quantifier: "not_exists"` form selects symbols with no matching edge.

### StructuralQuery

A [`StructuralQuery`](/docs/protocol/reference#StructuralQuery) asks by what the source looks like.
The pattern is written in the target language's own syntax, with `$NAME` standing for one node and
`$$$NAME` for a run of them:

```
{ "language": "python",
  "pattern": "requests.get($URL, timeout=$T)",
  "constraints": [ { "capture": "T", "cardinality": "one", "text_regex": "^[0-9]+$" } ] }
```

The grammar parses the pattern, so whitespace and a trailing comma preserve the same match.

A constraint combines a syntax match with compiler facts. For example, it can retain only calls whose
target carries the `test` facet. Rift evaluates caller-supplied regular expressions with one engine.
A second engine could accept different syntax, and backtracking could stall a shared adapter process.

### PathSelector

A [`PathSelector`](/docs/protocol/reference#PathSelector) limits either query to project-relative
paths. It contains `include` and `exclude` lists of Git-style globs.

```
{ "include": ["src/**"], "exclude": ["src/generated/**"] }
```

Rift applies `exclude` after `include`. The example searches `src` while skipping its generated
subtree.

## Reachability

Every answer reports how much source Rift inspected. This keeps an incomplete analysis from appearing
as a complete empty result.

### Coverage

A [`Coverage`](/docs/protocol/reference#Coverage) value accompanies the returned facts and records the
analysis state:

```
{ "state": "complete",    "scope": { "kind": "project" } }
{ "state": "partial",     "scope": { "kind": "unit", "unit": "rift://file/src/app.ts" },
                          "reason": "parse stopped at byte 4180" }
{ "state": "unsupported", "scope": { "kind": "request" },
                          "reason": "this adapter emits no source maps" }
```

Absence proves absence only under `complete`. Under `partial` the `reason` says what stopped it, and a
`continuation` says how to ask for the rest where there is a way to. `unsupported` means the adapter
cannot produce this at all; `not_applicable` means the language has no such concept, like source maps
for a language nothing generates.

Coverage is recorded separately for each fact family. An adapter can resolve every symbol in a file
while failing to type one of them, so one combined value would hide the incomplete type analysis.

### Diagnostic

A [`Diagnostic`](/docs/protocol/reference#Diagnostic) is one compiler finding under its original code,
such as `TS2345`. Rift forwards the compiler's message unchanged.

The `reliability` field is `recovered` when the parser repaired invalid source to continue, so facts in
that region may be approximate. The `continuation` field marks a diagnostic caused by source that ends
mid-construct, as it can while an agent is writing a file.

## Operations

An operation carries an address and the snapshot used to compute it.

### Address

An [`Address`](/docs/protocol/reference#Address) names the code an operation applies to:

```
{ "kind": "symbol", "symbol": "rift://symbol/python/pkg.util.load_config" }
{ "kind": "leaf",   "leaf": "rift://leaf/python/pkg/util.py@1204-1266", "region": "name" }
{ "kind": "source", "span": { "unit": "rift://file/LICENSE",
                              "range": { "start": 0, "end": 11 } } }
```

A symbol address lets a rename reach every leaf known to the compiler. A leaf address selects one
syntax-tree node. A source address selects raw bytes, including bytes in `LICENSE` or in an unclaimed
file.

### CodeActionDescriptor

A [`CodeActionDescriptor`](/docs/protocol/reference#CodeActionDescriptor) is one thing the compiler
offers to do here — add an import, extract a function. It carries no edits:

```
kind:          quickfix.import.add
title:         Import `Config` from `pkg.config`
applicability: always
target:        rift://leaf/python/pkg/api.py@88-94
```

Computing an action's edits costs about as much as performing it, and only one of the actions offered
gets picked, so listing and resolving are two calls.

`kind` is a dotted name whose prefixes nest. An agent can request `quickfix` to select that branch.
`applicability` records the checks still required. `always` records compiler-complete preconditions.
`conditional` records a condition the caller must verify. `speculative` records inferred intent.

### Action and match keys

An action or match points into one snapshot. After the source moves, its byte offsets can be stale.
Each result therefore carries a key bound to the snapshot, which Rift checks before applying it.

A [`MatchKey`](/docs/protocol/reference#MatchKey) contains the snapshot and matched span. It also
contains a digest of the query. One query produces at most one match for a given span, so these fields
identify the match.

An [`ActionKey`](/docs/protocol/reference#ActionKey) contains the snapshot and address. It also carries
the adapter's token. Two import actions can share one address, so the compiler uses that token to
distinguish them. Rift returns it unchanged.
