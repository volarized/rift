title: Core
---

Every answer Rift gives is answered against a revision, and a revision is a git object. A workspace
without git has nothing to resolve, so Rift needs one.

<Callout type="info" title="Git is required">
    If it isn't already enabled, run `git init` in the workspace.
</Callout>

`core.json` files every definition into a group under `rift:axes`, so which group a type belongs to is
part of the contract rather than a heading someone picked here. The six below are the ones that say
something about your code; the [reference](/docs/protocol/reference) also lists the contract's own
machinery and the shapes only MCP uses.

## Versioning

You ask against a revision. Git resolves it to a commit or to a working tree, and Rift reports what it
resolved to, because otherwise you could not ask the same question twice.

### Revision

By default Rift works with the default branch at its latest commit. Every tool and every resource also
takes an optional `rev` that points somewhere else. It is a git revision parameter —
[`gitrevisions(7)`](https://git-scm.com/docs/gitrevisions) — so anything git accepts on a command line
works here:

| `rev` | Points at |
| --- | --- |
| *(omitted)* | default branch, latest commit |
| `main`, `refs/heads/main` | a branch |
| `v1.2.0`, `tags/v1.2.0` | a tag |
| `dae86e1` | a commit |
| `HEAD~3`, `main@{yesterday}` | anything else the syntax allows |
| `worktrees/feature-x/HEAD` | the commit a linked worktree sits on |
| `worktrees/feature-x` | that worktree's **working** tree, uncommitted edits included |
| `main-worktree` | the main working tree, uncommitted edits included |

The worktree spellings are git's own — per-worktree refs are reachable from any other worktree as
`worktrees/<id>/HEAD` and `main-worktree/HEAD`. Dropping the `/HEAD` is Rift's one addition, because
gitrevisions has no way to name work that isn't committed yet, and that is usually what you are editing.

### Snapshot

Because `main` names a different commit tomorrow, and a working tree changes under you, the answer says
what it actually resolved to. A [`Snapshot`](/docs/protocol/reference#Snapshot) comes back with every
response:

```
{ "kind": "commit",   "commit": "dae86e1…" }
{ "kind": "worktree", "worktree": "worktrees/feature-x",
                      "base": "dae86e1…", "changes": "9f2c…" }
```

A working tree is derived state, so it is never restated in full: it names the commit it sits on and
digests only the files that differ. Editing one file leaves every other file's state, and the answers
derived from it, untouched.

A snapshot is the whole coordinate. Which dependencies are installed and how the compiler is
configured are read from the tree, and the tree is what the snapshot names — so the adapter tracks
them across a `Refresh` and nothing about them has to ride on a call. Which compiler is answering at
all is fixed when the server starts it, and the repository resource says so once.

## Filesystem

Everything here is addressed by path and byte offset, so it changes whenever the file does.

### File

Physically, a codebase is files. A file is identified by its path, relative to the project root:

```
rift://file/pkg/util.py
```

No language appears there. Bytes are bytes whether three adapters claim the path or none do, and the
same URI resolves to the entry — what Git records for it, which languages read it — and to its content.
A `LICENSE` file is as addressable as a source file.

Where more than one language claims a file, the entry says which bytes each one owns. `App.svelte`
lists `svelte`, `typescript` and `css`, and its `regions` are what tell you the TypeScript starts at
byte 412.

### Leaf

Parsing turns those bytes into a
[concrete syntax tree](https://en.wikipedia.org/wiki/Parse_tree): every token the source contains, in
the shape the grammar gives it. A leaf of that tree is one node of it, identified by the grammar that
produced it, the file, and the byte range it spans:

```
rift://leaf/python/pkg/util.py@1204-1266
```

The language is part of that identity rather than a fact about it, because there is no parse tree
without a grammar. One file can hold several: JavaScript inside Svelte, CSS inside Vue, SQL inside
Python. Two adapters reading the same bytes produce two trees, and `rift://leaf/svelte/App.svelte@100-200`
and `rift://leaf/typescript/App.svelte@100-200` are different nodes.

A leaf also marks out its named parts — `name`, `header`, `body`, `documentation` — so an operation can
address the body of a function without touching the docstring above it.

A leaf is where a [symbol](#symbol) is written. One symbol has many leaves: the place it is declared,
and every place it is mentioned.

### Edit

A change to the code is a value before it is a write to disk. An
[`Edit`](/docs/protocol/reference#Edit) is a byte range and what replaces it, or a file created,
deleted or renamed:

```
{ "kind": "replace",
  "span": { "unit":  "rift://file/pkg/util.py",
            "range": { "start": 1204, "end": 1266 } },
  "text": "def load_config(path: Path) -> Config:" }
```

Language adapters never write to the code they read. Ask for a fix or a refactor and the compiler
computes the change, hands it back in this shape, and Rift is what touches the file. So a change can be
read before it lands, and with several agents working in one repository, the one who asked is the only
one it reaches.

The same shape reads a change that already happened. A
[`FileChange`](/docs/protocol/reference#FileChange) is the file entry on each side of a comparison and
the edits between them, so a diff and a refactor speak one vocabulary:

```
before: rift://file/pkg/util.py   digest 3f8a…  1204 bytes
after:  rift://file/pkg/util.py   digest 9c21…  1198 bytes
edits:  [ { "kind": "replace", … } ]
```

The path and the kind of change are read from the two entries: a created file has no `before`, a
deleted one has no `after`, and a rename is two paths. So the edits in a comparison only ever replace
byte ranges — an edit that also claimed to delete the file could contradict them. Read the whole
comparison at
[`rift://diff/main..feature-x`](/docs/protocol/mcp).

## Semantic

Everything here is addressed by what the language calls it, so none of it moves when a file does.

### Symbol

A symbol is any entity of a given language that carries compiler-provided metadata, at a given revision.
Think of classes, functions or methods as examples of symbols. An arbitrarily large codebase can have
thousands of them.

What the rift server does well is indexing those symbols, the relationships between them, and other
compiler-driven facts — for instance the list of dependants and dependencies.

A declared type is a symbol as well. `struct Config` and `interface Props` are declarations like any
other, and they carry the `type` facet. Languages without types still have symbols.

A symbol is identified by the URI that resolves it: the language, then the name the language itself
gives the declaration.

```
rift://symbol/python/pkg.util.load_config
rift://symbol/rust/serde::de::Deserialize
```

No file appears there unless the language puts one there — a TypeScript module *is* a file, a Rust
one is not. Where a symbol is written is read from its leaves, so moving a file leaves every symbol
in it addressable by the same URI. The same spelling names a symbol the compiler invented, and one
whose declaration Rift cannot read; `origin` says which — your own source, a package the manager
installed, the standard library, or something the compiler synthesised.

Symbols live across revisions. That identity is the symbol itself, at whichever revision the request
resolved; attach `?rev=` to pin it to one:

```
rift://symbol/python/pkg.util.load_config?rev=v1.2.0
```

### Relationship

A [`Relationship`](/docs/protocol/reference#Relationship) is a directed edge from one symbol to
another: a call, an implementation, an import. Rift indexes the edges, so "every caller of
`parse_config`" is a lookup rather than a scan.

An edge carries `evidence` — the leaves the compiler read it from:

```
from:     rift://symbol/python/pkg.api.handler
to:       rift://symbol/python/pkg.util.load_config
evidence: rift://leaf/python/pkg/api.py@880-899
```

That reference and `Leaf.symbol` are the only two places the semantic and filesystem groups touch, and
they run in opposite directions. Past them a file never mentions a symbol and a symbol never mentions
a path, which is what lets you move a file without invalidating a single symbol URI.

Not every edge is worth the same. `derivation` grades how much the compiler knew when it produced
one, which decides whether a refactor can act on it or should only show it to you.

## Discovery

Nothing here is a fact about the code. You write it before there is an answer, and Rift turns it into
one. Two grammars do that, and they ask different questions.

### Filter

A [`Filter`](/docs/protocol/reference#Filter) asks by what the compiler knows. Every node is tagged —
`field`, `relation`, `all`, `any`, `not` — so the tree parses in one pass and nests without precedence
rules:

```
all: [ { field:    { field: "facets", op: "contains", value: "function" } },
       { relation: { direction: "incoming", facet: "call",
                     target: { field: { field: "facets", op: "contains", value: "test" } } } } ]
```

That reads "functions called from a test". The nested `target` is what makes it one query rather than
two queries and a join written in your own code.

A `relation` node walks edges instead of testing a value, so it is bounded: `max_depth` stops the walk,
because a call graph has cycles and a workspace has no natural end. `quantifier: "not_exists"` inverts
it, which is how "a symbol nothing calls" is asked.

### StructuralQuery

A [`StructuralQuery`](/docs/protocol/reference#StructuralQuery) asks by what the source looks like.
The pattern is written in the target language's own syntax, with `$NAME` standing for one node and
`$$$NAME` for a run of them:

```
{ "language": "python",
  "pattern": "requests.get($URL, timeout=$T)",
  "constraints": [ { "capture": "T", "cardinality": "one", "text_regex": "^[0-9]+$" } ] }
```

Grep would need that call spelled the same way every time. Here the grammar parses it, so whitespace,
line breaks and a trailing comma are the parser's problem rather than yours.

A constraint is where a pattern over syntax reaches the compiler's knowledge: match every call, then
keep only the ones whose target carries the `test` facet. Rift evaluates those and every
caller-supplied regex itself, never the adapter — two engines behind one wire field disagree silently,
and a backtracking one turns someone's pattern into a stall inside a process every workspace shares.

### PathSelector

Both grammars run over a set of files rather than the whole tree, and
[`PathSelector`](/docs/protocol/reference#PathSelector) is that set: two lists of git-style globs
matched against the project-relative path.

```
{ "include": ["src/**"], "exclude": ["src/generated/**"] }
```

`exclude` is applied after `include`, so sweeping a directory while skipping the generated output in it
is two patterns rather than an enumeration of what is left.

## Reachability

An empty answer has two readings: nothing is there, or Rift never got that far. Every answer carries
what tells them apart, because a caller that reads absence as proof would be wrong.

### Coverage

A [`Coverage`](/docs/protocol/reference#Coverage) rides beside the facts in an answer and says which
reading applies:

```
{ "state": "complete",    "scope": { "kind": "project" } }
{ "state": "partial",     "scope": { "kind": "unit", "unit": "rift://file/src/app.ts" },
                          "reason": "parse stopped at byte 4180" }
{ "state": "unsupported", "scope": { "kind": "request" },
                          "reason": "this adapter emits no source maps" }
```

Absence proves absence only under `complete`. Under `partial` the `reason` says what stopped it, and a
`continuation` says how to ask for the rest where there is a way to. `unsupported` means the adapter
cannot produce this at all; `not_applicable` means the language has no such concept, like source maps
for a language nothing generates.

Coverage is stated per fact family — source maps, symbols, leaves, relationships, types, diagnostics —
because an adapter can resolve every symbol in a file and still fail to type one of them, and one
number over the two would hide it.

### Diagnostic

A [`Diagnostic`](/docs/protocol/reference#Diagnostic) is one thing the compiler said, passed through in
its own words and under its own code — `TS2345`, `E0308`. A normalised message loses the detail that
makes it actionable, so nothing is rewritten on the way through.

Two fields say how far to trust the facts around it. `reliability` is `recovered` when the parser
repaired the source to keep going, so the tree there is a guess and so is anything read from it.
`continuation` says whether the finding is an artefact of source that stops mid-way, which is the
normal state of a file an agent is halfway through writing.

## Operations

An operation needs somewhere to apply, something to apply there, and a way to say which state of the
code it was computed against.

### Address

An [`Address`](/docs/protocol/reference#Address) is where an operation applies. There are three ways
to name a place, and they reach different amounts of code:

```
{ "kind": "symbol", "symbol": "rift://symbol/python/pkg.util.load_config" }
{ "kind": "leaf",   "leaf": "rift://leaf/python/pkg/util.py@1204-1266", "region": "name" }
{ "kind": "source", "span": { "unit": "rift://file/LICENSE",
                              "range": { "start": 0, "end": 11 } } }
```

A rename addressed at a symbol reaches every leaf the compiler knows about. The same rename addressed
at a leaf touches that one node. The `source` branch addresses bytes whether or not anything was
parsed there, which is what reaches a `LICENSE` file, or a region of a file no adapter claims.

### CodeActionDescriptor

A [`CodeActionDescriptor`](/docs/protocol/reference#CodeActionDescriptor) is one thing the compiler
offers to do here — add an import, extract a function. It carries no edits:

```
kind:          quickfix.import.add
title:         Import `Config` from `pkg.config`
applicability: always
target:        rift://leaf/python/pkg/api.py@88-94
```

Computing an action's edits costs about as much as performing it, and only one of the actions offered
gets picked, so listing and resolving are two calls.

`kind` is a dotted name whose prefixes nest, so an agent that wants a fix asks for `quickfix` and never
sees a refactor. `applicability` says how much has to be checked first: `always` is safe to apply
unread, `conditional` holds only under something the compiler could not check, `speculative` is a guess
at what you meant.

### Action and match keys

An action and a match are both discoveries about one state of the code, and neither survives into the
next: an action computed byte offsets, and a match points at bytes that have moved. So each comes back
with a key carrying the snapshot it was made in, and Rift checks that before applying anything.

A [`MatchKey`](/docs/protocol/reference#MatchKey) is the snapshot, the span, and a digest of the query.
One query cannot match the same span twice, so those pin a match exactly and there is nothing left to
hash.

An [`ActionKey`](/docs/protocol/reference#ActionKey) is the snapshot, the address, and the adapter's own
token. Two actions can sit at one address — `quickfix.import.add` for two different imports — and only
the compiler that offered them can tell those apart, so Rift passes its handle back unread rather than
inventing an identity it cannot derive.
