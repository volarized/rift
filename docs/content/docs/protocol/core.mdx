The core schema holds the values every surface shares: the shape of a projection, the structure
of source, the semantic facts providers resolve, and the changes the server applies.

## Projection state

A change names its target with a
[`ProjectionId`](/docs/protocol/reference#ProjectionId), or targets the workspace tree by
naming none. [`ProjectionState`](/docs/protocol/reference#ProjectionState) exposes the two
conditions a caller needs before paging through a changeset:

```json
{
  "dirty": true,
  "unaccepted": false
}
```

`dirty` indicates that the projection differs from its workspace base. `unaccepted` indicates
that its changeset contains a confirmation requirement. The server refuses
[`publish`](/docs/protocol/mcp#tool-publish) unless `accept` names every such change; path
and dependency conflicts remain visible only in the publication result. The changes come from the
[`rift://changes`](/docs/protocol/mcp#resource-changes) resource.

## Paths and files

[`ProjectPath`](/docs/protocol/reference#ProjectPath) is a normalized UTF-8 path relative
to the workspace root. It uses `/`, contains no `.` or `..` component, and cannot name `.rift` -
projections and the server lock live under there, and a path that could address it would let a
change reach the server's own state. Normalized means Unicode NFC: the server normalizes what it emits and
accepts, then compares byte-for-byte, and on a case-insensitive filesystem a create or rename
whose destination case-folds onto a different existing path refuses with `destination_legal`.

Every identifier that embeds a path - [`FileId`](/docs/protocol/reference#FileId), a node
id, the [`rift://fs`](/docs/protocol/mcp#resource-fs) form - carries a `ProjectPath` in
canonical percent-encoding, and the server re-validates it after decoding. The generated schema
patterns do not carry those exclusions, so the server re-validates each decoded value.

[`ProjectEntry`](/docs/protocol/reference#ProjectEntry) is a visible directory, regular
file or symlink. Visible means below the workspace root, outside `.rift`, and not excluded by
the workspace's VCS ignore rules. Visibility governs reads; publication carries every changed
path, visible or not.

Each variant carries what a consumer can act on:

- a regular file - its size and executable bit
- a symlink - its target, as base64, because the server never follows it and cannot assume the bytes
  are text
- a directory - only its path, so an empty one is still listed once something creates it

A symlink is listed and never followed, in every traversal:

- reads
- materialization
- the execution copy [`execute`](/docs/protocol/mcp#tool-execute) runs in
- publication
- prune

A `copy` of a symlink reproduces the link. A path that addresses through a symlink component
fails with `permission_denied`, because following it could leave the workspace.

## Source locations

[`TextRange`](/docs/protocol/reference#TextRange) is a pair of half-open UTF-8 byte
offsets, and [`SourceSpan`](/docs/protocol/reference#SourceSpan) puts one against a file.
Byte offsets rather than line and column, because every provider converts from whatever its own
toolchain counts in exactly once, at its own boundary, and after that two toolchains' column
numbers are on the same scale.

A [`NodeId`](/docs/protocol/reference#NodeId) is positional and witnessed:

```
rift://node/python/pkg/util.py@1204-1266#3f9a1c2e
```

The byte range names where the node stands; the fragment is the **witness** - the first eight
hex characters of the SHA-256 of the node's source bytes, minted when a listing returned the
identity. Resolution recomputes the witness before acting on the address, so an identity read
before the file changed refuses with a failed `source_unchanged` precondition rather than
splicing into bytes that moved. The witness makes a node address safe to hold across calls: the
address carries its own proof of freshness without depending on connection-scoped state.

## Source discovery

Source resolvers run before syntax or semantic analysis. They inspect workspace files and resolved
toolchain state, then publish a source catalog made of
[`SourceUnit`](/docs/protocol/reference#SourceUnit) records. A resolver discovers installed
dependencies; it does not download packages or change the environment.

Each unit separates two questions. [`SourceLocation`](/docs/protocol/reference#SourceLocation)
answers who owns it: project, dependency, standard library, or external source.
[`SourceKind`](/docs/protocol/reference#SourceKind) answers how it exists: authored or generated.
This represents generated dependency code without collapsing either fact. A generated unit names its
generator and can carry [`SourceMapping`](/docs/protocol/reference#SourceMapping) records back
to its inputs. A synthetic declaration has no source unit.

```json
{
  "id": "rift://source/pypi/pydantic/main.py",
  "location": {
    "kind": "dependency",
    "package": { "manager": "pypi", "name": "pydantic", "version": "2.8.2" }
  },
  "path": "pydantic/main.py",
  "source_kind": "authored",
  "languages": [{ "name": "python", "dialect": null }],
  "digest": "6f2a9c31",
  "generator": null,
  "mappings": []
}
```

An id is two parts: the resolver identity (`pypi`), then that resolver's own human-readable key
for the unit (`pydantic/main.py`). `digest` is the short form every content digest takes on the
wire - the first eight hex characters of a SHA-256, the same convention `NodeId`'s witness uses;
the full digest is computed and compared internally and never travels whole.

[`SourceResolverSummary`](/docs/protocol/reference#SourceResolverSummary) reports each resolver's
identity, locations, catalog revision, and lifecycle state. Resolver revisions change with files,
manifests, lockfiles, toolchains, installed packages, or generated-source metadata. Fact-provider
revisions change after providers analyze a catalog revision.

## Semantic facts

Providers return facts in families: symbols, the syntax nodes that write them, relationships
between symbols, resolved types, diagnostics, and history. Each of those is a
[`FactFamily`](/docs/protocol/reference#FactFamily), and each comes back with a
[`Coverage`](/docs/protocol/reference#Coverage). Signatures and documentation travel on
the symbol itself, covered under the `types` family.

`complete` coverage makes an empty fact list evidence of absence. Under any other coverage, an
empty list means only that the contributing providers returned no facts within their reported
scope.

Coverage also identifies provider inputs. Each
[`ProviderProvenance`](/docs/protocol/reference#ProviderProvenance) names the provider, its
immutable fact revision, the project-tree and source-catalog revisions it analyzed, and whether
that fact revision is current for the answer. Entries appear in merge precedence order. A family
no provider serves reports `unsupported` with no contributing providers.

Every semantic read carries a
[`ReadSnapshot`](/docs/protocol/reference#ReadSnapshot). Its `tree_revision` identifies
the targeted project tree; `source_revision` identifies its source catalog. Reads that search also
carry an `index` snapshot with both input revisions and its freshness. Cursor pages retain the same
snapshot even when later writes publish newer revisions.

[`SymbolOrigin`](/docs/protocol/reference#SymbolOrigin) keeps source location separate from
source kind. Its optional unit connects a declaration to readable catalog source. Synthetic symbols
have neither a location nor a unit; dependency and standard-library symbols can carry facts even
when their provider cannot return source bytes.

## History facts

The `history` family is resolved from the workspace's version-control history rather than from
the current tree. A [`SymbolHistory`](/docs/protocol/reference#SymbolHistory) is one
symbol's timeline - each [`SymbolVersion`](/docs/protocol/reference#SymbolVersion) names
the [`RevisionId`](/docs/protocol/reference#RevisionId) that touched it and what the
revision did: introduced it, changed its body, changed its signature, moved it, removed it.

The history provider correlates declarations across revisions using their parsed structure and
surrounding changes. A [`SymbolId`](/docs/protocol/reference#SymbolId) can change when a
language includes a module path in its qualified name; the timeline still records the move.

A [`CoChange`](/docs/protocol/reference#CoChange) records empirical coupling: of the
walked revisions that touched `subject`, how many also touched `partner`. The relation is
observed rather than resolved, so it reaches coupling no reference graph carries - two
implementations of one concept with no edge between them. The walk is bounded by the configured
history depth, and `SymbolHistory.coverage` says whether it reached the symbol's introduction.

Both ride a [`get_symbol`](/docs/protocol/mcp#tool-get_symbol) hit when the request asks
for history.

## Changes

An [`Edit`](/docs/protocol/reference#Edit) is one filesystem effect: replace these bytes,
create this file, delete it, move it, copy it, flip its executable bit. Edits in one set share
one input state, cannot overlap, and apply atomically.

The change tools resolve down to a set of those, plus the preconditions the server checked, the
effects the change had, the diagnostics it produced, and
[`GuaranteeEvidence`](/docs/protocol/reference#GuaranteeEvidence) for every property a
hook established.

When resolution yields no edits, the server returns a refusal and leaves the targeted tree unchanged:
`ambiguous_target`, `unmet_precondition`, `unsupported`, and the rest of
[`RefusalReason`](/docs/protocol/reference#RefusalReason). When it yields edits, the
change lands carrying its [`Advisory`](/docs/protocol/reference#Advisory) list - the
concerns providers and hooks attached to exactly this change. A checked advisory is a verdict
the emitter verified itself; an open warning carries the instruction that settles it.

In a projection, edits nothing will vouch for also carry a
[`ConfirmationRequirement`](/docs/protocol/reference#ConfirmationRequirement) per
problem - an open warning advisory, a hook that failed or didn't finish, a deletion - and
`publish` is where those get settled. A change applied directly to the workspace has no
publication to gate, so its confirmations list stays empty and its advisories are the caller's
to act on.

A process can write directly into a projection directory without producing an `Edit`. The server
reconciles that filesystem delta into a change whose `origin` is `filesystem`; its `paths` are
authoritative when a binary file or symlink has no portable edit form. The imported change
carries an `external` confirmation, so publication waits for an explicit review of writes that
bypassed a change tool request.

Transport and infrastructure failures use
[`ErrorData`](/docs/protocol/reference#ErrorData), with a code, a phase, and a retry
directive saying whether the same bytes are worth sending again.
