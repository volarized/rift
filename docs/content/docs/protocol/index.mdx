Rift reaches agents through MCP. Each agent talks to its own `rift mcp` process, over stdio.

That process is launched in a workspace — a distinct path on the filesystem of your machine:

```
~/projects/charming-aurora  ->  running rift mcp here
```

<Callout>
  An MCP server on the stdio transport is a subprocess of the client that launched it. Two agents means
  two `rift mcp` processes, and neither can see what the other is doing.
</Callout>

That is the constraint the rest of the design follows from. Several agents can be working in the same
workspace at once, and they need a central point behind them. That central point is the rift server.

So `rift mcp` is a proxy. It holds no state of its own — it forwards what the agent asks, and returns
what the server answers.

MCP is stateless, so nothing in it identifies a connection across calls. The rift server assigns its own
identifier when a `rift mcp` process connects, and remembers which workspace that connection belongs to.

When the rift server starts, it scans the repository and builds the semantic level using the language
adapters.

## A task gets a worktree

An agent does not edit your working tree. The server cuts it a `git worktree` from a recorded base
commit, on a branch of its own, and that tree belongs to it alone until the work is done:

```
base commit B
  ├── .rift/worktrees/a1   branch rift/a1   agent 1, and every compiler driven for it
  └── .rift/worktrees/a2   branch rift/a2   agent 2, and every compiler driven for it
```

The lifecycle of one of those:

1. Record the base commit
2. Create the branch and the worktree
3. Assign the worktree to one agent, exclusively
4. Point the adapters at its path
5. Let the tools read and write there
6. Compute the resulting git diff and validate it
7. Run tests and checks
8. Commit the result
9. Integrate it with a three-way merge or a cherry-pick
10. Remove the worktree

Step 9 is where the base commit earns being recorded rather than assumed. A revision is immutable, so
there is nothing to merge *into* it — the work merges into the branch that was based on it, and that
branch has probably moved on:

```
B ── X ── Y      target, three commits further along
 \
  └── A          rift/a1, still based on B
```

Rift integrates `A` onto `Y`. Three-way, with `B` as the base — never a fast-forward assumption that
`B` is still the tip.

Integration goes through git objects, not through copied files. Committing the agent's result and
merging that commit keeps renames, deletions, file modes, ancestry and conflict information; copying
changed files out of the worktree throws all five away and leaves you diffing text.

A tree moves through **preparing**, **active**, **validating**, **ready to integrate**, **integrating**
and **integrated**, and leaves that line at **conflicted** when step 9 cannot resolve or **failed**
when step 6 or 7 rejects the work. Either way the exit is the same: **disposed**, which is `git
worktree remove`. Rollback is deleting a directory.

<Callout>
  One writer per worktree. Several adapters read one tree at once, but source mutation in it is one
  party's at a time, which is what makes "what changed" answerable by `git diff` alone.
</Callout>

This is what buys the whole design out of filesystem virtualization. No mirroring source over gRPC,
no FUSE, no per-compiler VFS integration: compilers open real files, and concurrent agents are kept
apart by being in different trees. A virtual filesystem only becomes worth its cost if worktree
creation, disk usage or the number of live speculative trees turns out to be a measured bottleneck.

## Seams

The server sits between an agent and a compiler, and they want different things. So each side is its
own contract, and neither knows the other exists.

| | agent ↔ server | server ↔ adapter |
| --- | --- | --- |
| protocol | MCP, JSON-RPC | gRPC |
| transport | stdio, then Streamable HTTP over a Unix socket | Unix socket |
| described by | JSON Schema | Protobuf |
| audience | an agent choosing what to do next | a compiler being driven |

**MCP knows nothing about adapters.** It sees what Rift can do for a language, not how the adapter
recognises its files or what it reads from them. Workspace paths and refresh calls never reach it:
they are how the server keeps a compiler warm, which is the server's problem.

**The adapter knows nothing about agents.** It has no notion of a tool call, a cursor, or a resource
URI. It is handed a working tree and told what state that tree holds.

Because the compiler reads that tree off the disk itself, gRPC here carries control and results only —
what to analyze, and what was found. Source bytes cross it in one direction and one case: a file an
adapter *generated*, which has no on-disk original for anyone else to read.

<Callout>
  The adapter seam is gRPC over a Unix domain socket, one adapter per language, all owned by the
  server that started them. Rift itself is written in Rust; for languages with no native Rust API,
  the adapter is a subprocess speaking this service.
</Callout>

### Where the model lives

Both seams carry the same things — a symbol, a leaf, a file, a snapshot. Writing that model on each
side would guarantee it drifts, so it is written once:

```
core.json  ──generated──▶  core.proto
    │                          │
    ▼                          ▼
 mcp.json                 adapter.proto
 (JSON Schema)            (gRPC service)
```

`core.json` is the model. `core.proto` is generated from it, so a protobuf message and a JSON Schema
definition of the same name describe the same thing by construction — there is no second place to
edit. Each seam then adds only what is its own: `mcp.json` adds tools, resources and cursors;
`adapter.proto` adds workspaces, path claims and the service itself.
