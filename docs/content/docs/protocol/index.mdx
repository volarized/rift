title: Protocol
---

Rift uses JSON Schema at the agent boundary and Protobuf messages between its own processes. The
protocol fixes the conversion between those representations and the gRPC method each request calls.

Which processes exist and how they find each other is on the
[architecture page](/docs/architecture). This page is about what they say to each other:

| caller | callee | interface | transport | definition |
| --- | --- | --- | --- | --- |
| agent | `rift mcp` | [MCP](https://modelcontextprotocol.io/specification/latest) tools and resources | JSON-RPC over stdio | `mcp.json` |
| `rift mcp` | `rift server` | `rift.mcp.Rift` | gRPC over a Unix socket | `rift/mcp.proto` |
| SCIP client | `rift server` | `rift.scip.Projection` | gRPC | `rift/scip.proto`, `scip/scip.proto` |
| `rift server` | adapter | `rift.adapter.Adapter` | gRPC over a Unix socket | `rift/adapter.proto` |

The Rift server speaks gRPC. JSON ends at `rift mcp`, the only participant that ever sees it.

## Conversion

`rift mcp` validates the agent's JSON against `mcp.json`, converts the value to the Protobuf type the
schema names, and calls the gRPC method the same entry names. The response makes the return trip.

```json
"tree": { "rpc": "rift.mcp.Rift/Tree", "params": … , "result": … }
```

Every JSON definition carries its Protobuf identity in `rift:proto` metadata, so the converter reads
the mapping out of the schema it already loaded. There's no operation table anywhere else to keep in
step with it.

The tools defined this way are `tree`, `outline`, `search`, `match`, `actions`, `execute`,
`debug_start`, `debug_get_frame`, `debug_stop`, `apply`, `integrate`, and `persist`; the resources
are repository, symbol, diff, file, and preview. The
[MCP page](/docs/protocol/mcp) says what each one does.

## The SCIP seam

A SCIP client calls `rift.scip.Projection.Read` on the server directly. The server-streaming method
returns a header followed by official SCIP records. It has no MCP URI and no JSON envelope, and MCP
tools neither advertise it nor carry its records.

Protocol version 1 pins
[SCIP v0.9.0](https://github.com/scip-code/scip/blob/v0.9.0/scip.proto), whose schema fixes every
field number, alias and oneof membership those records use.

## The adapter seam

The server calls each adapter process through `rift.adapter.Adapter`. The server first resolves the
requested revision and reuses or allocates a worktree representing that exact snapshot. `Open` gives
the adapter its path; the adapter selects any revision-appropriate runtime and returns state. Source
bytes stay on disk, and worktree allocation never crosses the adapter seam.

The exception is source no adapter could open. An adapter that generates input for another language —
the TypeScript inside a `.svelte` file — sends those bytes over the wire, since there's no path to read
them from.

Execution uses the same revision-resolution seam with a different lifetime. Rift materializes a
disposable execution workspace for the exact `Snapshot`, opens a fresh `AdapterState`, and sends the
caller-provided `CodeBlock` over gRPC. `Execute` removes that state after one result. `DebugStart`
retains it behind a connection-bound public handle until `DebugStop`; `DebugGetFrame` reads one
adapter-retained stack frame. Repository writes made by evaluated code are discarded with the
workspace.

## Definitions

The definitions split where a process boundary changes ownership:

- [Core model](/docs/protocol/core) — entities shared by server services and adapters
- [MCP](/docs/protocol/mcp) — tools and resources provided to an agent
- [SCIP](/docs/protocol/scip) — export of retained facts as a SCIP index
- [Adapter](/docs/protocol/adapter) — the gRPC service through which the server calls adapters
- [Reference](/docs/protocol/reference) — shared and seam types, grouped by axis
