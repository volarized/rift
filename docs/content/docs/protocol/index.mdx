At the core of Rift there is a protocol. It describes how the components of the system behave, and how
they operate.

Rift reaches agents through MCP. Each agent talks to its own `rift mcp` process, over stdio.

That process is launched in a workspace — a distinct path on the filesystem of your machine:

```
~/projects/charming-aurora  ->  running rift mcp here
```

<Callout>
  An MCP server on the stdio transport is a subprocess of the client that launched it. Two agents means
  two `rift mcp` processes, and neither can see what the other is doing.
</Callout>

That is the constraint the rest of the design follows from. Several agents can be working in the same
workspace at once, and they need a central point behind them. That central point is the rift server.

So `rift mcp` is a proxy. It holds no state of its own — it forwards what the agent asks, and returns
what the server answers.

MCP is stateless, so nothing in it identifies a connection across calls. The rift server assigns its own
identifier when a `rift mcp` process connects, and remembers which workspace that connection belongs to.

When the rift server starts, it scans the repository and builds the semantic level using the language
adapters.

## Two seams, two contracts

The server sits between an agent and a compiler, and they want different things. So the two sides are
different contracts, and neither knows the other exists.

| | agent ↔ server | server ↔ adapter |
| --- | --- | --- |
| protocol | MCP, JSON-RPC | gRPC |
| transport | stdio, then Streamable HTTP over a Unix socket | Unix socket |
| described by | JSON Schema | Protobuf |
| audience | an agent choosing what to do next | a compiler being driven |

**MCP knows nothing about adapters.** It sees what Rift can do for a language, not how the adapter
recognises its files or what it fingerprints. Mirrors, sync streams and environment digests never
reach it — they are how the server keeps a compiler warm, which is the server's problem.

**The adapter knows nothing about agents.** It has no notion of a tool call, a cursor, or a resource
URI. It is told which mirror to make and which state that mirror holds.

<Callout>
  The adapter seam is gRPC over a Unix domain socket, one adapter per language, all owned by the
  server that started them. Rift itself is written in Rust; for languages with no native Rust API,
  the adapter is a subprocess speaking this service.
</Callout>

### One model, two spellings

Both seams carry the same things — a symbol, a leaf, a file, a snapshot. Writing that model twice
would guarantee it drifts, so it is written once:

```
core.json  ──generated──▶  core.proto
    │                          │
    ▼                          ▼
 mcp.json                 adapter.proto
 (JSON Schema)            (gRPC service)
```

`core.json` is the model. `core.proto` is generated from it, so a protobuf message and a JSON Schema
definition of the same name describe the same thing by construction — there is no second place to
edit. Each seam then adds only what is its own: `mcp.json` adds tools, resources and cursors;
`adapter.proto` adds mirrors, sync and the service itself.
