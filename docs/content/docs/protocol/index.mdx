Agents reach Rift via the [Model Context Protocol](https://modelcontextprotocol.io/specification/latest).
Each agent talks to its own `rift mcp` process over stdio.

That process is launched in a workspace — a distinct path on the filesystem of your machine:

```
~/projects/charming-aurora  ->  running rift mcp here
```

<Callout>
  On the stdio transport, the client launches the MCP server as a subprocess. Two agents therefore
  launch two `rift mcp` processes, each with its own client connection.
</Callout>

Several agents can work in the same workspace, but their MCP subprocesses cannot share memory. They
connect to one rift server, which owns the shared repository state.

`rift mcp` forwards each agent request to the server and returns the response. The shared state stays
in the server.

MCP calls carry no connection identity. When `rift mcp` connects, the server assigns an identifier and
binds it to the workspace path.

When the server starts, it asks each language adapter to analyze the repository and stores the returned
symbols and relationships in the semantic database.

## Task worktrees

Each task runs in a separate `git worktree`, created from a recorded base commit on a task branch. A
connected MCP client has at least one task worktree and may have more when it runs tasks concurrently:

```
base commit B
  ├── .rift/worktrees/a1   branch rift/a1   one task, and every compiler driven for it
  └── .rift/worktrees/a2   branch rift/a2   another task, possibly the same client
```

For task `a1`, the server records base commit `B` before creating its branch and worktree:

1. Record the base commit
2. Create the branch and the worktree
3. Assign the worktree to that one task, exclusively
4. Point the adapters at its path
5. Let the tools read and write there
6. Compute the resulting git diff and validate it
7. Run tests and checks
8. Commit the result
9. Integrate it with a three-way merge or a cherry-pick
10. Remove the worktree

The recorded base becomes the merge base during integration. The target branch may have advanced
while the task was running:

```
B ── X ── Y      target, three commits further along
 \
  └── A          rift/a1, still based on B
```

Rift integrates `A` onto `Y` with a three-way merge using `B` as the base.

Integration commits the task tree and merges the resulting Git object. The commit retains the tree
metadata and ancestry that Git needs to detect renames and conflicts. Copying changed files would
reduce the result to content differences.

The worktree state follows this path:

```
preparing -> active -> validating -> ready to integrate -> integrating -> integrated
                              \-> failed          \-> conflicted
```

Every outcome ends at `disposed`, after `git worktree remove` deletes the directory.

<Callout>
  One writer per worktree. Several adapters read one tree at once, but source mutation in it is one
  party's at a time, which is what makes "what changed" answerable by `git diff` alone.
</Callout>

Compilers open files directly in the task worktree. Separate worktrees isolate concurrent tasks and
keep source bytes off the gRPC connection. A virtual filesystem becomes relevant only if measurements
show that creating or retaining worktrees is the bottleneck.

## Seams

The server translates between an agent request and compiler operations. Each side has a contract for
the information it consumes:

| | agent ↔ server | server ↔ adapter |
| --- | --- | --- |
| protocol | MCP, JSON-RPC | gRPC |
| transport | stdio, then Streamable HTTP over a Unix socket | Unix socket |
| described by | JSON Schema | Protobuf |
| audience | an agent choosing what to do next | a compiler being driven |

MCP exposes the capabilities available for each language. The server handles workspace paths and
refresh calls while serving those capabilities.

The adapter receives a worktree path and its current state. Its service methods describe compiler
operations; the server maps MCP calls and resource URIs onto those methods.

The compiler reads source from the worktree, so gRPC carries requests and compiler results. For a file
generated by an adapter, the adapter sends the bytes because the file has no source entry on disk.

<Callout>
  The server owns one adapter per language and calls it through gRPC on a Unix domain socket. Rift is
  written in Rust. A compiler without a native Rust API runs in a subprocess that implements this
  service.
</Callout>

### Model

Both contracts refer to the same code entities. Their shared model has one source:

```
core.json  ──generated──▶  core.proto
    │                          │
    ▼                          ▼
 mcp.json                 adapter.proto
 (JSON Schema)            (gRPC service)
```

`core.json` defines the model, and `core.proto` is generated from it. A Protobuf message and a JSON
Schema definition with the same name therefore have the same shape. `mcp.json` defines the agent
calls. `adapter.proto` defines the compiler workspaces and service methods.

## Definitions

- [Adapter](/docs/protocol/adapter) — the gRPC service the server drives a compiler with
